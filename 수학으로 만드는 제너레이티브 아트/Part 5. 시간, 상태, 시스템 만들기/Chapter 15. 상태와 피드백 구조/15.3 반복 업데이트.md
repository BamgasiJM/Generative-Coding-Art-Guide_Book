# 15.3 반복 업데이트

상태 시스템은 한 번 계산하고 끝나지 않는다. 현재 상태를 읽고 일정한 시간 간격 동안 규칙을 적용해 다음 상태를 만든 뒤, 이 과정을 반복한다. 반복 업데이트는 입자를 움직이고 버퍼에 흔적을 쌓으며 격자를 확산시킨다. 단순한 규칙도 반복을 거치며 시간에 따른 행동을 만들어 낸다.

가장 단순한 갱신은 현재 상태 $\mathbf{s}_t$에 변화율을 더하는 형태다.

$$
\mathbf{s}_{t+\Delta t}=
\mathbf{s}_t+\frac{d\mathbf{s}}{dt}\Delta t
$$

위치와 속도의 경우에는 다음과 같이 쓸 수 있다.

$$
\mathbf{p}_{t+\Delta t}=\mathbf{p}_t+\mathbf{v}_t\Delta t
$$

프레임 간격은 일정하지 않을 수 있으므로 이동량에는 실제 $\Delta t$를 곱한다. 그렇지 않으면 장치의 프레임률이 곧 움직임 속도가 된다. 초당 60번 실행되는 환경과 30번 실행되는 환경에서 같은 코드가 서로 다른 결과를 내는 문제는, 반복 횟수와 실제 시간을 혼동할 때 자주 생긴다.

## 프레임 루프와 업데이트 루프

화면은 보통 프레임마다 한 번 렌더링되지만, 상태 갱신이 반드시 프레임당 한 번이어야 하는 것은 아니다. 렌더링은 화면을 보여 주는 작업이고, 업데이트는 시스템의 시간을 한 단계 전진시키는 작업이다. 단순한 애니메이션에서는 둘을 같은 횟수로 처리해도 충분하지만, 물리나 확산처럼 수치적 안정성이 중요한 시스템에서는 두 루프를 구분해야 한다.

```text
for each rendered frame:
    input = readInput()
    state = update(state, input, deltaTime)
    render(state)
```

위 구조는 가변 시간 단계(variable timestep)다. 각 프레임의 실제 시간 차이를 그대로 업데이트에 넣는다. 구현이 간결하고, 입자의 단순한 이동이나 카메라 보간처럼 오차에 민감하지 않은 시각 효과에 적합하다.

그러나 렌더링 속도가 순간적으로 느려지면 `deltaTime`이 커진다. 큰 한 번의 갱신은 작은 여러 번의 갱신과 같지 않을 수 있다. 입자가 얇은 벽을 통과하거나, 스프링이 과도하게 튀거나, 반응-확산의 값이 불안정해지는 현상이 생길 수 있다.

## 가변 시간 단계

가변 시간 단계에서는 현재 프레임과 이전 프레임 사이의 실제 시간 차이를 사용한다.

```text
deltaTime = secondsSincePreviousFrame()
state = update(state, input, deltaTime)
render(state)
```

업데이트 함수에서 위치와 속도의 변화량, 감쇠량을 계산할 때는 `deltaTime`을 반영해야 한다.

```text
velocity += acceleration * deltaTime
position += velocity * deltaTime
opacity *= exp(-fadeRate * deltaTime)
```

마지막 줄처럼 지수 감쇠를 사용하면 프레임마다 고정된 비율을 곱하는 방식보다 실제 시간에 따른 변화가 안정적이다. 반면 어떤 값을 매 프레임 일정량만큼 더하거나 빼는 코드는 프레임률에 의존한다. 값의 단위를 먼저 정하면 이런 오류를 줄일 수 있다. `velocity`는 픽셀/초, `acceleration`은 픽셀/초$^2$, `fadeRate`는 1/초처럼 해석한다.

가변 시간 단계에는 상한을 두는 것이 실용적이다. 창이 비활성화되었거나 일시적인 부하가 생긴 뒤 돌아오면 `deltaTime`이 비정상적으로 커질 수 있기 때문이다.

```text
measuredDeltaTime = secondsSincePreviousFrame()
deltaTime = min(measuredDeltaTime, maximumDeltaTime)
state = update(state, input, deltaTime)
```

이 처리는 긴 멈춤 뒤에 객체가 화면 밖으로 튀는 현상을 줄인다. 다만 실제 경과 시간 일부를 건너뛰는 것이므로, 정확한 시간 경과가 중요한 시뮬레이션에는 적합하지 않을 수 있다.

## 고정 시간 단계와 누적기

충돌, 제약 조건, 확산, 군집 행동처럼 작은 시간 간격을 가정한 규칙에는 고정 시간 단계(fixed timestep)가 유리하다. 렌더링이 언제 일어나든 시뮬레이션은 항상 같은 길이의 시간 조각 `fixedStep`만큼 전진한다.

```text
accumulator += measuredDeltaTime

while accumulator >= fixedStep:
    state = update(state, input, fixedStep)
    accumulator -= fixedStep

render(state)
```

여기서 `accumulator`는 렌더링 프레임 사이에 실제로 지나간 시간을 모아 둔다. 누적 시간이 `fixedStep`보다 크면, 그만큼 여러 번 업데이트해 따라잡는다. 예를 들어 `fixedStep = 1 / 60`이라면 시스템은 렌더링이 30fps로 떨어진 순간에도 한 화면을 그리기 전에 두 번의 시뮬레이션 단계를 진행할 수 있다.

고정 시간 단계를 사용하면 같은 초기 상태와 입력 순서가 주어졌을 때 결과를 예측하기 쉽다. 디버깅, 녹화, 재현 가능한 작품, 네트워크 동기화처럼 실행 환경이 달라도 같은 동작이 중요할 때 특히 유용하다.

## 따라잡기와 과부하 문제

고정 시간 단계의 `while` 루프에도 주의할 점이 있다. 한 프레임이 너무 오래 걸리면 누적 시간이 커져 다음 프레임에서 많은 업데이트를 실행해야 한다. 업데이트가 많아지면 다음 프레임도 늦어지고, 다시 더 많은 업데이트가 필요한 악순환으로 이어질 수 있다.

실시간 표현에서는 한 프레임에 처리할 최대 업데이트 횟수를 제한할 수 있다.

```text
accumulator += min(measuredDeltaTime, maximumFrameTime)
steps = 0

while accumulator >= fixedStep and steps < maximumStepsPerFrame:
    state = update(state, input, fixedStep)
    accumulator -= fixedStep
    steps += 1

if steps == maximumStepsPerFrame:
    accumulator = 0
```

이 방식은 시스템 시간이 실제 시간보다 조금 느려질 수 있지만, 화면 자체가 멈추는 것을 막는다. 정확성이 최우선인 시뮬레이션이라면 성능을 높이거나 업데이트 비용을 줄이는 편이 더 적절하다. 작품의 목표가 실시간 반응인지, 물리적 시간의 정확성인지에 따라 선택이 달라진다.

## 렌더링과 업데이트 사이의 보간

고정 시간 단계는 안정적이지만, 렌더링 시점이 업데이트 시점과 정확히 맞지 않으면 움직임이 계단처럼 보일 수 있다. 남은 누적 시간의 비율을 이용해 이전 상태와 현재 상태를 보간하면 더 부드럽게 그릴 수 있다.

$$
\beta=\frac{\text{accumulator}}{\text{fixedStep}}
$$

$$
\mathbf{p}_{\text{render}}=
\operatorname{mix}(\mathbf{p}_{\text{previous}},\mathbf{p}_{\text{current}},\beta)
$$

```text
renderAmount = accumulator / fixedStep
renderPosition = mix(previousPosition, currentPosition, renderAmount)
drawAt(renderPosition)
```

이를 위해서는 업데이트 직전의 상태 또는 렌더링에 필요한 일부 값을 보관해야 한다. 모든 시스템이 이 보간을 필요로 하지는 않지만, 느린 렌더링 환경에서 부드러운 카메라나 입자 움직임을 유지하고 싶을 때 유용하다.

## 업데이트 순서가 결과를 만든다

같은 규칙도 업데이트 순서에 따라 결과가 달라진다. 대표적인 예가 속도와 위치를 갱신하는 순서다.

```text
# 명시적 오일러 방식
position += velocity * deltaTime
velocity += acceleration * deltaTime
```

```text
# 반명시적 오일러 방식
velocity += acceleration * deltaTime
position += velocity * deltaTime
```

두 번째 방식은 갱신된 속도로 위치를 계산한다. 단순한 상황에서는 차이가 작지만, 중력이나 스프링처럼 힘이 계속 적용되는 시스템에서는 안정성과 에너지 변화가 달라질 수 있다. 선택한 갱신 순서를 이해하고 일관되게 유지하는 것이 중요하다.

객체 사이의 상호작용도 보통 다음 순서로 나눈다.

```text
forces = computeForces(currentState, input)
nextState = integrate(currentState, forces, fixedStep)
nextState = resolveConstraints(nextState)
state = nextState
```

힘 계산이 일부 객체만 먼저 갱신된 상태를 읽지 않도록, 현재 상태에서 필요한 정보를 먼저 읽고 다음 상태를 만드는 구조가 좋다. 이는 15.1에서 다룬 읽기 버퍼와 쓰기 버퍼의 분리 원칙을 시간 업데이트에도 적용한 것이다.

## 생성, 삭제, 입력 처리의 시점

입자나 에이전트는 업데이트 중에 생성되고 사라진다. 목록을 순회하면서 바로 삭제하면 다음 객체의 인덱스가 바뀌거나 일부 객체를 건너뛸 수 있다. 살아남을 객체를 새 목록에 넣고, 필요한 새 객체를 정해진 시점에 추가하는 방식이 안전하다.

```text
nextParticles = []

for each particle in particles:
    updated = updateParticle(particle, input, fixedStep)
    if isAlive(updated):
        nextParticles.add(updated)

nextParticles.addAll(spawnParticles(input))
particles = nextParticles
```

새 입자를 업데이트 전후 어느 시점에 추가할지도 규칙의 일부다. 업데이트 후에 추가하면 새 입자는 다음 단계부터 움직이고, 업데이트 전에 추가하면 생성된 첫 단계부터 힘과 충돌의 영향을 받는다. 표현의 의미에 맞춰 생성 시점과 나이의 기준을 명확히 정한다.

입력 역시 프레임마다 바뀔 수 있다. 고정 시간 단계를 한 프레임에 여러 번 실행할 때는, 그 프레임에서 읽은 입력을 모든 하위 단계에 같은 값으로 쓸지, 입력 이벤트의 시각을 따로 기록해 적절한 단계에 넣을지 결정해야 한다. 일반적인 시각 작업에서는 현재 입력을 모든 하위 단계에 사용하는 것으로 충분하지만, 정밀한 리듬이나 충돌 반응에는 이벤트 타임스탬프가 필요할 수 있다.

## 반복 업데이트를 점검하는 방법

업데이트 문제가 생기면 최종 렌더링을 보기 전에 시간과 상태의 변화를 기록한다. 예를 들어 실제 `deltaTime`, 한 프레임의 업데이트 횟수, 입자 수, 평균 속도를 표시하면 원인을 빨리 찾을 수 있다.

```text
debug("dt", deltaTime)
debug("simulation steps", steps)
debug("particle count", particles.count)
```

동일한 시드, 동일한 입력, 고정 시간 단계로 일정 횟수 업데이트한 뒤 상태를 비교하면 규칙이 재현 가능한지도 확인할 수 있다. 큰 `deltaTime`에서만 문제가 생긴다면 시간 간격 제한이나 고정 시간 단계를 검토하고, 특정 객체에서만 문제가 생긴다면 생성·삭제 순서와 값의 범위를 살핀다.

반복 업데이트의 동작은 `update()` 호출 횟수만으로 결정되지 않는다. 시간 간격, 갱신 순서, 입력 시점, 읽기 상태와 쓰기 상태의 구분이 시스템의 성장과 안정성을 좌우한다. 다음 절에서는 이전 출력이 입력으로 돌아오는 피드백 구조를 통해 반복이 더 복잡한 형태를 만드는 방식을 살펴본다.

## 이 절의 핵심

반복 업데이트는 상태를 실제 시간 간격과 함께 다음 단계로 전진시킨다. 가변 시간 단계는 간단한 애니메이션에 적합하고, 고정 시간 단계와 누적기는 수치적 안정성과 재현성이 필요한 시스템에 유리하다. 업데이트 순서, 객체의 생성과 삭제 시점, 입력을 반영하는 시점을 명확히 정하고, 필요하면 렌더링 보간과 단계 수 제한으로 부드러움과 성능을 함께 관리한다.
