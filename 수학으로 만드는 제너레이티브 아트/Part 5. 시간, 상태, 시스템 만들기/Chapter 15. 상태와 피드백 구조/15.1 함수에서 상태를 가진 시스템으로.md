# 15.1 함수에서 상태를 가진 시스템으로

앞 장에서 다룬 시간 함수는 현재 시각만으로 결과를 계산한다. 예를 들어 원운동의 위치는 시간 $t$를 식에 넣으면 바로 구할 수 있다. 어느 프레임을 건너뛰었는지, 그 전 프레임에서 무엇을 그렸는지는 결과에 영향을 주지 않는다. 같은 시간, 같은 매개변수, 같은 입력이라면 언제나 같은 화면을 다시 얻는다.

상태를 가진 시스템은 이전 순간의 값을 기억해 다음 순간의 값을 만든다. 현재 위치, 속도, 나이, 색, 입자 목록, 캔버스 버퍼, 셀룰러 오토마타의 격자처럼 시간이 지나도 남아야 하는 정보가 상태가 될 수 있다. 이제 장면은 단순히 $t$에서의 함수값이 아니라, 과거에 어떤 상태들을 거쳐 왔는가의 결과가 된다.

$$
\mathbf{s}_{t+\Delta t}=U(\mathbf{s}_t,\mathbf{i}_t,\Delta t)
$$

여기서 $\mathbf{s}_t$는 현재 상태, $\mathbf{i}_t$는 현재 입력, $\Delta t$는 업데이트 사이의 시간 간격, $U$는 상태를 갱신하는 규칙이다. 이 식은 시간 함수가 상태를 직접 계산하는 방식에서, 이전 상태를 입력으로 받는 반복 구조로 넘어가는 출발점이다.

## 시간 함수와 상태 시스템의 차이

시간 함수와 상태 시스템은 모두 움직이는 화면을 만들 수 있지만, 정보를 얻는 방식이 다르다. 다음 두 코드를 비교해 보자.

```text
# 시간 함수
position.x = centerX + radius * cos(time * angularSpeed)
position.y = centerY + radius * sin(time * angularSpeed)
```

```text
# 상태 갱신
velocity += acceleration * deltaTime
position += velocity * deltaTime
```

첫 번째 코드에서 위치는 현재 시간만으로 결정된다. 재생 위치를 10초로 옮기면 곧바로 10초의 위치를 얻을 수 있다. 두 번째 코드의 위치는 이전 프레임에서 계산한 `velocity`와 `position`을 사용한다. 10초 뒤의 위치를 알고 싶다면 초기 상태에서부터 업데이트를 반복하거나, 그 시점의 상태를 따로 저장해 두어야 한다.

| 구분 | 시간 함수 | 상태 시스템 |
| --- | --- | --- |
| 현재 결과의 입력 | 시간, 좌표, 고정 매개변수 | 이전 상태, 현재 입력, 시간 간격 |
| 임의 시점으로 이동 | 시간값만 넣으면 된다. | 상태를 복원하거나 다시 계산해야 한다. |
| 과거의 영향 | 직접 저장하지 않는다. | 이전 결과가 다음 결과에 남는다. |
| 적합한 예 | 주기 운동, 셰이더 패턴, 시간 노이즈 | 입자, 물리, 누적 드로잉, 시뮬레이션 |

두 방식은 경쟁 관계가 아니다. 상태 시스템도 현재 시간에 따라 변하는 힘, 노이즈, 입력값을 사용할 수 있다. 예를 들어 입자의 위치는 이전 위치에서 갱신하지만, 가속도는 시간에 따라 변하는 벡터 필드에서 얻을 수 있다. 시간은 규칙을 변화시키고, 상태는 그 규칙이 남긴 결과를 보존한다.

## 무엇을 상태로 둘 것인가

상태는 다음 업데이트에 필요한 값만 보관한다. 화면에 보이는 모든 값을 저장해야 하는 것은 아니다. 예를 들어 각 프레임에 입자의 색을 나이와 위치에서 다시 계산할 수 있다면 색은 파생값이고, 입자의 위치와 속도와 나이는 상태로 두는 편이 자연스럽다.

```text
particle = {
    position,
    velocity,
    age,
    lifetime,
    seed
}
```

이 입자에서 크기, 색, 투명도는 다음처럼 렌더링 시점에 계산할 수 있다.

```text
lifeAmount = clamp(particle.age / particle.lifetime, 0, 1)
size = mix(startSize, endSize, lifeAmount)
color = mix(startColor, endColor, lifeAmount)
```

상태를 작게 유지하면 메모리 사용량을 줄이고, 어떤 값이 시간에 따라 누적되는지 파악하기 쉬워진다. 반대로 다음 프레임에서 필요한 정보를 버리면 원하는 동작을 재현할 수 없다. 흔적이 점점 쌓이는 그림에는 이전 프레임의 이미지 버퍼가 필요하고, 충돌을 계산하려면 각 객체의 위치와 속도가 필요하며, 되감기를 만들려면 과거 상태 또는 재계산 가능한 입력 기록이 필요하다.

상태는 하나의 숫자일 수도, 여러 객체의 배열일 수도, 화면 전체 해상도를 가진 격자일 수도 있다.

| 상태의 형태 | 예 | 다음 프레임에 남는 것 |
| --- | --- | --- |
| 스칼라 | 누적 시간, 점수, 전역 위상 | 하나의 값 |
| 벡터 | 위치, 속도, 힘 | 방향과 크기 |
| 객체 목록 | 입자, 에이전트, 도형 | 각 객체의 개별 속성 |
| 격자 또는 텍스처 | 반응-확산, 유체, 잔상 | 공간 전체의 값 분포 |

## 업데이트와 렌더링을 분리하기

상태 시스템은 보통 업데이트 단계와 렌더링 단계를 구분한다. 업데이트는 이전 상태를 다음 상태로 바꾸는 계산이고, 렌더링은 현재 상태를 화면에 해석하는 계산이다.

```text
state = initialize(seed)

for each frame:
    input = readInput()
    state = update(state, input, deltaTime)
    image = render(state)
    present(image)
```

이 구조에서 `update`는 상태를 어떻게 변화시킬지에만 집중하고, `render`는 그 상태를 점, 선, 색, 텍스처로 어떻게 보일지에만 집중한다. 같은 상태를 선으로 그릴 수도, 입자 크기로 그릴 수도, 디버그 텍스트로 표시할 수도 있다. 렌더링 방식을 바꿔도 시뮬레이션 규칙을 건드릴 필요가 없다는 점이 큰 장점이다.

입력 처리의 순서도 의식해야 한다. 입력을 먼저 읽어 이번 업데이트에 반영할지, 업데이트한 뒤 다음 프레임부터 반영할지는 반응의 체감에 영향을 준다. 일반적으로는 현재 프레임에서 읽은 입력으로 상태를 갱신하고 그 결과를 그리면, 관람객이 입력에 즉시 반응한다고 느낀다.

## 이전 상태를 바로 덮어쓰지 않기

여러 값이 서로를 참조해 동시에 갱신되어야 할 때는 현재 상태를 읽는 버퍼와 다음 상태를 쓰는 버퍼를 분리해야 한다. 예를 들어 격자의 각 셀이 이웃 셀을 보고 다음 값을 계산하는 경우, 한 셀을 먼저 덮어쓰면 뒤의 셀은 이전 프레임과 현재 프레임이 섞인 데이터를 읽게 된다.

```text
for each cell p:
    next[p] = updateCell(current, p)

swap(current, next)
```

입자 목록에서도 반복 중에 객체를 바로 삭제하거나 추가하면 순회가 불안정해질 수 있다. 살아남은 객체를 새 목록에 모으거나, 삭제 대상을 표시한 뒤 순회가 끝난 후 정리하는 방식이 안전하다.

```text
nextParticles = []

for each particle in particles:
    updated = updateParticle(particle, input, deltaTime)
    if updated.age < updated.lifetime:
        nextParticles.add(updated)

particles = nextParticles
```

이처럼 "현재 상태를 읽고, 다음 상태를 만든 뒤, 한 번에 교체한다"는 원칙은 피드백, 셀룰러 오토마타, 물리 시뮬레이션, GPU 텍스처 연산까지 널리 쓰인다.

## 시간 간격과 프레임 독립성

상태 업데이트는 프레임마다 한 번 일어나지만, 실제 프레임 간격은 항상 같지 않다. 업데이트 식에 `deltaTime`을 곱하지 않으면 빠른 기기에서는 더 빨리 움직이고 느린 기기에서는 더 느리게 움직일 수 있다.

$$
\mathbf{p}_{t+\Delta t}=\mathbf{p}_t+
\mathbf{v}_t\Delta t
$$

```text
position += velocity * deltaTime
```

그러나 `deltaTime`이 매우 큰 프레임이 한 번 생기면 충돌을 통과하거나 힘이 과도하게 적용될 수 있다. 실시간 시스템에서는 큰 시간 간격을 제한하거나, 일정한 크기의 작은 단계로 여러 번 업데이트하는 고정 시간 단계(fixed timestep)를 고려할 수 있다.

```text
accumulator += measuredDeltaTime

while accumulator >= fixedStep:
    state = update(state, input, fixedStep)
    accumulator -= fixedStep
```

고정 시간 단계는 물리나 복잡한 상호작용처럼 수치적 안정성이 중요한 시스템에서 특히 유용하다. 반면 단순한 입자 애니메이션이라면 `deltaTime`을 곱하는 가변 시간 단계만으로도 충분한 경우가 많다. 어떤 방식을 쓰든 시간 단위와 업데이트 규칙을 명확하게 분리해 두는 것이 중요하다.

## 초기화, 리셋, 재현성

상태 시스템에는 반드시 시작 상태가 필요하다. `initialize` 함수는 객체의 초기 위치, 난수 시드, 버퍼의 초기 색, 전역 매개변수를 정한다. 시작 상태가 불분명하면 같은 작업을 다시 실행했을 때 다른 결과가 나오거나, 리셋 버튼이 무엇으로 돌아가야 하는지 정의하기 어려워진다.

```text
state = initialize(seed)

if resetRequested:
    state = initialize(seed)
```

고정 시드와 같은 초기 상태, 같은 입력 기록, 같은 시간 단계가 주어지면 결정론적인 시스템은 같은 결과를 재현할 수 있다. 그러나 실제 시간에 의존하는 `deltaTime`, 순서가 불안정한 객체 처리, 외부 입력, 부동소수점 계산의 차이는 결과를 조금씩 다르게 만들 수 있다. 작품을 저장하거나 디버깅해야 한다면 시드, 주요 매개변수, 입력 이벤트, 시간 단계를 기록하는 습관이 도움이 된다.

리셋은 실패를 숨기기 위한 기능이 아니라 시스템의 경계를 보여 주는 기능이기도 하다. 입자가 너무 많이 쌓이거나 피드백이 포화되었을 때, 초기 상태로 돌아갈 수 있어야 새로운 변형을 다시 관찰할 수 있다.

## 상태를 시각화하며 점검하기

상태 시스템이 예상대로 움직이지 않을 때는 최종 이미지만 보지 말고 상태 자체를 드러내야 한다. 입자에는 위치와 속도 방향을 작은 선으로 그릴 수 있고, 격자에는 값의 범위를 회색조로 표시할 수 있으며, 전체 객체 수나 평균 속도 같은 요약값을 확인할 수 있다.

```text
for each particle in state.particles:
    drawPoint(particle.position)
    drawLine(particle.position,
             particle.position + particle.velocity * debugScale)
```

업데이트를 한 번만 실행했을 때와 여러 번 실행했을 때를 비교하면, 오류가 첫 단계부터 있는지 누적으로 생기는지 구분하기 쉽다. 특정 프레임의 상태를 스냅샷으로 저장해 두면, 같은 문제를 반복해서 관찰하거나 렌더링만 바꿔 실험할 수 있다.

상태는 과거를 기억하는 값이며, 그 기억이 화면을 시간 함수보다 풍부하게 만든다. 동시에 초기화, 갱신 순서, 시간 간격, 메모리와 재현성까지 설계해야 하는 책임을 만든다. 다음 절부터는 이 상태가 프레임마다 어떻게 반복 업데이트되고, 이전 출력이 다음 입력으로 되돌아오는지 더 자세히 살펴본다.

## 이 절의 핵심

상태는 과거를 기억해 다음 결과에 전달하는 값이다. 시간 함수가 현재 시간만으로 장면을 계산하는 반면, 상태 시스템은 이전 상태와 현재 입력, 시간 간격으로 다음 상태를 계산한다. 업데이트와 렌더링을 분리하고, 현재 상태와 다음 상태를 구분하며, 초기화와 시간 단계를 명시적으로 설계해야 안정적이고 재현 가능한 시스템을 만들 수 있다.
