# 15.8 시스템 설계를 위한 파라미터 구조

상태 시스템은 시간이 지날수록 많은 값에 의존하게 된다. 생성률, 수명, 감쇠, 이동량, 블러 반경, 입력 강도, 난수 시드, 해상도, 시간 단계처럼 각 값은 다른 역할을 한다. 이 값들을 코드 여러 곳에 흩어 두면 무엇이 어떤 현상을 바꾸는지 알기 어렵고, 좋은 결과를 다시 만들거나 다른 결과와 비교하기도 어려워진다.

파라미터 구조는 값을 한곳에 모아 시스템의 규칙을 읽고 탐색하기 쉽게 만드는 설계 방식이다. 각 값이 무엇을 제어하는지, 어떤 단위를 쓰는지, 안전한 범위가 어디인지, 다른 값과 어떤 관계를 맺는지 드러나야 한다.

## 역할에 따라 파라미터를 묶기

먼저 값을 이름순이 아니라 시스템에서 맡는 역할에 따라 묶는다. Chapter 15에서 다룬 상태 시스템은 대체로 시간, 생성, 변화, 피드백, 렌더링, 재현성의 층으로 나눌 수 있다.

```text
parameters = {
    time: {
        fixedStep,
        timeScale,
        maximumFrameTime
    },
    emission: {
        rate,
        lifetime,
        maximumCount,
        spawnRegion
    },
    evolution: {
        responseRate,
        damping,
        threshold
    },
    feedback: {
        amount,
        decayRate,
        blurRadius,
        displacement
    },
    rendering: {
        markSize,
        opacity,
        palette,
        simulationScale
    },
    reproducibility: {
        seed,
        resetMode
    }
}
```

이 구조는 특정 언어의 문법이 아닌 설계 예시다. `emission.rate`에서는 생성률을, `feedback.decayRate`에서는 이전 결과의 감쇠와 관련된 값을 바로 알아볼 수 있다. `speed`, `amount`, `value2`처럼 의미가 넓은 이름은 시간이 지나면 어떤 규칙에 연결되었는지 파악하기 어렵다.

역할별 묶음은 제어 화면을 만들 때도 유리하다. 생성 관련 컨트롤과 피드백 관련 컨트롤을 서로 다른 패널에 두면 실험의 종류를 구분하기 쉽다. 그룹으로 나눈 값 사이에도 규칙상 의존성이 있을 수 있다. 예를 들어 생성률과 수명은 서로 다른 그룹에 두더라도 화면의 평균 요소 수를 함께 결정한다.

## 이름에 단위와 의미를 담기

파라미터 이름은 값의 의미를 알려 주어야 한다. `speed = 2`만으로는 초당 2픽셀인지, 초당 2라디안인지, 시간 배율이 2배인지 알 수 없다. 같은 숫자라도 단위에 따라 뜻이 달라진다.

| 값의 역할 | 권장 단위 또는 해석 | 이름 예 |
| --- | --- | --- |
| 생성량 | 요소/초 | `spawnRate` |
| 수명 | 초 | `lifetimeSeconds` |
| 속도 | 거리/초 | `particleSpeed` |
| 각속도 | 라디안/초 | `angularSpeed` |
| 감쇠 | 1/초 또는 반감기(초) | `decayRate`, `halfLife` |
| 블러 반경 | 픽셀 또는 정규화 거리 | `blurRadiusPixels` |
| 불투명도 | $[0,1]$ | `markOpacity` |
| 확률 | $[0,1]$ | `spawnProbability` |

특히 시간 기반 시스템에서는 프레임당 변화량과 초당 변화량을 구분해야 한다. `fade = 0.98`처럼 프레임마다 곱하는 값은 프레임 속도에 따라 실제 기억 길이가 달라질 수 있다. 반면 `decayRate`를 1/초 단위로 두고 $e^{-\lambda\Delta t}$로 변환하면 시간 기준의 의미를 유지할 수 있다.

```text
fadeForFrame = exp(-decayRate * deltaTime)
buffer *= fadeForFrame
```

사용자가 값을 직접 조절하는 인터페이스에서는 단위를 라벨이나 도움말에 드러내는 것이 좋다. 그러나 화면 안에 불필요하게 설명문을 늘리는 대신, 값의 이름과 그룹 제목, 적절한 입력 컨트롤의 범위가 의미를 전달하도록 설계할 수 있다.

## 원시 파라미터와 파생값을 구분하기

사용자가 직접 조절할 값과, 그 값에서 계산되는 값을 분리하면 시스템이 단순해진다. 예를 들어 사용자는 루프 길이와 반복 횟수를 정하고, 프로그램은 각속도를 계산할 수 있다.

$$
\omega=2\pi\frac{n}{T}
$$

```text
loopDuration = parameters.time.loopDuration
cycles = parameters.motion.cyclesPerLoop
angularSpeed = TAU * cycles / loopDuration
```

마찬가지로 생성률과 평균 수명에서 예상 총량을 계산하거나, 반감기에서 감쇠율을 계산할 수 있다.

$$
N_{\text{expected}}\approx r\overline{L}
$$

$$
\lambda=\frac{\ln 2}{h}
$$

```text
expectedCount = spawnRate * averageLifetime
decayRate = ln(2) / halfLife
```

원시 파라미터와 파생값을 모두 독립적인 슬라이더로 두면 모순된 상태가 생길 수 있다. 예를 들어 주기와 주파수를 모두 수정 가능하게 두면 둘 중 무엇이 실제 규칙인지 불분명해진다. 하나를 주된 제어값으로 정하고, 나머지는 읽기 전용 정보 또는 내부 계산값으로 두는 편이 좋다.

## 기본값, 범위, 중립값을 설계하기

파라미터에는 기본값과 허용 범위가 필요하다. 기본값은 처음 표시할 숫자에 그치지 않고, 시스템의 정체성을 보여 주는 출발점이 된다. 범위는 사용자가 탐색할 수 있는 공간을 정한다. 지나치게 넓으면 유효하지 않은 결과가 많아지고, 너무 좁으면 의미 있는 변화를 찾기 어렵다.

```text
parameterSpec = {
    spawnRate: { default: 20, min: 0, max: 200, unit: "elements/s" },
    halfLife: { default: 1.2, min: 0.05, max: 10, unit: "s" },
    feedbackAmount: { default: 0.94, min: 0, max: 0.999 },
    blurRadius: { default: 1, min: 0, max: 12, unit: "px" }
}
```

가능하다면 중립값도 정한다. 중립값은 해당 효과가 결과를 바꾸지 않거나 가장 약하게 만드는 값이다. 예를 들어 `blurRadius = 0`은 블러 없음, `displacement = (0, 0)`은 좌표 이동 없음, `spawnRate = 0`은 새 요소 생성 없음에 해당한다. 중립값을 알면 효과를 켠 상태와 끈 상태를 쉽게 비교할 수 있다.

모든 파라미터에서 $0$이 안전한 중립값인 것은 아니다. 스케일은 $0$이면 좌표 계산이 불가능할 수 있고, 수명은 $0$이면 요소가 즉시 사라질 수 있다. 이런 값에는 물리적 또는 수치적 하한을 두고, 인터페이스에서 로그 스케일이나 단계형 선택지를 사용할 수 있다.

## 선형 슬라이더만으로는 충분하지 않다

사람이 인지하는 변화와 파라미터의 수치 변화가 항상 선형으로 대응하지는 않는다. 수명, 주파수, 블러 반경, 입자 수처럼 넓은 범위를 갖는 값은 선형 슬라이더에서 한쪽 구간이 너무 민감하거나 둔하게 느껴질 수 있다.

양수 범위의 값에는 로그 매핑이 유용하다.

$$
v=v_{\min}\left(\frac{v_{\max}}{v_{\min}}\right)^u
$$

여기서 $u\in[0,1]$은 제어 입력이다. $u$가 일정하게 변해도 값은 비율적으로 변한다. 예를 들어 0.1초부터 10초까지의 수명이나, 0.01부터 10까지의 세기를 조절할 때 작은 값 부근도 충분히 세밀하게 다룰 수 있다.

```text
value = minimumValue * pow(maximumValue / minimumValue, normalizedControl)
```

방향, 팔레트, 블렌딩 방식, 경계 처리처럼 몇 가지 선택지로 표현하는 값은 메뉴나 세그먼트 컨트롤이 자연스럽다. 불리언 상태는 토글로, 색은 색상 선택기나 스와치로, 정수 개수는 스테퍼나 정수 입력으로 다루면 값의 성격이 잘 드러난다.

## 파라미터 사이의 의존성 드러내기

복잡한 시스템에서 파라미터는 서로 영향을 주고받는다. 생성률과 수명은 총량을 함께 결정하고, 피드백량과 입력 강도는 버퍼의 평균 밝기를 함께 바꾸며, 시뮬레이션 해상도와 블러 반경은 확산의 시각적 크기를 함께 정한다. 이런 의존성이 드러나지 않으면 한 값을 바꾸었을 때 다른 현상이 달라지는 이유를 파악하기 어렵다.

모든 관계를 자동으로 보정할 필요는 없다. 중요한 파생값을 표시하거나 안전한 상한을 둘 수 있다.

```text
estimatedCount = spawnRate * averageLifetime
maximumCount = max(maximumCount, ceil(estimatedCount))

if simulationScale < 0.5:
    blurRadius = min(blurRadius, safeBlurLimit)
```

자동 보정은 편리하지만 사용자가 의도한 극단적인 설정을 제한할 수 있다. 기본 모드에서는 안전한 범위를 유지하고, 실험 모드에서는 경고와 함께 범위를 넓히는 식으로 역할을 나눌 수 있다.

## 프리셋은 결과가 아니라 조건을 저장한다

결과를 재현하려면 이미지와 함께 그 결과가 나온 조건도 저장해야 한다. 여기에는 관련 파라미터와 시스템의 초기 조건이 포함된다.

```text
preset = {
    version: 1,
    seed,
    parameters,
    simulation: {
        width,
        height,
        fixedStep,
        initialStateMode
    }
}
```

시드, 해상도, 고정 시간 단계, 초기화 방식은 결과에 영향을 준다. 특히 버퍼 기반 시스템은 해상도가 바뀌면 텍셀 크기, 블러, 변위, 임계값의 의미까지 달라질 수 있다. 따라서 프리셋에는 시각적 파라미터와 실행 조건을 함께 저장한다.

`version`은 시간이 지나 파라미터 이름이나 규칙이 바뀔 때 중요하다. 이전 프리셋을 새 구조에 맞게 변환하거나, 어떤 버전의 규칙에서 나온 결과인지 기록할 수 있다. 이 정보는 작품을 저장하고 나중에 탐색 과정을 되짚는 데 필요하다.

## 변화 기록과 비교

파라미터 탐색은 값을 무작정 움직이는 과정이 아니라 가설을 시험하는 과정이 될 수 있다. 한 번에 하나의 값 또는 같은 역할의 작은 묶음만 바꾸고, 나머지 조건을 고정하면 어떤 변화가 어떤 결과를 만들었는지 판단하기 쉽다.

```text
experiment = {
    basePreset: "quiet-flow",
    changed: { feedbackAmount: 0.96 },
    note: "longer trails, same injection"
}
```

특정 시점의 스냅샷, 짧은 루프, 평균 밝기나 요소 수 같은 측정값을 프리셋과 함께 남기면, 며칠 뒤에도 탐색의 방향을 잃지 않는다. 사용자 입력이 있는 작품은 입력이 없을 때의 기본 상태와 대표 입력 시퀀스도 함께 기록해야 비교가 공정해진다.

파라미터를 바꿀 때 상태를 초기화해야 하는지도 구분한다. 팔레트나 선 굵기처럼 렌더링만 바꾸는 값은 즉시 적용할 수 있지만, 격자 해상도, 난수 시드, 초기 상태의 종류처럼 상태의 의미를 바꾸는 값은 재초기화가 필요할 수 있다.

```text
if changedParameter.requiresReset:
    state = initialize(parameters, seed)
else:
    applyParameterImmediately(changedParameter)
```

이 기준을 정해 두면 이전 상태의 영향으로 변화가 즉시 드러나지 않는 상황을 줄이고, 파라미터가 적용되는 시점도 명확히 할 수 있다.

## 점검을 위한 최소 구조

시스템이 커질수록 모든 파라미터를 한꺼번에 노출하기보다, 현재 탐색 중인 역할에 필요한 값만 우선 보이는 것이 좋다. 하지만 개발과 디버깅 단계에서는 최소한 다음을 확인할 수 있어야 한다.

- 현재 프리셋과 시드
- 실제 시간 단계와 누적 업데이트 횟수
- 요소 수 또는 버퍼 값의 범위
- 생성, 감쇠, 피드백에 관한 핵심 파라미터
- 상태를 초기화하는 리셋 동작

이 정보는 제작 과정에서 시스템을 안전하게 관찰하고 조절하는 작업 도구다. 최종 전시 화면에서는 감출 수 있지만, 제작 중에는 파라미터가 어떤 상태를 만드는지 확인하는 통로가 된다.

좋은 파라미터 구조는 시스템의 가능성을 줄이는 규칙집이 아니다. 오히려 어느 값이 무엇을 바꾸는지 분명히 하여, 의도적인 실험과 우연한 발견 모두를 더 멀리 밀어 주는 기반이다. Chapter 15에서 만든 시간, 상태, 누적, 피드백, 생애 주기 규칙은 이런 구조 안에서 비로소 반복해서 비교하고 발전시킬 수 있다.

## 이 절의 핵심

파라미터를 역할, 단위, 범위, 중립값에 따라 구조화하면 복잡한 시스템도 재현하고 탐색할 수 있다. 사용자가 조절할 원시 파라미터와 내부에서 계산할 파생값을 구분하고, 중요한 의존성과 안전 범위를 드러낸다. 프리셋에는 시드, 해상도, 시간 단계, 초기화 방식까지 저장하며, 변경 기록과 리셋 조건을 함께 관리해야 결과를 신뢰성 있게 비교할 수 있다.
