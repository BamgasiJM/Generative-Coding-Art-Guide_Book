# 23.5 이미지, 영상, 사운드와 데이터

openFrameworks는 도형을 직접 그리는 것 외에도 이미지, 영상, 사운드 파일과 실시간 미디어를 작품의 입력이나 재료로 사용할 수 있다. 이때 미디어는 단순히 화면에 표시되는 배경에 그치지 않는다. 이미지의 밝기, 영상 프레임의 색, 오디오의 진폭이나 주파수처럼 미디어에서 계산한 값을 좌표·크기·색상·입자 생성 규칙에 연결할 수 있다.

미디어마다 데이터가 갱신되는 단위가 다르다. 정지 이미지는 한 번 불러오면 같은 픽셀을 계속 제공하고, 영상은 시간이 지나며 프레임이 바뀌며, 오디오는 초당 수만 개의 샘플을 연속적으로 다룬다. 이 차이를 고려해 로드, 분석, 상태 갱신, 화면 표현을 설계해야 한다.

| 미디어 | 주요 데이터 단위 | 자주 쓰는 역할 |
| --- | --- | --- |
| 이미지 | 픽셀과 텍스처 | 정적 재료, 색·밝기 기반 배치 |
| 영상 | 시간에 따라 바뀌는 프레임 | 움직임 추출, 프레임 합성 |
| 오디오 파일 | 샘플과 재생 시간 | 음악 재생, 파형·특징 계산 |
| 실시간 오디오 | 짧은 샘플 버퍼 | 음량·주파수에 반응하는 시각화 |
| 숫자 데이터 | 시간표시가 있는 값의 열 | 그래프, 매핑, 시뮬레이션 입력 |

## 정지 이미지와 픽셀 데이터

`ofImage`는 이미지 파일을 불러오고 화면에 그릴 수 있게 해준다. 프로젝트의 미디어 파일은 보통 프로젝트의 `bin/data` 아래에 두고, 상대 경로로 불러온다.

```cpp
ofImage source;
bool sourceLoaded = false;

void ofApp::setup() {
    sourceLoaded = source.load("images/source.jpg");
}

void ofApp::draw() {
    ofBackground(248);
    if (sourceLoaded) {
        source.draw(0.0f, 0.0f);
    }
}
```

`load()`의 성공 여부를 확인하면 파일이 없거나 읽을 수 없는 상황을 처리할 수 있다. 크기를 지정해 `draw(x, y, width, height)`로 표시할 수도 있지만, 원본과 표시 영역의 가로세로 비율이 다르면 이미지가 늘어나거나 찌그러진다. 비율을 유지하려면 원본 크기와 캔버스 크기 중 어느 쪽에 맞출지 정하고 남는 여백을 계산한다.

이미지는 픽셀의 격자이기도 하다. `ofImage`의 픽셀 데이터는 `ofPixels`로 접근할 수 있고, 한 좌표의 색을 읽어 밝기나 색상에 따라 다른 규칙을 적용할 수 있다.

```cpp
const ofPixels& pixels = source.getPixels();
const ofColor sample = pixels.getColor(pixelX, pixelY);
const float brightness = sample.getBrightness() / 255.0f;
```

예를 들어 밝은 픽셀에 큰 원을 놓고 어두운 픽셀에는 작은 원을 놓으면 원본 이미지의 밝기 구조가 점 패턴으로 바뀐다. 좌표를 화면 전체에서 균일하게 샘플링할 수도 있고, 원본 픽셀의 밝기에 따라 샘플링 확률을 조절할 수도 있다. 이미지 데이터가 어떻게 기하학적 형태로 변환되는지에 따라 원본의 윤곽, 명암 또는 색이 작품의 구조가 된다.

CPU에서 `ofPixels`를 수정한 뒤 그 결과를 화면에 표시하려면 픽셀 데이터와 GPU 텍스처 간의 동기화가 필요하다. `ofImage`의 픽셀을 변경한 경우 `update()`를 호출해 변경된 픽셀을 텍스처에 반영한다. 반대로 이미지를 그리기만 한다면 매 프레임 모든 픽셀을 읽고 복사할 필요는 없다. 고해상도 이미지를 매 프레임 전부 순회하는 작업은 비용이 크므로, 샘플 간격을 넓히거나 저해상도 분석용 데이터를 따로 만들 수 있다. 픽셀마다 동일한 복잡한 계산을 대량으로 수행해야 한다면 23.7에서 다룰 GPU 셰이더가 더 적합할 수 있다.

## 영상과 시간에 따른 프레임

`ofVideoPlayer`는 영상 파일을 재생하고 현재 프레임을 화면에 표시하는 데 사용한다. 이미지를 한 번 읽는 것과 달리, 영상 플레이어는 재생 상태와 디코딩된 프레임을 계속 갱신해야 한다.

```cpp
ofVideoPlayer video;
bool videoLoaded = false;

void ofApp::setup() {
    videoLoaded = video.load("video/clip.mp4");
    if (videoLoaded) {
        video.play();
    }
}

void ofApp::update() {
    if (videoLoaded) {
        video.update();
    }
}

void ofApp::draw() {
    ofBackground(20);
    if (videoLoaded) {
        video.draw(0.0f, 0.0f,
                   static_cast<float>(ofGetWidth()),
                   static_cast<float>(ofGetHeight()));
    }
}
```

`update()`에서 플레이어를 갱신하고 `draw()`에서 현재 프레임을 그린다. 창 크기 전체에 바로 그리면 영상 비율과 창 비율이 다를 때 프레임이 늘어날 수 있으므로, 실제 작업에서는 비율을 유지한 출력 영역이나 크롭 방식을 선택한다. 영상은 프레임률이 화면의 프레임률과 다를 수 있으며, 디코더가 항상 새 프레임을 제공하는 것은 아니다. 화면이 그려질 때마다 영상 프레임의 번호가 반드시 하나씩 증가한다고 가정하지 않는다.

영상에서 픽셀이나 움직임을 분석할 때는 목적에 맞는 특징만 계산한다. 전체 해상도를 매 프레임 순회하는 대신 일정 간격으로 픽셀을 샘플링하거나, 밝기 평균과 같은 요약값을 구해 입자의 밀도나 도형의 크기에 연결할 수 있다. 과거 프레임과 현재 프레임의 차이는 움직임을 추정하는 단순한 방법이지만, 카메라 노이즈와 조명 변화도 차이로 나타날 수 있어 보정이 필요하다.

## 사운드 재생과 실시간 오디오

사운드 파일 재생에는 `ofSoundPlayer`를 사용할 수 있다.

```cpp
ofSoundPlayer player;
bool soundLoaded = false;

void ofApp::setup() {
    soundLoaded = player.load("audio/texture.wav");
    if (soundLoaded) {
        player.play();
    }
}
```

파일 재생은 미리 준비한 소리를 재생하는 방식이다. 마이크 입력을 분석하거나 직접 샘플을 생성하려면 `ofSoundStream`과 오디오 버퍼를 사용한다. 오디오 콜백은 일정한 길이의 샘플 블록을 빠르게 처리하도록 호출되며, 이 콜백의 시간 제약은 화면의 `draw()`와 다르다. 화면은 초당 수십 번 갱신될 수 있지만 오디오는 더 작은 시간 단위로 연속 처리되어야 한다.

실시간 오디오 콜백에서는 도형을 그리거나, 파일 입출력을 하거나, 오래 걸리는 메모리 할당과 대기 작업을 수행하지 않는 편이 좋다. 콜백이 늦어지면 오디오가 끊기거나 잡음이 생길 수 있다. 대신 샘플 블록에서 음량 같은 간단한 특징을 계산해 공유하고, 그래픽의 `update()`가 그 특징을 읽어 작품 상태에 반영하도록 한다. 오디오와 그래픽이 서로 다른 스레드에서 동작할 수 있으므로 값을 전달할 때는 스레드 안전한 구조나 짧고 명확한 동기화 방식을 사용한다.

가장 간단한 음량 특징 중 하나는 RMS(root mean square)다. 샘플을 제곱해 평균한 뒤 제곱근을 구하면 신호의 에너지를 나타내는 값이 된다.

$$
\mathrm{RMS}=\sqrt{\frac{1}{N}\sum_{i=0}^{N-1}x_i^2}
$$

실수 오디오 샘플이 대략 `-1`에서 `1` 사이로 정규화되어 있다면 RMS는 음량 변화의 요약값으로 사용할 수 있다. 이 값을 원의 반지름, 선의 두께, 입자 방출률에 연결하면 오디오 반응형 그래픽을 만들 수 있다. 높은 음과 낮은 음을 구분하려면 파형의 크기뿐 아니라 주파수 분석이 필요하며, FFT 같은 계산이나 관련 애드온을 활용할 수 있다. 음량은 소리 크기에 반응하지만 주파수 대역은 소리의 음색과 리듬에 반응한다는 차이가 있다.

## 숫자 데이터와 시각적 매핑

파일이나 센서에서 얻은 숫자 데이터도 미디어와 같은 방식으로 시각 규칙에 연결할 수 있다. 먼저 데이터의 의미와 단위를 확인하고, 작품의 파라미터 범위에 맞게 매핑한다. 예를 들어 온도, 시간, 주파수처럼 단위가 다른 값을 그대로 같은 축에 놓으면 비교가 왜곡될 수 있다.

$$
u=\operatorname{clamp}\left(\frac{x-x_{min}}{x_{max}-x_{min}},0,1\right),\qquad
y=y_{min}+u(y_{max}-y_{min})
$$

여기서 `x`는 입력 데이터, `[x_min, x_max]`는 입력 범위, `[y_min, y_max]`는 화면에서 사용할 출력 범위다. 입력 범위의 끝점이 같으면 나눗셈을 할 수 없으므로 데이터가 상수인 경우도 처리해야 한다. 값의 단위, 누락값, 측정 주기, 범위를 확인한 다음 색상·위치·크기·속도 같은 시각 속성으로 바꾸는 순서를 유지하면 데이터에서 어떤 시각적 차이가 나왔는지 설명하기 쉽다.

시간 데이터는 샘플 시각과 함께 보관한다. 일정한 시간 간격으로 기록되지 않은 값들을 단순히 인덱스 간격으로 나열하면 실제 시간 간격이 왜곡될 수 있다. 데이터의 시간표시를 이용해 x좌표를 계산하거나, 화면에 표현할 시간 구간을 먼저 정한다. 큰 데이터는 화면 픽셀 수보다 많은 점을 모두 그리는 대신 구간별 평균·최솟값·최댓값을 계산해 축약할 수 있다.

## 미디어를 다루는 공통 원칙

이미지, 영상, 오디오, 숫자 데이터는 모두 작품의 규칙에 들어가기 전에 해석과 변환을 거친다. 정지 이미지의 밝기는 한 번 계산해 저장할 수 있고, 영상 프레임의 밝기는 시간에 따라 갱신되며, 오디오 특징값은 그래픽 프레임보다 빠른 오디오 블록마다 바뀔 수 있다. 각 데이터가 언제 새로 생기는지에 맞춰 계산 위치를 정한다.

로드 실패와 입력 없음도 고려해야 한다. 이미지나 영상 파일이 없을 때 대체 화면을 보여주고, 오디오 장치가 없거나 권한이 거부되었을 때도 기본 상태로 스케치가 계속 동작하도록 만들 수 있다. 미디어를 반드시 읽어야만 작품이 실행되는 구조보다, 일부 입력이 없을 때에도 의미 있는 결과를 보여주는 구조가 설치와 배포에서 견고하다.

CPU에서 픽셀을 읽고 변환할지, GPU 텍스처와 셰이더로 처리할지는 계산의 종류와 크기에 따라 결정한다. 데이터의 일부 특징만 필요하다면 CPU에서 샘플링하는 편이 단순할 수 있고, 화면의 모든 픽셀에 같은 규칙을 적용해야 한다면 GPU 처리가 유리할 수 있다. 미디어 데이터를 어떤 표현으로 연결할지는 성능뿐 아니라 작품의 개념과도 관계가 있다.

## 이 절의 핵심

`ofImage`, `ofVideoPlayer`, `ofSoundPlayer`, `ofSoundStream`은 서로 다른 시간 구조의 미디어를 다루는 도구다. 이미지는 픽셀과 텍스처, 영상은 시간에 따라 바뀌는 프레임, 오디오는 샘플 버퍼와 요약 특징값으로 접근할 수 있다. 데이터를 작품 파라미터로 매핑하고 각 매체의 갱신 주기와 성능 제약을 고려하면 미디어를 제너레이티브 규칙의 입력이자 재료로 활용할 수 있다.
