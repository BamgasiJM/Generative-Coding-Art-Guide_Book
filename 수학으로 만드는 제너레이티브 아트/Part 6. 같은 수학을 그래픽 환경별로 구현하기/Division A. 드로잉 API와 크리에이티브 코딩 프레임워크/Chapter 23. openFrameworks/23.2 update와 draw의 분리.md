# 23.2 update와 draw의 분리

openFrameworks 애플리케이션은 프레임워크가 관리하는 반복 흐름 안에서 작품의 상태를 계산하고 화면에 표현한다. `setup()`은 시작할 때 초기화에 사용하고, `update()`는 다음 상태를 계산하며, `draw()`는 현재 상태를 화면에 그린다. 이 절에서는 특히 매 프레임 호출되는 `update()`와 `draw()`를 분리하는 이유를 살펴본다.

```text
setup()                 초기 상태 준비
update()                현재 상태를 갱신
draw()                  갱신된 상태를 화면에 표현
update() -> draw()      반복
```

`update()`는 위치, 속도, 각도, 입자 수명처럼 시간이 흐르며 변하는 값을 다룬다. `draw()`는 그 값을 도형이나 선으로 바꾸어 렌더링한다. 업데이트와 렌더링을 나누면 한 상태를 여러 표현 방식으로 그릴 수 있고, 화면을 다시 그리는 과정에서 시뮬레이션이 의도치 않게 진행되는 문제도 줄어든다.

## 상태를 갱신하는 `update()`

예를 들어 움직이는 원은 위치와 속도를 상태로 가진다. 매 프레임 위치를 일정한 값만큼 이동시키면 간단하지만, 그 이동량은 프레임 횟수에 종속된다.

```cpp
position.x += 2.0f;
```

이 코드는 프레임마다 2픽셀씩 움직인다. 초당 60프레임으로 실행되면 초당 약 120픽셀을 이동하고, 초당 120프레임으로 실행되면 약 240픽셀을 이동한다. 컴퓨터의 성능이나 창의 부하에 따라 움직임 속도가 달라질 수 있다.

프레임률에 덜 의존하는 움직임을 만들려면 프레임 사이의 실제 경과 시간 `dt`를 사용한다. openFrameworks의 `ofGetLastFrameTime()`은 직전 프레임 이후 흐른 시간을 초 단위로 제공한다. 속도를 픽셀/초 단위로 표현하면 위치 변화량은 속도에 `dt`를 곱해 계산할 수 있다.

$$
\mathbf{p}_{next} = \mathbf{p}_{current} + \mathbf{v}\,dt
$$

아래 예제는 원이 캔버스 안에서 움직이고 가장자리에 닿으면 방향을 바꾸는 상태를 구현한다.

```cpp
// ofApp.h에 둘 상태와 콜백 선언
class ofApp : public ofBaseApp {
public:
    void setup() override;
    void update() override;
    void draw() override;

private:
    glm::vec2 position {0.0f, 0.0f};
    glm::vec2 velocity {145.0f, 95.0f};
    float radius = 18.0f;
};
```

```cpp
// ofApp.cpp의 구현
void ofApp::setup() {
    ofSetFrameRate(60);
    position = glm::vec2(ofGetWidth() * 0.5f,
                         ofGetHeight() * 0.5f);
}

void ofApp::update() {
    const float dt = ofClamp(ofGetLastFrameTime(), 0.0f, 0.05f);
    position += velocity * dt;

    if (position.x < radius || position.x > ofGetWidth() - radius) {
        position.x = ofClamp(position.x, radius, ofGetWidth() - radius);
        velocity.x *= -1.0f;
    }

    if (position.y < radius || position.y > ofGetHeight() - radius) {
        position.y = ofClamp(position.y, radius, ofGetHeight() - radius);
        velocity.y *= -1.0f;
    }
}

void ofApp::draw() {
    ofBackground(248);
    ofSetColor(40, 120, 170);
    ofDrawCircle(position.x, position.y, radius);
}
```

`velocity`의 각 성분은 초당 이동하는 픽셀 수이고, `position`은 현재 위치다. `position += velocity * dt`는 실제로 지난 시간만큼 위치를 진행시킨다. `ofSetFrameRate(60)`은 프레임률의 목표를 설정할 뿐 모든 프레임이 정확히 같은 간격으로 도착한다고 보장하지 않는다. 따라서 움직임의 시간 단위를 분명히 하고 실제 경과 시간을 사용하는 편이 안정적이다. `ofGetFrameRate()`는 측정된 프레임률을 보여주는 값으로, 개별 프레임의 시간 간격인 `dt`와는 역할이 다르다.

예제의 `ofClamp()`는 `dt`가 최대 0.05초를 넘지 않도록 제한한다. 창이 가려지거나 디버거에서 실행을 멈췄다가 다시 시작하면 큰 시간 간격이 한 번에 들어와 원이 화면 밖으로 크게 이동할 수 있다. `dt`를 제한하면 한 번의 갱신에서 발생하는 큰 점프를 줄일 수 있지만, 멈춰 있던 시간 전체를 시뮬레이션에 반영하지는 않는다. 이는 시각적 안정성을 위한 선택이지 모든 시스템에 맞는 보정법은 아니다.

## 화면을 표현하는 `draw()`

`draw()`는 현재 상태를 읽어 화면을 그린다. 위 예제에서는 `position`을 참조해 원을 그리지만, 위치와 속도를 수정하지 않는다. 이 원칙 덕분에 같은 상태를 다시 그려도 시뮬레이션의 결과가 달라지지 않는다. 상태 계산과 화면 표현을 분리하면 같은 입자 데이터를 점, 원, 선, 이미지 등 여러 방식으로 시험할 수 있다.

`ofBackground(248)`는 매 프레임 화면을 배경색으로 채운다. 보통 이전 프레임의 그림을 지우고 현재 상태만으로 새 화면을 구성하므로, 원은 흔적을 남기지 않고 이동한다. 이 호출을 생략하거나 별도의 렌더 타깃에서 배경을 부분적으로 덮으면 이전 프레임의 흔적이 남아 궤적이나 잔상이 된다. 즉, 배경을 지우는 방식은 단순한 초기화가 아니라 작품의 시간 표현을 결정한다. 누적 드로잉은 16.8에서 다룬 원리와 연결된다.

한 프레임 안에서 그리는 순서도 화면에 영향을 준다. 배경을 먼저 그리고 원이나 입자를 나중에 그리면 앞의 요소가 위에 표시된다. 색이나 선 두께 같은 드로잉 스타일도 프레임마다 필요한 값을 명시하면 이전 그리기의 스타일에 기대지 않고 결과를 통제할 수 있다.

## 시간 간격과 시뮬레이션

`dt`를 사용하면 속도가 일정한 직선 운동은 프레임률에 비교적 독립적으로 표현할 수 있다. 가속도가 있는 운동에서는 가속도로 속도를 바꾸고, 새 속도로 위치를 바꾸는 순서를 사용한다.

```cpp
velocity += acceleration * dt;
position += velocity * dt;
```

이 계산은 매 프레임의 `dt`가 너무 크면 결과가 거칠어질 수 있다. 특히 입자 간 충돌, 스프링, 유체, 반응-확산처럼 상태가 서로 강하게 영향을 주는 시뮬레이션에서는 불규칙한 시간 간격이 안정성이나 재현성에 영향을 줄 수 있다.

그런 경우 렌더링 프레임과 시뮬레이션의 시간 간격을 분리해 고정 시간 단계(fixed timestep)를 사용할 수 있다. 개념적으로는 측정한 시간을 누적하고, 정해진 `fixedStep`만큼 시간이 쌓일 때마다 시뮬레이션을 한 번 갱신한다.

```cpp
accumulator += measuredDt;
while (accumulator >= fixedStep) {
    updateSimulation(fixedStep);
    accumulator -= fixedStep;
}
drawCurrentState();
```

예를 들어 `fixedStep`을 `1.0f / 60.0f`초로 두면 시뮬레이션은 일정한 간격으로 진행되고, 화면 그리기는 모니터와 시스템의 프레임 속도에 맞춰 수행할 수 있다. 프레임이 느려질 때 한 번의 렌더링 전에 여러 번 상태를 갱신해야 할 수 있으므로, 업데이트 비용이 너무 크지 않도록 설계해야 한다. 위치를 보간해 그리면 고정 단계와 렌더 프레임 사이의 움직임을 더 부드럽게 표현할 수도 있지만, 간단한 제너레이티브 드로잉에서는 가변 `dt` 방식으로 충분한 경우가 많다.

## 입력과 프레임의 관계

마우스나 키 입력은 보통 이벤트 콜백에서 읽거나, 프레임마다 현재 입력 상태를 확인해 `update()`에 반영한다. 예를 들어 마우스 위치를 목표점으로 삼는다면 `update()`에서 입자의 위치를 목표를 향해 이동시키고, `draw()`는 이동 결과를 표현한다. 입력을 어떤 시점에 읽고 적용할지는 한 프레임 안에서 입력, 업데이트, 그리기가 실행되는 순서와 관련된다. 이벤트 콜백과 장치 연결은 23.4에서 자세히 다룬다.

상태 변경을 `draw()`에 넣지 않으면 그리기를 일시 중지하거나 다른 렌더링 방식으로 바꾸기도 쉬워진다. 반대로 `draw()` 안에서 `position.x += ...`처럼 상태를 바꾸면 화면을 그리는 횟수 자체가 작품의 시간 진행을 결정하게 된다. 프레임률 변경이나 캡처·내보내기 과정에서 결과가 달라질 수 있으므로, 시간에 따른 계산은 `update()`에 두는 편이 의도를 분명히 한다.

## 이 절의 핵심

`update()`는 `dt`와 현재 상태를 이용해 다음 상태를 계산하고, `draw()`는 그 상태를 화면에 표현한다. `ofGetLastFrameTime()`으로 실제 경과 시간을 반영하면 프레임률 변화에 따른 이동 속도 차이를 줄일 수 있으며, `ofBackground()`를 호출할지 여부에 따라 이전 프레임을 지우거나 흔적을 남길 수 있다. 시뮬레이션의 성격에 따라 가변 시간 간격이나 고정 시간 단계를 선택하면 된다.
