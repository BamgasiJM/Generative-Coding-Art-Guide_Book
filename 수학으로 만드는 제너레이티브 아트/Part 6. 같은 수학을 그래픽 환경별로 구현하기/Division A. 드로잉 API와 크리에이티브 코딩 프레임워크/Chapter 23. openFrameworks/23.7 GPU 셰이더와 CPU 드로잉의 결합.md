# 23.7 GPU 셰이더와 CPU 드로잉의 결합

openFrameworks에서 `ofDrawCircle()`이나 `ofDrawRectangle()`을 호출한다고 해서 CPU가 화면의 모든 픽셀을 직접 칠하는 것은 아니다. C++ 애플리케이션은 장면과 드로잉 명령을 준비하고, 그래픽 드라이버는 이를 GPU의 렌더링 파이프라인으로 전달한다. 여기서 말하는 CPU 드로잉은 CPU 쪽 코드가 도형·상태·반복 규칙을 구성한다는 뜻에 가깝다. 기본 도형도 실제 픽셀로 바뀌는 과정에는 GPU가 참여한다.

CPU와 GPU의 역할을 나누면 제너레이티브 시스템을 효율적으로 설계할 수 있다. CPU는 입자 상태, 입력 이벤트, 구조체와 자료 구조, 복잡한 개체 간 상호작용을 관리하는 데 편리하다. GPU는 많은 정점이나 프래그먼트에서 비슷한 계산을 동시에 수행하는 데 강하다. 어느 한쪽이 항상 더 빠른 것은 아니며, 데이터가 어디에 있고 어떤 계산을 얼마나 반복하는지가 중요하다.

| 처리 위치 | 잘 맞는 작업 | openFrameworks에서 만나는 요소 |
| --- | --- | --- |
| CPU 애플리케이션 코드 | 입력, 상태 갱신, 입자 생성, 규칙과 자료 구조 | `ofApp`, `update()`, `std::vector` |
| GPU 렌더링 파이프라인 | 정점 변환, 픽셀 색 계산, 텍스처 합성 | `ofShader`, 그래픽 드로잉 API |
| 중간 렌더 표면 | 장면 저장, 여러 단계의 합성·후처리 | `ofFbo`, 텍스처 |

## CPU가 장면을 만들고 GPU가 픽셀을 계산하기

일반적인 CPU 기반 파티클 시스템은 `update()`에서 입자의 위치와 속도를 계산하고, `draw()`에서 입자마다 `ofDrawCircle()`을 호출한다. 이렇게 그린 원은 여러 개별 도형이며 각 입자의 상태를 C++ 코드에서 쉽게 제어할 수 있다. 반면 프래그먼트 셰이더(fragment shader)는 그려지는 표면의 각 프래그먼트에서 좌표와 파라미터로 색을 계산한다. 화면 전체에 원형 파동이나 거리 필드를 만들 때는 원마다 드로잉 명령을 내리는 대신, 화면을 덮는 사각형 하나에 셰이더를 적용해 각 위치의 색을 계산할 수 있다.

다음 예제는 OpenGL 3 계열에서 사용하는 GLSL 1.50 형식의 간단한 셰이더다. 두 파일을 프로젝트의 `bin/data/shadersGL3/` 경로에 `radial.vert`, `radial.frag`라는 이름으로 두고, C++ 쪽에서 파일의 공통 경로를 불러온다. 셰이더 문법과 `ofShader`의 동작에 관한 일반 설명은 26장에서 이어진다.

```glsl
// radial.vert
#version 150

uniform mat4 modelViewProjectionMatrix;
in vec4 position;

void main() {
    gl_Position = modelViewProjectionMatrix * position;
}
```

```glsl
// radial.frag
#version 150

uniform vec2 resolution;
uniform float time;
out vec4 outputColor;

void main() {
    vec2 uv = gl_FragCoord.xy / resolution;
    vec2 p = uv - vec2(0.5);
    p.x *= resolution.x / resolution.y;

    float wave = 0.5 + 0.5 * cos(length(p) * 50.0 - time * 1.5);
    vec3 color = mix(vec3(0.02, 0.04, 0.08),
                     vec3(0.15, 0.72, 0.62),
                     wave);
    outputColor = vec4(color, 1.0);
}
```

버텍스 셰이더는 사각형 정점의 최종 위치를 정하고, 프래그먼트 셰이더는 화면 위치에서 원점까지의 거리에 따라 색을 계산한다. `resolution`과 `time`은 C++ 애플리케이션이 전달하는 유니폼(uniform)이다. `resolution`으로 가로세로 비율을 보정해 파동이 타원으로 늘어지는 것을 줄이고, `time`을 통해 파동의 위상을 움직인다.

```cpp
// ofApp의 멤버
ofShader radialShader;
bool shaderReady = false;

void ofApp::setup() {
    shaderReady = radialShader.load("shadersGL3/radial");
}

void ofApp::draw() {
    if (!shaderReady) {
        ofBackground(20);
        return;
    }

    radialShader.begin();
    radialShader.setUniform2f(
        "resolution",
        static_cast<float>(ofGetWidth()),
        static_cast<float>(ofGetHeight()));
    radialShader.setUniform1f("time", ofGetElapsedTimef());
    ofDrawRectangle(0.0f, 0.0f,
                    static_cast<float>(ofGetWidth()),
                    static_cast<float>(ofGetHeight()));
    radialShader.end();
}
```

셰이더는 `setup()`에서 한 번 불러오고, 매 프레임 달라지는 값만 `draw()`에서 유니폼으로 전달한다. 화면 전체를 덮는 사각형을 그리는 명령은 CPU가 준비하지만, 각 프래그먼트의 파동 값과 색은 GPU가 계산한다. 셰이더 파일의 GLSL 버전은 애플리케이션이 만든 OpenGL 컨텍스트와 맞아야 한다. 로드나 컴파일이 실패할 수 있으므로 `load()`의 결과를 확인하고, 검은 화면이 나오면 경로·버전·컴파일 로그·유니폼 이름을 순서대로 점검한다.

## `ofFbo`로 드로잉과 후처리를 연결하기

셰이더가 화면의 수식 패턴을 직접 만드는 경우가 아니라면, CPU 쪽에서 만든 장면을 텍스처에 저장한 뒤 GPU 셰이더로 다시 처리할 수 있다. `ofFbo`는 화면이 아닌 렌더 표면에 장면을 그리는 프레임 버퍼 객체(framebuffer object)다. 렌더 결과는 텍스처로 사용할 수 있어 다음 렌더 단계의 입력이 된다.

```text
CPU update: 입자 위치·속도 갱신
        ↓
ofFbo: 입자와 도형을 텍스처에 렌더링
        ↓
ofShader: 텍스처를 샘플링해 색상·왜곡·블러 계산
        ↓
창: 최종 이미지를 화면에 표시
```

구조를 보여주는 C++ 의사 코드는 다음과 같다.

```cpp
sceneFbo.begin();
ofClear(0, 0, 0, 255);
drawParticles();
sceneFbo.end();

postShader.begin();
postShader.setUniformTexture("sourceTexture", sceneFbo.getTexture(), 0);
postShader.setUniform1f("time", ofGetElapsedTimef());
sceneFbo.draw(0.0f, 0.0f);
postShader.end();
```

첫 단계에서 C++은 입자 데이터를 읽어 도형 명령을 내리고 그 결과를 `sceneFbo`에 저장한다. 두 번째 단계에서는 그 텍스처를 프래그먼트 셰이더가 입력으로 읽어 왜곡, 색 보정, 가장자리 발광 같은 효과를 계산한다. 실제 셰이더에는 텍스처 샘플러와 텍스처 좌표 입력이 필요하며, 텍스처 좌표의 방향이나 픽셀 좌표 방식은 렌더 컨텍스트와 텍스처 형식에 맞춰 확인해야 한다. 위 코드는 처리 흐름을 나타내며, 구체적인 셰이더 입력 선언은 사용하는 FBO와 GLSL 컨텍스트에 맞춰 작성한다.

FBO를 여러 개 사용하면 여러 렌더 패스를 구성할 수 있다. 예를 들어 한 FBO에 입자를 그리고, 다른 FBO에서 흐림을 계산한 뒤, 최종 패스에서 색을 합성한다. 이전 프레임을 다음 프레임의 입력으로 사용하는 피드백 효과도 두 개의 FBO를 번갈아 읽고 쓰는 방식으로 구성할 수 있다. 이때 읽는 표면과 쓰는 표면을 분리하지 않고 같은 텍스처에 동시에 읽고 쓰면 결과가 정의되지 않거나 플랫폼별 문제가 생길 수 있다.

## 데이터를 CPU와 GPU 사이에 전달하기

GPU 셰이더는 C++의 `std::vector<Particle>` 내용을 자동으로 읽지 않는다. CPU에서 관리하는 값을 GPU에 전달하려면 유니폼, 정점 속성, 텍스처, 버퍼 같은 명시적 경로가 필요하다. 유니폼은 시간이나 색상처럼 실행 전체에서 공유되는 소량의 값에 적합하다. 입자 수가 적다면 CPU에서 입자마다 도형을 그리는 방식이 단순하다. 입자 수가 많아지면 정점 데이터를 묶어 한 번에 보내거나, 입자 정보를 텍스처·버퍼에 담아 GPU가 처리하도록 하는 방법을 고려할 수 있다.

성능은 계산 위치뿐 아니라 데이터 이동과 호출 횟수에도 좌우된다. CPU에서 매 프레임 전체 해상도의 픽셀 배열을 만들고 GPU 텍스처로 다시 올리면 셰이더로 계산을 옮긴 이점이 줄어들 수 있다. 가능하면 텍스처를 GPU에 유지하고 필요한 파라미터만 유니폼으로 갱신한다. GPU 결과를 CPU 메모리로 매 프레임 다시 읽는 작업도 동기화 대기를 일으킬 수 있어 신중하게 사용한다.

또한 GPU가 모든 시뮬레이션에 더 적합한 것은 아니다. CPU에서는 복잡한 분기와 객체 관계를 표현하기 쉽고 디버깅도 직접적이다. 셰이더는 같은 계산을 많은 정점이나 픽셀에 병렬로 적용하는 데 적합하지만, 개별 프래그먼트가 다른 프래그먼트의 상태를 직접 바꾸는 구조는 아니다. 작품의 계산량, 데이터 관계, 이동 비용을 보고 CPU와 GPU의 경계를 정한다.

## CPU 시뮬레이션과 GPU 표현의 조합

제너레이티브 아트에서는 CPU에서 입자를 생성하고 힘을 계산하되, 입자를 화면에 표현할 때 셰이더를 쓰는 혼합 구조가 실용적이다. CPU는 입력과 상태, 입자 생성·소멸, 충돌 규칙을 관리하고 GPU는 각 입자의 색상·모양 또는 최종 화면의 효과를 계산한다. 반대로 시뮬레이션 자체가 수십만 개의 독립적인 격자 셀을 반복 갱신해야 한다면 컴퓨트 셰이더나 GPU 버퍼를 고려할 수 있지만, 이는 데이터 업로드와 동기화까지 설계해야 하는 더 큰 구조다.

단계적으로 옮기는 접근이 좋다. 먼저 CPU에서 규칙을 구현해 결과와 수학을 확인하고, 병목이 확인된 뒤 동일한 계산을 정점 또는 프래그먼트 셰이더로 옮긴다. 이렇게 하면 시각적 차이가 수식의 오류인지, 좌표계·텍스처·셰이더 연결의 문제인지 분리해 파악하기 쉽다.

## 이 절의 핵심

openFrameworks의 C++ 코드는 상태와 드로잉 명령을 구성하고, GPU는 정점과 프래그먼트의 렌더링 계산을 수행한다. `ofShader`에 유니폼을 전달해 화면 수식을 계산하거나, `ofFbo`에 그린 CPU 장면을 셰이더 입력으로 사용해 후처리할 수 있다. 성능을 결정하는 것은 CPU와 GPU 중 어느 쪽을 쓰는가뿐 아니라 데이터 이동량, 호출 횟수, 계산의 병렬성이다.
