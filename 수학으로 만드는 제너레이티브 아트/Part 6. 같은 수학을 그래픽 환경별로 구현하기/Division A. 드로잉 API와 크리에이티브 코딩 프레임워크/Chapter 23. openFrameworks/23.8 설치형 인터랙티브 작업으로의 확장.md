# 23.8 설치형 인터랙티브 작업으로의 확장

작업실에서 실행되는 스케치와 전시장에 설치되는 작품은 같은 코드를 사용하더라도 요구 조건이 다르다. 작업실에서는 개발자가 창 크기와 입력 장치를 알고 실행하지만, 설치 작품은 프로젝터나 대형 디스플레이, 센서, 스피커, 컴퓨터가 정해진 공간에서 오랜 시간 함께 동작해야 한다. 관람객은 프로그램의 내부 상태를 알지 못하고, 운영자는 작품이 시작된 뒤 매 프레임을 지켜볼 수 없다.

따라서 설치를 위한 구현에는 화면에 그림을 그리는 일 외에도 출력 크기와 좌표의 대응, 자산과 설정의 배포, 예외 상황에서의 대체 동작, 장시간 실행과 현장 점검이 포함된다. 작품은 코드와 실행 파일만이 아니라 컴퓨터, 연결 장치, 공간, 관람객의 행동이 함께 이루는 시스템이다.

## 기준 좌표계와 실제 출력

프로젝터와 디스플레이의 해상도나 가로세로 비율은 개발 중 사용한 모니터와 다를 수 있다. 작품을 특정 픽셀 크기에만 맞춰 그리면 다른 출력 장치에서 잘리거나, 원과 원이 타원으로 늘어지거나, 인터랙션 위치가 어긋날 수 있다. 먼저 작품의 논리적 기준 크기(reference size)를 정하고, 실제 출력 영역으로 옮기는 규칙을 둔다.

다음 예제는 1920×1080 좌표계로 장면을 작성한 뒤, 창 안에 비율을 유지하며 최대한 크게 맞춘다. 출력 비율이 기준과 다르면 남는 영역은 좌우 또는 위아래 여백이 된다.

```cpp
#include <algorithm>

void ofApp::draw() {
    ofBackground(8);

    constexpr float referenceWidth = 1920.0f;
    constexpr float referenceHeight = 1080.0f;
    const float outputWidth = static_cast<float>(ofGetWidth());
    const float outputHeight = static_cast<float>(ofGetHeight());

    const float scale = std::min(outputWidth / referenceWidth,
                                 outputHeight / referenceHeight);
    const float offsetX = (outputWidth - referenceWidth * scale) * 0.5f;
    const float offsetY = (outputHeight - referenceHeight * scale) * 0.5f;

    ofPushMatrix();
    ofTranslate(offsetX, offsetY);
    ofScale(scale, scale);
    drawSceneInReferenceCoordinates();
    ofPopMatrix();
}
```

`drawSceneInReferenceCoordinates()`는 작품의 도형과 배치를 기준 좌표계에서 그리는 프로젝트 함수다. 배율은 출력 영역을 넘지 않도록 가로·세로 배율 중 작은 값을 택하고, 이동량은 남는 공간의 절반씩 배분한다. 이를 레터박스(letterboxing)라고 한다. 출력 비율이 기준과 다르면 위아래 또는 좌우에 여백이 생긴다. 화면을 빈틈없이 채우려면 비율을 유지한 채 일부 가장자리를 자르는 크롭(cropping) 방식이나, 이미지를 늘려 비율을 바꾸는 방식을 선택할 수 있다. 어떤 방식이 작품의 구도에 맞는지 결정하고, 출력 장치가 바뀌어도 핵심 요소가 가장자리에 잘리지 않도록 안전 여백을 둔다.

운영체제의 디스플레이 배율이나 창 모드에 따라 앱이 사용하는 논리 좌표 크기와 물리 픽셀 해상도가 다를 수 있다. 따라서 프로젝터의 설정 화면에 표시된 숫자만 기준으로 삼지 말고, 실제 실행 중 openFrameworks가 보고하는 창 크기와 투사된 결과를 함께 확인한다.

기준 좌표계로 입력을 받는다면 그리기에 적용한 변환을 반대로 적용해야 한다. 창 좌표 `(x, y)`에서 기준 좌표를 구하는 식은 다음과 같다.

$$
x_{ref}=\frac{x-offsetX}{scale},\qquad
y_{ref}=\frac{y-offsetY}{scale}
$$

여백 영역에서 발생한 입력은 기준 화면 바깥에 해당하므로 무시하거나 별도의 동작으로 취급할 수 있다. 마우스나 센서가 프로젝터에 비친 면을 직접 감지하는 경우에는 창 좌표와 실제 표면 좌표가 일치하지 않을 수 있다. 그때는 입력의 설치 위치와 출력 변환을 함께 보정해야 한다. 장치의 종류와 값 정규화는 23.4에서 다룬 방법을 기반으로 하고, 여기서는 설치된 출력과 입력 사이의 공간적 대응을 확인한다.

프로젝터는 해상도만 맞춘다고 투사면과 정확히 겹치지 않는다. 투사 거리와 초점, 기울기, 사다리꼴 왜곡, 벽이나 오브젝트의 굴곡도 확인한다. 평면이 아닌 표면에 투사하거나 여러 프로젝터를 이어 붙이는 작업은 보정 메시(mesh), 워핑(warping), 블렌딩(blending) 같은 별도 기하 보정이 필요할 수 있다. 이 보정은 작품 좌표계와 구분된 출력 단계로 두면, 시각 규칙을 바꾸지 않고 설치 위치에 맞출 수 있다.

## 실행 파일과 자산을 함께 배포하기

개발 환경에서 성공한 프로젝트라도 다른 컴퓨터에서 실행하면 이미지나 셰이더, 영상 파일을 찾지 못할 수 있다. openFrameworks 프로젝트의 이미지·영상·오디오·셰이더 같은 파일은 일반적으로 `bin/data` 아래에 두고, 애플리케이션에서는 그 위치를 기준으로 한 상대 경로를 사용한다. 개인 컴퓨터의 절대 경로나 개발 폴더 구조에 의존하면 배포 환경에서 경로가 달라져 로드가 실패한다.

실행 파일만 전달하지 말고, 빌드 결과와 필요한 데이터 파일, 설정, 사용 라이선스 및 설치 메모를 하나의 배포 단위로 관리한다. 배포한 파일은 프로젝트 폴더나 IDE에서가 아니라 실제 설치할 위치에서 실행해 본다. 실행 시 현재 작업 디렉터리가 개발 때와 다를 수 있으므로, 데이터 경로가 실행 위치에 따라 어떻게 해석되는지 확인한다. 자산을 불러올 때는 성공 여부를 확인하고, 파일이 없을 때 어떤 화면이나 동작을 보여줄지 마련한다. 필수 자산을 읽지 못했다고 아무 설명 없이 검은 화면에 머물게 두기보다, 오류 로그를 남기고 현장에서 구분할 수 있는 상태를 표시하는 편이 운영에 유리하다.

설정값과 작품의 시각 규칙을 분리하는 것도 도움이 된다. 창 크기, 기준 캔버스, 방출량, 센서 보정값, 오디오 레벨처럼 설치마다 조정할 값을 한곳에 모으면 코드를 수정하고 다시 빌드하지 않고도 환경에 맞출 수 있다. 다만 현장 설정과 작품의 기본값이 뒤섞이면 어떤 변경이 적용되었는지 알기 어려우므로, 기본 설정과 설치별 설정을 구분하고 사용한 값을 기록한다.

전체 화면 실행이나 마우스 커서 숨김은 설치 환경에서 유용할 수 있지만, 개발 중부터 적용하면 오류 화면에 접근하기 어려울 수 있다. 디버그 실행과 전시 실행의 동작을 구분하고, 전시 모드에서도 운영자가 종료·재시작하거나 상태를 확인할 방법을 남긴다. 여러 디스플레이를 사용하는 경우에는 운영체제의 화면 배치와 실제 케이블 연결이 바뀌어도 의도한 장치에 출력되는지 확인한다. 디스플레이 번호가 항상 같다고 가정하기보다 설치 컴퓨터에서 실제 출력 대상을 점검한다.

## 장시간 실행을 위한 시간과 자원 관리

전시장에서는 애플리케이션이 몇 시간 또는 며칠 동안 계속 실행될 수 있다. 짧은 테스트에서는 드러나지 않던 메모리 증가, 누적 오차, 장치 연결 문제, 열에 따른 성능 저하가 나타날 수 있다. 특히 프레임 횟수를 시간으로 간주하면 실제 실행 속도나 프레임률이 달라질 때 작품의 속도가 변한다. 애니메이션과 시뮬레이션은 실제 경과 시간 또는 `dt`를 기준으로 갱신하고, 긴 프레임 지연이 생겼을 때 한 번에 너무 크게 이동하지 않도록 상한을 두거나 고정 시간 단계를 사용한다. 시간 단계의 구체적인 구성은 23.2를 참고한다.

60 FPS를 목표로 하면 한 프레임 전체에 쓸 수 있는 시간은 약 16.7ms다. 이 시간 안에 업데이트, 드로잉, 영상 갱신, 후처리가 모두 끝나야 하지만, 목표 프레임률을 설정했다고 매 프레임이 그 속도로 실행되는 것은 아니다. 설치 해상도와 실제 장면에서 프레임률과 자원 사용량을 관찰하고, 필요한 경우 입자 수, 분석 해상도, 렌더 패스 수를 조정한다. 계산을 CPU와 GPU 중 어디에 둘지에 관한 원칙은 23.7과 연결된다.

계속 쌓이는 궤적이나 이벤트 기록은 저장 공간과 메모리에 상한을 둔다. 입자나 임시 객체를 반복 생성·폐기하는 코드는 예상 최대 개수와 재사용 방식을 검토한다. 매 프레임 파일을 쓰거나 디버그 메시지를 과도하게 출력하면 성능과 저장 공간에 영향을 줄 수 있으므로, 기록 수준과 저장 주기를 정한다. 프레임률이 낮아지거나 입력 장치가 빠져도 시각 결과가 완전히 멈추지 않도록, 장치가 없을 때 사용할 기본값이나 자동 시각 모드를 준비할 수 있다.

장치 연결, 카메라·마이크 권한, 영상 디코딩 실패는 모두 가능한 상태로 취급한다. 23.4와 23.5에서 다룬 입력·미디어 처리에서 로드 실패와 연결 해제를 감지하고, 작품이 유지할 상태를 정한다. 예를 들어 센서가 잠시 응답하지 않으면 마지막 값을 짧게 유지한 뒤 중립값으로 서서히 되돌리거나, 입력 없이도 자체적인 생성 규칙으로 계속 움직이게 할 수 있다. 이때 오류를 숨기는 것이 목적은 아니다. 작품은 관람객에게 계속 의미 있는 화면을 제공하고, 운영자에게는 로그나 상태 표시로 문제의 원인을 알려야 한다.

## 관람객과 공간을 함께 설계하기

인터랙션은 장치가 작동하는 것만으로 충분하지 않다. 관람객이 무엇을 할 수 있는지 알아차리고, 행동에 대한 결과를 이해할 수 있어야 한다. 행동과 시각 반응 사이의 지연이 길거나 결과가 약하면 입력이 전달되었는지 알기 어렵다. 가까이 다가가기, 손을 움직이기, 버튼을 누르기처럼 작품이 요구하는 행동은 공간에서 자연스럽게 발견될 수 있도록 단서와 피드백을 설계한다. 안내 문구가 필요하다면 짧고 명확하게 두되, 작품이 관람객에게 먼저 반응하는 방식도 고려한다.

여러 사람이 동시에 참여하는지, 한 사람의 입력이 전체 화면을 제어하는지, 관람객이 떠난 뒤 상태를 초기화할지를 정한다. 이전 참여자의 움직임이나 설정이 다음 사람에게 어떻게 이어지는지도 작품의 일부다. 매번 초기화하는 것이 적절할 수도 있고, 하루 동안의 흔적을 축적하는 것이 개념에 맞을 수도 있다. 선택한 정책이 기술적으로도 일관되게 동작하도록 대기 상태와 입력 재개 상태를 분리한다.

작품 주변의 실제 공간도 인터랙션의 일부다. 프로젝터와 센서의 시야를 가리는 구조물이 없는지, 관람객의 키나 휠체어 높이에서도 참여할 수 있는지, 케이블이 이동 경로를 가로지르지 않는지 점검한다. 소리를 사용하는 작품은 전시장 주변 작품과 겹치는 음량을 고려하고, 빛이 강한 공간에서는 대비와 밝기를 현장에서 확인한다. 카메라나 마이크를 사용한다면 어떤 입력을 수집하고 저장하는지, 저장하지 않는다면 그 사실을 어떻게 알릴지도 기관의 정책과 함께 검토한다.

## 현장 설치와 운영 점검

현장에서는 개발 컴퓨터의 화면을 복제하는 것만으로 점검을 마칠 수 없다. 실제 프로젝터나 디스플레이, 전원, 센서와 케이블, 주변 조명, 관람객의 시선 높이를 포함한 최종 배치에서 시험해야 한다. 특히 차가운 상태에서의 첫 실행과 장시간 구동 후의 상태는 다를 수 있으므로 둘 다 확인한다.

설치 전후 점검 항목은 다음처럼 정리할 수 있다.

- 전시용 빌드가 개발 도구 없이 시작되고, 모든 데이터 파일과 설정을 찾는가?
- 실제 출력 장치의 해상도와 화면 비율에서 내용이 잘리거나 찌그러지지 않는가?
- 센서나 미디어 장치가 분리되거나 권한을 사용할 수 없을 때 대체 동작이 있는가?
- 관람객이 입력을 발견하고, 행동과 화면 반응의 관계를 이해할 수 있는가?
- 예상 운영 시간보다 충분히 오래 실행해 메모리 증가, 발열, 프레임 저하, 누적 흔적을 확인했는가?
- 애플리케이션이 종료되거나 컴퓨터가 재시작된 뒤 운영자가 정상 상태로 복구할 수 있는가?
- 전원, 환기, 초점, 케이블, 음량과 주변 작품에 미치는 영향을 확인했는가?

자동 시작이나 시스템 재시작 후 실행은 운영체제와 전시장 장비에 맞춰 설정할 수 있지만, 애플리케이션 자체의 복구 상태와 운영자의 종료 방법을 먼저 마련한다. 문제가 생겼을 때 무한히 재시작하며 같은 오류를 반복하지 않도록 실패 원인을 남기고, 복구가 불가능한 경우 알아볼 수 있는 오류 상태를 표시한다. 실행 파일의 버전, 설정값, 설치 날짜와 알려진 문제를 기록하면 현장 교체나 재설치가 훨씬 수월하다.

## 이 절의 핵심

설치형 인터랙티브 작업은 코드뿐 아니라 출력 장치, 공간, 입력 장치, 배포 자산, 관람객과 운영 절차가 함께 만드는 시스템이다. 기준 좌표계와 실제 화면의 변환을 정하고, 입력에도 대응되는 좌표 변환을 적용한다. 배포한 빌드와 자산을 현장 조건에서 시험하고, 장시간 실행·장치 부재·재시작에 대한 동작과 관람객의 접근성을 미리 설계하면 작품이 전시장에서도 안정적으로 작동할 가능성이 높아진다.
