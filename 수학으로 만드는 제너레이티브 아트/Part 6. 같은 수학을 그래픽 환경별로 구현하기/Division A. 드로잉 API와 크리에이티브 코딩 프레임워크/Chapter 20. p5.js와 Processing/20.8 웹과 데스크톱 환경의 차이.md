# 20.8 웹과 데스크톱 환경의 차이

p5.js와 Processing은 비슷한 수학과 드로잉 개념을 사용하지만, 작품이 실행되는 장소는 다르다. p5.js는 JavaScript 프로그램으로 웹 브라우저의 페이지 안에서 실행되고, Processing Java 모드의 스케치는 데스크톱 창에서 실행된다. 이 차이는 캔버스를 만드는 문법에 그치지 않는다. 화면 크기와 입력, 파일 접근, 자산 관리, 배포 방법까지 영향을 준다.

## 실행 구조가 다르다

p5.js 스케치는 웹 페이지의 일부다. 페이지가 p5.js 라이브러리와 스케치 코드를 불러오고, 스케치는 보통 페이지 안에 캔버스를 만든다. 코드는 p5.js 웹 에디터에서 작성할 수도 있고, 로컬 프로젝트에서 HTML과 JavaScript 파일로 관리할 수도 있다. 현대적인 프로젝트에서는 모듈이나 빌드 도구를 이용하기도 하므로, 라이브러리를 불러오는 방식은 프로젝트 설정에 맞춘다.

```text
my-sketch/
  index.html       페이지와 스케치 연결
  sketch.js        p5.js 스케치
  assets/          이미지, 소리, 데이터 등
```

Processing Java 모드에서는 보통 Processing 개발 환경에서 스케치 폴더를 열고 실행한다. `.pde` 파일은 일반 Java 소스 파일과 완전히 같은 형식이 아니다. Processing이 스케치 문법을 Java 프로그램 구조에 맞게 준비한 뒤 컴파일하고 실행한다. 스케치의 자산은 관례적으로 `data` 폴더에 둔다.

```text
MySketch/
  MySketch.pde     Processing Java 모드 스케치
  data/            이미지, 글꼴, 소리, 데이터 등
```

두 환경 모두 코드와 자산을 프로젝트 단위로 관리할 수 있지만, p5.js 프로젝트는 웹 페이지의 리소스 구조를 따르고 Processing 프로젝트는 스케치와 데스크톱 실행 흐름을 따른다. 따라서 한쪽 프로젝트 폴더를 다른 쪽에서 그대로 열어 실행하는 방식은 아니다.

## 화면과 좌표의 수명 주기

브라우저에서는 캔버스가 페이지의 레이아웃 안에 놓인다. 주변에 제목이나 버튼을 배치할 수 있고, CSS로 캔버스의 화면상 크기와 정렬을 조정할 수도 있다. 다만 CSS로 캔버스를 확대·축소하는 것과 `createCanvas()` 또는 `resizeCanvas()`로 실제 그리기 표면의 크기를 바꾸는 것은 다르다. CSS만으로 크기를 바꾸면 그림이 늘어나거나 흐려질 수 있고, 코드가 참조하는 `width`, `height`는 그대로일 수 있다. 화면 크기에 맞춰 좌표 계산도 바꾸려면 캔버스 크기와 레이아웃을 함께 조정한다.

데스크톱 Processing에서는 스케치가 별도의 창을 만든다. 창 크기, 화면 배치, 운영체제의 창 관리가 실행 환경의 일부가 된다. 창 크기가 바뀔 수 있는 작업이라면 크기 변화 뒤에도 배치가 유지되도록 `width`와 `height`를 기준으로 좌표를 계산한다. 두 환경 모두 화면의 왼쪽 위를 기본 원점으로 삼고, 픽셀 밀도에 따라 논리 좌표와 실제 픽셀 수가 달라질 수 있다는 공통 원리는 같다. 캔버스의 논리 좌표와 픽셀 버퍼를 구분하는 방법은 20.2절과 20.6절을 참고한다.

브라우저는 창 크기뿐 아니라 페이지 확대율, 기기 픽셀 비율, 모바일 화면 방향의 영향을 받는다. 고해상도 화면에서 `pixelDensity`가 커지면 같은 논리 크기의 캔버스도 더 많은 실제 픽셀을 그릴 수 있다. 데스크톱에서도 고밀도 디스플레이와 렌더러 설정을 고려해야 한다. 그러므로 화면 크기를 픽셀 단위로 고정하기보다, 캔버스 크기에서 파생되는 비율과 기준 길이를 사용하면 여러 화면에 대응하기 쉽다.

## 입력과 브라우저 보안

브라우저 안의 스케치는 마우스와 키보드 외에도 터치, 페이지 버튼, 폼, HTML 요소와 연결될 수 있다. 웹 페이지의 다른 부분과 상태를 주고받기 쉽다는 장점이 있지만, 브라우저의 이벤트 흐름과 페이지 스크롤도 함께 고려해야 한다. 모바일에서 캔버스가 화면을 차지한다면 터치 동작이 페이지 스크롤이나 확대 제스처와 충돌하지 않는지 확인한다.

Processing은 스케치 창 안의 마우스와 키 입력을 중심으로 작업하기 쉽다. 데스크톱 애플리케이션처럼 창의 수명과 입력을 관리할 수 있고, 필요한 경우 파일 선택 대화상자나 운영체제 기능과 연동한다. 다만 구체적인 입력 API와 지원 기능은 Processing 버전과 사용하는 라이브러리에 따라 달라질 수 있다.

파일 접근 방식에는 중요한 차이가 있다. 브라우저의 JavaScript는 보안상 사용자의 컴퓨터에 있는 임의의 파일을 경로만 지정해 읽을 수 없다. 사용자가 파일 입력 창에서 선택하거나, 브라우저가 제공하는 권한 기반 기능을 사용해야 한다. 웹 서버의 파일이나 외부 자산을 불러올 때도 출처 정책과 서버 설정의 영향을 받는다. 모듈, `fetch()` 또는 일부 자산 로딩을 사용하는 프로젝트는 `file://` 주소로 직접 여는 대신 로컬 웹 서버에서 실행하는 편이 안정적이다.

Processing 데스크톱 스케치는 스케치의 `data` 폴더에 둔 자산이나 파일 API를 이용할 수 있다. 외부 파일에 접근하는 범위는 운영체제의 권한과 실행 방식에 따라 달라진다. 사용자가 고른 파일만 읽어야 한다면 파일 선택 UI를 제공하고, 작품을 다른 사람에게 전달할 때는 필요한 자산을 프로젝트에 포함하거나 저장 위치와 권한을 안내한다.

## 실행과 배포의 선택

| 고려 사항 | p5.js 웹 스케치 | Processing 데스크톱 스케치 |
| --- | --- | --- |
| 실행 장소 | 브라우저의 웹 페이지 | 운영체제의 별도 창 |
| 공유 | 웹 호스팅이나 온라인 에디터 링크로 공유하기 편리 | 스케치 소스 또는 대상 환경에 맞춘 애플리케이션으로 전달 |
| 페이지와의 결합 | HTML, CSS, DOM 요소와 결합 가능 | 데스크톱 창과 Processing 라이브러리를 중심으로 구성 |
| 파일과 자산 | 브라우저 권한, URL, 출처 정책을 고려 | `data` 폴더와 데스크톱 파일 접근 방식을 고려 |
| 화면 대응 | 브라우저 창, 모바일 뷰포트, 페이지 레이아웃에 대응 | 창 크기와 데스크톱 화면 환경에 대응 |
| 사용자의 시작 과정 | 페이지를 열면 실행할 수 있음 | 실행 환경과 배포한 애플리케이션의 호환성을 고려 |

p5.js를 고르면 사용자는 링크를 열어 바로 결과를 볼 수 있고, 작품은 웹페이지의 글·버튼·데이터와 함께 동작할 수 있다. 대신 서로 다른 브라우저와 화면 크기, 권한 정책을 고려해야 한다. Processing은 독립적인 창에서 키오스크나 설치 작업, 데스크톱 중심 도구를 구성하기 편리하다. 다른 운영체제에서 실행할 애플리케이션을 배포할 때는 해당 플랫폼에서의 빌드와 라이브러리·런타임 호환성을 확인해야 한다. 어느 쪽이든 `frameRate()`는 목표 실행률을 지정할 뿐 실제 프레임률을 보장하지 않는다. 브라우저 탭이 비활성화되거나 시스템 부하가 커지면 실행 간격이 달라질 수 있으므로 시간에 기반한 갱신 원리는 20.4절처럼 적용한다.

## 수학은 유지하고 연결부를 바꾼다

환경을 옮길 때 모든 코드를 다시 설계할 필요는 없다. 작품의 수학적 모델과 실행 환경에 붙는 부분을 구분하면 재사용 범위가 선명해진다.

| 대체로 유지할 수 있는 것 | 환경에 맞춰 다시 연결할 것 |
| --- | --- |
| 기하학적 수식과 좌표 변환 | 캔버스 생성과 크기 변경 |
| 패턴 파라미터와 색상 매핑 규칙 | 마우스·키보드·터치 입력 처리 |
| 입자나 시뮬레이션의 상태 갱신 규칙 | 파일과 이미지·소리 자산의 불러오기 |
| 함수와 반복 구조의 의도 | 화면 배치, 저장, 배포 방식 |

예를 들어 입자 위치를 속도와 시간 간격으로 갱신하는 식은 두 환경에서 그대로 사용할 수 있다. 하지만 현재 시간을 얻는 방법, 창이나 페이지의 크기를 읽는 방법, 이미지를 어디서 불러오는지는 환경별 API와 보안 정책에 맞게 작성해야 한다. 수학 계산을 별도 함수로 모으고, 캔버스·입력·파일 처리를 바깥쪽에 두면 나중에 실행 환경을 바꿀 때 수정할 범위를 줄일 수 있다.

## 환경을 고르는 질문

작업을 시작하기 전에 결과를 누가 어디서 실행할지 생각해 본다. 브라우저 링크로 공유하거나 웹페이지와 결합할 작품이라면 p5.js가 자연스럽다. 인터넷 연결 없이 창 하나로 실행하는 데스크톱 작품, Java 코드와의 연계, 운영체제 기능 활용이 중요하다면 Processing이 편리할 수 있다. 교육과 실험에서는 이미 익숙한 언어와 배포 경로를 우선해도 좋다.

실행 환경은 작품의 수학적 가능성을 제한하는 경계라기보다, 입력·출력·배포를 결정하는 조건이다. Part 6의 앞 절에서 살펴본 공통 드로잉 원리와 환경별 API를 구분해 두면 같은 수학적 아이디어를 웹 스케치와 데스크톱 스케치 양쪽에서 발전시킬 수 있다.

## 이 절의 핵심

p5.js는 브라우저 페이지의 캔버스와 웹 보안·레이아웃 정책 안에서 실행되고, Processing Java 모드는 데스크톱 창과 Java 실행 흐름 안에서 실행된다. 입력, 파일 접근, 화면 크기, 공유와 배포 방식은 환경에 맞게 설계해야 한다. 반면 수식과 상태 갱신 규칙은 대부분 유지할 수 있으므로, 수학적 모델과 환경 의존적인 입출력을 분리하는 것이 이식성과 유지보수에 도움이 된다.
