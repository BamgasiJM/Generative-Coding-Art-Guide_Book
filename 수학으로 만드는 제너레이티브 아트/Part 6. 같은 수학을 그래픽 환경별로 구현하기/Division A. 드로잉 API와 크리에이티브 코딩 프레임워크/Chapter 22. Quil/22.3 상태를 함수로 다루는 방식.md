# 22.3 상태를 함수로 다루는 방식

정지 이미지에서는 한 번 계산한 좌표와 색을 그리면 된다. 애니메이션이나 인터랙션에서는 다음 프레임에 이어질 값도 필요하다. 움직이는 점이라면 현재 위치와 속도를, 선택 가능한 도형이라면 선택 여부를, 시간에 따라 변하는 패턴이라면 위상이나 진행 시간을 기억해야 한다. 이렇게 다음 계산에 필요한 현재 값을 상태(state)라고 한다.

Clojure에서는 상태를 여러 전역 변수를 직접 바꾸는 대신 맵이나 벡터 같은 값으로 묶고, 함수를 통해 다음 값으로 변환할 수 있다. 현재 상태, 입력, 시간 간격을 받아 다음 상태를 반환하는 구조는 다음처럼 나타낼 수 있다.

$$
S_{n+1} = F(S_n, I_n, \Delta t)
$$

여기서 `S_n`은 현재 상태, `I_n`은 이번 단계의 입력, `Δt`는 단계 사이의 시간, `F`는 갱신 규칙이다. 함수는 현재 값을 직접 덮어쓰는 대신 새로운 상태를 반환한다.

## 상태와 파라미터

파라미터(parameter)는 작품의 규칙이나 모양을 조정하는 값이고, 상태는 실행 중 시간과 입력에 따라 변하는 값이다. 예를 들어 격자의 열 수나 원의 기본 반지름은 파라미터로, 점의 현재 위치나 경과 시간은 상태로 둘 수 있다. 어떤 값이 항상 파라미터이거나 상태인 것은 아니다. 사용자가 반지름을 바꿀 수 있다면 시작 설정에서는 파라미터였던 값도 실행 중에는 상태의 일부가 된다.

관련된 값은 맵으로 함께 묶을 수 있다.

```clojure
(def initial-state
  {:position [120.0 160.0]
   :speed 180.0
   :elapsed 0.0})
```

이 맵은 2D 위치, 이동 속도, 경과 시간을 표현한다. `:position`의 벡터는 x와 y 순서이고, 맵의 키는 각 값이 무엇을 뜻하는지 이름으로 알려 준다. 이런 구조에서는 객체가 늘어도 위치와 속도 같은 관련 데이터를 하나의 상태 값으로 전달할 수 있다.

## 이전 상태에서 다음 상태 만들기

다음 함수는 현재 상태와 이동 방향, 시간 간격을 받아 새 위치와 경과 시간을 가진 맵을 반환한다.

```clojure
(defn advance-state
  [state direction dt]
  (let [[x y] (:position state)
        [dx dy] direction
        speed (:speed state)]
    (-> state
        (assoc :position [(+ x (* dx speed dt))
                          (+ y (* dy speed dt))])
        (update :elapsed + dt))))

(def next-state
  (advance-state initial-state [1.0 0.0] (/ 1.0 60.0)))
```

`let`은 현재 위치와 방향의 성분을 이름으로 꺼내 계산에 사용한다. `assoc`는 맵의 `:position`에 새 벡터를 넣고, `update`는 기존 `:elapsed`에 `dt`를 더한다. `->`는 첫 번째 상태 값을 다음 연산의 첫 인자로 전달하므로, 여러 변환이 위에서 아래로 이어지는 것처럼 읽힌다.

초기 위치가 `[120.0 160.0]`, 속도가 초당 180 단위, 방향이 오른쪽 `[1.0 0.0]`, 시간 간격이 `1/60`초라면 다음 위치는 약 `[123.0 160.0]`이 된다. 중요한 점은 `initial-state`의 값이 바뀌지 않는다는 것이다. `next-state`는 원래 맵을 수정한 별도 복사본이라기보다, 기존 컬렉션과 구조를 효율적으로 공유하면서 바뀐 값을 표현하는 새로운 불변 값이다.

같은 상태·방향·시간 간격을 다시 전달하면 같은 다음 상태가 나온다. 이 성질은 갱신 함수를 테스트하고, 어떤 입력이 문제를 만들었는지 재현하고, 렌더링과 시뮬레이션을 나누는 데 도움이 된다. 방향 벡터가 대각선으로 입력될 때 이동 속도를 일정하게 유지하려면 방향의 길이를 1로 정규화해야 한다. 그렇지 않으면 x와 y 변화가 동시에 적용되어 더 빠르게 움직일 수 있다.

## 입력과 시간도 값으로 전달하기

순수한 상태 갱신 함수는 키보드나 마우스를 직접 읽기보다, 이번 단계의 입력을 인자로 받는다. 그러면 입력 장치와 이동 규칙이 분리된다. 키보드에서 만든 방향 벡터든 게임패드 축에서 만든 방향 벡터든 같은 `advance-state` 함수에 전달할 수 있다.

시간도 마찬가지다. `dt`를 함수 바깥에서 전달하면 갱신 규칙이 프레임 시계에 직접 의존하지 않는다. 실제 스케치에서는 프레임워크가 제공하는 시간 값을 읽어 `dt`로 만들고, 그 값을 상태 함수에 전달한다. 고정된 시간 간격을 사용하는 시뮬레이션에서도 같은 갱신 함수를 다른 `dt`로 호출할 수 있다. 시간 API를 상태 계산과 분리하면 실행 속도와 수학 규칙을 따로 점검하기 쉽다.

랜덤값도 상태 갱신 중에 전역 난수 함수를 즉시 부르는 대신, 난수 시드나 난수 상태를 명시적으로 전달하거나 생성된 값을 입력으로 다룰 수 있다. 그래야 같은 입력에서 같은 결과를 얻고 실험을 재현하기 쉽다. 모든 프로젝트에서 난수 생성기를 직접 상태로 구현해야 한다는 뜻은 아니다. 다만 숨겨진 난수 호출이 결과를 바꿀 수 있다는 점을 함수의 입력·출력 관계에 포함해 생각해야 한다.

## Quil의 함수형 상태 흐름

Quil은 `quil.middleware/fun-mode`를 통해 상태를 함수에 명시적으로 전달하는 스케치 방식을 제공한다. 개념적으로 초기화 함수가 최초 상태를 만들고, 갱신 함수가 현재 상태에서 다음 상태를 반환하며, 그리기 함수가 현재 상태를 읽어 화면을 그린다.

```text
setup()             -> 초기 상태
update(state)       -> 다음 상태
draw(state)         -> 현재 상태를 화면에 표현
```

이 방식에서 `update`는 앞 절의 `advance-state` 같은 순수 계산을 호출하고 그 결과를 반환할 수 있다. `draw`는 상태를 읽어 Quil의 드로잉 함수를 호출한다. 그리기 자체는 화면에 명령을 보내는 부수 효과지만, 상태 계산과 화면 출력을 별도 함수로 나누면 그 부수 효과가 어디에서 일어나는지 분명해진다. Quil 스케치의 실제 `setup`, `update`, `draw` 연결과 프레임 흐름은 22.4에서 구체적으로 다룬다.

## 불변 상태가 주는 이점과 비용

불변 상태는 이전 값을 그대로 보존하므로 디버깅과 테스트가 쉬워진다. 함수 호출 전후를 비교하거나, 이전 상태를 기록해 특정 단계로 되돌아가거나, 입력을 다시 재생하는 구조를 만들기 좋다. 파티클 시스템처럼 상태가 많은 경우에도 각 단계의 입력과 출력을 명확하게 나누면 문제를 추적하기 쉽다.

반면 모든 상태를 한 덩어리의 거대한 맵에 넣으면 어떤 함수가 어느 값을 바꾸는지 흐려질 수 있다. 관련된 값끼리 묶고, 각 갱신 함수가 책임지는 필드를 제한한다. 컬렉션 업데이트는 구조를 공유해 효율적으로 수행되지만, 상태가 매우 크거나 매 프레임 불필요한 전체 데이터를 다시 구성하면 비용이 커질 수 있다. 실제로 바뀌는 값과 프레임마다 유지되는 데이터를 구분하고, 필요한 경우 입자 배열이나 캐시를 별도의 구조로 설계한다.

Clojure가 모든 부수 효과를 막는 것은 아니다. `atom` 같은 참조형 상태, 난수, 파일 입출력, 화면 그리기를 사용할 수 있다. 함수형 접근은 이 기능을 금지하기보다, 상태 변화를 명확한 경계에 두어 계산을 더 예측하기 쉽게 만든다. 스케치의 규모에 맞춰 순수 함수와 프레임워크 상태를 조합하면 된다.

## 이 절의 핵심

상태는 다음 계산에 필요한 현재 값이며, Clojure에서는 이를 불변 맵과 벡터로 묶어 표현할 수 있다. `F(state, input, dt)` 형태의 함수는 현재 상태를 직접 바꾸지 않고 다음 상태를 반환한다. Quil의 `fun-mode`는 이 명시적 상태 전달 방식과 잘 맞으며, 입력·시간·계산·그리기를 구분하면 스케치를 테스트하고 확장하기 쉬워진다.
