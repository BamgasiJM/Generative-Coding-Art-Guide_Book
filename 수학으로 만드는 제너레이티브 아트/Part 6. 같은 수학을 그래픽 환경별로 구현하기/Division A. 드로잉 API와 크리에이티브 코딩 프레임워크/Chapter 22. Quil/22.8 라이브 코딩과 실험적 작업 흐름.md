# 22.8 라이브 코딩과 실험적 작업 흐름

라이브 코딩(live coding)은 프로그램을 실행한 채 코드를 조금씩 바꾸고, 그 결과를 빠르게 확인하는 작업 방식이다. 완성된 코드를 한 번에 작성한 뒤 실행하는 대신, 규칙을 만들고 결과를 관찰하고 파라미터를 조정하는 사이클을 짧게 반복한다. 제너레이티브 아트에서는 작은 수식이나 파라미터 변화가 전체 화면의 인상에 영향을 주므로, 빠른 피드백이 탐색의 중요한 도구가 된다.

Quil은 Clojure REPL(Read-Eval-Print Loop)과 함께 쓰면 이런 실험을 하기 좋다. REPL은 입력한 표현식을 평가하고 결과를 바로 보여준다. 생성 규칙의 계산을 작은 함수로 분리해두면 전체 스케치를 다시 작성하지 않고도 함수와 파라미터를 하나씩 시험할 수 있다.

## 계산부터 REPL에서 확인하기

예를 들어 원 둘레에 점을 배치하는 규칙을 만든다고 하자. 먼저 Quil을 실행하지 않고 좌표를 계산하는 함수를 정의한다.

```clojure
(def parameters
  {:count 32
   :radius 120.0
   :center-x 320.0
   :center-y 240.0})

(defn ring-points
  [{:keys [count radius center-x center-y]}]
  (mapv
   (fn [index]
     (let [angle (* 2.0 Math/PI (/ index count))]
       {:x (+ center-x (* radius (Math/cos angle)))
        :y (+ center-y (* radius (Math/sin angle)))}))
   (range count)))
```

이 함수는 파라미터 맵을 받아 점 데이터 벡터를 반환한다. 화면에 그리는 부수 효과가 없으므로 결과를 작은 단위로 확인할 수 있다.

```clojure
(def preview (ring-points parameters))
(count preview)
(take 3 preview)

(ring-points (assoc parameters :count 12 :radius 70.0))
```

첫 두 표현식으로 점이 몇 개 만들어졌는지와 앞쪽 좌표를 살펴보고, 마지막 표현식으로 점 수와 반지름을 바꾼 결과를 곧바로 비교한다. 예상한 데이터가 만들어진 뒤에 Quil의 `draw` 콜백에 연결하면 수학 계산의 문제와 화면 표현의 문제를 따로 찾을 수 있다. 이처럼 파라미터를 맵으로 모아두면 한 번에 하나씩 바꾸고, 이전 결과와 차이를 비교하기도 쉽다.

REPL에서 함수를 다시 정의할 때는 작은 변화만 주는 편이 좋다. 예를 들어 각도 계산, 점 수, 반지름을 동시에 바꾸면 어떤 변화가 결과를 만들었는지 알기 어렵다. 먼저 하나의 파라미터를 바꾸고 좌표나 화면을 확인한 뒤 다음 변화를 적용한다. 실험이 잘못된 방향으로 가더라도 마지막으로 의도한 결과를 만든 규칙을 알고 있으면 되돌아가기 쉽다.

## 화면으로 연결하는 짧은 반복

계산한 데이터를 화면에 표현할 때는 22.4에서 다룬 `setup`, `update`, `draw` 구조를 사용한다. 정지 패턴이라면 `setup`에서 점 데이터를 만들고 상태에 저장한 뒤, `draw`에서 그 데이터를 순회해 그릴 수 있다. 애니메이션이라면 프레임마다 바뀌는 값만 `update`에서 계산한다.

실험 사이클은 다음처럼 정리할 수 있다.

1. 만들고 싶은 변화 하나를 파라미터나 함수로 표현한다.
2. REPL에서 작은 입력으로 함수 결과를 확인한다.
3. 예상한 데이터가 나오면 Quil의 화면에 연결한다.
4. 한 번에 하나의 파라미터를 바꾸고 결과를 비교한다.
5. 의도한 결과와 파라미터를 기록한 뒤 다음 변형을 시도한다.

순수 함수의 반환값을 먼저 확인하면 스케치 창을 매번 다시 시작하지 않아도 된다. 반대로 화면에 그리기, 입력 읽기, 파일 저장처럼 외부 효과가 필요한 코드는 Quil 콜백에 두고 REPL에서 함수 단위로 평가할 수 있는 계산과 분리한다. 이 분리는 실험 속도뿐 아니라 오류가 발생한 위치를 찾는 데도 도움이 된다.

## 시드와 비교 가능한 실험

랜덤을 사용하는 스케치에서는 시드를 고정해 두면 파라미터 변화의 효과를 비교하기 쉽다. 같은 시드로 시작하면 동일한 난수열에서 출발하므로, 예를 들어 점 수나 크기 범위만 바꿨을 때 어떤 시각적 변화가 생기는지 관찰할 수 있다. 작업의 방향을 찾은 뒤에는 시드를 바꾸어 다른 구성을 탐색할 수 있다.

난수 생성기는 값을 순서대로 내놓기 때문에 코드에 난수 호출을 추가하거나 제거하면 이후 값들이 달라질 수 있다. 파라미터 변화만 비교하고 싶다면 난수 기반 데이터를 `setup`에서 한 번 생성하고 재사용하거나, 생성에 쓰인 시드와 주요 설정을 함께 기록한다. 노이즈를 사용하는 경우에도 노이즈 시드와 샘플 좌표 배율을 기록하면 형태를 다시 만들기 쉽다. 재현 가능한 생성의 세부 원리는 11장에서 다룬 내용을 바탕으로 생각할 수 있다.

화면에서 우연히 마음에 드는 결과를 발견했다면 그 장면의 설정을 보존하는 것이 중요하다. 시드, 점 수, 간격, 노이즈 입력 배율, 색상 범위처럼 결과를 결정하는 값을 하나의 파라미터 맵이나 작품 기록에 함께 남긴다. 결과 이미지뿐 아니라 그것을 다시 만들 수 있는 규칙도 함께 보존해야 이후 수정과 변형이 가능하다.

## 코드 재평가와 스케치 상태

Clojure에서 `defn`을 다시 평가하면 해당 함수의 정의가 갱신되고, 이후 그 함수를 호출하는 코드에 새 규칙이 적용된다. 하지만 이미 실행 중인 Quil 스케치의 상태가 자동으로 처음부터 다시 만들어지는 것은 아니다. 예를 들어 `setup`에서 생성한 점 벡터는 `setup`이 다시 실행되기 전까지 기존 값을 유지할 수 있다. 함수 정의를 바꾼 것과 초기 상태를 재생성한 것은 서로 다른 작업이다.

또한 실행 중인 스케치에 등록된 콜백이 새 함수 정의를 즉시 사용하는지 여부를 항상 가정해서는 안 된다. 콜백 연결 방식과 개발 환경에 따라 기존 함수 참조가 계속 사용될 수 있다. 변경한 함수가 화면에 반영되지 않으면 새 데이터를 명시적으로 다시 만들거나 스케치를 다시 시작해 확인한다. 개발 중에는 이 초기화 절차를 알아보기 쉽게 두고, 완성 단계에서는 재현 가능한 파라미터와 시드에서 상태를 다시 만들 수 있게 구성한다.

이 구분은 특히 난수와 애니메이션에서 중요하다. 랜덤 배치를 `setup`에서 만들면 재시작 전까지 그 배치는 그대로 유지된다. 반면 `update`에서 매번 새 난수를 뽑으면 실행 중 계속 바뀐다. 어느 쪽이 맞는지는 작품의 의도에 달려 있지만, 값이 언제 생성되고 어떤 계기로 다시 계산되는지 명확히 정해야 한다.

## 실험을 안정적으로 이어가기

라이브 코딩은 빠르게 바꾸는 것만으로 완성되지 않는다. 너무 많은 계산을 매 프레임 다시 수행하거나, 작업이 끝난 코드를 정리하지 않으면 스케치의 구조를 이해하기 어려워진다. 화면에 고정된 요소는 초기화 때 미리 만들고, 실제로 변해야 하는 값만 갱신 단계에서 계산한다. 데이터 생성, 상태 변화, 그리기를 분리해 두면 어느 부분이 성능을 차지하는지 살피기도 쉽다.

디버깅할 때는 결과를 간결하게 관찰한다. 점 전체를 매 프레임 터미널에 출력하면 출력량이 커지고 프레임도 느려질 수 있다. 계산 함수의 소수 입력만 REPL에서 확인하거나, 요소 개수와 일부 좌표만 살펴보는 편이 낫다. 문제가 생겼을 때는 마지막 변경을 좁혀 보고, 작동하던 버전이나 파라미터를 저장해두면 실험을 계속할 수 있다.

## 이 절의 핵심

Quil과 Clojure REPL을 이용한 실험은 작은 함수와 파라미터를 평가하고 결과를 확인하는 반복으로 이루어진다. 계산을 먼저 데이터로 검증하고, 고정 시드와 설정을 기록하면 변화를 비교하고 결과를 재현하기 쉽다. 함수 정의의 재평가, `setup`에서 만들어진 상태의 재생성, 실행 중인 콜백의 갱신은 각각 다를 수 있으므로 스케치가 언제 어떤 값을 다시 계산하는지 명확히 관리해야 한다.
