# 24.2 Cargo 프로젝트와 Rust의 타입 및 소유권

nannou 프로그램은 Rust 프로젝트로 구성하고 Cargo로 의존성, 빌드, 실행을 관리한다. 이 과정은 그래픽 API를 호출하기 전의 기반 작업이다. 프로젝트 파일은 어떤 라이브러리를 사용할지 선언하고, Rust 소스는 상태와 계산 규칙을 표현하며, Cargo는 필요한 crate를 준비해 실행 가능한 프로그램으로 만든다.

## Cargo 프로젝트의 구조

터미널에서 실행 파일을 만드는 기본 프로젝트를 생성할 수 있다.

```sh
cargo new --bin nannou-study
cd nannou-study
```

생성되는 기본 구조는 다음과 같다.

```text
nannou-study/
├── Cargo.toml
├── Cargo.lock
└── src/
    └── main.rs
```

`Cargo.toml`은 패키지의 이름, 버전, Rust 에디션, 의존성을 선언하는 매니페스트(manifest)다. 이 책의 예제처럼 nannou 0.20 계열을 사용한다면 의존성을 다음과 같이 둔다.

```toml
[package]
name = "nannou-study"
version = "0.1.0"
edition = "2024"

[dependencies]
nannou = "0.20"
```

Rust 2024 에디션은 언어 규칙과 기본 lint를 묶어 선택하는 프로젝트 설정이다. nannou는 crates.io에서 가져오는 외부 crate이고, 프로젝트 코드는 `src/main.rs`에 작성한다. `cargo run`은 필요한 의존성과 프로그램을 빌드한 뒤 실행하고, `cargo check`는 전체 링크를 생략한 빠른 타입·오류 검사를 수행한다. 배포를 위한 최적화 빌드는 `cargo build --release`로 만든다.

`Cargo.lock`에는 실제로 선택된 nannou와 하위 의존성들의 구체적인 버전이 기록된다. `Cargo.toml`의 `nannou = "0.20"`은 0.20 계열의 호환 가능한 버전을 허용하지만, 잠금 파일은 각 빌드에서 어떤 세부 버전 조합을 사용했는지 고정한다. 실행 애플리케이션에서는 보통 잠금 파일을 버전 관리에 포함해 다른 컴퓨터에서도 같은 의존성 조합을 재현한다. 의존성을 갱신하면 잠금 파일도 바뀔 수 있으므로, 작품 결과가 달라지지 않았는지 확인하며 업데이트한다.

자주 사용하는 Cargo 명령은 다음과 같다.

| 명령 | 역할 |
| --- | --- |
| `cargo check` | 소스와 타입을 빠르게 검사 |
| `cargo run` | 빌드하고 기본 실행 파일을 실행 |
| `cargo build` | 디버그용 실행 파일 빌드 |
| `cargo build --release` | 최적화된 배포용 빌드 |
| `cargo doc --open` | 의존성 문서를 생성하고 브라우저에서 열기 |

Cargo 명령을 실행하는 위치는 `Cargo.toml`이 있는 패키지 디렉터리다. 오류가 나면 먼저 현재 디렉터리, crate 이름과 버전, Rust 툴체인, 오류 메시지가 가리키는 파일과 줄을 확인한다. Cargo는 의존성을 내려받고 빌드하지만, nannou의 화면이나 작품 규칙을 시각적으로 편집해 주지는 않는다.

## 변수와 타입

Rust에서 `let`으로 선언한 변수는 기본적으로 변경할 수 없다. 값을 바꿔야 하는 변수에만 `mut`를 붙인다.

```rust
let radius: f32 = 18.0;
let mut phase: f32 = 0.0;

phase += 0.04;
```

`radius`는 읽을 수 있지만 다시 대입할 수 없다. `phase`는 여러 업데이트를 거치며 변하므로 가변 변수(mutable variable)로 선언했다. 불필요하게 많은 변수를 `mut`로 열어 두지 않으면 어떤 상태가 실제로 바뀌는지 파악하기 쉽다.

타입은 명시적으로 적을 수도 있고, 컴파일러의 타입 추론(type inference)에 맡길 수도 있다. Rust에서 소수점이 있는 숫자의 기본 타입은 보통 `f64`지만, nannou의 도형 좌표와 색상 계산은 `f32`를 자주 사용하므로 의도한 정밀도를 명시하는 편이 혼란을 줄인다. 반복 횟수는 `usize`, 참·거짓 조건은 `bool`, 여러 값을 모은 목록은 `Vec<T>`처럼 목적에 맞는 타입을 선택한다.

```rust
let particle_count: usize = 240;
let is_paused: bool = false;
let speed: f32 = 0.75;
```

Rust는 서로 다른 숫자 타입을 자동으로 섞어 계산하지 않는다. `f32`와 `f64`, 부호 있는 정수와 부호 없는 정수를 연산하려면 적절한 변환이 필요하다. 이는 좌표 계산에서 정수 나눗셈이나 의도하지 않은 정밀도 변화를 일찍 발견하게 해준다. 변환은 단순히 컴파일 오류를 없애는 데 그치지 않고, 값의 범위와 단위가 적절한지도 확인하면서 수행한다.

구조체(struct)는 작품에서 함께 관리할 값들을 하나의 타입으로 묶는다. 다음 구조체는 입자 하나의 위치와 속도를 저장하고, `Model`은 여러 입자와 중력을 소유한다.

```rust
struct Particle {
    x: f32,
    velocity_x: f32,
}

struct Model {
    particles: Vec<Particle>,
    gravity: f32,
}
```

`Vec<Particle>`는 길이가 바뀔 수 있는 입자 목록이다. 프레임마다 이 목록을 갱신하는 방식은 nannou의 `Model` 구조와 잘 맞는다. 실제 좌표는 뒤의 24.6에서 nannou가 제공하는 벡터 타입으로 확장한다. 이 절에서는 타입과 소유권의 원리를 보기 위해 위치를 스칼라 값으로 단순화했다.

## 소유권: 값의 책임자를 정하기

Rust의 모든 값에는 소유자(owner)가 있다. 소유자가 범위를 벗어나면 그 값은 정리된다. `f32`나 `bool`처럼 크기가 작고 복사 가능한 타입은 변수에 대입하거나 함수에 전달할 때 값이 복사된다. 반면 `String`이나 `Vec<T>`처럼 힙 메모리를 소유하는 값은 기본적으로 임의로 복사되지 않는다. 소유권을 옮기면(move) 기존 변수는 더 이상 그 값을 사용할 수 없다.

```rust
let first = String::from("flow");
let second = first;

// 여기서는 first를 다시 사용할 수 없다.
println!("{second}");
```

`first`와 `second`가 같은 문자열 메모리를 동시에 해제하려는 상황을 막기 위해, 대입 시 소유권이 `second`로 이동한다. 문자열 내용의 독립된 복사본이 필요하면 `clone()`을 호출할 수 있지만, 큰 입자 목록이나 이미지 데이터에서 반복적으로 복사하면 비용이 커질 수 있다. 소유권을 넘길 필요가 없는 함수는 참조(reference)를 받아 읽거나 수정하도록 설계한다.

## 빌림: 소유권을 유지한 채 사용하기

참조는 값을 소유하지 않고 잠시 빌려 사용한다. `&T`는 읽기 전용 참조이고, `&mut T`는 값을 바꿀 수 있는 가변 참조다. Rust는 동시에 여러 개의 읽기 전용 참조를 허용하지만, 가변 참조가 있는 동안 같은 값에 대한 다른 참조나 접근은 허용하지 않는다. 이 규칙은 한 프레임의 상태를 여러 경로가 서로 충돌하게 수정하는 일을 막는다.

nannou의 전형적인 콜백에서도 이 차이를 볼 수 있다. `update()`는 `&mut Model`을 받아 시뮬레이션 상태를 바꾸고, `view()`는 `&Model`을 받아 상태를 읽어 그린다.

```rust
fn update(model: &mut Model, dt: f32) {
    let gravity = model.gravity;

    for particle in &mut model.particles {
        particle.velocity_x += gravity * dt;
        particle.x += particle.velocity_x * dt;
    }
}

fn view(model: &Model) {
    for particle in &model.particles {
        let _screen_x = particle.x;
        // 현재 상태를 읽어 도형을 구성한다.
    }
}
```

`&mut Model`은 함수가 호출자로부터 모델을 잠시 독점적으로 빌려 상태를 바꾸도록 한다. `&Model`은 모델을 수정하지 않고 읽기만 하겠다는 약속이다. 실제 nannou 콜백에는 `App`, `Update`, `Frame` 등의 인자도 전달되며, 이 예제는 `Model`을 빌리는 방식만 보여준다. 콜백이 연결되는 전체 실행 순서는 24.3에서 확인한다.

컬렉션을 순회할 때 `&model.particles`는 각 입자를 읽기 전용으로 빌리고, `&mut model.particles`는 각 입자를 가변으로 빌린다. 따라서 `view()`에서는 위치를 읽어 화면 좌표로 바꾸고, `update()`에서는 속도와 위치를 바꿀 수 있다. 순회하는 동안 같은 벡터에 새 입자를 추가하거나 제거하려 하면 벡터 전체를 빌린 참조와 충돌할 수 있다. 먼저 갱신을 끝내고 생성·제거를 별도 단계에서 수행하거나, 변경할 항목을 임시 목록에 모아 순회 이후 반영한다.

이 구분은 CPU와 GPU 사이의 메모리 복사와는 다른 개념이다. 소유권과 빌림은 Rust 프로그램 안에서 값에 접근하는 규칙이고, 그래픽 API에 데이터를 전달하는 과정은 별도의 렌더링 단계다. 참조를 전달한다고 해서 자동으로 GPU에 복사되거나 화면에 그려지는 것은 아니다.

## 타입과 오류를 읽는 방법

컴파일러가 타입을 추론하지 못하거나 참조의 사용 범위가 겹치면 컴파일 오류를 표시한다. 이때 오류가 난 줄만 고치기보다 값이 어디서 생성되고, 누가 소유하며, 어느 함수가 읽거나 수정하는지를 따라간다. 예를 들어 숫자 타입 불일치는 좌표 계산의 타입을 통일해 해결하고, 빌림 충돌은 변경과 읽기의 단계를 분리해 해결하는 경우가 많다.

실행 중 실패할 수 있는 작업은 `Result<T, E>`로 성공값 또는 오류값을 반환할 수 있고, 값이 없을 수도 있는 상황은 `Option<T>`로 표현할 수 있다. `?`는 오류를 호출자에게 전달하고, `expect()`는 실패하면 메시지와 함께 실행을 중단한다. 짧은 예제에서는 `expect()`가 원인을 눈에 띄게 하지만, 관람객이 사용하는 작품에서는 오류를 기록하고 대체 화면을 제공하는 등 상황에 맞는 처리가 필요하다. 무조건 오류를 무시하거나 빈 기본값으로 감추면 원인을 찾기 어려워진다.

타입과 소유권은 처음에는 그래픽 코드에 앞서 배워야 할 장벽처럼 느껴질 수 있다. 하지만 상태가 `Model`에 모이고, `update()`가 그 상태를 수정하며, `view()`가 읽기만 한다는 구조를 타입으로 표현하면 수정 가능한 경계가 분명해진다. 프레임 단위로 상태를 갱신하는 제너레이티브 작업에서는 이 경계가 버그를 찾고 기능을 확장하는 기준이 된다.

## 이 절의 핵심

Cargo는 `Cargo.toml`에서 패키지와 의존성을 선언하고, `Cargo.lock`에서 실제 사용 버전을 고정하며, `check`, `run`, `build`로 검사와 실행을 관리한다. Rust의 타입은 좌표·시간·목록의 의미를 명시하고, 소유권은 값의 책임자를 정하며, 참조와 빌림은 소유권을 넘기지 않고 읽거나 수정하게 한다. nannou에서는 `Model`이 상태를 소유하고 `update()`가 가변 참조로 갱신하며 `view()`가 읽기 전용으로 표현하는 구조를 기본으로 삼을 수 있다.
