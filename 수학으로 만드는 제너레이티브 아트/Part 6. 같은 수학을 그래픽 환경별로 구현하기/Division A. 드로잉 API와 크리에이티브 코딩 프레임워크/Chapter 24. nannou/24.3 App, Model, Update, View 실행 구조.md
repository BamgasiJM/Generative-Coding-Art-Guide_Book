# 24.3 App, Model, Update, View 실행 구조

nannou 프로그램은 운영체제 이벤트를 받아 창을 갱신하는 반복 구조를 프레임워크가 관리한다. 작가는 시작할 때 필요한 상태를 만들고, 반복 중에는 그 상태를 갱신하고, 화면을 그리는 함수를 연결한다. 이 역할을 나누는 대표적인 이름이 `App`, `Model`, `update`, `view`다.

```text
main()
  ↓ nannou 앱과 콜백 등록
model() ── 초기 상태와 창 준비
  ↓
이벤트 처리 ── 입력이나 창 사건을 상태에 반영
  ↓
update() ── 시간 간격에 따라 작품 상태 갱신
  ↓
view() ── 현재 상태를 프레임으로 표현
  └──────── 반복
```

이 흐름은 책임을 이해하기 위한 개요다. 이벤트는 운영체제와 창에서 발생할 때 이벤트 루프를 통해 전달되고, 상태 갱신과 화면 제시는 서로 다른 콜백이다. 모든 입력마다 화면을 다시 그리는 식의 일대일 관계를 가정하기보다, 각 함수가 언제 어떤 자료를 읽고 바꾸는지에 집중한다.

## 앱 빌더와 콜백 등록

`main()`은 nannou의 앱 빌더를 만들고 실행한다. 업데이트 함수는 앱 빌더에 연결하고, 화면을 그리는 함수는 창을 만들 때 지정한다.

```rust
use nannou::prelude::*;

fn main() {
    nannou::app(model)
        .update(update)
        .run();
}
```

`nannou::app(model)`은 실행 환경을 구성할 앱 빌더를 반환한다. `.update(update)`는 프레임워크가 상태 갱신 시점에 호출할 함수를 등록한다. `.run()`이 이벤트 루프를 시작하면 프로그램은 창을 열고, 운영체제 이벤트와 업데이트·드로잉을 처리하며 실행 상태를 유지한다. 이 루프를 직접 `while`문으로 작성하지 않는 것이 이벤트 기반 프레임워크의 특징이다.

키보드나 마우스 같은 이벤트를 별도의 함수에서 처리하려면 `.event(event)`를 앱 빌더에 추가할 수 있다. 이벤트 콜백은 앱과 가변 모델 참조, 이벤트 값을 받는다. 입력 이벤트의 종류와 창 좌표 처리는 24.4에서 자세히 다룬다.

## `App`과 초기 상태 `Model`

`App`은 nannou가 관리하는 실행 환경에 접근하는 매개변수다. 창을 만들거나, 창 크기와 시간 같은 실행 정보를 확인할 때 사용한다. `Model`은 작품이 직접 정의하는 구조체로, 생성된 입자와 운동 파라미터처럼 프레임 사이에 유지해야 하는 상태를 담는다.

```rust
struct Model {
    phase: f32,
    speed: f32,
}

fn model(app: &App) -> Model {
    app.new_window()
        .size(800, 600)
        .view(view)
        .build()
        .expect("창을 만들지 못했습니다");

    Model {
        phase: 0.0,
        speed: 1.0,
    }
}
```

`model()`은 앱 시작 시 초기화에 사용된다. 창 크기와 `view` 콜백을 지정해 창을 만들고, 애니메이션 위상과 속도의 시작값을 가진 `Model`을 반환한다. 반환된 모델은 실행 중 프레임워크가 보관하고 각 콜백에 전달한다. 입자 목록, 난수 시드, 입력 상태, 미리 계산한 기하 데이터처럼 여러 프레임에 걸쳐 유지할 정보도 이 구조체에 넣을 수 있다.

초기화와 프레임 갱신을 분리하면 매 프레임 다시 만들 필요가 없는 자료를 반복 생성하지 않게 된다. 예를 들어 작품을 구성하는 고정된 점 집합은 `model()`에서 한 번 생성하고, `update()`에서는 움직이는 속성만 변경할 수 있다. 반대로 시간에 따라 새로 만들어져야 하는 입자는 업데이트 규칙에 따라 생성한다.

## `update`: 상태 전이

`update()`는 현재 모델을 다음 상태로 바꾸는 함수다. nannou는 작품 상태를 바꿀 수 있도록 `&mut Model`을 전달하고, `Update`에는 이전 업데이트 이후의 시간 간격 같은 정보가 들어 있다.

```rust
fn update(_app: &App, model: &mut Model, update: Update) {
    let dt = update.since_last.as_secs_f32();
    model.phase += model.speed * dt;
}
```

`dt`는 초 단위의 경과 시간이다. 위상에 매번 고정된 양을 더하는 대신 속도와 실제 경과 시간을 곱하면, 프레임률이 조금 달라져도 초당 회전 속도를 비슷하게 유지할 수 있다. 물리 시뮬레이션에서는 매우 긴 프레임 지연이 큰 위치 변화로 이어지지 않도록 `dt`에 상한을 두거나 고정 시간 단계(fixed timestep)를 사용할 수 있다. 게임 루프와 시간 간격의 선택은 20.4와 23.2의 설명을 참고한다.

상태 전이를 함수로 보면 다음처럼 쓸 수 있다.

$$
M_{n+1}=F(M_n,\Delta t,I_n)
$$

`M_n`은 현재 모델, `M_{n+1}`은 다음 모델, `Δt`는 경과 시간, `I_n`은 입력이나 이벤트에서 전달된 값이다. `update()`는 이 정보를 받아 위치·속도·색상 단계·생성 개수 등을 계산한다. `Model`에 변경 가능한 상태를 모아 두면 프로그램이 프레임마다 무엇을 기억하고 어떻게 변화시키는지 추적하기 쉽다.

## `view`: 상태를 화면으로 표현하기

`view()`는 현재 모델을 읽어 한 프레임을 구성한다. 모델은 `&Model`로 전달되어 읽기 전용이고, 출력 대상 프레임은 `Frame` 값으로 전달된다.

```rust
fn view(app: &App, model: &Model, frame: Frame) {
    let draw = app.draw();
    draw.background().color(BLACK);

    let x = model.phase.cos() * 180.0;
    let y = model.phase.sin() * 120.0;
    draw.ellipse()
        .x_y(x, y)
        .w_h(28.0, 28.0)
        .color(rgb(0.25, 0.68, 0.82));

    draw.to_frame(app, &frame)
        .expect("프레임을 렌더링하지 못했습니다");
}
```

`view()`는 `Model`의 위상에서 타원 궤도의 좌표를 계산하고, `Draw` API로 원을 만든 다음 `to_frame()`으로 현재 프레임에 결과를 제출한다. 여기서 그리기 호출은 상태의 표현이지 상태 자체의 갱신은 아니다. `view()` 안에서 `model.phase`를 바꾸거나 입자를 추가할 수 없으며, 그 상태 변경은 `update()`나 이벤트 콜백에서 수행한다.

이 분리는 화면 갱신 횟수와 작품의 시간 상태를 구분하게 해준다. 그리기 함수가 여러 번 호출되어도 같은 `Model`이면 같은 장면을 재구성할 수 있다. 반면 `view()`에서 매번 새로운 난수를 뽑아 위치를 정하면 화면을 다시 그릴 때마다 결과가 바뀌어 깜박임이 생길 수 있다. 변화시킬 난수는 초기화나 상태 갱신 단계에서 뽑아 `Model`에 저장하고, `view()`는 저장된 값을 표현하는 편이 제어하기 쉽다.

## 이벤트, 업데이트, 화면 제시의 경계

입력 사건을 다루는 이벤트 콜백은 버튼을 눌렀거나 창 크기가 바뀌었다는 사실을 전달한다. 이벤트 콜백에서 모델의 입력 상태를 바꾸고, `update()`가 그 상태를 시간에 따라 해석하며, `view()`가 결과를 보여주는 구조가 흔하다.

```text
키 누름 이벤트: paused = true
        ↓
update: paused이면 phase를 진행하지 않음
        ↓
view: 현재 phase로 장면을 다시 그림
```

이처럼 이벤트를 작품 규칙으로 즉시 확장하지 않고 상태 값으로 변환하면, 입력 처리와 수학 규칙을 분리할 수 있다. 마우스 좌표를 입자 생성 위치로 바꾸거나, 키 입력으로 속도를 변경하는 동작도 같은 방식으로 설계한다. 입력값의 종류와 좌표 변환은 24.4에서 이어진다.

애니메이션이 아닌 정적 이미지는 `Model`을 한 번 준비한 뒤 한 프레임을 렌더링하는 구성으로도 만들 수 있다. 반대로 실시간 시뮬레이션은 `update()`에서 매번 상태를 진행시키고 그 결과를 보여준다. 두 작업은 모두 같은 실행 구조를 사용할 수 있으며, 달라지는 것은 상태를 얼마나 자주 바꾸고 프레임을 언제 다시 그리는가이다.

## 역할 분리로 얻는 것

`Model`, `update()`, `view()`를 나누는 목적은 함수 이름을 늘리는 데 있지 않다. 상태의 소유 위치, 시간에 따른 계산, 화면 표현을 구별해 변경의 영향을 좁히는 데 있다. 궤적의 속도를 조절할 때는 업데이트 수식을 바꾸고, 색이나 도형을 바꿀 때는 뷰 코드를 바꿀 수 있다. 입자 자료 구조가 커져도 `update()`의 규칙과 `view()`의 표현을 단계적으로 확장할 수 있다.

이 구조가 모든 부작용을 자동으로 막아 주는 것은 아니다. 파일 저장이나 오디오 출력처럼 외부 자원이 관여하면 해당 작업을 어느 단계에서 수행할지 정해야 한다. 화면을 그릴 때마다 저장하거나 소리를 새로 시작하면 의도하지 않은 반복이 생길 수 있다. 사건에 한 번 반응할 작업과 프레임마다 반복할 작업을 구별하고, 지속 상태는 `Model`에 명시적으로 기록한다.

## 이 절의 핵심

`main()`은 nannou 앱과 콜백을 연결해 실행을 시작하고, `model()`은 창과 초기 상태를 준비한다. `update()`는 `&mut Model`을 받아 시간과 입력에 따라 다음 상태를 계산하며, `view()`는 `&Model`을 읽어 `Frame`으로 표현한다. 이벤트는 입력 사실을 상태로 바꾸는 경계로 두고, 갱신과 그리기를 구분하면 애니메이션의 시간과 화면 표현을 독립적으로 다루기 쉽다.
