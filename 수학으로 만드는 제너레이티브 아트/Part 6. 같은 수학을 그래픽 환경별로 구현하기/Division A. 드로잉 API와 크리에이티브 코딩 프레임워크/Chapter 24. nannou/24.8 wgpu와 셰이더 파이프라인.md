# 24.8 wgpu와 셰이더 파이프라인

nannou의 `Draw` API는 원과 선 같은 도형을 간결하게 표현하지만, 그 결과도 내부적으로는 그래픽 장치의 렌더링 과정을 거친다. 픽셀마다 수식을 평가하거나 정점의 위치를 GPU에서 변형하는 등 더 세밀한 처리가 필요하면 wgpu와 셰이더를 직접 사용할 수 있다. 이 절에서는 nannou 0.20 계열을 기준으로, Rust 애플리케이션과 WGSL 셰이더가 렌더 파이프라인에서 어떤 역할을 맡는지 살펴본다.

## nannou, wgpu, WGSL의 역할

nannou는 창과 이벤트 루프, 프레임 흐름, 고수준 드로잉 API를 제공한다. wgpu는 GPU 리소스와 명령을 관리하는 Rust 그래픽 API이며, WGSL(WebGPU Shading Language)은 GPU에서 실행할 셰이더를 작성하는 언어다. Rust 코드와 WGSL 코드는 서로 다른 환경에서 실행되지만, 버퍼·텍스처·바인딩을 통해 데이터를 주고받는다.

`Draw`로 도형을 그리는 경로에서는 nannou가 필요한 GPU 작업을 대신 구성한다. 셰이더를 직접 작성하는 경로에서는 애플리케이션이 셰이더 모듈, 데이터 연결, 렌더 파이프라인, 드로우 명령을 더 구체적으로 준비한다. 따라서 셰이더를 사용한다고 GPU를 처음 도입하는 것은 아니다. 렌더링의 세부 단계를 직접 제어하는 선택에 가깝다.

일반적인 렌더링 흐름은 다음과 같다.

1. Rust에서 정점 버퍼, 유니폼 버퍼, 텍스처와 같은 GPU 리소스를 준비한다.
2. WGSL 코드를 셰이더 모듈로 만들고, 리소스와 셰이더의 연결 규칙을 정한다.
3. 셰이더 단계와 정점 입력, 색상 출력 형식 등을 묶어 렌더 파이프라인을 만든다.
4. 프레임마다 필요한 데이터와 드로우 명령을 GPU 명령 버퍼에 기록한다.
5. 명령을 GPU 큐에 제출하고, 렌더 결과를 현재 프레임의 출력 대상으로 표시한다.

파이프라인은 매 프레임 새로 만드는 대상이 아니다. 보통 초기화할 때 생성해 보관하고, 프레임마다 바뀌는 시간이나 파라미터만 작은 버퍼에 갱신한다.

## 렌더 파이프라인의 단계

렌더 파이프라인(render pipeline)은 셰이더 단계와 그래픽 상태를 조합해 GPU가 드로우 명령을 어떻게 처리할지 정의한다. 흔히 다음 역할을 가진다.

| 단계 또는 설정 | 역할 |
| --- | --- |
| 정점 셰이더(vertex shader) | 정점 입력을 화면에 투영할 좌표로 변환하고 다음 단계에 값을 전달 |
| 프리미티브 처리와 래스터화 | 정점으로 선·삼각형을 구성하고 화면의 픽셀 샘플로 변환 |
| 프래그먼트 셰이더(fragment shader) | 각 프래그먼트의 색과 기타 출력값 계산 |
| 파이프라인 상태 | 정점 형식, 삼각형 처리, 색상 타깃 형식, 블렌딩, 깊이 테스트 등을 지정 |

정점 셰이더의 대표적인 출력은 클립 공간의 위치다. 클립 공간 좌표는 화면 픽셀 좌표와 다르며, 보이는 영역은 대체로 x와 y가 `-1`에서 `1` 사이인 정규화 장치 좌표(normalized device coordinates, NDC)로 표현된다. GPU가 이 좌표를 뷰포트에 맞춰 래스터화하면, 프래그먼트 셰이더가 덮인 영역의 색을 계산한다.

WGSL은 함수에 `@vertex`와 `@fragment` 같은 속성(attribute)을 붙여 셰이더 진입점(entry point)을 표시한다. `@builtin(position)`은 렌더링 위치와 연결되고, `@location(n)`은 정점 입력이나 셰이더 사이의 값 또는 색상 출력을 연결한다. 이 번호와 자료형은 파이프라인의 입력·출력 계약과 맞아야 한다.

## 전체 화면 삼각형으로 픽셀마다 계산하기

절차적 이미지(procedural image)는 이미지 파일을 읽는 대신 각 픽셀의 좌표를 수식에 넣어 색을 계산한다. 전체 화면을 덮는 두 삼각형 사각형을 그릴 수도 있지만, 아래 예제처럼 큰 삼각형 하나를 사용하면 정점 데이터를 별도 버퍼에 담지 않고도 화면을 덮을 수 있다. `vertex_index`로 세 정점의 위치를 선택한다.

```wgsl
struct VertexOut {
    @builtin(position) position: vec4<f32>,
    @location(0) uv: vec2<f32>,
};

struct Params {
    resolution_time: vec4<f32>,
};

@group(0) @binding(0)
var<uniform> params: Params;

@vertex
fn vs_main(@builtin(vertex_index) vertex_index: u32) -> VertexOut {
    let positions = array<vec2<f32>, 3>(
        vec2<f32>(-1.0, -1.0),
        vec2<f32>( 3.0, -1.0),
        vec2<f32>(-1.0,  3.0),
    );

    let p = positions[vertex_index];
    var output: VertexOut;
    output.position = vec4<f32>(p, 0.0, 1.0);
    output.uv = p * 0.5 + vec2<f32>(0.5);
    return output;
}

@fragment
fn fs_main(input: VertexOut) -> @location(0) vec4<f32> {
    let resolution = params.resolution_time.xy;
    let elapsed = params.resolution_time.z;
    let centered = (input.uv * resolution - resolution * 0.5)
        / min(resolution.x, resolution.y);
    let radius = length(centered);
    let phase = radius * 28.0 - elapsed * 1.3;
    let color = 0.5 + 0.5 * cos(
        vec3<f32>(phase, phase + 2.1, phase + 4.2)
    );

    return vec4<f32>(color, 1.0);
}
```

정점 셰이더는 삼각형의 세 정점을 클립 공간에 놓고, `uv`라는 보간값을 프래그먼트 셰이더로 전달한다. 실제 화면의 프래그먼트에서는 삼각형의 세 정점에 지정한 값이 위치에 따라 보간된다. 정점이 화면보다 크게 뻗어 있어도 클리핑된 화면 전체를 덮기 때문에 각 픽셀에서 `fs_main()`이 실행된다.

프래그먼트 셰이더는 `uv`를 화면 크기 단위의 좌표로 바꾸고 중심을 원점으로 옮긴다. 짧은 변의 길이로 나누면 창의 가로세로 비율이 달라도 원형 무늬가 타원으로 늘어나는 것을 줄일 수 있다. 중심으로부터의 거리 `radius`를 색의 위상에 넣어 동심원 형태를 만들고, 시간에 따라 위상을 이동시켜 고리의 색이 흐르게 한다.

여기서 `resolution_time`은 x와 y 성분에 화면의 픽셀 너비와 높이, z 성분에 경과 시간을 담는 4개 부동소수점 값이다. 하나의 `vec4<f32>`로 묶으면 WGSL의 유니폼 정렬 규칙을 따르기 쉽고, 호스트 쪽에서도 네 값을 연속된 데이터로 갱신할 수 있다. 이 변수 선언은 셰이더의 요구사항을 보여 주는 것이며, Rust 쪽에서는 이에 대응하는 유니폼 버퍼와 바인딩을 만들어야 한다.

## 셰이더와 GPU 리소스 연결하기

셰이더의 바인딩 표시는 호스트 코드가 제공해야 할 자원을 선언한다. WGSL의 `@group(0) @binding(0)`은 0번 그룹의 0번 슬롯에서 `Params` 유니폼을 읽겠다는 뜻이다. Rust 측에서는 이 계약에 맞는 바인드 그룹 레이아웃(bind group layout)을 만들고, 실제 버퍼를 연결한 바인드 그룹(bind group)을 준비한다.

| WGSL 표기 | 호스트 측에서 준비할 것 |
| --- | --- |
| `@group(0) @binding(0)` | 해당 그룹과 슬롯을 포함하는 바인드 그룹 레이아웃 및 바인드 그룹 |
| `var<uniform>` | 작은 프레임 파라미터에 적합한 유니폼 버퍼 |
| `@location(0)` 정점 입력 | 정점 버퍼를 사용할 때 속성 번호·자료형·보폭이 맞는 정점 레이아웃 |
| `@builtin(vertex_index)` | 드로우 명령이 제공하는 정점 인덱스. 예제에서는 정점 버퍼가 필요 없음 |
| 프래그먼트 `@location(0)` 출력 | 렌더 파이프라인의 색상 타깃과 호환되는 출력 형식 |

정점 버퍼는 위치, 색, UV처럼 정점마다 달라지는 데이터를 GPU에 전달한다. 반대로 전체 화면 예제는 정점 위치를 `vertex_index`로 만들기 때문에 이 입력이 필요 없다. 이미지 텍스처나 노이즈 테이블을 셰이더에서 읽으려면 텍스처와 샘플러를 바인딩에 추가하고, WGSL 선언과 호스트 레이아웃을 일치시킨다.

렌더 파이프라인은 셰이더 진입점뿐 아니라 프레임 출력 대상의 색상 형식, 프리미티브 종류, 블렌딩 방식 등의 설정과도 맞아야 한다. 예를 들어 셰이더가 하나의 색상 타깃을 출력하는데 파이프라인에는 다른 개수나 형식의 타깃이 지정되면 호환되지 않는다. 알파를 사용하는 경우에도 셰이더가 출력하는 알파값과 파이프라인의 블렌딩 설정이 함께 의도한 합성 결과를 내는지 확인한다.

## nannou 프레임 안에서 사용자 파이프라인 사용하기

nannou 프로그램에서 GPU 작업은 별도의 창 루프를 새로 만들기보다 기존 애플리케이션의 프레임 흐름에 연결한다. `model()` 단계에서는 장치에 맞는 셰이더와 파이프라인, 지속해서 쓸 버퍼를 준비하고 `Model`이 이를 소유하도록 구성한다. `update()`는 시뮬레이션 상태나 파라미터 값을 갱신한다. 프레임을 그리는 단계에서는 현재 창의 출력 대상으로 렌더 명령을 기록하고, nannou가 관리하는 프레임 제출 흐름에 맞춰 결과를 표시한다.

개념적으로 한 프레임의 흐름은 다음과 같다.

```text
model: shader + layout + pipeline + buffers 생성
update: 시간과 시뮬레이션 상태 갱신
view: uniform 갱신 -> pipeline과 bind group 지정 -> draw 명령 기록
frame: GPU 명령 제출 -> 창에 결과 표시
```

이 순서는 개념을 나타내며, 그 자체가 복사해 실행할 Rust 코드 블록은 아니다. nannou 0.20에서는 사용하는 nannou 및 wgpu API 문서에 맞춰 장치 접근, 파이프라인 생성자, 렌더 패스, 프레임 연결 방식을 확인해야 한다. GPU API는 파이프라인 디스크립터와 셰이더 모듈 생성 방식이 버전에 따라 바뀔 수 있으므로, 이전 nannou나 wgpu 버전의 초기화 코드를 그대로 가져오지 않는다. 특히 창의 현재 색상 형식과 프레임의 명령 인코딩을 가져오는 방법은 설치한 버전의 공식 예제와 대조한다.

`Draw` 결과와 사용자 렌더 패스를 한 프레임에 함께 쓸 때는 작업 순서를 의식한다. 먼저 배경과 기본 도형을 그린 뒤 사용자 패스로 덮을지, 셰이더 결과 위에 `Draw` 도형을 올릴지에 따라 패스의 순서와 타깃의 로드·클리어 설정이 달라진다. 같은 프레임을 서로 독립적으로 제출하거나 표면을 중복 획득하려고 하면 표시 순서와 자원 사용이 충돌할 수 있다. 기존 프레임에 통합하는 구체적인 방법은 nannou 0.20이 제공하는 프레임 및 인코더 API에 맞춘다.

## CPU와 GPU에 나눠 맡길 일

GPU는 많은 정점이나 픽셀에 같은 연산을 병렬 적용하는 데 적합하다. 이미지의 각 픽셀에 동일한 거리 함수와 색상 함수를 적용하는 작업은 자연스러운 예다. 반면 셰이더를 사용한다고 전체 계산이 자동으로 빨라지지는 않는다. CPU에서 GPU로 데이터를 복사하거나 매 프레임 큰 버퍼를 다시 업로드하는 비용, 드로우 호출과 동기화 비용도 함께 고려해야 한다.

| 작업 특성 | 고려할 위치 |
| --- | --- |
| 창 이벤트, 파일 입출력, 작품 상태와 복잡한 자료 구조 관리 | Rust 애플리케이션의 CPU 코드 |
| 수많은 정점의 변환, 픽셀별 색상 계산 | 렌더 파이프라인의 GPU 셰이더 |
| 반복마다 이전 결과에 의존하는 시뮬레이션 | 데이터 의존성과 저장 방식에 따라 CPU 또는 별도 GPU 파이프라인 |
| GPU 결과를 CPU가 즉시 읽어야 하는 작업 | 읽기 전환 및 동기화 비용까지 포함해 판단 |

매 프레임 변하는 값은 시간, 해상도, 몇 개의 조절값처럼 작은 유니폼으로 전달하고, 변하지 않는 정점·텍스처·파이프라인은 재사용한다. GPU 계산 결과를 곧바로 CPU로 되가져오면 GPU의 비동기 실행을 기다리게 되어 이득이 사라질 수 있다. 결과를 다음 셰이더 단계나 텍스처 입력으로 이어서 처리할 수 있는지도 고려한다.

또한 셰이더의 좌표는 nannou `Draw`의 창 좌표와 자동으로 같지 않다. 예제의 `uv`는 삼각형 정점에서 보간한 0~1 범위의 좌표이고, `position`은 클립 공간 좌표다. 창 크기와 픽셀 밀도, 텍스처의 행 방향, 색상 형식과 선형·sRGB 변환도 결과에 영향을 준다. 화면 가장자리에서 뒤집힌 이미지나 비율이 맞지 않는 도형이 보이면 좌표계와 타깃 크기부터 확인한다.

## 이 절의 핵심

nannou는 애플리케이션과 프레임 흐름을 관리하고, wgpu는 GPU 리소스와 명령을 구성하며, WGSL 셰이더는 정점과 프래그먼트의 계산을 정의한다. 셰이더의 바인딩·입출력 계약은 호스트의 레이아웃과 파이프라인 설정에 정확히 맞아야 한다. 픽셀 단위의 반복 계산은 GPU에 잘 맞지만, 데이터 업로드와 동기화 비용을 포함해 CPU와 GPU의 역할을 나누어야 한다. nannou 0.20에서 실제 파이프라인을 구성할 때는 이전 버전 예제의 Rust API를 복사하지 말고 해당 버전의 문서와 예제에서 프레임 연결법을 확인한다.
