# 24.9 이미지, 텍스처, 출력

nannou에서 이미지는 화면에 그리는 그림인 동시에 픽셀 데이터의 묶음이다. 이 데이터를 CPU 메모리에서 직접 계산하거나 파일에서 읽을 수 있고, GPU 텍스처로 올려 셰이더에서 표본화할 수도 있다. 작업 결과를 창에 보여 주는 것과 이미지 파일로 저장하는 것은 별개의 단계이므로, 원하는 출력에 맞춰 데이터의 위치와 형식을 선택해야 한다. 이 절은 nannou 0.20 계열을 기준으로 이미지와 GPU 텍스처의 역할을 구분한다.

## 이미지, 텍스처, 렌더 타깃

세 용어는 서로 연관되어 있지만 같은 대상을 가리키지는 않는다.

| 대상 | 주된 역할 | 데이터가 사용되는 곳 |
| --- | --- | --- |
| 이미지(image) | 디코딩하거나 계산한 픽셀 값의 집합 | CPU 메모리, 파일 인코더 |
| 텍스처(texture) | GPU가 샘플링할 픽셀·수치 데이터 | GPU 메모리, 셰이더와 드로잉 |
| 렌더 타깃(render target) | GPU가 색상이나 수치를 써 넣는 표면 | 렌더 패스, 후처리, 화면 출력 |

같은 픽셀 정보가 CPU 이미지에서 GPU 텍스처로 업로드될 수 있고, GPU 렌더 타깃의 결과를 CPU로 읽어 와 파일로 저장할 수도 있다. 하지만 두 방향 모두 데이터 이동이 수반된다. 이미지가 텍스처라고 해서 자동으로 화면에 나타나는 것은 아니며, 텍스처를 도형이나 전체 화면 셰이더에 연결해 렌더링해야 한다. 반대로 렌더 타깃도 그 결과를 파일로 만들려면 별도의 읽기 및 인코딩 단계가 필요하다.

## CPU에서 픽셀 이미지 생성하기

각 픽셀의 색을 CPU에서 계산할 때는 보통 행 단위로 RGBA 바이트 배열을 만든다. 다음 함수는 정규화 좌표를 이용해 색상 띠와 동심원 무늬가 섞인 이미지를 생성한다. 배열은 행 우선이며 픽셀마다 빨강, 초록, 파랑, 알파 순서로 네 바이트를 둔다.

```rust
fn procedural_rgba(width: u32, height: u32) -> Vec<u8> {
    let width = width as usize;
    let height = height as usize;
    let mut pixels = vec![0_u8; width * height * 4];
    let scale = width.min(height).max(1) as f32;

    for y in 0..height {
        for x in 0..width {
            let nx = (x as f32 + 0.5 - width as f32 * 0.5) / scale;
            let ny = (y as f32 + 0.5 - height as f32 * 0.5) / scale;
            let radius = (nx * nx + ny * ny).sqrt();

            let red = (127.5 + 127.5 * (nx * 12.0).sin()).round() as u8;
            let green = (127.5 + 127.5 * (ny * 12.0).sin()).round() as u8;
            let blue = (127.5 + 127.5 * (radius * 36.0).cos()).round() as u8;
            let index = 4 * (x + y * width);

            pixels[index..index + 4].copy_from_slice(&[red, green, blue, 255]);
        }
    }

    pixels
}
```

여기서는 픽셀의 정수 좌표 대신 중심에 해당하는 `x + 0.5`, `y + 0.5`를 사용한다. `scale`로 짧은 변의 길이에 맞춰 정규화했기 때문에 가로세로 비율이 달라도 거리 기반 무늬가 원형에 가깝게 유지된다. 함수의 결과는 이미지 인코더가 받을 수 있는 원시 RGBA 데이터다. PNG 같은 파일로 저장하려면 여기에 너비·높이와 채널 형식을 함께 전달해 이미지 버퍼를 만들고, 선택한 이미지 라이브러리의 인코더를 호출한다.

파일을 읽어 이미지로 사용하는 경우도 큰 흐름은 같다. 디코더가 파일 형식과 압축을 처리해 픽셀 배열을 만들고, 작품은 그 배열을 CPU에서 분석하거나 GPU 텍스처로 전달한다. 입력 경로, 디코딩 실패, 색상 채널과 알파의 의미를 확인해 두면 이미지가 검게 나오거나 색이 뒤바뀌는 문제를 줄일 수 있다.

## 텍스처로 업로드하고 표본화하기

GPU 텍스처는 CPU에서 만든 이미지나 디코딩한 이미지의 내용을 GPU 메모리에 보관해 셰이더가 읽도록 한다. 일반적인 흐름은 다음과 같다.

```text
이미지 파일 또는 CPU 픽셀 계산
        -> 픽셀 형식과 크기 확인
        -> GPU 텍스처로 업로드
        -> 도형의 UV 좌표 또는 셰이더 입력으로 표본화
        -> 렌더 타깃에 합성
```

정적인 이미지는 초기화할 때 한 번 업로드하고 여러 프레임에서 재사용하는 편이 효율적이다. 애니메이션 중 일부 픽셀만 달라진다면 전체 텍스처를 매번 다시 올리기보다 변경 영역만 갱신할 수 있는지 살펴본다. GPU에서 만들어진 결과를 다음 단계에서 쓸 때는 CPU로 되가져오지 않고 다른 텍스처나 셰이더에 이어 붙이면 불필요한 왕복을 피할 수 있다.

텍스처의 색을 읽는 위치는 UV 좌표로 지정한다. 보통 `(0, 0)`에서 `(1, 1)`까지의 범위를 이미지 전체에 대응시키지만, 이미지의 첫 행과 GPU 좌표계의 위아래 방향이 다를 수 있다. 텍스처를 사각형에 붙였을 때 위아래가 뒤집히면 버퍼를 다시 뒤집기 전에 UV의 세로 성분을 `1 - v`로 바꾸는 방식이 가능한지 확인한다. 종횡비가 다른 이미지를 정사각형 영역에 그대로 맞추면 늘어나므로, 화면 영역의 비율을 보존하거나 잘라내는 규칙도 정해야 한다.

샘플링 방식은 텍스처를 확대·축소할 때 결과를 결정한다.

| 필터 | 동작 | 자주 쓰는 경우 |
| --- | --- | --- |
| 최근접(nearest) | 가장 가까운 텍셀 하나의 값을 선택 | 픽셀 아트, 분류 마스크, 정수 상태 격자 |
| 선형(linear) | 주변 텍셀 값을 보간 | 사진, 부드러운 확대·축소 |

텍스처 바깥 좌표의 처리 방식도 중요하다. 가장자리 값 고정 방식은 경계의 색을 바깥으로 늘리고, 좌표 반복 방식은 타일 패턴을 만든다. 거리장이나 마스크처럼 값 자체가 의미인 데이터는 필터링이 값을 바꾸어도 되는지 검토해야 한다. 셀 단위의 상태를 보존해야 한다면 최근접 샘플링이 알맞을 수 있다.

## 색상 텍스처와 수치 텍스처

사진이나 팔레트 이미지는 색상으로 해석해야 하므로 sRGB와 선형 색 공간의 차이를 고려한다. sRGB 값은 사람의 시각에 맞춰 비선형으로 인코딩되어 있다. 색상 텍스처를 셰이더에서 조명·보간 계산에 사용할 때는 샘플링과 출력 타깃의 색상 공간이 어떻게 처리되는지 확인해야 한다. 텍스처와 렌더 타깃에서 변환이 중복되면 지나치게 밝거나 어두운 결과가 나올 수 있다.

높이, 마스크, 속도, 온도처럼 수치 자체가 데이터인 텍스처는 색상 이미지와 다르게 취급한다. 이러한 데이터에 sRGB 변환을 적용하면 저장한 값과 셰이더가 읽는 값이 비선형으로 달라진다. 데이터의 범위와 정밀도에 맞는 선형 형식을 선택하고, 필요하다면 값의 범위를 명시적으로 인코딩·디코딩한다. 알파 채널은 마스크나 투명도를 담을 수 있지만, RGB 색상과 같은 색 공간 변환 대상으로 혼동하지 않도록 한다.

## 렌더 타깃과 여러 단계의 합성

셰이더나 드로잉 결과를 다시 입력으로 사용하려면 화면 밖의 텍스처를 렌더 타깃으로 만들 수 있다. 예를 들어 저해상도 노이즈를 한 텍스처에 그린 뒤 크게 확대하거나, 한 단계의 색 보정 결과를 다음 후처리 셰이더에 전달한다. 이때 텍스처는 한 단계에서는 쓰기 대상이고 이후 단계에서는 읽기 대상이 된다.

같은 텍스처를 한 패스에서 동시에 읽고 쓰면 결과가 정의되지 않거나 GPU 자원 사용 규칙에 어긋날 수 있다. 피드백이나 반복 필터에서는 입력과 출력을 별도 텍스처로 분리하고 패스마다 역할을 교환하는 ping-pong 구조를 사용한다. 오프스크린 렌더링과 읽기·쓰기 분리는 19.8절의 일반 원칙을 따르며, 여기서는 그 표면이 nannou의 GPU 텍스처와 연결된다는 점이 핵심이다.

24.8에서 살펴본 것처럼 셰이더를 직접 작성하면 텍스처와 샘플러를 바인딩해 표본화 규칙을 제어할 수 있다. 반면 단순히 이미지를 화면에 배치하거나 기본적인 레이어를 구성할 때는 nannou의 고수준 드로잉 경로가 적절할 수 있다. 두 경로의 선택 기준은 텍스처의 색을 그대로 표시하는지, 아니면 각 픽셀에서 사용자 정의 계산과 합성을 수행해야 하는지다.

## 화면 표시와 파일 출력

창에 표시되는 프레임은 애플리케이션의 현재 크기와 픽셀 밀도에 맞춰 렌더링된다. 화면 캡처는 그 순간의 화면 구성을 저장하는 편리한 방법이지만, 인쇄용 고해상도 이미지나 특정 비율의 출력을 만들 때는 화면 크기에 의존하지 않는 별도의 렌더 타깃을 구성하는 편이 낫다. 작품의 수식과 파라미터는 공유하고, 출력 단계에서 목표 너비·높이와 해상도를 지정하면 화면 미리보기와 최종 렌더를 일관되게 유지할 수 있다.

파일 저장 경로는 픽셀 데이터가 어디에 있는지에 따라 달라진다.

| 결과가 있는 곳 | 출력 흐름 | 주의할 점 |
| --- | --- | --- |
| CPU 이미지 버퍼 | 버퍼를 이미지 인코더에 전달해 파일로 저장 | 너비·높이·채널 순서와 파일 형식을 확인 |
| GPU 렌더 타깃 | GPU 텍스처를 읽기 가능한 버퍼로 복사한 뒤 CPU로 전달하고 인코딩 | 비동기 읽기, 행 정렬, 색상 형식 변환을 처리 |
| 창의 현재 프레임 | 화면 캡처 또는 별도 출력 렌더 타깃 사용 | 창 크기·픽셀 밀도·UI 포함 여부를 확인 |

GPU 결과를 파일로 저장하려면 일반적으로 GPU 텍스처를 CPU가 읽을 수 있는 버퍼로 복사해야 한다. GPU 작업 완료를 기다리는 과정은 비동기일 수 있고, 텍스처의 행 바이트 수가 읽기 버퍼의 정렬 요구와 다를 수도 있다. 따라서 행마다 패딩이 포함되었는지 확인해 이미지 데이터에 옮길 때 제거해야 한다. 이 절차는 wgpu 버전의 복사·읽기 API와 맞물리므로 구체적인 호출은 nannou 0.20 및 해당 wgpu 버전의 문서를 따른다.

매 프레임 GPU 결과를 CPU로 읽어 저장하면 동기화와 메모리 전송이 병목이 될 수 있다. 정지 이미지 한 장이나 간헐적 캡처라면 괜찮지만, 연속 프레임을 기록하려면 비동기 저장, 제한된 캡처 빈도, 별도 인코딩 작업 등을 고려한다. PNG는 무손실이고 투명도를 보존하지만, 사진 계열 결과에는 다른 형식이 더 효율적일 수 있다. 출력 형식과 색상 프로필도 최종 사용처에 맞춘다.

## 해상도와 성능 조절

RGBA 8비트 이미지 한 장은 대략 `너비 * 높이 * 4`바이트를 차지한다. 1920 x 1080 이미지라면 약 8.3 MB이고, 같은 크기의 여러 오프스크린 텍스처와 읽기 버퍼를 함께 두면 메모리 사용량이 빠르게 커진다. 화면보다 큰 렌더 타깃을 여러 장 유지할 때는 실제로 필요한 레이어만 고해상도로 만들고, 임시 텍스처는 더 이상 쓰지 않을 때 재사용하거나 해제한다.

CPU 계산이 충분히 빠른지, 텍스처 업로드가 얼마나 자주 일어나는지, GPU에서 수행하는 편이 유리한지 각각 측정한다. 픽셀 수를 줄이면 CPU 계산과 업로드, GPU 표본화 비용 모두 감소한다. 반대로 셰이더로 옮기면 CPU 픽셀 반복은 줄어들 수 있지만, 파이프라인 구성과 출력 읽기 비용은 남는다. 한 번 정한 이미지를 재사용하거나 저해상도 버퍼를 확대하는 방법은 품질과 속도의 실용적인 절충이 된다.

## 이 절의 핵심

이미지는 CPU의 픽셀 데이터, 텍스처는 GPU의 표본화 가능한 데이터, 렌더 타깃은 GPU가 새 결과를 기록하는 표면이다. CPU에서 만든 이미지는 파일 인코더에 직접 전달할 수 있지만, GPU 렌더 결과를 저장하려면 보통 읽기 버퍼로 복사하고 CPU에서 인코딩해야 한다. 텍스처를 사용할 때는 좌표 방향, 종횡비, 샘플링 필터, 색상 공간을 확인하고, nannou 0.20에서 텍스처 생성과 읽기 API는 해당 버전의 wgpu 문법에 맞춘다.
