# 25.1 OPENRNDR과 Kotlin 기반 크리에이티브 코딩

OPENRNDR은 Kotlin으로 그래픽과 인터랙티브 작업을 만드는 오픈소스 크리에이티브 코딩 프레임워크다. 도형과 경로를 그리는 기능부터 이미지, 입력, 애니메이션, 셰이더에 이르는 도구를 하나의 프로그램 안에서 조합할 수 있다. 이 장은 OPENRNDR 0.5.0과 Kotlin 2.4.20을 기준으로 설명한다. 프레임워크 버전과 Kotlin 컴파일러 버전은 서로 다른 의존성 축이므로, 실제 프로젝트에서는 두 버전과 Gradle 플러그인 구성을 함께 고정해야 한다. 프로젝트 설정은 25.2에서 다룬다.

## 스케치에서 프로그램으로

크리에이티브 코딩 환경은 간단한 도형을 빠르게 그리는 것만으로 설명되지 않는다. 작품이 커지면 좌표와 색을 계산하는 수식, 입자나 경로의 상태, 사용자 입력, 이미지 자원, 렌더링 순서가 함께 관리되어야 한다. OPENRNDR은 이런 요소를 Kotlin 애플리케이션의 구조 안에 배치하고, 프레임워크가 창과 그래픽 출력을 맡도록 한다.

그래서 OPENRNDR은 한 파일의 명령을 순서대로 실행하는 스케치 도구라기보다, 그래픽 프로그램을 구성하는 프레임워크로 보는 편이 정확하다. 작품은 프레임워크가 제공하는 프로그램 구조와 드로잉 기능을 사용하고, 작성자는 그 안에 작품의 계산 규칙과 시각적 결정을 구현한다. 프로그램의 실행 단계와 확장 지점은 25.3에서, 실제 좌표와 도형을 그리는 API는 25.4와 25.5에서 살펴본다.

이 구분은 수학을 코드로 옮길 때 유용하다. 예를 들어 극좌표에서 점들을 계산하는 규칙은 Kotlin 함수와 자료로 표현하고, 계산한 점을 화면에 연결하는 일은 드로잉 API에 맡길 수 있다. 같은 수학적 모델을 유지한 채 색, 도형, 변환, 시간에 따른 상태를 따로 바꾸면 알고리즘과 표현을 분리해 실험하기 쉽다.

## Kotlin이 더하는 표현력

Kotlin은 정적 타입 언어이며 JVM 생태계와 연결된다. 정적 타입은 좌표, 색, 숫자, 컬렉션처럼 코드가 다루는 값의 종류를 명시하고, 일부 오류를 실행 전에 발견하도록 돕는다. `val`과 `var`로 불변·가변 참조를 구분하고, 데이터 클래스와 컬렉션으로 작품의 상태를 표현할 수 있다. 람다와 확장 함수는 반복적인 그래픽 작업을 간결한 도메인 표현으로 구성하는 데 쓰인다.

OPENRNDR의 API는 Kotlin의 함수와 람다를 활용해 그래픽 작업을 선언적으로 적을 수 있게 한다. 이러한 문법은 단순히 짧은 표기법에 그치지 않는다. 반복 규칙을 함수로 추출하고, 파라미터를 바꾸며 결과를 관찰하고, 관련 작업을 작은 단위로 조합하는 방식을 자연스럽게 만든다. Kotlin 문법과 타입을 프로젝트에서 사용하는 방법은 다음 절에서 다루므로, 여기서는 언어의 성격과 작업 방식의 연결만 기억하면 된다.

정적 타입과 구조화는 코드가 커질 때 도움이 되지만, 처음부터 모든 클래스를 만들거나 복잡한 추상화를 도입해야 한다는 뜻은 아니다. 작은 식과 함수로 시작하고, 같은 규칙이 반복되거나 작품의 상태가 명확한 경계를 가질 때 자료 구조를 도입한다. 그래픽 결과를 빠르게 바꾸어 보는 실험성과, 프로젝트를 여러 모듈로 나누어 관리하는 확장성을 함께 고려할 수 있다.

## OPENRNDR의 작업 범위

OPENRNDR은 화면에 벡터 도형만 그리는 라이브러리에 머물지 않는다. 같은 애플리케이션에서 기하 구조를 생성하고, 프레임마다 값을 갱신하며, 이미지와 렌더 타깃을 이용하고, 필요하면 셰이더로 픽셀 단위 계산을 수행할 수 있다. 이 기능들은 작품의 요구에 따라 점진적으로 도입할 수 있다.

| 작업 | OPENRNDR에서 연결되는 영역 |
| --- | --- |
| 반복 규칙으로 선·원·경로 생성 | 드로잉 API와 기하 자료 |
| 시간에 따라 위치와 형태 갱신 | 프로그램의 프레임 실행과 상태 |
| 사진·텍스처·레이어 합성 | 이미지와 렌더 타깃 |
| 픽셀마다 색이나 마스크 계산 | 셰이더와 그래픽 파이프라인 |
| 노이즈·필터·입력 등 기능 확장 | 선택적으로 추가하는 ORX 모듈 |

ORX는 OPENRNDR과 함께 사용하는 확장 라이브러리들의 생태계다. 기본 기능을 대신하는 단일 패키지라기보다, 노이즈나 합성, 효과, 입력과 같은 작업에 필요한 모듈을 프로젝트에 선택적으로 추가하는 방식이다. 모듈의 종류와 의존성, 배포 방식은 25.10에서 자세히 살펴본다. 처음에는 핵심 API로 작품의 구조를 만들고, 필요한 기능이 분명해졌을 때 확장을 더하는 편이 의존성을 이해하기 쉽다.

## 다른 크리에이티브 코딩 환경과 비교

같은 수학적 규칙은 Processing, p5.js, openFrameworks, nannou, OPENRNDR 어디에서나 구현할 수 있지만, 프로젝트를 구성하는 언어와 API의 성격은 다르다. OPENRNDR의 특징은 Kotlin/JVM 프로젝트의 타입과 라이브러리 생태계를 활용하면서, 그래픽 코드를 Kotlin다운 함수와 DSL로 작성할 수 있다는 점이다.

| 환경 | 주된 언어·작업 성격 | OPENRNDR과 구별되는 점 |
| --- | --- | --- |
| p5.js | 브라우저 중심의 JavaScript 스케치 | 웹에서 시작하고 배포하기 쉬운 흐름에 강점 |
| Processing | Java 기반의 교육·실험 환경 | 작은 스케치를 빠르게 만들고 공유하는 경험에 초점 |
| openFrameworks | C++ 기반의 확장 가능한 툴킷 | C++ 생태계와 저수준 시스템 통합에 익숙한 작업에 적합 |
| nannou | Rust 기반 그래픽 프레임워크 | Rust의 소유권과 타입 체계로 상태와 자원을 관리 |
| OPENRNDR | Kotlin/JVM 기반의 그래픽 프레임워크 | Kotlin 문법과 Gradle 의존성 관리, 선택형 확장 모듈을 활용 |

이 비교는 우열이 아니라 작업 조건의 차이를 보여 준다. 브라우저에서 바로 실행되는 결과가 중요하면 웹 기반 환경이 편리할 수 있고, C++ 라이브러리나 특정 네이티브 장치와 긴밀히 연결해야 한다면 openFrameworks가 자연스러울 수 있다. Kotlin을 이미 사용하거나 JVM 도구와 라이브러리를 활용하고 싶고, 드로잉 API와 셰이더를 한 프로젝트 안에서 오가려 한다면 OPENRNDR이 잘 맞는다.

반면 Kotlin과 Gradle의 프로젝트 구조를 익혀야 하고, 의존성 및 런타임 설정도 관리해야 한다. 간단한 한 번짜리 스케치를 시작할 때는 브라우저 기반 도구보다 초기 준비가 많을 수 있다. 프레임워크가 그래픽 파이프라인을 감싸 주더라도 모든 GPU 자원과 셰이더 동작이 자동으로 해결되는 것은 아니다. 작품이 요구하는 해상도, 입력 장치, 배포 대상, 성능을 기준으로 필요한 API 층을 선택한다.

## 버전과 예제 읽기

이 장의 예제 기준은 OPENRNDR 0.5.0과 Kotlin 2.4.20이다. 버전 번호가 같거나 비슷해도 라이브러리의 API와 Kotlin 컴파일러 플러그인의 호환 관계가 자동으로 보장되는 것은 아니다. 의존성 버전, 플러그인 버전, Gradle 설정을 구분해 확인하고, 프로젝트의 잠금 또는 버전 카탈로그가 실제로 선택한 구성을 기준으로 예제를 읽는다.

특히 0.x 계열 프레임워크는 릴리스에 따라 함수와 확장 모듈의 구성이 변할 수 있다. 과거 예제를 가져올 때는 코드 조각만 옮기지 말고 해당 버전의 공식 문서와 예제 프로젝트를 함께 확인한다. 이 절은 환경의 개요에 집중하며, 구체적인 프로젝트 선언은 25.2, 프로그램 실행 구조는 25.3, 드로잉과 변환은 25.4·25.5에서 각각 다룬다.

## 이 절의 핵심

OPENRNDR은 Kotlin/JVM으로 그래픽과 인터랙티브 프로그램을 만드는 크리에이티브 코딩 프레임워크다. Kotlin의 타입, 함수, 람다와 Gradle 프로젝트 구조를 활용해 계산 규칙과 시각적 표현을 하나의 애플리케이션 안에 구성한다. 이 장은 OPENRNDR 0.5.0과 Kotlin 2.4.20을 기준으로 하며, 프로젝트 설정·실행 생명주기·드로잉·애니메이션·이미지·셰이더·ORX의 세부 사용법은 후속 절에서 나누어 살펴본다.
