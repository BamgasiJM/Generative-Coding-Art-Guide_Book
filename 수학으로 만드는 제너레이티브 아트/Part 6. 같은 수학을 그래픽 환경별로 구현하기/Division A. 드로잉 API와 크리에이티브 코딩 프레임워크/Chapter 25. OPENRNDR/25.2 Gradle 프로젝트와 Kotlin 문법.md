# 25.2 Gradle 프로젝트와 Kotlin 문법

OPENRNDR은 한 개의 Kotlin 파일만 실행하는 스케치 환경이 아니라, Gradle이 의존성과 빌드를 관리하는 JVM 프로젝트로 작업한다. 이 절은 OPENRNDR 0.5.0, Kotlin 2.4.20을 기준으로 프로젝트 파일의 역할과 그래픽 코드에서 자주 만나는 Kotlin 문법을 정리한다. 0.5.0 계열의 빌드 기준에는 Gradle 9.7.1도 포함된다. 프로젝트를 처음 만들 때는 이 버전에 맞는 `openrndr-template`을 출발점으로 삼고, 생성된 설정을 임의로 과거 예제의 구조로 바꾸지 않는 편이 안전하다.

## 프로젝트를 이루는 파일

Gradle 프로젝트에서는 소스 코드와 의존성 선언, 빌드 도구 설정이 서로 다른 파일에 놓인다.

| 파일 또는 디렉터리 | 역할 |
| --- | --- |
| `gradlew`, `gradlew.bat` | 프로젝트가 지정한 Gradle Wrapper 실행 파일 |
| `gradle/wrapper/` | Wrapper가 사용할 Gradle 배포판 설정 |
| `settings.gradle.kts` | 프로젝트 이름, 모듈, 플러그인 탐색 설정 |
| `build.gradle.kts` | Kotlin 플러그인, 의존성, 빌드와 실행 태스크 설정 |
| `gradle/libs.versions.toml` | 라이브러리와 플러그인 버전 및 별칭 관리 |
| `src/main/kotlin/` | Kotlin 소스 코드 |
| `src/main/resources/` | 실행 중 읽을 이미지, 폰트 등 리소스 |

`.kts`는 Gradle 설정을 Kotlin DSL로 작성한다는 뜻이다. `build.gradle.kts` 안에서 쓰는 설정 함수와 문법은 애플리케이션의 Kotlin 코드와 닮았지만, 빌드 스크립트라는 별도 맥락에서 해석된다. `dependencies`에 선언한 라이브러리는 애플리케이션의 컴파일 또는 실행 클래스 경로에 들어가고, 소스 파일의 `import`는 그 라이브러리 안에서 사용할 클래스나 함수를 이름으로 가져온다. 두 단계는 관련되지만 같은 기능은 아니다.

## 템플릿과 버전 카탈로그

OPENRNDR 0.5.0의 시작 프로젝트는 `openrndr-template`을 이용할 수 있다. 템플릿은 플러그인, 렌더링 백엔드, 라이브러리 별칭 등 서로 맞물리는 설정을 기본 프로젝트에 배치한다. 이 버전에서는 `openrndr-module-catalog`과 `openrndr-dependency-catalog`도 의존성 선언을 정리하는 데 활용되므로, 새 프로젝트에서는 템플릿이 생성한 카탈로그와 Gradle 설정을 우선 확인한다.

버전 카탈로그 파일의 버전 구역은 다음과 같은 형태다.

```toml
[versions]
kotlin = "2.4.20"
openrndr = "0.5.0"
orx = "0.5.0"
```

이 코드는 `gradle/libs.versions.toml`의 일부만 보여 준다. 실제 템플릿에는 플러그인과 모듈을 참조하는 별칭 선언도 포함될 수 있다. 버전 번호를 이곳에 모으면 여러 모듈이 같은 OPENRNDR 릴리스를 사용하게 관리하기 쉽고, ORX를 추가할 때도 호환되는 버전을 한곳에서 맞출 수 있다. ORX 모듈은 사용하는 기능에 필요한 것만 추가하며, 구체적인 모듈 선택과 배포는 25.10에서 다룬다.

0.5.0에서는 SDL3 기반 백엔드가 추가되고 GLFW 백엔드는 deprecated 상태가 되었다. 따라서 과거 설정 예제의 백엔드 의존성을 무심코 복사하지 말고, 템플릿이 선택한 백엔드와 현재 공식 가이드를 확인한다. LWJGL을 포함한 네이티브 런타임 의존성도 직접 숫자를 맞춰 중복 선언하기보다 템플릿과 카탈로그의 구성을 따른다. Kotlin 버전, OPENRNDR 버전, Gradle Wrapper 버전은 각각 다른 설정이므로 한 값을 바꾸었다고 나머지가 자동으로 호환되는 것은 아니다.

Gradle Wrapper를 사용하면 컴퓨터에 설치된 Gradle 버전과 무관하게 프로젝트에 기록된 버전으로 작업을 실행한다.

```bash
./gradlew tasks
./gradlew build
./gradlew run
```

Windows에서는 `gradlew.bat`을 실행한다. `tasks`는 현재 프로젝트가 제공하는 작업을 보여 주고, `build`는 컴파일과 검증 작업을 수행한다. `run`은 템플릿의 애플리케이션 플러그인과 프로젝트 설정이 실행 태스크를 제공할 때 사용한다. IntelliJ IDEA에서 프로젝트를 열면 Gradle 동기화가 의존성을 가져오고 Kotlin 코드 분석에 필요한 클래스 경로를 구성한다. 버전 카탈로그를 수정했다면 Gradle 프로젝트를 다시 동기화한다.

## `val`, `var`, 타입 추론

Kotlin에서 `val`은 변수 이름에 새 값을 다시 대입할 수 없고, `var`는 다시 대입할 수 있다. 그래픽 프로그램에서는 고정된 매개변수와 프레임마다 바뀌는 상태를 구분하는 데 유용하다.

```kotlin
val ringCount = 12
val radius = 80.0
var phase = 0.0

phase += 0.02
```

`val`은 참조의 재대입을 막지만, 그 참조가 가리키는 객체까지 자동으로 불변으로 만들지는 않는다. 예를 들어 `val`로 선언한 가변 컬렉션은 참조를 다른 컬렉션으로 바꿀 수 없더라도 원소를 변경할 수 있다. 상태를 추적하기 쉽도록 먼저 `val`을 선택하고, 값 자체를 갱신해야 할 때 `var`를 사용한다.

Kotlin은 값에서 타입을 추론할 수 있지만 숫자 타입을 자동으로 서로 변환하지 않는다. 정수 리터럴 `12`는 보통 `Int`, 소수점이 있는 `12.0`은 `Double`이다. OPENRNDR의 창 너비와 높이는 정수로 다뤄지는 반면 좌표·반지름·시간 계산은 대개 `Double`이므로, 계산의 의도에 맞는 타입을 처음부터 지정한다.

```kotlin
val centerX = width / 2.0
val integerHalf = width / 2
val preciseHalf = width.toDouble() / 2.0
```

`width / 2`는 두 피연산자가 정수이므로 정수 나눗셈을 한다. 홀수 너비에서 소수 부분이 사라질 수 있다. `width / 2.0`처럼 한쪽을 `Double`로 쓰거나 `.toDouble()`로 변환하면 실수 계산이 된다. 서로 다른 숫자 타입을 받는 함수에 전달할 때도 필요한 변환을 명시한다. 이런 타입 선택은 25.4의 좌표와 25.5의 기하 계산에서도 계속 등장한다.

## 함수와 데이터 모델

작품의 수식은 입력과 출력이 분명한 함수로 분리하면 반복해서 사용하고 시험하기 쉽다. Kotlin 함수는 매개변수와 반환 타입을 선언할 수 있고, 본문이 하나의 식이면 `=`로 반환값을 표현할 수 있다.

```kotlin
import kotlin.math.sin

fun wave(x: Double, time: Double, frequency: Double): Double =
    sin(x * frequency + time)
```

매개변수 타입을 적어 두면 함수가 기대하는 자료가 명확해지고, 반환 타입은 수식이 만들어 내는 값을 드러낸다. 간단한 결과를 계산하는 함수와 상태를 변경하거나 그리기를 수행하는 코드를 구별하면, 수학 로직을 화면 API에 덜 의존하게 만들 수 있다.

관련된 값 여러 개를 한 단위로 다룰 때는 데이터 클래스를 사용할 수 있다.

```kotlin
data class Orbit(
    val centerX: Double,
    val centerY: Double,
    val radius: Double,
    var phase: Double,
)
```

생성자에 `val`이나 `var`를 붙이면 프로퍼티가 된다. 위 예에서 중심과 궤도 반지름은 고정값이고, 위상은 애니메이션이 갱신할 값이다. 이 문법은 좌표나 입자 상태처럼 관련 데이터를 묶을 때 편리하다. 프레임마다 상태를 어떻게 보관하고 갱신하는지는 25.3과 25.7에서 이어서 설명한다.

## 람다와 리시버 문맥

람다는 이름 없이 전달하는 함수 값이다. 함수가 동작을 인자로 받으면 호출 위치에서 그 동작을 간결하게 작성할 수 있다.

```kotlin
val square: (Double) -> Double = { value -> value * value }
val result = square(3.0)
```

마지막 매개변수가 람다인 함수는 람다를 괄호 바깥에 적을 수 있다. Kotlin 표준 라이브러리의 `buildString`은 리시버가 있는 람다의 읽기 쉬운 예다.

```kotlin
val title = buildString {
    append("OPENRNDR ")
    append("0.5.0")
}
```

`StringBuilder.() -> Unit`처럼 수신 객체 타입이 붙은 함수 타입을 리시버가 있는 람다라고 한다. 블록 안의 `append()`는 암묵적 수신 객체인 `StringBuilder`의 함수다. OPENRNDR API도 람다와 리시버 문맥을 활용해 설정이나 드로잉 코드를 DSL처럼 표현한다. 실제 `application`, `program`, `extend` 블록에서 어느 객체가 문맥을 제공하는지는 25.3에서 다루므로, 여기서는 블록 문법과 리시버 개념을 구분해 읽는 데 집중한다.

## 확장 함수와 널 가능 타입

확장 함수(extension function)는 기존 타입의 소스 코드를 수정하지 않고 그 타입에 새 호출 문법을 제공한다. 실제로는 수신 객체를 첫 번째 인자로 받는 함수이며, 기존 클래스에 새 멤버를 추가하거나 상속 관계를 바꾸지는 않는다.

```kotlin
fun Double.normalizedBetween(start: Double, end: Double): Double {
    require(start != end)
    return (this - start) / (end - start)
}

val unit = 25.0.normalizedBetween(0.0, 100.0)
```

`this`는 확장 대상인 `Double` 값이다. 이런 문법은 `Vector2` 같은 그래픽 타입에 반복적으로 쓰는 수학 연산을 붙일 때 유용하지만, 너무 많은 함수를 추가하면 원래 라이브러리 API와 직접 만든 확장 API가 혼동될 수 있다. 작품의 개념을 분명하게 해 주는 연산만 선택한다.

Kotlin 타입은 기본적으로 `null`이 아닌 값을 담는다. 값이 없을 수 있으면 `String?`처럼 타입에 물음표를 붙이고, 안전 호출 `?.`이나 기본값 연산자 `?:`로 처리한다.

```kotlin
val caption: String? = null
val visibleCaption = caption ?: "Untitled"
```

`!!`는 값이 null이 아니라고 강제로 단언하며, 실제로 null이면 실행 중 예외를 일으킨다. 입력이나 파일에서 올 수 있는 값은 안전 호출과 기본값, 명시적인 오류 처리를 우선한다. 특히 그래픽 자원 로딩 실패를 감추기보다 원인을 확인할 수 있게 처리하는 편이 좋다.

## 이 절의 핵심

OPENRNDR 0.5.0 프로젝트는 템플릿과 Gradle Wrapper, 버전 카탈로그를 중심으로 구성하고 Kotlin 2.4.20 및 Gradle 9.7.1과 백엔드 의존성을 함께 관리한다. Kotlin에서는 `val`과 `var`, 명시적인 숫자 변환, 타입이 드러나는 함수, 람다와 리시버 문맥을 익히면 OPENRNDR 코드의 구조를 읽기 쉬워진다. 실행 DSL은 25.3, 좌표·도형은 25.4와 25.5, 컬렉션 기반 패턴은 25.6에서 더 구체적으로 다룬다.
