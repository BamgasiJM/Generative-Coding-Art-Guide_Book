# 25.10 ORX 확장 생태계와 프로젝트 배포

OPENRNDR의 핵심 API는 창, 드로잉, 이미지와 셰이더를 위한 기반을 제공하고, ORX는 그 위에 더 구체적인 기능을 모듈별로 확장한다. 필요한 모듈을 골라 프로젝트에 포함하면 반복해서 구현할 일을 줄일 수 있다. 이 절은 OPENRNDR과 ORX 0.5.0, Kotlin 2.4.20을 기준으로 모듈 선택과 배포 준비를 살펴본다. 렌더 타깃과 레이어 합성의 사용법은 25.8, `ShadeStyle`과 GLSL은 25.9에서 설명했으므로 여기서는 각 기능을 어떤 모듈에 맡길지에 집중한다.

## OPENRNDR과 ORX의 관계

ORX는 OPENRNDR 프로젝트에서 사용할 수 있는 확장 라이브러리 모음이다. 모든 기능이 하나의 API에 들어 있는 것이 아니라, 합성, 도형 생성, 셰이딩 프리셋, 이미지 효과처럼 목적이 다른 모듈로 나뉜다. 따라서 ORX를 쓴다는 말은 대개 작품에 필요한 기능의 모듈을 의존성으로 추가한다는 뜻이다.

| 모듈 | 맡는 역할 | 선택할 때 떠올릴 작업 |
| --- | --- | --- |
| `orx-shapes` | 곡선과 도형을 구성하거나 다루는 보조 기능 | 점들로 부드러운 곡선을 만들거나 윤곽을 따라 일정한 간격으로 배치 |
| `orx-shade-styles` | 바로 적용할 수 있는 셰이딩 스타일과 그라디언트 | 직접 GLSL을 쓰기 전에 색 변화나 그라디언트 프리셋 적용 |
| `orx-compositor` | 여러 렌더 레이어의 합성과 마스크 구성 | 배경, 전경, 마스크, 합성 순서를 별도 단계로 관리 |
| `orx-fx` | 이미지와 렌더 결과에 적용하는 효과 | 흐림과 같은 후처리 효과를 렌더 단계에 추가 |

표의 기능은 모듈의 성격을 요약한 것이다. 구체적인 함수와 인자, 제공 범위는 릴리스마다 바뀔 수 있으므로 실제 프로젝트의 0.5.0 API와 생성된 템플릿의 의존성 카탈로그를 기준으로 확인한다. 특히 ORX 모듈마다 패키지와 import가 다르다. Kotlin 파일에 `import`를 적는 일은 이름을 가져오는 것이지, Gradle에 라이브러리를 추가하는 과정은 아니다.

## 필요한 모듈을 고르는 순서

먼저 작품에서 필요한 결과를 문장으로 적는다. 예를 들어 “점 목록으로 부드러운 닫힌 윤곽을 만든다”면 도형 보조 기능을, “도형을 여러 장의 투명한 결과로 나누어 합성한다”면 compositor를 찾는다. 기능이 명확하면 비슷한 이름의 의존성을 무작정 추가하지 않고도 모듈 범위를 좁힐 수 있다.

OPENRNDR 0.5.0과 ORX 0.5.0을 함께 사용할 때는 템플릿이 생성한 `gradle/libs.versions.toml`과 모듈 카탈로그를 먼저 살핀다. 필요한 기능이 이미 템플릿 번들이나 프로젝트 의존성에 들어 있을 수 있다. 없다면 카탈로그에 정의된 별칭으로 해당 모듈을 직접 추가하고, 버전은 프로젝트의 ORX 기준값과 맞춘다. 별칭의 실제 표기는 템플릿 버전에 따라 다를 수 있으므로 예제에서 이름을 추측해 복사하기보다 카탈로그에 선언된 이름을 사용한다. 프로젝트 구조와 버전 카탈로그의 역할은 25.2에서 다루었다.

기능을 확인하는 실용적인 순서는 다음과 같다.

1. OPENRNDR 핵심 API만으로 가능한지 살핀다.
2. 필요한 동작에 대응하는 ORX 모듈을 공식 문서나 프로젝트 카탈로그에서 찾는다.
3. 해당 모듈이 이미 의존성에 포함되어 있는지 확인한다.
4. 없다면 ORX 버전을 프로젝트 기준에 맞춰 추가하고, IDE에서 제공하는 import를 확인한다.
5. 최소 예제로 호출한 뒤 기능을 작품 코드에 통합한다.

필요한 기능이 여러 모듈에 흩어져 있을 수는 있지만, ORX 전체를 한꺼번에 추가하는 것이 기본 해법은 아니다. 사용하지 않는 모듈은 의존성 그래프와 런타임 구성만 복잡하게 만들 수 있다. 반대로 템플릿이 관리하는 번들이 이미 필요한 모듈을 제공한다면 같은 기능을 별도 버전으로 중복 선언하지 않는다. 템플릿 설정을 바꿀 때는 버전 카탈로그와 실제 의존성 선언이 함께 일치하는지도 확인한다.

## 개발 실행과 배포 산출물은 다르다

IDE에서 실행이 된다는 사실만으로 다른 컴퓨터에서도 실행 가능한 배포물이 만들어진 것은 아니다. 개발 실행은 Gradle이 프로젝트의 클래스 경로와 리소스를 구성해 주지만, 최종 사용 환경에는 필요한 라이브러리, 네이티브 런타임, 리소스 파일을 함께 전달해야 한다.

OPENRNDR 프로젝트의 Gradle 태스크는 템플릿과 플러그인 설정에 따라 달라질 수 있다. 먼저 프로젝트가 제공하는 태스크를 확인하고, 그중 빌드와 배포에 맞는 태스크를 사용한다.

```bash
./gradlew tasks --all
./gradlew build
```

`build` 성공은 소스가 컴파일되고 구성된 빌드 검사가 끝났다는 뜻이지, 반드시 독립 실행형 설치 프로그램이 생성되었다는 뜻은 아니다. 프로젝트에 Gradle `application` 플러그인과 distribution 구성이 있다면 `installDist` 같은 태스크가 실행 스크립트와 런타임 의존성을 포함한 배포 디렉터리를 만들 수 있다. 해당 태스크가 없다면 템플릿의 Gradle 플러그인이 제공하는 실행·패키징 절차를 확인한다. 만들어진 파일의 위치와 포함 내용도 빌드 설정에서 확인한다.

JAR 하나만 복사하는 방식은 특히 주의해야 한다. 일반 JAR에는 의존 라이브러리가 자동으로 모두 들어 있다고 보장할 수 없으며, 실행에 필요한 플랫폼별 네이티브 파일이나 작품 리소스도 별도로 누락될 수 있다. 반대로 Gradle distribution 디렉터리는 설정된 JVM 런타임 의존성을 모을 수 있지만, 보통 JVM 자체까지 포함하는지는 별도 설정에 달려 있다. 설치 프로그램이나 자체 런타임을 묶으려면 JDK의 `jpackage` 등 별도 패키징 도구를 고려하고, 대상 운영체제에서 패키지를 만들어 검증한다.

## 리소스와 네이티브 런타임 점검

이미지, 폰트, 오디오, 설정 파일 같은 외부 리소스는 개발 환경에서 사용하던 상대 경로가 배포 후에도 유효한지 확인한다. 프로젝트의 `data` 디렉터리를 현재 작업 디렉터리를 기준으로 읽는 구조라면, 실행 파일과 함께 그 디렉터리를 배치하거나 빌드 설정에서 리소스를 패키지에 포함해야 한다. 클래스패스에서 읽는 리소스와 파일 시스템 경로에서 읽는 리소스는 배포 방식이 다르므로, 프로그램이 어느 방식을 쓰는지 확인한다. 상대 경로가 IDE의 작업 디렉터리에서만 우연히 동작하는 상태로 남지 않도록 한다.

그래픽 애플리케이션에는 플랫폼별 네이티브 구성도 관여한다. OPENRNDR 0.5.0에서는 SDL3 기반 백엔드가 추가되었고 GLFW 백엔드는 deprecated 상태다. 오래된 설정을 복사해 백엔드나 LWJGL 네이티브 의존성을 직접 고정하기보다, 현재 템플릿과 의존성 카탈로그가 선택한 구성을 유지한다. 배포 대상으로 삼는 운영체제와 CPU 아키텍처에서 네이티브 라이브러리가 선택되고 로드되는지 확인해야 한다. 개발 PC에서 성공한 빌드가 다른 운영체제나 아키텍처에 그대로 맞는다고 가정하지 않는다.

## 배포 전 확인 목록

- OPENRNDR과 ORX 모듈의 버전이 프로젝트의 0.5.0 기준과 일치하는가?
- 실제 사용 기능에 필요한 모듈만 추가했으며, 템플릿 번들과 중복 선언하지 않았는가?
- 배포 산출물에 실행에 필요한 런타임 의존성이 포함되었는가?
- 이미지와 폰트 등 외부 파일이 정해진 경로에 포함되거나 패키징되었는가?
- 창 생성에 필요한 네이티브 백엔드가 대상 OS와 아키텍처에서 동작하는가?
- IDE가 아닌 배포 디렉터리에서 실행해 파일 경로와 그래픽 장치를 확인했는가?
- 작품을 재현해야 한다면 난수 시드, 캔버스 크기, 생성 매개변수와 출력 위치를 기록했는가?

마지막 항목은 특히 생성형 작품에서 중요하다. 실행 파일만 전달하면 특정 결과를 다시 만들 수 있다고 보장할 수 없다. 생성에 쓰인 시드와 입력값, 내보낸 이미지나 영상의 위치를 함께 관리하면 빌드와 작품 결과를 구분해 보존할 수 있다.

## 이 절의 핵심

ORX는 OPENRNDR 기능을 모듈별로 확장하므로, 먼저 필요한 동작을 정한 뒤 대응 모듈과 템플릿 카탈로그를 확인한다. OPENRNDR과 ORX 버전을 맞추고, 이미 번들에 포함된 의존성을 중복 추가하지 않는다. 배포 시에는 빌드 성공과 독립 실행 가능성을 구별하고, 런타임 라이브러리·리소스 경로·SDL3 등 플랫폼별 네이티브 구성까지 대상 환경에서 확인한다.
