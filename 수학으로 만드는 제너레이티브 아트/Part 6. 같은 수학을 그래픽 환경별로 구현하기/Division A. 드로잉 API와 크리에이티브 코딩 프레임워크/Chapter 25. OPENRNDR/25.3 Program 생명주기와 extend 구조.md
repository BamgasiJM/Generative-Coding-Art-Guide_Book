# 25.3 Program 생명주기와 extend 구조

OPENRNDR 프로그램은 `main()`에서 애플리케이션을 시작하고, 초기 설정을 거쳐 `Program`을 구성한 다음 프레임 단위의 작업을 반복한다. 이 흐름을 이해하면 초기화할 값과 매 프레임 다시 계산할 값을 올바른 위치에 둘 수 있다. 이 절의 예제는 OPENRNDR 0.5.0과 Kotlin 2.4.20을 기준으로 하며, Gradle 설정과 Kotlin의 기본 문법은 25.2에서 다룬 내용을 전제로 한다.

## 실행 흐름 한눈에 보기

핵심 구조는 다음과 같다.

```text
JVM 진입
  -> main()
    -> application { } 애플리케이션 구성 및 시작
      -> configure { } 창과 실행 환경 설정
      -> program { } Program 초기화
        -> extend { } 프레임 작업을 등록
          -> 창이 실행되는 동안 프레임마다 반복
```

각 이름은 Kotlin의 예약어가 아니라 OPENRNDR API가 제공하는 함수와 DSL 블록이다. 중괄호 안에는 해당 함수가 요구하는 람다를 전달한다. Kotlin의 후행 람다와 리시버 문맥은 이 구조를 간결하게 만들며, 각 블록에서 사용할 수 있는 속성과 객체는 그 API가 정한다.

| 구성 | 생명주기에서 맡는 일 |
| --- | --- |
| `main()` | 프로그램의 진입점에서 애플리케이션을 시작 |
| `application { }` | OPENRNDR 애플리케이션과 플랫폼 실행 흐름을 구성 |
| `configure { }` | 창의 크기나 제목 등 시작 전에 적용할 설정을 지정 |
| `program { }` | `Program`에 속하는 초기 상태와 확장 기능을 한 번 구성 |
| `extend { }` | 프레임마다 수행할 동작을 확장으로 등록 |

이 흐름은 p5.js의 `setup()`과 `draw()`를 떠올리면 이해하기 쉽지만 완전히 같은 구조는 아니다. `configure`는 시작 설정을, `program`은 프로그램 구성을, `extend`는 프레임마다 실행될 확장 동작을 각각 맡는다. `extend`는 작성자가 직접 `while` 루프를 돌리는 코드가 아니라, OPENRNDR이 관리하는 프레임 흐름에 동작을 연결하는 지점이다.

## 창 설정과 Program 초기화

다음 예제는 시작 시 창 크기를 정하고, `Program`이 구성될 때 한 번만 고정 파라미터를 만든다. 프레임 작업에서는 경과 시간으로 원의 위치를 계산해 그린다.

```kotlin
import kotlin.math.cos
import kotlin.math.sin
import org.openrndr.application
import org.openrndr.color.ColorRGBa

fun main() = application {
    configure {
        width = 800
        height = 600
    }

    program {
        val orbitRadiusX = 150.0
        val orbitRadiusY = 90.0

        extend {
            drawer.clear(ColorRGBa.BLACK)
            drawer.fill = ColorRGBa.PINK
            drawer.stroke = null

            val phase = seconds * 0.8
            val x = width / 2.0 + cos(phase) * orbitRadiusX
            val y = height / 2.0 + sin(phase) * orbitRadiusY

            drawer.circle(x, y, 18.0)
        }
    }
}
```

`application { }`는 애플리케이션을 구성하고 실행한다. `configure { }`에서 지정한 `width`와 `height`는 창 설정이며 정수 값이다. `program { }`은 해당 프로그램의 실행 환경을 구성하는 자리다. 궤도의 반지름처럼 실행 중 계속 바뀌지 않는 값은 이곳에서 한 번 선언한다.

`extend { }` 안의 코드는 프레임마다 평가된다. 매 프레임의 `seconds` 값으로 위상을 계산하고, 그 위상으로 좌표를 얻은 뒤 현재 프레임에 원을 그린다. `width / 2.0`처럼 실수 리터럴을 쓰면 좌표 계산이 `Double`로 수행된다. 좌표계의 방향과 도형 인자의 의미는 25.4에서 이어서 살펴본다.

## `extend`는 반복문이 아니라 프레임 확장점

프레임마다 동작해야 하는 코드를 직접 반복문으로 둘 필요는 없다. `extend { }`를 호출하면 프레임워크의 프로그램에 확장 동작을 등록하고, 프레임워크가 실행 중 그 동작을 반복 호출한다. 블록 안에서는 드로잉 API로 화면을 구성하거나, 현재 프로그램의 값과 상태를 읽어 다음 계산을 수행할 수 있다.

이름에 `extend`가 들어가는 것은 `Program`이 확장 가능한 구조를 가진다는 점을 나타낸다. 화면 그리기뿐 아니라 입력 반응, 합성, 후처리 같은 동작도 확장으로 구성할 수 있다. 다만 각 확장이 실행되는 세부 단계와 기능별 확장 사용법은 해당 API에 따라 달라지므로, 이 절에서는 기본 프레임 블록을 중심으로 이해한다. 입력과 애니메이션 기법은 25.7, 이미지와 렌더 타깃은 25.8, 셰이더는 25.9에서 다룬다.

일반적인 `extend` 블록은 매 프레임의 장면을 다시 그린다. `drawer.clear()`는 이번 프레임의 배경을 명시적으로 설정한다. 각 프레임에서 배경을 지운 뒤 현재 상태를 그리면 이전 프레임의 도형이 남지 않는 애니메이션이 된다. 잔상이나 프레임 누적을 만들려면 기본 화면에 우연히 남아 있기를 기대하지 말고, 별도의 렌더 타깃과 합성 방식을 설계한다. 이 구조는 25.8의 렌더 타깃에서 다룬다.

## 상태의 위치와 수명

중괄호의 위치는 변수의 수명과 계산 빈도를 결정한다. `program { }` 안에서 `extend { }` 바깥에 만든 객체와 값은 프로그램을 구성할 때 한 번 만들어져 프레임 작업에서 재사용할 수 있다. 반대로 `extend { }` 내부의 지역 변수는 프레임 작업이 실행될 때마다 새로 계산된다.

| 둘 위치 | 일반적인 수명 | 적합한 값 |
| --- | --- | --- |
| `program { }`에서 확장 등록 전 | 프로그램이 실행되는 동안 유지 | 고정 파라미터, 초기 상태, 재사용할 자원 |
| `extend { }` 내부 | 해당 프레임 계산 중 사용 | 현재 좌표, 현재 색, 임시 중간값 |
| 별도의 상태 객체 | 프로그램이 유지되는 동안 갱신 | 입자 목록, 시뮬레이션 상태, 작품의 매개변수 |

Kotlin의 람다는 바깥에서 선언한 변수를 캡처할 수 있다. 따라서 `program` 범위에서 선언한 `var`를 `extend` 안에서 갱신하면 프레임 사이에도 같은 상태가 유지된다.

```kotlin
program {
    var phase = 0.0

    extend {
        drawer.clear(ColorRGBa.BLACK)
        drawer.circle(400.0 + cos(phase) * 120.0, 300.0, 16.0)
        phase += 0.02
    }
}
```

이 예에서 `phase`는 프레임 블록 밖에서 한 번 만들어지고, 매 프레임 그 값을 사용한 뒤 조금 증가한다. 증가량을 프레임마다 고정했기 때문에 실제 초당 속도는 프레임률에 따라 달라진다. 시간 기반 움직임이나 프레임률과 독립적인 시뮬레이션은 25.7에서 설명한다. 중요한 것은 값의 선언 위치가 매 프레임 초기화 여부를 결정한다는 점이다.

이미지나 셰이더, 복잡한 기하 자료처럼 생성 비용이 큰 객체도 필요할 때마다 `extend` 안에서 만들지 않는다. 프로그램 초기화 시 한 번 만들고 프레임마다 재사용하면 반복 할당과 불필요한 업로드를 줄일 수 있다. 반면 매 프레임 달라지는 좌표와 색은 프레임 안에서 계산해도 된다. 초기화와 갱신을 나누면 코드의 성능 의도도 분명해진다.

## 업데이트와 그리기의 순서

간단한 작품은 `extend` 안에서 상태를 읽고, 새 값을 계산하고, 그리는 일을 연달아 처리할 수 있다. 복잡한 시뮬레이션에서는 이 순서를 명시적으로 나누는 편이 이해하기 쉽다.

```text
입력과 현재 시각 읽기
  -> 시뮬레이션 상태 갱신
    -> 현재 상태로 도형 계산
      -> 프레임에 그리기
```

상태를 그린 다음 갱신하면 화면은 갱신 전 상태를 보여 주고, 갱신한 다음 그리면 갱신 후 상태를 보여 준다. 둘 중 하나가 항상 옳은 것은 아니지만, 순서를 섞어 쓰면 한 프레임의 동작을 추적하기 어려워진다. 파티클처럼 여러 개체의 상태가 서로 영향을 주는 경우에는 상태 갱신 함수와 표현 코드를 분리하고, 언제 값을 바꾸는지 한곳에서 결정한다.

`extend`가 프레임마다 실행된다는 사실은 `program` 블록 안의 모든 코드도 매번 실행된다는 뜻이 아니다. `program` 본문에 둔 초기화는 확장을 등록할 때 실행되고, 등록된 블록 안의 문장이 프레임마다 실행된다. 실행 빈도를 판단할 때는 중괄호가 어느 함수 호출에 전달되었는지 살펴보면 된다.

## 구조를 나누는 기준

작은 스케치에서는 하나의 `extend`에 배경, 도형, 계산을 함께 둘 수 있다. 코드가 길어지면 한 프레임의 내용을 역할별 함수로 나누거나, 별도의 상태 클래스로 시뮬레이션을 표현한다. 그리기 함수는 가능하면 현재 상태를 화면 명령으로 바꾸는 데 집중하고, 계산 함수는 좌표나 색처럼 화면 독립적인 값을 돌려주도록 구성한다.

반복되는 코드를 분리하더라도 프레임 실행 시점이 바뀌지 않도록 주의한다. 초기 상태를 만드는 함수는 `program` 구성 중 호출하고, 매 프레임의 위치 계산은 `extend`가 실행될 때 호출한다. 반대로 큰 텍스처나 정적인 형상을 매 프레임 다시 생성하면 화면은 같아 보여도 CPU와 GPU에 불필요한 일이 반복될 수 있다.

## 이 절의 핵심

`application`은 애플리케이션 실행을 시작하고, `configure`는 창과 실행 환경을 설정하며, `program`은 프로그램 상태와 확장을 구성한다. `extend`는 직접 만든 무한 루프가 아니라 프레임워크의 프레임 흐름에 반복 동작을 등록하는 확장점이다. 초기화할 값과 재사용할 자원은 `extend` 바깥에, 프레임마다 달라지는 값은 안에 두고, 상태 갱신과 그리기의 순서를 의식하면 OPENRNDR 프로그램을 안정적으로 확장할 수 있다.
