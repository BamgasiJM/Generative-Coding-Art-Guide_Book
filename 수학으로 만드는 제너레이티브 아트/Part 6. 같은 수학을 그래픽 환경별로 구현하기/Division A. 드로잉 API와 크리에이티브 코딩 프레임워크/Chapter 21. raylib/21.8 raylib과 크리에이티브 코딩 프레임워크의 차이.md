# 21.8 raylib과 크리에이티브 코딩 프레임워크의 차이

raylib과 p5.js, Processing은 모두 코드로 그래픽을 만들 수 있지만 프로그램을 시작하고 화면을 갱신하는 구조는 다르다. p5.js와 Processing은 스케치의 생명주기와 작업 흐름을 마련해 주는 크리에이티브 코딩 환경에 가깝다. raylib은 C 프로그램에서 창과 반복문을 직접 관리하면서 그래픽·입력·오디오 기능을 호출하는 라이브러리다. 차이는 표현할 수 있는 수학보다, 수학을 실행 가능한 프로그램으로 연결하는 방식에 있다.

## 같은 그림, 다른 실행 구조

캔버스 가운데 원 하나를 그리는 일은 어느 환경에서도 간단하다. 하지만 스케치 환경에서는 프레임워크가 `setup()`과 `draw()`를 호출하고, raylib에서는 프로그램이 `main()` 안에서 창과 반복을 관리한다.

```javascript
// p5.js
function setup() {
  createCanvas(400, 300);
  noLoop();
}

function draw() {
  background(248);
  circle(width / 2, height / 2, 40);
}
```

```c
// raylib: main() 안의 초기화와 프레임 루프
InitWindow(400, 300, "one circle");

while (!WindowShouldClose())
{
    BeginDrawing();
    ClearBackground(RAYWHITE);
    DrawCircle(200, 150, 20.0f, BLUE);
    EndDrawing();
}

CloseWindow();
```

두 예제는 같은 중심과 같은 지름의 원을 그린다. p5.js의 `circle()`은 지름 `40`을 받고, raylib의 `DrawCircle()`은 반지름 `20`을 받는다. 코드 모양을 그대로 옮기는 대신 함수가 요구하는 기준점과 단위를 맞춰야 하는 이유다. p5.js에서 `noLoop()`를 호출해 정지 그림으로 만들었다면, raylib은 반복문을 유지하면서도 매 프레임 같은 장면을 그릴 수 있다. 반복을 직접 관리하는 만큼 언제 갱신하고 언제 그릴지도 프로그램이 정한다.

## 작업 방식의 차이

| 관점 | p5.js·Processing의 일반적인 스케치 | raylib의 일반적인 C 프로그램 |
| --- | --- | --- |
| 시작과 반복 | 프레임워크가 `setup()`과 `draw()` 같은 생명주기를 제공 | 개발자가 `main()`과 `while` 루프를 작성 |
| 언어와 실행 | p5.js는 JavaScript, Processing Java 모드는 Java | C로 작성하고 프로젝트를 컴파일 |
| 그리기 문맥 | 캔버스와 스케치 실행 도구가 작업 흐름에 포함 | 창을 초기화하고 `BeginDrawing()`과 `EndDrawing()`을 호출 |
| 입력과 시간 | 프레임워크의 이벤트·시간 API를 사용 | 루프에서 입력 상태와 `GetFrameTime()` 등을 직접 확인 |
| 표현 API | 채우기·외곽선 등 현재 스타일 상태를 설정하는 패턴이 흔함 | 기본 도형 호출에 색과 좌표를 인자로 명시 |
| 실행과 공유 | 브라우저 또는 Processing 실행 환경을 통해 빠르게 확인 | 컴파일 설정과 실행 파일·자원 배포를 고려 |

표는 대표적인 사용 흐름을 비교한 것이다. Processing에는 여러 모드와 라이브러리가 있고, p5.js도 브라우저 편집기만으로 제한되지 않는다. raylib 역시 창과 그래픽 문맥, 입력, 도형, 카메라 같은 작업을 대신 처리하므로 저수준 그래픽 API를 직접 다루는 것과 같지는 않다. 다만 스케치 프레임워크보다 프로그램의 생명주기와 자료 흐름을 C 코드에서 더 직접적으로 구성한다.

## 공통 수학과 환경별 표현

원 둘레의 점, 격자, 파동, 벡터 필드 같은 수학적 규칙은 라이브러리에 속하지 않는다. 예를 들어 반지름 `r`과 각도 `theta`에서 점의 수학적 위치는 `x = r * cos(theta)`, `y = r * sin(theta)`로 계산할 수 있다. 이 계산을 p5.js의 `circle()`에 전달하든 raylib의 `DrawCircleV()`에 전달하든 관계식은 같다. 달라지는 부분은 다음과 같다.

- 함수 이름과 인자 형태: 원의 지름인지 반지름인지, 좌표가 정수인지 실수인지 확인한다.
- 자료형과 문법: JavaScript의 숫자와 객체 표현을 C의 `float`, `Vector2`, 구조체에 맞게 옮긴다.
- 좌표계와 시간: y축 방향, 화면 크기, 프레임 간격과 시간 단위를 확인한다.
- 자원과 실행: 이미지 로드·해제, 창 종료, 빌드와 배포 과정을 해당 환경에 맞춘다.

계산 규칙과 렌더링 호출을 나누면 이런 변환이 수월해진다. 예를 들어 `pointOnCircle(angle, radius)` 같은 함수가 위치를 계산하고, 별도 렌더링 코드가 그 위치에 점을 그리게 할 수 있다. 수학 부분은 그대로 유지하면서 화면에 연결하는 부분만 각 API에 맞춰 바꾸는 것이다. 코드가 커질수록 데이터 모델, 시간 갱신, 입력 처리, 드로잉을 각각의 역할로 나누는 것도 도움이 된다.

## 프레임과 상태를 이해하는 깊이

스케치 환경은 빠른 시각 실험을 위해 반복 구조와 일부 상태 관리를 감싼다. 예를 들어 개발자는 `draw()` 안에 프레임별 코드를 적고, 프레임워크가 그 함수를 반복 호출하도록 할 수 있다. raylib에서는 같은 반복을 직접 작성해 `GetFrameTime()`을 상태 갱신에 전달하고, 그리기 구간을 명시한다. 이 명시성은 코드가 길어지는 대신 프레임마다 어떤 값이 변하고 어떤 명령이 화면에 쓰이는지 추적하기 쉽다.

반대로 빠르게 결과를 관찰하고 브라우저에서 공유하는 것이 중요하면 스케치 환경의 준비된 실행 흐름이 유리할 수 있다. C 프로그램으로 창·입력·카메라를 다루거나, 기존 C 코드와 결합하고, 빌드와 자료 구조를 직접 통제하고 싶다면 raylib이 자연스럽다. 이를 성능의 단순한 우열로 해석해서는 안 된다. 실제 성능은 알고리즘, 렌더링 방식, 호출 수, 자원 사용과 실행 환경에 따라 달라진다.

## 환경을 옮길 때의 점검 순서

한 환경에서 만든 작품을 다른 환경으로 옮길 때는 전체 코드를 한 번에 번역하기보다, 다음 순서로 의미를 확인한다.

1. **수학 모델**: 어떤 입력과 파라미터로 위치·크기·색을 계산하는가?
2. **단위와 좌표**: 화면 원점, 축 방향, 각도 단위, 픽셀과 월드 단위가 맞는가?
3. **상태와 시간**: 정지 이미지인지 애니메이션인지, 시간 간격에 따라 변화량을 계산하는가?
4. **드로잉 API**: 도형의 기준점, 반지름·지름, 색·알파 인자가 일치하는가?
5. **실행 자원**: 창과 이미지의 생성·해제, 입력, 빌드·배포 방식이 준비되어 있는가?

이 순서는 이번 장에서 raylib으로 살펴본 작업 흐름과도 같다. 좌표를 계산하고 도형을 그리는 작은 프로그램에서 시작해, 시간과 입력을 추가하고, 필요에 따라 텍스처와 카메라를 더한다. 한 번에 하나씩 연결하면 오류가 수학 모델에서 비롯된 것인지 API 사용에서 비롯된 것인지 구분하기 쉽다.

## 이 장을 마치며

raylib은 C로 그래픽 프로그램의 프레임 반복과 상태를 직접 구성할 수 있는 도구다. p5.js와 Processing은 스케치 방식으로 아이디어를 빠르게 실험하고 시각화하는 흐름을 제공한다. 어느 쪽을 선택해도 수학적 패턴의 핵심은 좌표, 함수, 반복, 상태라는 공통 개념에 있다. 환경을 바꾸어도 그 개념을 보존하고, 각 라이브러리의 실행 구조와 드로잉 API에 맞게 표현을 다시 연결하면 같은 생성 규칙을 여러 형태의 작품으로 발전시킬 수 있다.

## 이 절의 핵심

raylib과 크리에이티브 코딩 프레임워크의 가장 큰 차이는 수학이 아니라 프로그램의 생명주기와 작업 흐름에 있다. 스케치 환경은 반복과 실행 편의를 제공하고, raylib은 창·프레임·입력·그리기를 C 코드에서 더 직접적으로 제어하게 한다. 수학 모델과 렌더링 API를 분리해 생각하면 도구마다 다른 문법을 익히면서도 생성 규칙의 의미를 유지할 수 있다.
