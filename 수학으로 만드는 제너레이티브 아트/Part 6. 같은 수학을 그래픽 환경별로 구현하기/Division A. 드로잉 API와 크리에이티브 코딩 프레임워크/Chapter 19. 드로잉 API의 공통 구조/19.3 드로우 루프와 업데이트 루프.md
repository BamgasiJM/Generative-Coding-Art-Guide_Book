# 19.3 드로우 루프와 업데이트 루프

드로잉 API를 처음 사용할 때는 `draw()`나 `render()` 함수 안에 모든 코드를 넣어도 화면이 움직인다. 그러나 시간이 흐르는 작업이 복잡해질수록 "무엇을 계산하는가"와 "무엇을 그리는가"를 구분해야 한다. 업데이트 루프(update loop)는 상태를 다음 시점으로 바꾸고, 드로우 루프(draw loop)는 현재 상태를 렌더링 표면에 표현한다.

```text
input = readInput()
update(state, input, deltaTime)
draw(state)
presentFrame()
```

이 순서는 환경마다 하나의 콜백에 숨어 있을 수도 있고, 명시적으로 여러 함수로 나뉘어 있을 수도 있다. p5.js와 Processing의 `draw()`는 보통 업데이트와 렌더링을 함께 수행한다. openFrameworks는 `update()`와 `draw()`를 구분하며, raylib은 `while (!WindowShouldClose())` 안에서 두 단계를 직접 작성하는 방식에 가깝다.

## 정적인 드로잉과 반복 렌더링

정적인 패턴은 한 번만 계산해도 된다. 예를 들어 고정된 시드로 격자 도형을 배치하고 이미지를 파일로 저장하는 작업은 창이 열린 뒤 매 프레임 같은 도형을 다시 그릴 이유가 없다.

```text
setup():
    createCanvas()
    drawStaticPattern()
    saveImage()
```

하지만 많은 크리에이티브 코딩 환경은 기본적으로 매 프레임 화면을 다시 그린다. 정적 장면을 매 프레임 반복 렌더링해도 결과는 같지만 불필요한 비용이 생긴다. p5.js에서는 `noLoop()`로 `draw()` 반복을 멈출 수 있고, 다른 환경에서는 상태가 바뀔 때만 다시 그리거나, 정적 배경을 오프스크린 표면에 한 번 그려 재사용할 수 있다.

```javascript
// p5.js 예제
function setup() {
  createCanvas(800, 800);
  noLoop();
}

function draw() {
  background(250);
  drawPattern();
}
```

정적인 작업에서도 반복 루프가 쓸모없는 것은 아니다. 시드를 바꿔 여러 후보를 자동으로 만들거나, 해상도를 단계적으로 높이며 결과를 비교하거나, 입력 이벤트가 있을 때만 다시 렌더링하는 방식에 사용할 수 있다. 핵심은 화면이 변하지 않는데도 반복하고 있는지 의식하는 것이다.

## 업데이트는 상태를 바꾼다

업데이트는 이전 상태와 현재 입력을 받아 다음 상태를 계산한다. 위치, 속도, 회전, 나이, 색상, 입자 목록, 카메라, 오프스크린 버퍼의 내용이 상태가 될 수 있다.

$$
\mathbf{s}_{t+\Delta t}=U(\mathbf{s}_t,\mathbf{i}_t,\Delta t)
$$

```text
function updateParticle(particle, deltaTime):
    particle.velocity += particle.acceleration * deltaTime
    particle.position += particle.velocity * deltaTime
    particle.age += deltaTime
```

업데이트 단계는 보통 도형을 그리지 않는다. 상태를 바꾸는 일과 화면에 남기는 일을 섞으면, 같은 상태를 다른 스타일로 표현하거나 렌더링을 건너뛰는 일이 어려워진다. 예를 들어 입자의 위치는 한 번만 갱신하고, 현재 위치를 점·선·글리프·텍스처 인스턴스로 각각 그려 비교할 수 있다.

반대로 렌더링은 상태를 변경하지 않는 편이 좋다. 같은 상태를 두 번 그렸을 때 두 번째 그림이 달라진다면, 드로우 함수 안에서 난수를 새로 뽑거나 위치를 갱신하고 있을 가능성이 있다. 이런 구조는 디버깅과 이미지 내보내기에서 예기치 않은 차이를 만든다.

```text
function drawParticle(particle):
    setFill(colorFromAge(particle.age))
    drawCircle(particle.position, sizeFromAge(particle.age))
```

## 프레임 간격과 시간 단위

프레임 루프는 매초 정확히 같은 횟수로 실행되지 않는다. 렌더링 부하, 창의 상태, 운영체제의 작업에 따라 두 프레임 사이의 시간은 달라진다. 따라서 이동량과 변화량에는 프레임 수가 아니라 실제 경과 시간 `deltaTime`을 곱한다.

$$
\mathbf{p}\leftarrow\mathbf{p}+\mathbf{v}\Delta t
$$

```text
angle += angularSpeed * deltaTime
opacity -= fadePerSecond * deltaTime
```

이 규약에서 속도는 픽셀/초, 각속도는 라디안/초, 감쇠율은 초당 변화량이 된다. 반대로 매 프레임 `position.x += 2`처럼 쓰면 120fps 화면에서는 60fps 화면보다 두 배 빠르게 움직인다. 라이브러리가 주는 시간값의 단위가 밀리초인지 초인지도 확인해야 한다.

프레임이 너무 오래 걸려 `deltaTime`이 비정상적으로 커지는 상황도 있다. 창이 백그라운드에 있다가 다시 활성화되거나, 디버거가 멈춘 뒤 재개될 때가 대표적이다. 큰 시간 간격 하나가 입자를 화면 멀리 보내지 않도록 상한을 둘 수 있다.

```text
deltaTime = min(measuredDeltaTime, maximumDeltaTime)
```

물리적 상호작용이나 반응-확산처럼 계산 안정성이 중요한 시스템은 실제 프레임과 별개로 일정한 시간 단계로 여러 번 업데이트할 수 있다. 이른바 고정 시간 단계 방식이다. 렌더링은 화면 상황에 맞춰 수행하되, 시뮬레이션은 항상 예를 들어 $1/60$초 단위로 진행한다.

```text
accumulator += measuredDeltaTime
while accumulator >= fixedStep:
    update(state, fixedStep)
    accumulator -= fixedStep
draw(state)
```

## 그리기 순서와 레이어

2D 드로잉 API에서는 대체로 나중에 그린 내용이 먼저 그린 내용을 덮는다. 따라서 드로우 루프의 순서는 장면의 레이어 순서이기도 하다. 배경, 멀리 있는 요소, 큰 형태, 세부, UI처럼 의미 있는 순서로 코드를 구성하면 장면을 읽고 수정하기 쉽다.

```text
clearBackground()
drawBackgroundField()
drawParticles()
drawForegroundMarks()
drawInterface()
```

투명도와 블렌딩을 사용하면 단순한 앞뒤 관계보다 복잡한 합성이 생긴다. 특히 누적 드로잉에서는 먼저 배경을 얼마나 지울지, 새 선을 어느 버퍼에 그릴지, 최종 합성은 어디서 할지를 분리해서 생각한다. 화면 전체를 매 프레임 지우는 기본 캔버스와, 과거 흔적을 보존하는 오프스크린 버퍼를 함께 쓰는 방식이 대표적이다.

## 입력 처리와 업데이트 순서

마우스와 키보드 입력도 프레임 루프의 일부다. 입력을 읽은 뒤 상태를 갱신하면 사용자가 방금 움직인 포인터가 같은 프레임에 반영된다. 반대로 이전 상태를 먼저 그린 다음 입력을 처리하면 화면 반응이 한 프레임 늦어진다.

```text
input = pollInput()
target = input.pointerPosition
state.position = moveToward(state.position, target, deltaTime)
draw(state)
```

이벤트 기반 API에서는 키를 누르는 순간에 상태를 한 번 변경하는 콜백과, 매 프레임 지속적으로 상태를 갱신하는 루프를 구분한다. 예를 들어 스페이스바를 누를 때 입자 방출 여부를 전환하고, 방출이 켜진 동안에는 업데이트에서 일정한 생성률로 입자를 추가할 수 있다.

## 루프를 설계하는 습관

작업이 커질수록 프레임 루프에 다음과 같은 경계를 두는 편이 좋다.

| 단계 | 책임 | 피해야 할 일 |
| --- | --- | --- |
| 입력 | 장치 값을 읽고 정규화 | 도형을 직접 그리며 상태를 뒤섞기 |
| 업데이트 | 다음 상태 계산 | 프레임마다 새 렌더링 상태를 무작정 누적하기 |
| 렌더링 | 현재 상태를 시각화 | 위치·나이 같은 모델 상태 변경 |
| 표시·내보내기 | 완성 버퍼를 화면·파일로 전달 | 시뮬레이션 규칙 변경 |

이 구분은 엄격한 규칙이라기보다, 변화의 원인을 찾기 위한 구조다. 작은 스케치에서는 하나의 `draw()` 함수로 시작해도 좋다. 다만 상태가 늘어나거나 프레임 버퍼를 여러 개 쓰기 시작하면, 업데이트와 드로우를 분리하는 순간 코드의 의도가 훨씬 잘 보인다.

## 이 절의 핵심

드로우 루프는 현재 상태를 화면에 표현하고, 업데이트 루프는 시간·입력·이전 상태를 바탕으로 다음 상태를 만든다. `deltaTime`을 사용해 프레임률과 독립적인 움직임을 만들고, 입력·업데이트·렌더링·버퍼 합성의 순서를 분명히 하면 정적 패턴부터 상태 기반 시뮬레이션까지 안정적으로 구성할 수 있다.
