# 19.8 픽셀 접근과 오프스크린 렌더링

드로잉 API의 기본 단위는 원, 선, 경로 같은 도형이다. 그러나 때로는 화면을 이루는 각 픽셀의 색을 직접 계산해야 한다. 노이즈 필드, 거리 함수, 이미지 분석, 셀룰러 오토마타, 데이터 기반 마스크처럼 "이 위치의 값은 무엇인가"가 핵심인 작업이 그렇다. 픽셀 접근은 렌더링 표면을 도형을 그리는 대상인 동시에 숫자 배열로 다루는 방법이다.

## 픽셀은 색상 값의 격자다

가로 $W$, 세로 $H$인 이미지 표면은 $W\times H$개의 위치를 가진다. 각 위치에는 보통 빨강, 초록, 파랑, 알파 채널이 저장된다. 픽셀 단위 작업은 이 위치를 순회하며 색 값을 읽거나 바꾼다.

```text
for y from 0 to height - 1:
    for x from 0 to width - 1:
        color = colorAt(x, y)
        setColorAt(x, y, transform(color))
```

이 반복은 Chapter 19.5의 격자 반복과 닮았지만, 셀 하나가 곧 출력 이미지의 최소 단위라는 점이 다르다. 픽셀 배열의 인덱스는 대개 행 우선 순서로 계산한다.

$$
i=x+yW
$$

RGBA 채널을 별도 배열 값으로 저장하는 환경에서는 픽셀 하나에 네 개의 연속된 값이 필요하다.

$$
i_{RGBA}=4(x+yW)
$$

실제 배열 인덱스를 직접 계산하는 대신 환경이 제공하는 `getPixel`, `setPixel`, `loadPixels` 같은 함수를 쓸 수 있다. 다만 함수 호출이 픽셀마다 추가 비용을 만들 수 있으므로, 대량 처리에서는 배열을 한 번 가져와 순회한 뒤 한 번에 반영하는 방식이 흔하다.

```text
loadPixels()
for each pixel index i:
    pixels[i] = calculatedColor(i)
updatePixels()
```

## 픽셀 좌표를 함수의 입력으로 바꾸기

픽셀 인덱스는 이산 정수지만, 제너레이티브 규칙은 보통 연속 좌표를 입력으로 받는다. 픽셀 중심 $(x+0.5,y+0.5)$을 화면 크기로 나누면 $[0,1]$ 범위의 UV 좌표를 얻는다.

$$
u=\frac{x+0.5}{W},\qquad v=\frac{y+0.5}{H}
$$

화면 중심 기준의 거리나 회전을 계산하려면 정규화한 좌표를 중심에서 빼고, 가로세로 비율을 보정한다.

$$
\mathbf{p}=\left(u-\frac{1}{2},v-\frac{1}{2}\right),\qquad
p_x\leftarrow p_x\frac{W}{H}
$$

```text
u = (x + 0.5) / width
v = (y + 0.5) / height
p = (u - 0.5, v - 0.5)
p.x *= width / height
```

이 좌표를 거리 함수에 넣으면 원과 윤곽을, 노이즈 함수에 넣으면 질감을, 파동 함수에 넣으면 간섭 무늬를 만들 수 있다. 드로잉 API에서 원을 수백 번 호출하는 방식과 달리, 픽셀 방식은 화면의 모든 위치에서 같은 규칙을 평가한다.

```text
d = length(p) - radius
mask = 1 - smoothstep(-edge, edge, d)
color = interpolate(background, foreground, mask)
setPixel(x, y, color)
```

`smoothstep`은 두 경계 사이를 부드럽게 보간하는 함수의 의사코드다. 해당 함수를 제공하지 않는 환경에서도 클램프한 보간 곡선을 구현할 수 있다. 중요한 점은 거리 $d$를 바로 색으로 바꾸지 않고, 마스크와 색상 보간이라는 중간 단계를 두면 가장자리 두께와 팔레트를 독립적으로 조절할 수 있다는 것이다.

## 픽셀 밀도와 배열 크기

고밀도 디스플레이에서는 논리적 캔버스 크기보다 실제 픽셀 배열이 클 수 있다. 논리적 $(x,y)$ 하나가 실제 픽셀 여러 개와 대응하므로, `width * height`만큼만 순회하면 일부 픽셀을 건너뛸 수 있다. 픽셀 접근 API를 사용할 때는 현재 표면의 픽셀 밀도와 배열 길이를 확인한다.

```text
physicalWidth = logicalWidth * pixelDensity
physicalHeight = logicalHeight * pixelDensity
```

정확한 픽셀 제어가 필요하지 않은 작업에서는 픽셀 밀도를 1로 고정하면 인덱싱이 단순해진다. 반대로 고밀도 화면의 선명함이 중요하다면 실제 크기를 기준으로 계산하거나, API가 제공하는 고수준 접근 함수를 사용한다. 이 선택은 이미지 품질과 계산량을 함께 바꾼다.

## 직접 픽셀 처리의 비용

1,920 x 1,080 표면은 약 207만 픽셀이다. 매 프레임 각 픽셀에서 여러 번의 노이즈, 삼각함수, 이미지 표본화를 수행하면 CPU에는 상당한 부담이 된다. 픽셀 처리 비용은 대략 다음 요소에 비례한다.

$$
\text{cost}\propto W\times H\times\text{operations per pixel}
$$

따라서 정적인 필드는 한 번 계산해 이미지로 캐시하고, 매 프레임 바뀌는 부분만 갱신하는 전략이 유용하다. 낮은 해상도의 오프스크린 표면에서 효과를 계산한 뒤 확대하거나, 일정한 프레임 간격으로만 다시 계산하는 방법도 있다.

```text
if frameIndex mod updateInterval == 0:
    updateNoiseTexture()
drawImage(noiseTexture, fullCanvas)
```

화면 전체의 독립적인 픽셀 계산이 지속적으로 필요하다면, CPU 픽셀 배열보다 프래그먼트 셰이더가 더 적합할 수 있다. GPU는 많은 픽셀에서 같은 식을 병렬로 평가하도록 설계되어 있다. 그렇다고 모든 픽셀 작업을 즉시 셰이더로 옮길 필요는 없다. 낮은 해상도 이미지, 오프라인 생성, 이미지 분석처럼 CPU 접근이 더 단순하고 충분히 빠른 작업도 많다.

## 오프스크린 렌더링 표면

오프스크린 렌더링은 화면에 즉시 표시하지 않는 별도의 표면에 도형이나 픽셀을 그리는 방식이다. 환경에 따라 그래픽 버퍼, 캔버스, 프레임 버퍼 객체(FBO), 렌더 텍스처 등 다른 이름을 사용한다. 기본 원리는 같다. 렌더링 대상을 잠시 바꾸고, 그 결과를 나중에 이미지처럼 사용한다.

```text
beginRender(offscreen)
clear(offscreen)
drawPattern()
endRender(offscreen)

drawImage(offscreen, mainCanvas)
```

오프스크린 표면은 여러 목적에 사용된다.

| 목적 | 방식 | 예 |
| --- | --- | --- |
| 캐싱 | 한 번 그린 결과를 재사용 | 복잡한 정적 배경, 텍스트 레이어 |
| 마스킹 | 한 표면의 알파·밝기로 다른 표면을 제한 | 원 안에만 보이는 노이즈 |
| 후처리 | 표면 이미지를 변형해 다시 그리기 | 블러, 색 보정, 픽셀화 |
| 합성 | 여러 표면을 순서와 모드에 따라 겹치기 | 배경·입자·UI 레이어 |
| 피드백 | 이전 프레임을 다음 프레임의 입력으로 사용 | 잔상, 확산, 화면 왜곡 |
| 고해상도 출력 | 화면보다 큰 표면에 렌더링 | 인쇄용 이미지 저장 |

도형을 오프스크린 표면에 그린 뒤 최종 표면으로 복사하는 것만으로도 레이어를 독립적으로 관리할 수 있다. 예를 들어 가산 합성이 필요한 입자만 별도 표면에 그리고, 본문과 UI는 일반 알파 합성으로 유지하면 블렌딩 상태가 서로 섞이지 않는다.

```text
drawBackground(main)
drawParticles(particleLayer, additiveBlend)
composite(main, particleLayer, normalBlend)
drawLabels(main)
```

## 마스크와 합성의 예

두 개의 오프스크린 표면을 생각해 보자. 하나에는 노이즈 패턴을, 다른 하나에는 원과 문자로 만든 마스크를 그린다. 최종 합성에서는 마스크의 알파가 큰 곳에서만 노이즈를 보이게 한다.

$$
\mathbf{C}_{out}=\alpha_{mask}\mathbf{C}_{pattern}+(1-\alpha_{mask})\mathbf{C}_{background}
$$

```text
patternLayer = renderNoiseField()
maskLayer = renderCircleMask()
result = compositeWithMask(patternLayer, maskLayer, background)
```

이 방식은 패턴의 생성 규칙과 드러나는 영역의 규칙을 분리한다. 노이즈 함수나 색상 팔레트를 바꾸어도 마스크의 기하는 유지되고, 반대로 마스크를 바꾸어도 패턴 함수는 그대로 쓸 수 있다. 복잡한 화면을 한 캔버스에서 순서로만 해결하는 것보다 구조가 명확해진다.

## 피드백 버퍼와 읽기·쓰기 분리

이전 프레임을 읽어 다음 프레임을 만들면 오프스크린 표면은 상태 저장소가 된다. 예를 들어 이전 이미지를 조금 이동하고 흐리게 한 뒤 새 선을 더하면, 움직임의 잔상이나 액체 같은 왜곡을 만들 수 있다.

```text
nextBuffer = fade(warp(previousBuffer))
drawNewInput(nextBuffer)
swap(previousBuffer, nextBuffer)
```

같은 표면을 동시에 읽고 쓰면 처리 순서에 따라 결과가 달라질 수 있다. 따라서 피드백에는 보통 두 개의 버퍼를 번갈아 쓰는 ping-pong 구조가 필요하다. 한 버퍼는 이전 상태를 읽는 용도, 다른 버퍼는 새 결과를 쓰는 용도다. 프레임이 끝나면 두 역할을 교환한다.

```text
readBuffer  -> sample as input
writeBuffer -> render next state
swap(readBuffer, writeBuffer)
```

GPU FBO 환경에서는 이 구조가 특히 중요하지만, CPU 이미지 배열에서도 이전 배열과 다음 배열을 분리하는 원리는 같다. 셀룰러 오토마타, 반응-확산, 블러, 컨볼루션처럼 이웃이나 이전값을 읽는 계산은 한 배열에서 즉시 덮어쓰지 않도록 주의한다.

## 해상도와 스케일의 선택

오프스크린 표면은 반드시 최종 캔버스와 같은 크기일 필요가 없다. 작은 표면에서 블러나 노이즈를 계산하면 비용이 줄고, 확대할 때 부드러운 보간 또는 거친 픽셀화라는 다른 표현을 얻을 수 있다.

```text
lowRes = createSurface(width / 4, height / 4)
renderField(lowRes)
drawImageScaled(lowRes, mainCanvas, smoothing=true)
```

반대로 큰 표면은 고해상도 인쇄와 세밀한 선을 위한 출력을 만든다. 다만 표면의 면적이 두 배가 되면 픽셀 수는 네 배가 된다. 여러 패스를 가진 작업에서는 모든 레이어를 최고 해상도로 만들기보다, 실제로 선명해야 하는 레이어만 높은 해상도를 쓰는 편이 효율적이다.

## 이 절의 핵심

픽셀 접근은 렌더링 표면을 색상 값의 격자로 다루며, 좌표를 정규화해 거리·노이즈·파동 같은 함수를 각 픽셀의 색으로 바꾼다. 오프스크린 표면은 캐싱, 마스킹, 후처리, 레이어 합성, 피드백, 고해상도 출력에 사용된다. 이전 결과를 읽어 새 결과를 만들 때는 읽기와 쓰기 버퍼를 분리하고, 해상도·픽셀 밀도·계산 비용을 함께 관리해야 한다.
