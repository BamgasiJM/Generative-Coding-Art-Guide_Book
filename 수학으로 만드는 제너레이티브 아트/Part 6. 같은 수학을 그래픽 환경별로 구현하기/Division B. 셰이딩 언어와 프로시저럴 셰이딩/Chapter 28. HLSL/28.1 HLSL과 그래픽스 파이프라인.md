# 28.1 HLSL과 그래픽스 파이프라인

HLSL(High-Level Shading Language)은 GPU에서 실행할 그래픽·컴퓨트 셰이더를 작성하는 언어다. C 계열 문법과 벡터·행렬 자료형을 제공하지만, C++처럼 운영체제에서 독립적으로 실행되는 프로그램을 만드는 언어는 아니다. 그래픽 애플리케이션이 어떤 셰이더 단계를 실행할지 정하고, HLSL 코드는 그 단계에서 정점이나 픽셀, 데이터 항목을 어떻게 계산할지 표현한다.

HLSL은 Direct3D와 밀접하게 연결되어 발전했지만, HLSL과 Direct3D는 같은 것이 아니다. HLSL은 셰이더의 계산을 기술하고, Direct3D는 GPU 자원과 파이프라인 상태, 명령 제출을 관리하는 API다. 셰이더는 컴파일된 뒤 애플리케이션이 만든 파이프라인에 들어가며, 버퍼·텍스처·상수값을 연결하고 실제 드로우나 디스패치 명령을 내리는 일은 호스트 프로그램의 몫이다.

## 언어, 컴파일러, API

HLSL을 사용한 렌더링에서는 서로 다른 세 요소가 협력한다.

| 요소 | 역할 |
| --- | --- |
| HLSL | GPU 단계에서 수행할 계산과 단계 간 데이터 인터페이스를 작성한다. |
| 셰이더 컴파일러 | HLSL과 선택한 대상 프로필을 검사하고, 실행 환경이 사용하는 중간 표현이나 셰이더 바이트코드로 변환한다. |
| 그래픽 API와 드라이버 | 셰이더를 파이프라인에 연결하고 GPU 자원을 바인딩해 명령을 실행한다. |

현대적인 Direct3D 12 개발에서는 Microsoft의 DirectX Shader Compiler(DXC)가 대표적인 HLSL 컴파일러다. Shader Model 6 계열 대상의 HLSL을 컴파일하면 DirectX Intermediate Language(DXIL) 형태의 결과를 얻는다. 애플리케이션은 이 셰이더 결과를 파이프라인 상태와 결합하고, GPU 버퍼와 텍스처를 연결한 뒤 렌더 명령을 제출한다. 드라이버는 대상 GPU에서 실행할 수 있도록 파이프라인을 준비한다.

이것은 HLSL 소스가 GPU에서 곧바로 한 줄씩 실행된다는 뜻이 아니다. 소스는 컴파일과 검증을 거쳐 API가 받아들이는 형태가 되고, 이후 실제 장치의 명령으로 준비된다. 셰이더가 컴파일되어도 입력 버퍼의 형식이나 리소스 바인딩이 맞지 않으면 올바른 결과를 얻지 못한다. 셰이더 코드는 렌더링 프로그램의 일부이지, 창 생성부터 화면 출력까지 모두 해결하는 완성된 애플리케이션은 아니다.

간단한 픽셀 셰이더는 다음처럼 색 하나를 반환할 수 있다.

```c
float4 PSMain() : SV_Target0
{
    return float4(0.05, 0.62, 0.60, 1.0);
}
```

`float4`는 네 개의 실수 성분을 가진 벡터이고, `SV_Target0`은 반환값을 첫 번째 색상 출력으로 사용하라는 시스템 의미(semantic)다. 이 함수 하나만으로 화면에 무언가가 나타나는 것은 아니다. 애플리케이션은 이를 픽셀 단계의 진입점으로 지정하고, 렌더링할 기하와 나머지 파이프라인을 준비해야 한다. 진입점과 시스템 의미의 상세한 규칙은 28.2와 28.3에서 살펴본다.

## Direct3D 12와 이전 컴파일 흐름

HLSL의 역사적 사용 환경은 Direct3D다. 특히 Direct3D 12에서는 애플리케이션이 셰이더와 고정 기능 상태를 명시적으로 모아 파이프라인 상태 객체(Pipeline State Object, PSO)를 만들고, 커맨드 리스트에서 GPU 작업을 제출한다. 셰이더 프로그램을 바인딩하고 호출하는 과정은 그래픽 API의 책임이며, HLSL은 그 파이프라인 안에서 실행될 사용자 프로그램을 제공한다.

오래된 Direct3D 프로젝트에서는 FXC와 DXBC를 중심으로 한 컴파일 결과와 Shader Model 5 계열의 대상 프로필을 볼 수 있다. 새로운 D3D12 작업은 대체로 DXC와 DXIL을 중심으로 구성된다. 기존 프로젝트의 셰이더를 읽거나 수정할 때는 `.hlsl` 확장자만 보고 컴파일 체인을 단정하지 말고, 빌드 설정과 대상 프로필, 실제 컴파일러를 함께 확인해야 한다. HLSL 언어 기능과 Shader Model의 버전 관계, 프로필 이름은 다음 절에서 다룬다.

HLSL은 Direct3D 전용 소스 형식에만 머물지도 않는다. DXC는 HLSL에서 SPIR-V를 생성하는 경로도 제공하므로 Vulkan을 대상으로 한 개발에서도 HLSL을 작성 언어로 선택할 수 있다. 이때 Vulkan은 SPIR-V 모듈과 Vulkan의 리소스·파이프라인 규칙을 사용한다. 즉 “HLSL로 작성했다”는 사실만으로 실행 API가 Direct3D라고 결론 내릴 수 없으며, 컴파일 대상과 호스트 API를 함께 보아야 한다.

## 그래픽 엔진에서 만나는 HLSL

게임 엔진은 HLSL을 애플리케이션 렌더링 시스템의 일부로 제공한다. Unity에서는 ShaderLab이 셰이더의 패스와 머티리얼 속성을 감싸고, 실제 정점·프래그먼트 계산을 HLSL로 작성하는 경우가 많다. 렌더 파이프라인과 플랫폼에 맞춘 셰이더 변형·컴파일은 엔진이 관리하므로, 개발자가 Direct3D의 PSO를 모두 직접 구성하지 않아도 된다.

Unreal Engine에서는 머티리얼 그래프가 엔진의 셰이더 코드를 생성하며, 필요한 경우 사용자 정의 HLSL 조각을 머티리얼에 넣을 수 있다. 그래프의 출력은 조명·재질 시스템과 결합되고, 엔진의 셰이더 컴파일 파이프라인이 대상 플랫폼에 맞는 결과를 만든다. 그래프를 사용하든 HLSL을 직접 쓰든 최종 GPU 연산이 존재하지만, 엔진이 제공하는 입력과 출력, 매크로, 머티리얼 계약은 독립적인 Direct3D 프로그램과 다르다.

이 차이는 GLSL과 비교할 때도 중요하다. GLSL 예제의 `main()`을 HLSL로 단순히 이름만 바꾸는 것으로는 옮길 수 없다. 벡터 자료형의 표기, 단계별 진입점, 시스템 의미, 리소스 바인딩, 행렬 규약, 컴파일러 옵션이 달라진다. 더구나 엔진의 셰이더 코드에는 엔진이 추가하는 헤더와 매크로, 자동 생성된 선언이 포함될 수 있다. 재사용하려는 것이 수학적 알고리즘인지, 특정 API와 엔진의 셰이더 인터페이스인지 먼저 구분해야 한다.

## HLSL을 읽는 관점

HLSL 코드를 접했을 때는 다음 질문부터 확인하면 전체 구조를 빠르게 파악할 수 있다.

1. 어떤 셰이더 진입점과 대상 프로필로 컴파일되는가?
2. `float2`, `float3`, `float4` 같은 값은 어디에서 입력되고 어느 단계로 전달되는가?
3. 텍스처, 샘플러, 상수 버퍼는 어떤 레지스터 또는 엔진 바인딩에 연결되는가?
4. 결과는 색상 출력, 위치, 깊이, 또는 다른 GPU 자원 중 어디에 기록되는가?
5. 이 코드는 순수한 HLSL인가, 아니면 엔진이 정의한 매크로와 인터페이스를 전제로 하는가?

이 질문들은 언어 문법뿐 아니라 실행 계약을 함께 보게 한다. HLSL은 수식과 데이터 흐름을 표현하지만, 수식의 입력이 어디서 오고 결과가 렌더링의 어느 단계에 쓰이는지는 셰이더 프로필과 호스트 파이프라인을 통해 결정된다.

## 이 절의 핵심

HLSL은 GPU 셰이더를 작성하는 언어이고 Direct3D는 이를 파이프라인에서 실행시키는 API다. 현대 D3D12에서는 DXC와 DXIL이 대표적인 컴파일 흐름이며, HLSL은 Vulkan용 SPIR-V를 만드는 작성 언어로도 활용될 수 있다. Unity와 Unreal 같은 엔진은 컴파일·자원 연결·렌더링 상태의 상당 부분을 관리하지만, 자체적인 셰이더 인터페이스를 추가한다. 따라서 HLSL을 이해할 때는 문법뿐 아니라 컴파일 대상, 진입점, 리소스 연결, 실행 호스트를 함께 확인해야 한다.
