# 28.9 Unity, Unreal Engine, DirectX 환경으로의 확장

HLSL은 GPU 계산을 표현하는 언어지만, 실제 프로젝트에서는 엔진이나 그래픽 API가 정한 셰이더 입력 계약 안에서 사용된다. 28.1에서 HLSL·컴파일러·실행 API의 관계를 살펴보았다. 여기서는 Unity, Unreal Engine, Direct3D 애플리케이션에서 HLSL이 어떤 형태로 삽입되고, 각 환경이 어떤 작업을 대신하거나 개발자에게 맡기는지 비교한다.

| 환경 | 셰이더를 작성하는 위치 | 호스트가 주로 맡는 일 |
| --- | --- | --- |
| Unity | ShaderLab 패스의 HLSL 프로그램, 또는 Shader Graph의 노드·사용자 함수 | 렌더 파이프라인별 패스 구성, 셰이더 변형 컴파일, 머티리얼과 엔진 데이터 연결 |
| Unreal Engine | 머티리얼 그래프의 Custom 노드, 또는 `.usf` 전역 셰이더 | 머티리얼 코드 생성·플랫폼 컴파일, 혹은 엔진 렌더 그래프와 셰이더 자원 관리 |
| Direct3D | 애플리케이션이 지정한 HLSL 진입점과 프로파일 | 셰이더 컴파일, 파이프라인·리소스 구성, 명령 제출과 동기화 |

이 차이를 이해하면 엔진에서 작성한 HLSL을 독립적인 Direct3D 프로그램처럼 취급하거나, 반대로 그래픽 API가 엔진의 머티리얼 기능을 자동으로 제공한다고 오해하는 일을 피할 수 있다.

## Unity: ShaderLab 패스 안의 HLSL

Unity의 셰이더 파일은 HLSL만으로 이루어지지 않는다. ShaderLab이 셰이더 이름, 머티리얼 속성, 서브셰이더와 패스를 선언하고, 각 패스의 `HLSLPROGRAM` 블록 안에 실제 HLSL 진입점을 둔다. 다음은 Unity 6의 URP를 대상으로 오브젝트를 단색으로 그리는 작은 셰이더다.

```c
Shader "Book/URPUnlitTint"
{
    Properties
    {
        _Tint ("Tint", Color) = (0.2, 0.8, 0.7, 1.0)
    }

    SubShader
    {
        Tags { "RenderPipeline" = "UniversalPipeline" "RenderType" = "Opaque" }

        Pass
        {
            HLSLPROGRAM
            #pragma vertex Vert
            #pragma fragment Frag
            #include "Packages/com.unity.render-pipelines.universal/ShaderLibrary/Core.hlsl"

            CBUFFER_START(UnityPerMaterial)
                float4 _Tint;
            CBUFFER_END

            struct Attributes
            {
                float3 positionOS : POSITION;
            };

            struct Varyings
            {
                float4 positionHCS : SV_Position;
            };

            Varyings Vert(Attributes input)
            {
                Varyings output;
                output.positionHCS = TransformObjectToHClip(input.positionOS);
                return output;
            }

            half4 Frag(Varyings input) : SV_Target
            {
                return half4(_Tint.rgb, 1.0);
            }
            ENDHLSL
        }
    }
}
```

여기에는 ShaderLab과 HLSL이 한 파일에 함께 있다. `Properties`는 에디터에서 머티리얼의 `_Tint` 값을 편집할 수 있게 하고, HLSL의 `UnityPerMaterial` 상수 버퍼는 그 값을 셰이더 계산에 연결한다. `#pragma vertex`와 `#pragma fragment`는 각 단계의 진입점 함수를 지정한다. 버텍스 단계는 URP의 `TransformObjectToHClip` 함수를 이용해 오브젝트 좌표를 클립 공간으로 보내고, 프래그먼트 단계는 머티리얼 색을 출력한다.

이 예제는 URP의 `Core.hlsl`과 변환 함수를 사용하므로 독립 HLSL 셰이더가 아니다. Built-in Render Pipeline이나 HDRP로 옮길 때는 파이프라인에 맞는 include, 변환 함수와 패스 태그를 사용해야 한다. `UnityPerMaterial` 같은 상수 버퍼 배치도 SRP Batcher 호환성에 영향을 준다. 셰이더 파일이 컴파일되는지만 확인하지 말고, 선택한 렌더 파이프라인에서 패스가 실제로 선택되는지와 머티리얼 속성이 바인딩되는지 확인한다.

Shader Graph에서는 노드 그래프가 HLSL 코드를 생성한다. 간단한 절차 수식은 노드로 구성하고, 필요한 일부 계산만 Custom Function 노드의 HLSL 함수로 보충할 수 있다. 이 경우 작성하는 HLSL은 완성된 정점·프래그먼트 셰이더가 아니라 그래프의 값 하나를 계산하는 조각이다. 노드가 입력과 출력 타입을 정하고, 그래프가 머티리얼의 나머지 파이프라인을 만든다. 생성 코드를 직접 관리해야 하는 특수 효과라면 ShaderLab 패스가 더 적합할 수 있다.

Unity의 렌더 파이프라인은 여러 플랫폼용 셰이더 변형을 생성하고, 대상 백엔드의 컴파일 도구와 규칙에 맞춰 빌드한다. 따라서 URP 또는 HDRP의 HLSL include와 매크로를 사용한 코드는 그 파이프라인의 지원 범위 안에서 이식성을 갖는다. `CGPROGRAM` 블록이나 Surface Shader를 사용하는 오래된 예제는 Built-in Render Pipeline을 전제로 하는 경우가 많으며, URP와 HDRP의 셰이더 코드와 동일한 방식으로 사용할 수 없다.

## Unreal Engine: 머티리얼 그래프와 전역 셰이더

Unreal Engine의 일반적인 표면 재질 작업은 머티리얼 그래프에서 시작한다. 그래프의 노드가 색, 거칠기, 금속성, 노멀, 이미시브 등의 값을 계산하고, 머티리얼 출력이 엔진의 조명·그림자·렌더링 경로와 연결된다. 그래프를 컴파일하면 엔진이 필요한 HLSL을 만들고 플랫폼별 셰이더를 준비하므로, 대부분의 머티리얼 작업에서 개발자는 버텍스·픽셀 셰이더 전체를 직접 작성하지 않는다.

특정 수학 계산이 그래프 노드만으로 불편할 때 Custom 노드를 사용할 수 있다. 예를 들어 UV의 한 성분으로 반복 밴드 마스크를 계산하는 아래 HLSL 조각을 생각해 보자.

```c
float phase = frac(Time * Speed + UV.x * Frequency);
return smoothstep(0.45, 0.50, phase);
```

이 코드는 독립 픽셀 셰이더가 아니다. `Time`, `Speed`, `UV`, `Frequency`를 Custom 노드의 입력 핀으로 선언하고, 반환한 스칼라를 머티리얼 그래프의 다음 입력에 연결해야 한다. 즉 HLSL은 패턴 계산을 맡고, 그래프는 표면 속성으로 연결되는 데이터 흐름을 맡는다. 재사용할 계산은 머티리얼 함수나 공유 HLSL include로 정리할 수 있지만, 노드 핀 이름과 생성 코드의 문맥을 일반 HLSL 전역 변수처럼 가정해서는 안 된다.

화면 전체 후처리, 특수 렌더 패스, 대량 데이터 처리처럼 머티리얼 표면 모델을 벗어나는 작업에는 전역 셰이더가 더 적합하다. Unreal의 전역 셰이더는 보통 `.usf` 파일에 셰이더 코드를, `.ush` 파일에 공유 선언과 함수를 둔다. C++에서 `FGlobalShader` 계열 클래스로 셰이더와 파라미터를 선언하고 `IMPLEMENT_GLOBAL_SHADER`로 엔진에 등록한다. 렌더 스레드에서는 렌더 그래프(RDG)에 입력·출력 자원을 등록하고 패스를 추가해 실행한다. 컴퓨트 작업이라면 스레드 그룹 크기와 디스패치도 셰이더 선언 및 렌더 그래프 패스와 일치시켜야 한다.

머티리얼 Custom 노드는 그래프 안에서 계산 하나를 확장할 때, 전역 셰이더는 엔진 렌더링 흐름에 별도 패스를 추가할 때 선택한다. 전역 셰이더는 HLSL 파일만 작성해서 끝나는 것이 아니라 C++ 등록, 파라미터 바인딩, 렌더 그래프 자원 의존성까지 구현해야 한다. 엔진 버전이 제공하는 매크로와 렌더 그래프 API를 따라야 하며, 엔진 내부 셰이더의 선언을 복사해 장기간 유지 가능한 공용 API로 간주하지 않는다.

## Direct3D: 애플리케이션이 파이프라인을 직접 구성하기

Direct3D 12에서는 HLSL 소스와 GPU 작업 사이의 여러 단계를 애플리케이션이 명시적으로 관리한다. 전형적인 흐름은 다음과 같다.

```text
HLSL 파일과 진입점·프로파일
    -> DXC 컴파일 및 셰이더 바이트코드 검증
        -> 루트 시그니처와 그래픽/컴퓨트 파이프라인 상태 생성
            -> 디스크립터와 리소스 상태 구성
                -> 커맨드 리스트에 드로우 또는 디스패치 기록
```

DXC로 HLSL을 컴파일할 때는 진입점 함수와 대상 프로파일을 지정한다. 예를 들어 버텍스와 픽셀 단계는 각각 다른 진입점 및 `vs_6_x`, `ps_6_x` 계열 프로파일로 컴파일한다. Shader Model은 사용할 수 있는 셰이더 기능의 범위를 제한하지만, 그것만으로 자원이나 파이프라인이 만들어지지는 않는다. 컴파일 결과의 입력·출력 서명과 리소스 바인딩이 호스트 쪽 설정과 일치해야 한다.

특히 Direct3D 12에서는 HLSL의 `register(b0)`, `register(t0)`, `register(u0)` 선언만으로 GPU 자원이 연결되지 않는다. 루트 시그니처와 디스크립터 테이블을 만들고, 상수 버퍼·텍스처·UAV를 적절한 슬롯에 채워야 한다. 또한 리소스가 현재 어떤 용도로 쓰이는지를 상태 전환으로 관리하고, 컴퓨트 쓰기 결과를 그래픽 셰이더가 읽는다면 필요한 동기화를 넣는다. GPU 시뮬레이션의 ping-pong 버퍼와 상태 전환은 28.7의 데이터 흐름을 Direct3D 애플리케이션에서 실제로 구성하는 단계다.

Direct3D 11은 기존 프로젝트와 도구에서 여전히 볼 수 있으며, 전통적으로 FXC와 DXBC를 사용하는 코드가 많다. Direct3D 12의 Shader Model 6 계열에서는 DXC와 DXIL이 일반적인 현대 경로다. 오래된 프로젝트를 빌드하거나 이식할 때는 파일 확장자만으로 컴파일러를 추측하지 말고, 빌드 스크립트와 셰이더 프로파일을 확인한다.

Direct3D 애플리케이션을 직접 작성하면 렌더링 상태와 자원 생명주기를 세밀하게 제어할 수 있지만, 창·장치·메모리·동기화·셰이더 오류 처리까지 애플리케이션이 책임져야 한다. Unity나 Unreal이 숨겨 주던 설정을 직접 관리하는 대신, 엔진의 머티리얼 모델에 맞추기 어려운 특수한 패스와 GPU 데이터 흐름을 구현할 수 있다. HLSL을 DXC로 Vulkan용 SPIR-V에 컴파일하는 경로도 존재하지만, Direct3D의 루트 시그니처와 바인딩 규칙이 Vulkan에서 자동으로 동일하게 작동하는 것은 아니다.

## 어느 수준에서 HLSL을 작성할까

| 필요 | 적합한 작성 경로 | 고려할 점 |
| --- | --- | --- |
| 재질의 색·거칠기·노멀을 조절 | Unity Shader Graph 또는 Unreal 머티리얼 그래프 | 조명과 렌더 파이프라인이 제공하는 표면 모델을 활용한다. |
| 그래프에 없는 짧은 수학 함수 추가 | Shader Graph Custom Function 또는 Unreal Custom 노드 | 입력·출력 핀과 타입은 그래프가 정한 계약을 따른다. |
| 엔진의 후처리·화면 효과·GPU 계산 패스 추가 | Unity의 사용자 셰이더 패스 또는 Unreal 전역 셰이더 | 엔진 렌더링 확장 API와 자원 관리 규칙을 익혀야 한다. |
| 파이프라인과 GPU 자원 접근을 직접 제어 | Direct3D 12 애플리케이션 | 루트 시그니처, 파이프라인 상태, 메모리와 동기화를 직접 구성한다. |

셰이더를 다른 환경으로 옮길 때는 수학 함수와 엔진 연결부를 분리하는 편이 좋다. 예를 들어 `frac`, 노이즈, 거리 계산처럼 순수한 수식은 가능한 한 입력과 출력을 명확히 한 함수로 두고, 머티리얼 핀이나 `cbuffer`, 텍스처 슬롯, 렌더 그래프 자원에 연결하는 코드는 플랫폼별 얇은 계층으로 분리한다. 이 방법은 HLSL 코드 전체의 호환성을 보장하지 않지만, 어떤 부분이 수학이고 어떤 부분이 Unity·Unreal·Direct3D의 계약인지 드러내 준다.

디버깅도 작성 수준에 맞춰 진행한다. Unity에서는 선택된 패스와 머티리얼 입력, 셰이더 변형을 확인하고, Unreal에서는 머티리얼 컴파일 결과나 렌더 그래프의 패스·자원 연결을 점검한다. Direct3D에서는 DXC의 오류와 셰이더 서명, 루트 시그니처, GPU 캡처의 리소스 상태를 확인한다. 셰이더 소스가 컴파일된다는 사실은 파이프라인의 모든 입력과 출력이 올바르게 연결되었다는 뜻이 아니다.

## 이 절의 핵심

Unity에서는 ShaderLab 패스와 렌더 파이프라인이 HLSL을 감싸고, Shader Graph는 노드로부터 HLSL을 생성한다. Unreal에서는 머티리얼 그래프의 계산 확장에 Custom 노드를, 별도 렌더 패스에는 C++에 등록한 전역 셰이더를 사용할 수 있다. Direct3D 12에서는 애플리케이션이 컴파일 프로파일부터 루트 시그니처, 자원 바인딩, 파이프라인과 동기화까지 직접 구성한다. HLSL 수식은 재사용할 수 있어도 엔진 include, 입력 의미, 머티리얼 계약, 자원 바인딩은 각 실행 환경에 맞게 다시 연결해야 한다.
