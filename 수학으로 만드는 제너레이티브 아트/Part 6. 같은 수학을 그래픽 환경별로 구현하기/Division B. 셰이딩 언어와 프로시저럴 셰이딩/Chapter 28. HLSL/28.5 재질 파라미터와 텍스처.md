# 28.5 재질 파라미터와 텍스처

HLSL에서 셰이더 입력은 값의 크기와 성격에 따라 상수 버퍼, 텍스처, 샘플러, 읽기·쓰기 리소스로 나뉜다. 재질의 기본 색이나 UV 반복률처럼 드로우 동안 공유되는 작은 값은 상수 버퍼(constant buffer)에 두고, 표면의 각 위치에 따라 다른 색과 데이터를 담은 이미지는 텍스처로 읽는다. HLSL은 각 자원의 타입과 레지스터 자리를 선언하지만, 실제 메모리와 GPU 자원을 만들고 연결하는 일은 호스트 프로그램이나 엔진이 맡는다.

이 절에서는 재질 파라미터를 HLSL 리소스로 표현하고, 텍스처와 샘플러를 픽셀 셰이더에서 사용하는 흐름을 살펴본다. 재질 값이 색·거칠기·금속성에 어떤 의미를 갖는지는 26.6, 텍스처 데이터의 일반적인 역할은 26.7을 참고한다.

## HLSL 리소스 레지스터

HLSL은 `register()` 안의 접두 문자로 자원 종류를 구분한다.

| 레지스터 | 자원 종류 | 대표 용도 |
| --- | --- | --- |
| `b` | 상수 버퍼(CBV) | 프레임·카메라·재질의 작은 공통 파라미터 |
| `t` | 셰이더 리소스(SRV) | 읽기 전용 텍스처와 버퍼 |
| `s` | 샘플러 | 텍스처 필터링과 주소 지정 방식 |
| `u` | 순서 없는 접근 리소스(UAV) | 셰이더에서 읽고 쓰는 텍스처와 버퍼 |

예를 들어 `register(b1)`은 상수 버퍼 슬롯 1을, `register(t0)`은 셰이더 리소스 슬롯 0을 가리킨다. 숫자가 같아도 접두 문자가 다르면 다른 종류의 슬롯이다. `register(t0, space1)`처럼 레지스터 공간(register space)을 지정하면 같은 번호를 다른 네임스페이스에서 사용할 수 있다. 단, 이 선언은 슬롯을 지정할 뿐 실제 자원을 만들거나 그 자리에 자동으로 연결하지 않는다.

Direct3D 11에서는 애플리케이션이 상수 버퍼, 셰이더 리소스 뷰(SRV), 샘플러를 각 셰이더 단계의 슬롯에 설정한다. Direct3D 12에서는 루트 시그니처가 HLSL의 레지스터와 레지스터 공간을 루트 파라미터, 디스크립터 테이블, 디스크립터 힙 등의 바인딩 구조에 연결한다. 엔진을 사용하면 이 과정의 상당 부분이 머티리얼 시스템 뒤에 감춰질 수 있지만, 셰이더 선언과 엔진의 바인딩 규약은 여전히 일치해야 한다.

## 재질 파라미터를 상수 버퍼로 묶기

상수 버퍼는 셰이더가 하나의 드로우 호출 동안 공통으로 읽는 값들을 묶는다. 색조, UV 스케일과 오프셋, 거칠기, 금속성, 애니메이션 속도처럼 비교적 작은 값이 대표적이다.

```c
cbuffer MaterialData : register(b1)
{
    float4 baseColor;
    float2 uvScale;
    float2 uvOffset;
};
```

이 예제의 `baseColor`는 기본 색과 알파를, `uvScale`과 `uvOffset`은 텍스처 좌표 변환을 나타낸다. 재질을 바꿀 때 호스트가 이 버퍼의 데이터를 갱신하면 동일한 셰이더를 여러 재질에 재사용할 수 있다. 프레임 전체에서 공유하는 카메라 데이터와 오브젝트마다 달라지는 모델 행렬, 머티리얼별 값은 업데이트 빈도와 수명에 따라 별도 버퍼로 나누는 것이 일반적이다.

상수 버퍼는 16바이트 단위의 레지스터 경계를 기준으로 패킹된다. 작은 값은 한 16바이트 묶음 안에서 함께 배치될 수 있지만, 배열·구조체·행렬은 추가 정렬 규칙을 가진다. 예를 들어 `float3` 뒤에 `float`를 두는 구조가 한 묶음에 들어갈 수는 있지만, CPU 구조체의 정렬이 셰이더와 자동으로 동일해지는 것은 아니다. 패딩과 행렬 배치가 어긋나면 셰이더는 오류 없이도 잘못된 값을 읽을 수 있으므로, HLSL 선언과 CPU 업로드 레이아웃을 맞춘다. 행렬의 행·열 패킹은 28.4에서 다룬 규칙을 따른다.

## 텍스처와 샘플러는 서로 다른 입력이다

HLSL에서는 읽을 이미지와 그 이미지를 어떤 방식으로 표본화할지 별도로 선언한다.

```c
Texture2D<float4> albedoTexture : register(t0);
SamplerState materialSampler : register(s0);
```

`Texture2D<float4>`는 각 텍셀에서 네 개 성분을 읽을 2D 텍스처를 나타낸다. `SamplerState`는 확대·축소 시의 필터링, 텍스처 경계를 벗어났을 때의 반복·고정 같은 주소 지정 규칙을 나타낸다. 텍스처 자체에는 이미지와 뷰가, 샘플러에는 필터와 주소 모드가 설정되며 호스트가 이를 셰이더의 해당 슬롯에 연결한다.

다음 픽셀 셰이더는 보간된 UV를 변환해 텍스처를 읽고 기본 색을 곱한다.

```c
struct PSInput
{
    float2 uv : TEXCOORD0;
};

float4 PSMain(PSInput input) : SV_Target0
{
    float2 uv = input.uv * uvScale + uvOffset;
    float4 texel = albedoTexture.Sample(materialSampler, uv);
    return texel * baseColor;
}
```

이 계산은 텍스처 색상에 재질 색조를 곱하는 간단한 예다. 실제 물리 기반 조명, 알파 모드, 톤 매핑은 포함하지 않는다. UV가 반복되는 타일 무늬를 원한다면 샘플러의 주소 모드를 반복으로 설정하고, 경계에서 늘려 보이게 하려면 고정(clamp) 모드를 사용할 수 있다. 셰이더 안에서 좌표를 `frac()`으로 접는 것과 샘플러 주소 모드를 사용하는 것은 이음새와 미분 계산에서 동작이 다를 수 있으므로 목적에 맞춰 선택한다.

## 샘플링 함수와 셰이더 단계

픽셀 셰이더에서 `Texture2D.Sample()`을 사용하면 GPU는 주변 픽셀에서 UV가 어떻게 변하는지 미분해 적절한 밉 레벨과 필터링을 선택할 수 있다. 이 방식은 표면이 멀어지거나 비스듬해질 때 텍스처가 반짝이는 것을 줄이는 데 도움을 준다.

버텍스나 컴퓨트 셰이더처럼 화면 프래그먼트 미분을 기본 제공하지 않는 단계에서는 필요에 따라 `SampleLevel()`로 밉 레벨을 직접 지정하거나, `SampleGrad()`에 기울기를 전달한다. 텍셀 위치를 정수 좌표로 정확히 읽는 데이터 처리에는 `Load()`를 사용할 수 있다. 어떤 함수를 쓸지는 텍스처가 필터링되어야 하는 이미지인지, 정해진 격자의 데이터를 읽어야 하는지에 따라 달라진다.

## 색 텍스처와 데이터 텍스처

재질에서 눈으로 보는 색을 담은 알베도 텍스처와, 계산에 쓰는 수치 데이터를 담은 텍스처는 색 공간을 다르게 처리해야 한다.

- 알베도·기본 색처럼 표시용 색을 담은 텍스처는 sRGB 형식의 SRV로 읽을 수 있다. GPU가 샘플링할 때 색상 성분을 선형 공간으로 변환하므로 조명 계산을 선형 값으로 수행하기 쉽다.
- 거칠기·금속성·마스크·높이처럼 숫자로 해석하는 데이터는 보통 선형 형식으로 읽는다. sRGB 변환이 적용되면 원래 저장한 수치와 다른 값이 되어 효과가 달라질 수 있다.
- 노멀 맵은 흔히 0~1 범위의 색으로 저장된 벡터다. 읽은 RGB를 보통 `2 * rgb - 1`로 변환해 -1~1 범위의 접선 공간 방향으로 복원하고, 적절한 접선·법선 기준으로 월드 또는 뷰 공간에 옮긴다.

셰이더만 보고 색이 너무 어둡거나 마스크 값이 틀렸다고 판단하기 전에 텍스처의 리소스 형식과 SRV 설정을 확인한다. 텍스처가 sRGB로 해석되는지는 HLSL의 `Texture2D` 자료형만으로 정해지지 않고, 호스트가 생성하는 뷰의 포맷에도 달려 있다.

## 재질 입력을 장면에 연결하기

한 재질과 렌더 패스에 연결하는 GPU 자원은 역할별로 구분할 수 있다.

| 역할 | HLSL 선언 | 데이터 예 | 장면에서의 용도 |
| --- | --- | --- | --- |
| 재질 파라미터 | `cbuffer` (`b`) | 기본 색, UV 스케일, 거칠기, 금속성 | 드로우마다 재질의 조절값을 셰이더에 전달 |
| 표면 텍스처 | SRV (`Texture2D`, `t`) | 알베도, 노멀, 거칠기, 마스크 | 픽셀 셰이더가 표면 좌표에서 이미지 데이터를 읽음 |
| 표본화 규칙 | `SamplerState` (`s`) | 필터와 주소 모드 | 텍스처의 확대·축소 및 경계 처리 방식을 결정 |
| 쓰기 가능한 출력(선택) | UAV (`RWTexture2D`, `u`) | 중간 이미지나 계산 필드 | 보통 재질 입력이 아니라 컴퓨트·중간 패스의 출력으로 사용 |

재질 편집기는 이 입력들을 아티스트가 조절할 수 있는 속성으로 노출하고, 렌더러는 각 재질에 맞는 상수 버퍼와 텍스처 뷰를 바인딩한다. HLSL 파일이 여러 재질에서 공유되면 셰이더 코드를 복제하기보다 파라미터와 텍스처만 바꾸는 구성이 효율적이다. 반대로 셰이더가 기대하는 `register()` 번호나 버퍼 레이아웃을 바꾸면 호스트 측 머티리얼과 루트 시그니처도 함께 수정해야 한다.

## 흔한 바인딩 문제

| 증상 | 먼저 확인할 항목 |
| --- | --- |
| 텍스처가 검거나 전혀 나오지 않음 | SRV가 선언한 `t` 슬롯에 연결됐는지, 올바른 리소스 뷰인지 확인 |
| 흐릿하거나 깜빡이는 패턴 | 샘플러 필터, 밉맵, UV 밀도와 샘플링 함수를 확인 |
| 재질 파라미터가 엉뚱한 값으로 읽힘 | 상수 버퍼의 슬롯, 16바이트 패킹, CPU 구조체 패딩을 확인 |
| 색이 기대보다 어둡거나 과포화됨 | sRGB/선형 포맷, 셰이더 계산 공간, 렌더 타깃 변환을 확인 |
| 일부 GPU에서만 셰이더가 작동하지 않음 | 셰이더 모델, 리소스 포맷·차원, API와 드라이버 지원을 확인 |

HLSL 소스의 레지스터 선언, CPU 측 자원 생성, 엔진의 머티리얼 설정은 하나의 바인딩 계약을 이룬다. 문제를 찾을 때는 셰이더가 텍스처를 읽는 코드만 보는 대신 자원이 생성되고 뷰로 만들어져 실제 슬롯에 묶이는 전체 흐름을 확인한다.

## 이 절의 핵심

HLSL은 `cbuffer`, `Texture2D`, `SamplerState` 등으로 자원의 종류와 레지스터 슬롯을 선언하고, 호스트는 실제 GPU 자원을 만들어 그 선언에 연결한다. 상수 버퍼는 작은 공통 파라미터를 전달하고, 텍스처와 샘플러는 각각 이미지 데이터와 읽는 규칙을 담당한다. 색 텍스처와 수치 데이터 텍스처는 sRGB 처리 여부가 다르며, 샘플링 함수는 셰이더 단계와 필요한 밉 선택에 맞춰야 한다. 재질 문제를 해결할 때는 HLSL 선언과 CPU·엔진의 바인딩 계약을 함께 점검한다.
