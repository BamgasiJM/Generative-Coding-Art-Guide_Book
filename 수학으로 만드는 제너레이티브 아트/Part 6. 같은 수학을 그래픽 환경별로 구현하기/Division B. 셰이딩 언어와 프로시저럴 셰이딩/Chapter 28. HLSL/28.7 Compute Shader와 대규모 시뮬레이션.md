# 28.7 Compute Shader와 대규모 시뮬레이션

컴퓨트 셰이더는 정점이나 프래그먼트가 아니라 스레드 그룹을 실행 단위로 삼아 GPU 버퍼와 텍스처의 데이터를 계산한다. 입자 수만 개의 위치와 속도를 갱신하거나, 2차원 격자의 각 셀에서 반응·확산 규칙을 반복할 때 유용하다. 특히 시뮬레이션 상태를 GPU 메모리에 유지하고 그 결과를 바로 렌더링하면, 매 프레임 전체 데이터를 CPU로 복사하는 비용을 줄일 수 있다.

28.3에서 컴퓨트 셰이더의 기본 문법과 스레드 ID를 살펴보았다. 여기서는 대규모 상태 갱신의 데이터 흐름, 읽기와 쓰기 버퍼 분리, 프레임 간 동기화, 시뮬레이션의 안정성을 중심으로 확장한다.

## CPU와 GPU의 작업 분담

대규모 시뮬레이션에서는 CPU가 매 입자의 새 위치를 계산해 다시 GPU에 보내기보다, 초기 상태와 소수의 조절값을 전달하고 GPU에서 상태를 갱신하는 구성이 흔하다.

```text
CPU: 초기 데이터와 매개변수 준비
    -> GPU Compute Shader: 모든 항목의 다음 상태 계산
        -> GPU Graphics Pipeline: 새 상태를 이용해 장면 렌더링
            -> 다음 프레임의 Compute Shader 입력
```

이 구조에서 CPU는 디스패치 횟수와 그룹 수, 시간 간격, 외력 같은 파라미터를 관리한다. GPU의 각 스레드는 입자 하나나 격자 셀 하나를 맡아 입력 상태를 읽고 새 상태를 쓴다. 상태를 CPU로 매 프레임 읽어오지 않으므로, 계산과 렌더링 사이의 데이터 왕복을 피할 수 있다.

## 입자 상태를 병렬로 갱신하기

다음 HLSL 예제는 정규화된 2D 공간에서 입자 위치와 속도를 갱신한다. 입자마다 하나의 스레드가 실행되며, 원점으로 끌어당기는 힘과 회전 흐름, 작은 시간 변화 힘을 합성한다. 위치는 화면 경계를 넘으면 반대편으로 이어지는 주기 경계를 사용한다.

```c
struct Particle
{
    float2 position;
    float2 velocity;
};

StructuredBuffer<Particle> particlesIn : register(t0);
RWStructuredBuffer<Particle> particlesOut : register(u0);

cbuffer SimulationParameters : register(b0)
{
    uint particleCount;
    float deltaTime;
    float swirlStrength;
    float attractionStrength;
    float drag;
    float time;
    float2 padding;
};

[numthreads(256, 1, 1)]
void CSMain(uint3 dispatchThreadID : SV_DispatchThreadID)
{
    uint id = dispatchThreadID.x;
    if (id >= particleCount)
    {
        return;
    }

    Particle particle = particlesIn[id];
    float2 offset = particle.position - float2(0.5, 0.5);

    float2 vortex = float2(-offset.y, offset.x) * swirlStrength;
    float2 attraction = -offset * attractionStrength;
    float2 wind = 0.02 * float2(
        sin(time + particle.position.y * 6.0),
        cos(time + particle.position.x * 6.0)
    );
    float2 acceleration = vortex + attraction + wind;

    particle.velocity += acceleration * deltaTime;
    particle.velocity *= exp(-drag * deltaTime);
    particle.position = frac(particle.position + particle.velocity * deltaTime);

    particlesOut[id] = particle;
}
```

`StructuredBuffer<Particle>`는 현재 상태를 읽고, `RWStructuredBuffer<Particle>`는 다음 상태를 쓴다. 각 스레드는 `SV_DispatchThreadID.x`로 고유한 입자 인덱스를 얻는다. 입자 개수가 스레드 수로 나누어떨어지지 않을 수 있으므로, `particleCount`를 넘는 스레드는 초기에 종료한다.

`[numthreads(256, 1, 1)]`은 그룹마다 256개의 스레드를 만든다. 호스트는 입자 개수 $N$에 대해 대략 $\lceil N/256\rceil$개의 그룹을 디스패치한다. `256`은 시작점으로 쓸 수 있는 값이지 모든 GPU와 작업에서 최적이라는 뜻은 아니다. 데이터의 접근 패턴과 목표 장치에서 여러 그룹 크기를 측정해 선택한다.

## 읽기와 쓰기를 분리하는 이유

같은 버퍼에서 한 스레드는 값을 읽고 다른 스레드는 그 값을 덮어쓰도록 만들면, 스레드 실행 순서에 따라 계산 결과가 달라질 수 있다. GPU 스레드의 실행 순서는 일반적으로 정해져 있지 않으며, 한 그룹 안의 동기화 장벽도 다른 그룹의 실행이 끝났다는 보장을 주지 않는다.

그래서 시뮬레이션은 보통 **ping-pong 버퍼**를 사용한다.

1. 버퍼 A를 현재 상태로 읽고 버퍼 B에 다음 상태를 쓴다.
2. 디스패치가 끝나면 B를 새 현재 상태로 삼는다.
3. 다음 프레임에는 B를 읽고 A에 쓴다.
4. 프레임마다 읽기·쓰기 역할을 서로 바꾼다.

모든 스레드가 입력 버퍼를 읽기 전용으로 보고, 각자 출력 버퍼의 서로 다른 인덱스에 쓰므로 입자별 힘 계산은 데이터 경쟁 없이 진행된다. 또한 시뮬레이션 결과가 같은 프레임 안에서 일부 입자는 새 위치, 일부 입자는 옛 위치를 참조하는 혼합 상태가 되지 않는다.

Direct3D 12에서는 쓰기 대상의 리소스 상태와 다음 사용처에 맞는 상태 전환 및 필요한 UAV 동기화를 명시해야 한다. 예를 들어 컴퓨트 셰이더가 쓴 버퍼를 버텍스 셰이더가 읽는다면, 디스패치와 렌더링 사이에 자원 사용 상태를 맞춘다. Direct3D 11이나 엔진에서는 바인딩 해제와 전환을 API 또는 엔진이 관리할 수 있지만, 한 자원을 동시에 읽기와 쓰기에 바인딩하는 충돌을 피해야 한다.

## 시간 간격과 적분 안정성

입자 상태는 프레임의 시간 간격에 따라 변한다. 예제는 가속도를 속도에 더한 뒤 새 속도로 위치를 이동하는 간단한 반암시적 오일러 적분을 사용한다.

$$
\mathbf{v}_{n+1}=\mathbf{v}_n+\mathbf{a}_n\Delta t,\qquad
\mathbf{x}_{n+1}=\mathbf{x}_n+\mathbf{v}_{n+1}\Delta t
$$

고정된 힘을 적용하더라도 프레임마다 `deltaTime`이 크게 달라지면 궤적이 불안정해질 수 있다. 물리적인 일관성이 중요하다면 CPU에서 고정 시간 간격의 누적기를 두고 한 프레임 안에 필요한 횟수만큼 컴퓨트 디스패치를 수행한다. 프레임이 오래 멈춘 뒤 큰 시간값 한 번을 전달하기보다 경과 시간을 제한하거나 여러 작은 스텝으로 나누는 편이 안정적이다.

속도 감쇠를 `exp(-drag * deltaTime)`으로 두면 시간 간격 변화에 비교적 부드럽게 대응한다. 그래도 가속도와 속도가 지나치게 커지면 입자가 한 스텝에 공간 전체를 건너뛸 수 있으므로, 힘의 크기와 속도 상한, 시간 스텝을 함께 조절한다. `frac()`은 예제의 주기 경계 조건을 구현한다. 벽에서 튕기게 하거나 입자를 제거하려면 반사·클램프·수명 만료 등 다른 경계 규칙을 적용한다.

## 입자 간 상호작용의 비용

입자마다 독립적인 외력만 계산하는 예제는 입자 수 $N$에 비례하는 작업량을 가진다. 하지만 모든 입자가 다른 모든 입자와 상호작용하도록 각 스레드에서 전체 입자 배열을 순회하면 계산량이 대략 $N^2$으로 늘어난다. 수만 개 이상의 입자에서는 이 방식이 빠르게 병목이 된다.

근접 입자만 영향을 주는 힘이라면 공간을 셀로 나누고 주변 셀만 조회하는 균일 격자나 해시 그리드를 고려한다. 밀도가 크게 달라지는 장면에서는 계층적 구조나 정렬된 공간 인덱스가 더 적합할 수 있다. 이 과정은 단순한 입자 업데이트와 달리 인덱스 생성, 카운팅, 누적, 동기화 단계가 추가되므로, 먼저 단순한 기준 구현을 만들고 실제 병목을 측정한 뒤 확장한다.

여러 스레드가 같은 위치에 동시에 쓰는 경우에는 원자 연산이나 별도의 누적 단계를 설계해야 한다. 원자 연산은 충돌을 안전하게 만들 수 있지만 경쟁이 몰리면 성능이 떨어지고, 더하기 순서가 바뀌어 부동소수점 결과도 실행마다 미세하게 달라질 수 있다. 가능하면 출력 인덱스를 스레드마다 고유하게 배정하고, 공유 누적은 별도 패스에서 처리한다.

## 렌더링과 연결하고 GPU에 상태를 유지하기

시뮬레이션 상태를 매 프레임 CPU로 읽지 않고 GPU 안에 유지하면 큰 배열의 읽기 되돌림 비용을 피할 수 있다. 렌더 패스는 컴퓨트 결과 버퍼를 구조화된 데이터로 읽어 각 입자의 위치나 색을 얻고, 점·인스턴스·카메라 방향 빌보드로 표현할 수 있다. 이때 컴퓨트 출력과 그래픽 입력 사이에 필요한 자원 상태 전환을 수행한다.

시뮬레이션이 이미지나 격자값으로 표현된다면 `RWTexture2D`를 쓰고, 현재 텍스처에서 다음 텍스처를 만드는 ping-pong 패턴을 사용할 수 있다. 반응-확산이나 셀룰러 오토마타처럼 한 셀의 다음 상태가 주변 셀의 이전 값에 의존하는 경우에도, 입력 텍스처는 읽기 전용으로 두고 출력 텍스처에 결과를 쓴다. 이전 상태를 별도 텍스처에 보존하면 모든 스레드가 같은 시점의 데이터를 읽는다.

작은 시뮬레이션에서는 디스패치와 자원 관리의 고정 비용 때문에 CPU 계산이 더 간단하거나 빠를 수 있다. 버퍼는 보통 초기화 때 만들고 반복해서 재사용하며, 상태를 매 프레임 CPU에 복사하는 방식은 GPU 계산의 이점을 줄일 수 있다. 입자 수와 갱신량이 충분히 크고 상태가 렌더링에도 바로 쓰일 때 GPU 기반 구조의 이점이 커진다.

## 이 절의 핵심

컴퓨트 셰이더는 많은 입자나 격자 항목의 상태를 병렬로 갱신하고, 그 결과를 GPU 메모리에 유지해 렌더링에 넘길 수 있다. 안전한 기본 구조는 읽기 상태와 쓰기 상태를 분리하는 ping-pong 버퍼이며, 그룹 크기·시간 간격·자원 동기화는 호스트와 함께 설계해야 한다. 독립 업데이트는 효율적으로 확장되지만, 모든 항목이 서로를 검사하는 상호작용은 $O(N^2)$ 비용이 될 수 있으므로 공간 분할과 단계별 측정이 필요하다.
