# 28.2 셰이더 모델과 렌더링 단계

HLSL 셰이더를 컴파일할 때는 소스 코드뿐 아니라 어떤 종류의 셰이더인지, 어떤 기능 집합을 대상으로 하는지 지정해야 한다. 이를 나타내는 핵심 개념이 **셰이더 모델(Shader Model)**과 **대상 프로필(target profile)**이다. 대상 프로필은 단계와 모델 버전을 결합해 `vs_6_0`, `ps_6_0`, `cs_6_0`처럼 표현한다. 각각 버텍스, 픽셀, 컴퓨트 셰이더를 Shader Model 6.0 기능 집합으로 컴파일하라는 뜻이다.

셰이더 모델은 HLSL 문법 버전이나 GPU 세대 이름과 동일하지 않다. HLSL 언어 버전은 소스에서 사용할 수 있는 언어 기능을, 셰이더 모델은 해당 단계에서 사용할 수 있는 GPU 셰이더 기능과 컴파일 대상의 능력 범위를 설명한다. 실제로 셰이더를 실행할 수 있는지는 컴파일러뿐 아니라 Direct3D 런타임, 운영체제, 드라이버, GPU가 함께 결정한다.

## 대상 프로필이 알려주는 것

컴파일 명령에서 진입점과 대상 프로필을 지정하는 예는 다음과 같다.

```text
dxc -E PSMain -T ps_6_0 shader.hlsl
```

`-E`는 진입점 함수 이름을, `-T`는 대상 프로필을 지정한다. 이 명령에서 `PSMain`은 픽셀 셰이더로 컴파일되고 `ps_6_0`이 가리키는 모델 기능을 대상으로 한다. 실제 프로젝트에서는 빌드 시스템이나 엔진이 이 옵션을 대신 설정할 수 있으므로, 에디터에서 셰이더를 수정할 때도 프로젝트가 사용하는 프로필을 확인해야 한다.

| 프로필 예 | 의미 |
| --- | --- |
| `vs_6_0` | Shader Model 6.0 대상의 버텍스 셰이더 |
| `ps_6_0` | Shader Model 6.0 대상의 픽셀 셰이더 |
| `cs_6_0` | Shader Model 6.0 대상의 컴퓨트 셰이더 |
| `vs_5_0`, `ps_5_0` | Direct3D 11 시대 프로젝트에서 흔히 만나는 Shader Model 5.0 프로필 |

셰이더 모델 6 계열은 DXC와 DXIL을 중심으로 발전한 현대 HLSL 개발의 기준이다. 이후 모델 버전은 새로운 자료형, 연산, 셰이더 기능과 하드웨어 활용 방식을 추가할 수 있지만, 그 버전 번호만 보고 모든 기능이 모든 단계와 장치에 적용된다고 판단하면 안 된다. 예를 들어 특정 기능은 별도의 프로필이나 런타임 기능 지원을 요구할 수 있다.

이전 Direct3D 프로젝트에는 FXC로 컴파일하는 `*_5_0` 프로필과 DXBC 결과가 남아 있을 수 있다. 이를 최신 프로필로 바꿀 때는 대상 기기, 사용 중인 렌더 API, 엔진이 지원하는 컴파일러와 셰이더 기능을 먼저 확인한다. 파일 확장자가 `.hlsl`이라는 사실만으로 컴파일러나 셰이더 모델이 결정되지는 않는다.

## 모델 버전과 장치 지원은 따로 확인한다

컴파일러가 어떤 프로필을 받아들인다고 해서 실행할 GPU가 그 기능을 반드시 지원하는 것은 아니다. 반대로 최신 GPU를 사용하더라도 애플리케이션이 오래된 런타임이나 셰이더 모델을 대상으로 빌드되어 있으면 새로운 기능을 쓸 수 없다. Direct3D 12에서는 장치의 기능 수준(feature level)과 지원 셰이더 모델을 확인해 셰이더 선택이나 대체 경로를 결정할 수 있다.

이를 실무에서는 세 단계로 점검한다.

1. 빌드 도구와 컴파일러가 해당 대상 프로필을 지원하는가?
2. 실행 중인 운영체제·Direct3D 런타임·드라이버가 해당 셰이더 바이트코드를 허용하는가?
3. 실제 GPU가 사용하려는 셰이더 기능과 자원 한도를 지원하는가?

모든 기능이 공통으로 지원되는 애플리케이션이라면 최소 지원 프로필을 기준으로 작성한다. 선택적 기능을 쓰는 경우에는 장치 기능을 확인하고, 지원되지 않을 때 사용할 간단한 셰이더나 렌더링 경로를 준비한다. 대상 프로필은 빌드 설정의 숫자에 그치지 않고 작품이 실행될 수 있는 범위를 정하는 약속이다.

## 전통적인 래스터화 파이프라인

삼각형 메시를 화면에 그리는 전통적인 그래픽 파이프라인은 프로그래머블 셰이더 단계와 고정 기능 단계를 번갈아 통과한다.

```text
정점·인덱스 버퍼
    -> 입력 조립기
        -> 버텍스 셰이더
            -> [선택: 헐 셰이더 -> 고정 기능 테셀레이터 -> 도메인 셰이더]
                -> [선택: 지오메트리 셰이더]
                    -> 래스터라이저
                        -> 픽셀 셰이더
                            -> 출력 병합: 깊이·스텐실·블렌딩
```

입력 조립기와 래스터라이저, 출력 병합기는 그래픽 API와 GPU가 제공하는 파이프라인 기능이며, 각각을 HLSL 함수로 작성하지 않는다. 버텍스 셰이더는 각 정점에 대한 계산을 수행하고, 픽셀 셰이더는 래스터화된 프래그먼트의 출력값을 계산한다. 테셀레이션과 지오메트리 셰이더는 필요할 때 추가하는 선택 단계다. 모든 장면이 모든 셰이더 단계를 필요로 하지는 않는다.

픽셀 셰이더가 화면에 쓸 색을 계산하더라도 최종 픽셀은 그 값만으로 결정되지 않을 수 있다. 깊이·스텐실 검사와 블렌딩은 셰이더 바깥의 파이프라인 상태에서 수행된다. 반대로 깊이만 기록하는 패스처럼 픽셀 셰이더 출력이 생략되거나 제한되는 구성도 있다. 렌더링 결과를 이해할 때는 HLSL 코드와 함께 파이프라인 설정을 읽어야 한다.

## 래스터화 밖의 셰이더 경로

모든 GPU 프로그램이 삼각형을 화면에 그리는 경로에 들어가는 것은 아니다.

**컴퓨트 셰이더**는 그래픽 프리미티브를 입력으로 삼지 않고, 애플리케이션이 디스패치한 스레드 그룹 단위로 데이터를 처리한다. 결과는 버퍼나 텍스처에 저장되고 이후 렌더링 단계에서 읽힐 수 있다. 이미지 처리, 입자 상태 갱신, 필드 계산처럼 화면에 직접 대응하지 않는 병렬 작업에 적합하다.

**메시 셰이더 파이프라인**은 전통적인 입력 조립기와 버텍스·테셀레이션·지오메트리 단계 조합에 대한 대안이다. Direct3D 12의 Shader Model 6.5부터 관련 메시·증폭 셰이더 기능을 제공하며, 메시 셰이더가 정점과 프리미티브 묶음을 생성해 뒤쪽 래스터화로 넘긴다. 이 경로는 지원 장치와 API 기능 확인이 필요하므로, 기존 버텍스 셰이더 파이프라인의 단순한 이름 변경으로 생각하면 안 된다.

레이 트레이싱은 또 다른 파이프라인으로, 광선 생성·교차·히트 처리 셰이더가 레이 트레이싱 API의 호출 구조에 따라 실행된다. 이 역시 전통적인 버텍스에서 픽셀로 이어지는 단계열과 다르다. 각 경로에서 사용하는 셰이더 종류와 작성법은 28.3에서 더 살펴본다.

## 파이프라인을 먼저 그려 보기

복잡한 HLSL 셰이더를 읽기 전에 입력과 출력의 흐름을 간단히 그려 두면 좋다. 정점 버퍼가 버텍스 셰이더에 들어가 메시를 만들고 픽셀 셰이더에서 색을 출력하는지, 아니면 컴퓨트 셰이더가 텍스처를 갱신하는지에 따라 필요한 대상 프로필과 자원 연결이 달라진다. 셰이더 함수만 읽고 이 흐름을 놓치면 데이터가 어디에서 왔고 결과가 어디로 가는지 파악하기 어렵다.

프로시저럴 아트에서도 같은 기준을 적용할 수 있다. 전체 화면 패턴을 만들 때는 전체 화면 도형의 픽셀 셰이더에서 좌표별 색을 계산할 수 있고, 입자 수가 많아 상태 갱신이 병목이 되면 컴퓨트 경로를 검토할 수 있다. 어느 방식을 택할지는 수학식의 종류뿐 아니라 데이터가 생성되고 소비되는 위치, 대상 GPU의 기능, 결과를 다른 패스와 공유해야 하는지에 따라 결정한다.

## 이 절의 핵심

셰이더 모델은 HLSL 코드의 대상 단계와 사용 가능한 GPU 기능 범위를 나타내며, 대상 프로필은 이를 `vs_6_0`처럼 구체화한다. 프로필, HLSL 언어 버전, GPU 기능 수준은 서로 관련되지만 같은 값은 아니므로 컴파일러와 실행 장치에서 따로 확인해야 한다. 전통적인 래스터화는 여러 프로그래머블·고정 기능 단계가 이어지는 경로이고, 컴퓨트·메시·레이 트레이싱은 별도의 실행 구조를 가진다. 각 셰이더 단계의 입출력과 문법은 다음 절에서 자세히 다룬다.
