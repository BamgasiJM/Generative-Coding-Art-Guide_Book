# 28.8 GLSL과 HLSL의 공통점과 차이

GLSL과 HLSL은 모두 GPU에서 정점, 픽셀, 컴퓨트 작업을 실행하기 위한 셰이딩 언어다. 두 언어로 같은 수학적 함수를 구현할 수 있지만, 입력과 출력의 선언 방식, 텍스처 접근, 행렬 연산, 그래픽 API와의 연결은 다르다. 따라서 셰이더를 다른 언어로 옮기는 일은 함수 이름만 바꾸는 번역이 아니라, 그 함수가 파이프라인에서 어떤 데이터를 받아 어디에 기록하는지 다시 연결하는 작업이다.

이 절에서는 같은 화면 패턴을 두 언어로 표현해 공통 수학과 다른 인터페이스를 비교한다. GLSL은 OpenGL 계열에서 사용하는 GLSL 4.60 코어 문법, HLSL은 Shader Model 6.x를 대상으로 하는 문법을 기준으로 한다. 두 버전 표기가 서로 일대일로 대응하는 것은 아니다.

## 같은 수학, 다른 인터페이스

다음 두 픽셀 셰이더는 화면 중앙에 부드러운 원형 고리를 그린다. 거리 계산과 안티앨리어싱 방식은 같고, 프래그먼트의 화면 위치를 얻고 색을 내보내는 인터페이스와 보간 함수 이름이 다르다. 두 예제는 화면을 덮는 도형으로 실행하며, 해상도 값을 호스트 프로그램이 전달한다고 가정한다.

```glsl
#version 460 core

uniform vec2 u_resolution;
layout(location = 0) out vec4 outColor;

void main() {
    vec2 p = (gl_FragCoord.xy - 0.5 * u_resolution) / u_resolution.y;
    float d = abs(length(p) - 0.28);
    float aa = max(fwidth(d), 1e-4);
    float ring = 1.0 - smoothstep(0.012 - aa, 0.012 + aa, d);

    vec3 background = vec3(0.025, 0.04, 0.07);
    vec3 ink = vec3(0.2, 0.85, 0.75);
    outColor = vec4(mix(background, ink, ring), 1.0);
}
```

HLSL에서는 픽셀 셰이더의 입력 매개변수에 `SV_Position` 의미를 붙여 화면 위치를 받고, 반환값에 `SV_Target0`을 붙여 첫 번째 색 출력으로 연결한다.

```c
cbuffer FrameData : register(b0)
{
    float2 resolution;
    float2 padding;
};

float4 PSMain(float4 position : SV_Position) : SV_Target0
{
    float2 p = (position.xy - 0.5 * resolution) / resolution.y;
    float d = abs(length(p) - 0.28);
    float aa = max(fwidth(d), 1e-4);
    float ring = 1.0 - smoothstep(0.012 - aa, 0.012 + aa, d);

    float3 background = float3(0.025, 0.04, 0.07);
    float3 ink = float3(0.2, 0.85, 0.75);
    return float4(lerp(background, ink, ring), 1.0);
}
```

GLSL의 `main()`은 해당 셰이더 단계의 진입점이다. 반면 HLSL은 `PSMain`처럼 함수를 진입점으로 지정해 컴파일하며, `SV_Position`과 `SV_Target0` 같은 의미(semantic)가 파이프라인의 입력·출력 역할을 나타낸다. 예제에서 `fwidth`, `length`, `smoothstep`은 두 언어에 공통으로 제공되는 연산이고, `mix`와 `lerp`는 같은 두 값을 보간하는 함수다.

`fwidth`는 인접한 프래그먼트 사이의 값 변화를 이용하는 화면 미분 연산이므로, 이 셰이더를 컴퓨트 단계로 옮겨 그대로 호출할 수는 없다. 컴퓨트 셰이더에서 가장자리 부드러움이 필요하면 차분을 직접 계산하거나, 해상도와 샘플 간격을 고려한 별도 근사를 설계한다.

픽셀 위치의 원점과 방향은 그래픽 API와 파이프라인 설정에 영향을 받는다. 이 예제처럼 중심 대칭 도형은 y축 방향 차이가 결과에 드러나지 않지만, 방향성이 있는 패턴이나 텍스처를 옮길 때는 화면 좌표의 원점과 y축 방향을 확인해야 한다.

## 자주 만나는 문법 대응

| 개념 | GLSL | HLSL | 주의점 |
| --- | --- | --- | --- |
| 2·3·4차원 실수 벡터 | `vec2`, `vec3`, `vec4` | `float2`, `float3`, `float4` | HLSL은 정수형에 `int2`, 부호 없는 정수형에 `uint2` 같은 타입을 쓴다. |
| 행렬 타입 | `mat4`, `mat3` | `float4x4`, `float3x3` | 메모리 배치와 벡터 곱 순서는 별도로 맞춘다. |
| 두 값의 보간 | `mix(a, b, t)` | `lerp(a, b, t)` | 두 함수 모두 보통 `a * (1 - t) + b * t`에 해당한다. |
| 소수 부분 | `fract(x)` | `frac(x)` | 반복 좌표나 주기 패턴에 쓸 수 있다. |
| 역제곱근 | `inversesqrt(x)` | `rsqrt(x)` | 정규화나 거리 계산에서 자주 만난다. |
| 프래그먼트 출력 | 사용자 `out` 변수 | 반환값 또는 출력 구조체의 `SV_Target` | 렌더 타깃의 연결은 호스트가 준비한다. |
| 텍스처 표본 | `texture(sampler, uv)` | `texture.Sample(sampler, uv)` | 자원 선언과 샘플러 연결 방식이 다르다. |

함수 이름이 달라도 수학적 역할이 같은 경우가 많지만, 모든 함수가 완전히 동일한 경계 조건과 정밀도를 보장하는 것은 아니다. 특히 모듈로 연산, 정수 변환, 부동소수점 정밀도, 미정의 입력을 처리하는 코드는 대상 언어의 명세와 컴파일러 결과를 확인한다. 번역 과정에서는 이름 대응표만으로 끝내지 말고 입력 범위와 출력 범위도 비교해야 한다.

## 단계 입출력의 표현

두 언어는 단계 사이로 데이터를 전달하는 방법이 다르다. GLSL은 셰이더 단계의 전역 변수에 `in`과 `out`을 선언하고, `layout(location = n)`으로 속성이나 인터페이스 슬롯을 지정할 수 있다. 버텍스 셰이더의 위치 출력은 `gl_Position`이라는 내장 변수다.

HLSL은 함수의 매개변수와 반환값, 또는 구조체 필드에 semantic을 붙인다. 일반 정점 속성은 `POSITION`, `TEXCOORD0`처럼 이름을 지정하고, 파이프라인이 정한 시스템 값은 `SV_Position`, `SV_Target`처럼 `SV_` 접두어를 사용한다. 버텍스 셰이더의 출력 구조체와 픽셀 셰이더의 입력 구조체가 호환되는 semantic과 타입을 가져야 단계 간 값이 전달된다.

| 역할 | GLSL의 표현 | HLSL의 표현 |
| --- | --- | --- |
| 정점 속성 위치 | `layout(location = 0) in vec3 position` | 입력 구조체의 `float3 position : POSITION` 등 |
| 단계 간 값 | 버텍스 단계의 `out`, 다음 단계의 `in` | 출력·입력 구조체 필드의 semantic |
| 클립 공간 위치 | 버텍스 단계의 `gl_Position` | 버텍스 출력의 `SV_Position` |
| 컬러 타깃 출력 | `layout(location = 0) out vec4 color` | 반환값 또는 필드의 `SV_Target0` |

HLSL의 semantic 이름과 GLSL의 location 번호는 언어 수준에서 단순 치환되는 요소가 아니다. Direct3D에서는 입력 레이아웃과 semantic이 연결되고, Vulkan으로 컴파일할 때는 컴파일러와 셰이더 인터페이스 설정이 semantic을 location에 대응시킬 수 있다. 엔진이나 프레임워크가 이 연결을 자동 생성하는 경우에도 실제 컴파일 결과의 인터페이스를 확인해야 한다.

## 유니폼과 리소스 바인딩

셰이더 변수에 값을 선언하는 것과 GPU 자원에 실제로 연결하는 것은 별개의 일이다. GLSL에서는 단일 `uniform` 변수, `uniform` 블록, 이미지·샘플러 변수를 사용한다. OpenGL 호스트 코드는 유니폼 값을 설정하고 텍스처를 텍스처 유닛에 연결한다. Vulkan에서는 디스크립터 집합과 바인딩 규칙에 맞춘 선언과 바인딩이 필요하다.

HLSL에서는 상수 데이터를 `cbuffer`에 넣고, 텍스처와 버퍼를 `Texture2D`, `StructuredBuffer`, `RWStructuredBuffer` 등으로 선언한다. `register(b0)`, `register(t0)`, `register(s0)`, `register(u0)`는 각각 상수 버퍼, 읽기 리소스, 샘플러, 읽기·쓰기 리소스의 슬롯을 나타내는 전형적인 Direct3D 표기다. Direct3D 12에서는 루트 시그니처와 디스크립터 테이블이 이를 실제 GPU 자원과 연결한다.

GLSL에서 `sampler2D` 하나로 표현하는 텍스처 표본 접근은 HLSL에서 텍스처 객체와 샘플러 상태를 별도로 선언해 `Sample()`에 함께 전달하는 형태가 흔하다. 기능적으로는 모두 UV 좌표를 사용해 텍스처 값을 읽지만, 필터링·주소 지정 상태와 자원 슬롯을 호스트가 구성하는 방식은 다르다. HLSL을 Vulkan SPIR-V로 컴파일하는 경우에는 Direct3D의 `register` 체계를 그대로 런타임 바인딩이라고 간주할 수 없다. DXC 옵션이나 바인딩 어트리뷰트, 파이프라인 레이아웃을 통해 대상 API의 디스크립터 규약으로 대응시켜야 한다.

따라서 포팅 시에는 셰이더 안의 수학뿐 아니라 상수 버퍼의 정렬과 크기, 자원 슬롯, 샘플러 상태, 렌더 타깃 형식까지 확인한다. 같은 이름의 `resolution` 유니폼을 선언했다고 해서 호스트 코드가 두 언어에서 자동으로 같은 위치에 값을 쓰는 것은 아니다.

## 행렬과 좌표 규약은 따로 점검하기

GLSL에서는 열 벡터에 행렬을 왼쪽에서 곱하는 `M * v` 표기가 일반적이다. HLSL에서는 행렬 곱에 `mul()`을 명시적으로 쓰며, `mul(M, v)`와 `mul(v, M)`은 서로 다른 계산 순서다. HLSL의 `row_major`와 `column_major`, GLSL 행렬의 기본 열 우선 저장 같은 메모리 배치 규칙도 곱셈 순서와 별개다. 두 언어 사이에서 행렬을 옮길 때는 CPU가 만드는 행렬 조합, 셰이더의 곱셈 방향, 상수 버퍼의 배치를 함께 확인한다. 자세한 HLSL 행렬 규칙은 28.4를 참고한다.

깊이 범위 또한 언어만 보고 결정할 수 없다. 전통적인 OpenGL 클립 공간의 깊이는 보통 $[-w, w]$ 범위를 사용하고, Direct3D는 $[0, w]$를 사용한다. Vulkan은 GLSL을 사용하더라도 기본 깊이 범위가 $[0, w]$인 등 대상 API의 규칙을 따른다. 프로젝션 행렬, 뷰포트 변환, 깊이 비교 설정이 그 규약에 맞아야 한다. 좌수계·우수계, 화면의 y축 방향, 텍스처의 위아래 방향도 프로젝트와 API의 설정에 달려 있으므로 HLSL과 GLSL의 고유한 차이라고 단정하지 않는다.

## 버전 표기를 일대일로 비교하지 않기

GLSL은 `#version 460 core`처럼 소스에서 언어 버전과 프로파일을 지정하는 방식이 익숙하다. HLSL은 소스에 같은 형식의 버전 지시문을 두기보다 컴파일러 옵션으로 진입점과 대상 프로파일을 지정하는 경우가 많다. 예를 들어 `ps_6_0`은 픽셀 셰이더 단계와 Shader Model 6.0 대상 프로파일을 나타낸다. HLSL 언어 버전 선택과 Shader Model은 서로 관련되지만 같은 개념은 아니다.

그러므로 GLSL 4.60을 HLSL Shader Model 6.0과 같은 기능 목록이라고 보거나, 한쪽에서 컴파일되면 다른 쪽에서도 동일하게 지원된다고 가정하면 안 된다. 실제 사용 가능 기능은 언어 명세뿐 아니라 컴파일러, 그래픽 API, GPU 기능, 엔진의 셰이더 파이프라인에 따라 달라진다. HLSL도 DXC를 통해 Vulkan용 SPIR-V로 컴파일할 수 있고, GLSL도 OpenGL 외의 환경에서 사용할 수 있지만, 대상별 바인딩과 내장 변수, 확장 지원을 다시 점검해야 한다.

## 셰이더를 포팅하는 순서

다른 언어로 옮길 때는 먼저 수학적 핵심을 분리하고, 그 뒤 파이프라인 연결을 맞춘다.

1. 거리 함수, 노이즈, 보간처럼 언어에 종속되지 않는 계산을 정리한다.
2. 버텍스 입력, 단계 간 값, 픽셀 출력의 선언을 대상 언어의 인터페이스로 다시 쓴다.
3. 유니폼·상수 버퍼·텍스처·샘플러·저장 버퍼를 대상 API의 바인딩에 맞춘다.
4. 행렬 곱 순서와 패킹, 클립 깊이, 화면 좌표 방향을 확인한다.
5. 대상 컴파일러와 프로파일에서 빌드하고, 컴파일 리플렉션이나 프레임 디버거로 실제 입력·출력과 자원 연결을 검사한다.

먼저 단색 출력이나 이 절의 단순한 고리처럼 결과를 쉽게 예측할 수 있는 셰이더로 인터페이스를 검증하면, 수식 오류와 바인딩 오류를 구분하기 쉽다. 이후 노이즈, 다중 패스, 컴퓨트 버퍼처럼 의존성이 많은 부분을 옮긴다.

## 이 절의 핵심

GLSL과 HLSL은 벡터 연산, 보간, 거리 함수, 노이즈 같은 GPU 수학을 공유하지만, 단계 입출력과 자원 연결 방식은 다르다. `mix`와 `lerp`처럼 직접 대응하는 문법도 있는 반면, `gl_Position`과 `SV_Position`, 샘플러와 텍스처 바인딩처럼 파이프라인과 호스트 코드까지 함께 바꿔야 하는 부분도 있다. 행렬 곱 순서, 메모리 배치, 깊이 범위는 언어 표기와 그래픽 API의 규약을 구분해 점검해야 한다. 포팅의 기준은 이름을 바꾸는 것이 아니라 수학적 의미와 파이프라인 계약을 모두 보존하는 것이다.
