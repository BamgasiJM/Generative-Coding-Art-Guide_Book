# 30.8 흐름 필드

흐름 필드는 공간의 각 위치에 벡터를 대응시킨다. 벡터를 따라 위치를 반복해서 갱신하면 입자 궤적이나 유선이 되고, 이미 정의한 색·명암 필드를 그 경로를 따라 운반할 수도 있다. 이 절에서는 같은 2D 벡터장을 따라 화면 표본에서 뒤로 이동한 뒤, 도착한 위치의 줄무늬 값을 읽는다. 이는 반-라그랑주(semi-Lagrangian) 방식의 역추적을 단순한 화면 예제로 적용한 것이다. p5.js는 몇 픽셀 간격의 표본마다 이 적분을 수행하고, GLSL은 각 프래그먼트에서 독립적으로 같은 과정을 계산한다.

이 예제는 입자 경로를 직접 선으로 그리는 대신 스칼라 무늬를 역추적해 화면에 재구성한다. 이렇게 하면 양쪽이 같은 시작 무늬와 적분 규칙을 사용하면서, Drawing API의 표본별 작업과 프래그먼트 셰이더의 픽셀별 작업을 비교할 수 있다.

## 벡터장과 역추적 규칙

위치 $\mathbf{p}=(x,y)$에서의 속도를 회전 벡터장으로 정의한다.

$$
\mathbf{F}(\mathbf{p}) = \omega(r)(-y,x), \qquad
r^2 = x^2+y^2, \qquad
\omega(r) = 0.8 + \frac{0.7}{1+4r^2}
$$

벡터는 원점을 중심으로 회전시키며, 회전 속도 $\omega$는 반지름에 따라 달라진다. 따라서 서로 다른 반지름의 점들은 다른 각도로 이동한다. 시작 위치의 줄무늬를 $S_0(\mathbf{p})=0.5+0.5\sin(18x)$로 두고, 화면의 각 위치 $\mathbf{p}$에서 벡터장을 거슬러 올라가 시작 위치 $\mathbf{q}$를 구한 뒤 $S_0(\mathbf{q})$를 출력한다.

역추적은 다음 미분 방정식을 고정된 단계 수만큼 적분하는 과정이다.

$$
\frac{d\mathbf{q}}{d\tau} = -\mathbf{F}(\mathbf{q}), \quad \mathbf{q}(0)=\mathbf{p}, \qquad
S(\mathbf{p}) = S_0(\mathbf{q}(T))
$$

적분에는 중점법(RK2)을 사용한다. 단계 길이가 $\Delta\tau$일 때 현재 위치에서 속도를 구하고, 역방향으로 반 단계 이동한 중간점의 속도로 전체 단계를 갱신한다. 이 예제에서는 전체 추적 시간 $T=2.0$, 단계 수 64, 단계 길이 $\Delta\tau=2/64$로 고정한다.

## p5.js: 표본마다 경로를 순차 적분하기

p5.js 코드는 캔버스를 4×4픽셀 블록으로 나누고 각 블록 중심을 시작점으로 삼는다. 각 중심에서 중점법으로 64단계를 역추적하고, 도착한 위치의 사인 줄무늬를 회색값으로 바꿔 블록을 채운다.

```javascript
function setup() {
  createCanvas(640, 480);
  pixelDensity(1);
  noLoop();
}

function draw() {
  const shortSide = Math.min(width, height);
  const sampleStep = 4;
  const traceSteps = 64;
  const dt = 2.0 / traceSteps;
  noStroke();
  background(14, 22, 34);

  for (let y = 0; y < height; y += sampleStep) {
    for (let x = 0; x < width; x += sampleStep) {
      const sampleX = x + sampleStep * 0.5;
      const sampleY = y + sampleStep * 0.5;
      let qx = (sampleX - width * 0.5) / shortSide;
      let qy = (height * 0.5 - sampleY) / shortSide;

      for (let step = 0; step < traceSteps; step++) {
        const r2 = qx * qx + qy * qy;
        const omega = 0.8 + 0.7 / (1.0 + 4.0 * r2);
        const velocityX = -omega * qy;
        const velocityY = omega * qx;
        const midX = qx - 0.5 * dt * velocityX;
        const midY = qy - 0.5 * dt * velocityY;

        const midR2 = midX * midX + midY * midY;
        const midOmega = 0.8 + 0.7 / (1.0 + 4.0 * midR2);
        qx -= dt * (-midOmega * midY);
        qy -= dt * (midOmega * midX);
      }

      const value = 0.5 + 0.5 * Math.sin(18.0 * qx);
      fill(value * 255);
      rect(x, y, sampleStep, sampleStep);
    }
  }
}
```

각 표본의 적분 단계는 이전 단계의 위치에 의존하므로 한 경로 안에서는 순서대로 계산해야 한다. 하지만 한 블록 중심에서 시작하는 경로와 다른 블록 중심에서 시작하는 경로 사이에는 의존성이 없다. JavaScript는 예제처럼 바깥 루프에서 표본을 순회하고 안쪽 루프에서 그 표본의 궤적을 차례로 추적한다.

좌표는 짧은 변을 1로 정규화하고 수학적 y축이 위로 증가하도록 바꿨다. 따라서 캔버스 크기가 바뀌어도 벡터장의 공간 단위와 줄무늬 간격이 같은 기준을 따른다. `sampleStep = 4`는 계산과 그리기 호출 수를 줄이는 대신 4×4 블록의 거친 표본을 만든다.

## GLSL: 프래그먼트별로 같은 궤적 계산하기

프래그먼트 셰이더에서도 한 표본의 64개 단계를 순차적으로 처리한다. 다만 각 프래그먼트는 자기 화면 위치에서 독립적으로 시작하므로, GPU는 많은 프래그먼트의 궤적 계산을 병렬로 진행할 수 있다.

```glsl
#version 460 core

uniform vec4 uViewport;

layout(location = 0) out vec4 outColor;

vec2 flow(vec2 p) {
    float omega = 0.8 + 0.7 / (1.0 + 4.0 * dot(p, p));
    return omega * vec2(-p.y, p.x);
}

vec2 backtrace(vec2 position) {
    const int TRACE_STEPS = 64;
    const float DT = 0.03125;
    vec2 q = position;

    for (int step = 0; step < TRACE_STEPS; ++step) {
        vec2 velocity = flow(q);
        vec2 midpoint = q - 0.5 * DT * velocity;
        q -= DT * flow(midpoint);
    }

    return q;
}

void main() {
    vec2 size = uViewport.zw;
    vec2 pixel = gl_FragCoord.xy - uViewport.xy;
    float shortSide = min(size.x, size.y);
    vec2 p = (pixel - 0.5 * size) / shortSide;

    vec2 sourcePosition = backtrace(p);
    float value = 0.5 + 0.5 * sin(18.0 * sourcePosition.x);
    outColor = vec4(vec3(value), 1.0);
}
```

호스트는 실제 프레임버퍼 픽셀 단위의 `(x, y, width, height)`를 `uViewport`로 전달하고 전체 화면을 덮는 도형을 렌더링한다. GLSL의 `DT`는 p5.js의 `2.0 / 64`와 같은 값이다. `gl_FragCoord`의 y축은 위쪽으로 증가하므로 p5.js 코드처럼 화면 y를 뒤집어 같은 공간 좌표를 얻는다. JavaScript는 일반적으로 배정밀도 수를 쓰고 셰이더의 `float`는 단정밀도이므로, 같은 적분 규칙과 횟수라도 긴 누적 계산의 마지막 값에는 작은 차이가 날 수 있다. 이 GLSL은 프래그먼트 셰이더에서 계산한 결과를 직접 화면색으로 출력한다.

## 순차성 안의 병렬성

| 비교 항목 | p5.js | GLSL 프래그먼트 셰이더 |
| --- | --- | --- |
| 시작 위치 | 4×4 블록의 중심 | 각 프래그먼트의 픽셀 위치 |
| 한 경로의 계산 | 64단계를 순서대로 적분 | 같은 64단계를 순서대로 적분 |
| 여러 경로의 배치 | JavaScript가 표본 루프를 순회 | 많은 프래그먼트가 독립적으로 실행 |
| 결과 기록 | 한 값으로 4×4 사각형을 채움 | 프래그먼트마다 색을 기록 |
| 주요 비용 요인 | 표본 수 × 적분 단계 수와 도형 명령 | 프래그먼트 수 × 적분 단계 수와 벡터장 평가 비용 |

GPU가 한 경로의 시간 단계를 마음대로 재배열하는 것은 아니다. 다음 위치가 이전 위치에서 나오므로 각 경로의 적분은 여전히 순차적이다. 병렬 처리는 서로 다른 화면 위치나 입자 씨앗에 해당하는 경로들 사이에서 일어난다. 반대로 CPU도 스레드나 작업 큐를 이용해 여러 씨앗을 병렬 처리할 수 있으므로, 차이를 CPU와 GPU라는 이름만으로 단정하지 말고 실제 실행 구조를 살펴야 한다.

이 예제는 p5.js가 4픽셀 간격으로 표본화하므로, GLSL의 픽셀별 결과보다 거칠고 총 경로 수도 적다. `sampleStep`을 1로 줄이면 표본 밀도는 화면 픽셀과 가까워지지만 640×480에서 약 30만 개의 경로를 각각 64단계 적분해야 한다. GLSL 역시 전체 화면의 각 프래그먼트에서 64단계를 수행하므로 높은 해상도에서는 계산량이 크다. 해상도, 단계 수, 표본 간격을 함께 고정하지 않으면 성능이나 품질 비교는 공정하지 않다.

중점법은 한 단계마다 벡터장을 두 번 평가한다. 단계를 너무 크게 잡으면 수치 오차가 커지고, 너무 작게 잡으면 계산량이 증가한다. 이 회전 벡터장은 이론상 반지름을 보존하지만 수치 적분에서는 작은 드리프트가 생길 수 있다. 두 구현에서 적분 방식과 단계 수를 맞추면 오차의 성격을 비교할 수 있으며, 긴 궤적이나 강하게 변하는 장에서는 더 작은 단계나 고차 적분법이 필요할 수 있다.

## 이 절의 핵심

흐름 필드의 각 궤적은 이전 위치에 의존하므로 시간 단계는 순차적으로 계산되지만, 서로 다른 시작점의 궤적은 독립적이다. p5.js는 표본 위치를 순회해 경로를 적분하고 Drawing API로 결과를 기록하며, GLSL 프래그먼트 셰이더는 각 픽셀에서 같은 적분을 수행한다. 차이를 비교할 때는 벡터장, 적분법, 시간 간격, 단계 수, 표본 밀도를 함께 맞춰야 한다.
