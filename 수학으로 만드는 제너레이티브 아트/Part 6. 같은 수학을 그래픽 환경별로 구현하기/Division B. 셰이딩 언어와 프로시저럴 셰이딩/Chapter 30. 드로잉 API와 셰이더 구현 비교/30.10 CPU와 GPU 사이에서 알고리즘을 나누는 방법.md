# 30.10 CPU와 GPU 사이에서 알고리즘을 나누는 방법

CPU와 GPU의 작업 분담은 코드를 어느 언어로 작성했는가만으로 결정되지 않는다. 먼저 알고리즘을 입력 준비, 반복 계산, 상태 갱신, 결과 렌더링처럼 의미 있는 단계로 나누고, 각 단계가 어떤 데이터에 의존하는지 살핀다. 독립적인 계산을 많이 만들 수 있는지, 결과를 다음 단계로 얼마나 자주 옮겨야 하는지, 사용자가 기다리는 동안 어떤 작업이 끝나야 하는지가 실제 배치에 영향을 준다.

목표는 모든 계산을 GPU로 옮기는 것이 아니다. 병목이 있는 계산을 그 데이터가 이미 머무는 위치에서 효율적으로 수행하고, CPU와 GPU 사이의 왕복과 동기화를 필요한 만큼으로 제한하는 것이다. Drawing API와 셰이더는 CPU와 GPU를 가르는 단순한 두 상자가 아니며, API 호출이 GPU에 제출될 수도 있고 셰이더도 렌더러나 프레임워크의 관리 아래 실행된다.

## 먼저 의존성과 병렬 단위를 찾기

알고리즘의 반복 횟수보다 중요한 질문은 “한 항목의 다음 계산이 무엇에 의존하는가?”이다. 다음 유형을 구별하면 어떤 수준에서 병렬화할 수 있는지 보인다.

| 계산 구조 | 예 | 병렬화 가능성 | 주의점 |
| --- | --- | --- | --- |
| 독립적인 위치 평가 | 각 픽셀의 색, 마스크, 노이즈 | 위치마다 계산이 독립적이어서 프래그먼트 단위 병렬화에 적합 | 모든 픽셀에서 같은 복잡한 계산을 하면 해상도에 비례해 비용이 증가 |
| 독립적인 개체 갱신 | 각 입자의 힘과 위치 계산 | 입자별 작업을 나란히 실행할 수 있음 | 각 입자의 시간 단계는 이전 상태에 의존해 순서가 남음 |
| 순차적 경로 추적 | 유선·궤적의 다음 위치 계산 | 경로 하나의 단계는 순차적이지만 여러 시작점의 경로는 독립적 | 경로 길이와 종료 조건이 크게 다르면 실행 효율이 낮아질 수 있음 |
| 전체 데이터 집계 | 평균, 히스토그램, 최대값 | 부분 결과를 병렬 계산한 뒤 단계적으로 결합 가능 | 한 값을 여러 실행 항목이 동시에 갱신하면 경쟁 상태와 동기화가 생김 |
| 이웃 데이터 의존 | 입자 충돌, 셀 오토마타, 주변 입자 힘 | 타일·격자·분할 자료구조로 국소 계산을 묶을 수 있음 | 메모리 접근과 경계 교환, 단계 사이의 동기화가 중요 |

예를 들어 픽셀마다 같은 노이즈 함수만 평가한다면 픽셀들은 서로 독립적이다. 반면 한 입자의 위치를 64단계 적분할 때 12번째 위치는 11번째 위치를 알아야 하므로 한 경로 안의 단계는 임의로 병렬 실행할 수 없다. 다만 여러 입자의 현재 위치가 서로 독립적이라면 입자 간 병렬 처리는 가능하다. “알고리즘 전체가 순차적” 또는 “GPU는 모든 일을 병렬로 한다”는 식으로 뭉뚱그리지 말고, 독립성이 있는 축을 찾아야 한다.

## 어디에서 나눌지 결정하기

대체로 CPU는 입력·상태·자원·작업 순서를 관리하고, GPU는 큰 데이터 집합에 반복 적용되는 계산을 처리한다. 이것은 출발점이지 고정 법칙은 아니다. 어떤 작업이 작은지, 데이터가 어디에 있는지, 결과를 어느 단계에서 소비하는지에 따라 달라진다.

| 조건 | 우선 검토할 선택 | 이유 |
| --- | --- | --- |
| 항목 수가 적고 매 항목의 분기와 제어 흐름이 복잡함 | CPU 계산 | 작업 제출과 데이터 준비 비용이 계산 자체보다 커질 수 있음 |
| 같은 수식이 수만 개 이상의 픽셀·입자·정점에 반복됨 | GPU 셰이더 또는 컴퓨트 작업 | 많은 독립 실행 항목을 처리하는 구조와 잘 맞음 |
| 데이터가 이미 렌더 타깃이나 GPU 버퍼에 있음 | GPU에서 계속 계산 | CPU로 가져왔다가 다시 보내는 왕복을 피할 수 있음 |
| 결과를 즉시 사용자 인터페이스나 복잡한 로직에 사용해야 함 | CPU 또는 지연을 허용한 readback | GPU 결과를 CPU가 읽으려면 동기화와 복사 비용이 발생할 수 있음 |
| 계산이 렌더 파이프라인의 특정 결과와 결합됨 | 해당 파이프라인 셰이더 단계 | 중간 결과를 별도 버퍼로 옮기지 않고 다음 단계로 넘길 수 있음 |
| 셰이딩 위치의 재질 반응이 목적임 | 렌더러의 재질 시스템 또는 OSL | 렌더러가 조명·표면 평가와의 연결을 관리함 |

GPU에 보내는 코드가 짧아 보여도 준비와 전달이 공짜는 아니다. 반대로 CPU 쪽 루프가 많아 보이더라도 그래픽 프레임워크가 도형들을 한꺼번에 모아 GPU에서 래스터화할 수 있다. 특히 p5.js의 드로잉 API와 GLSL 셰이더를 비교할 때 “p5.js는 CPU, GLSL은 GPU”라고 바로 등치하지 않는다. API 호출을 만드는 코드의 위치, 그래픽 백엔드가 실제로 처리하는 방식, 중간 데이터의 위치를 따로 확인한다.

## 분할 경계를 데이터 흐름에 맞추기

좋은 분할은 계산 단위를 나누는 데서 끝나지 않고 결과가 다음 소비자에게 자연스럽게 전달되도록 만든다. 가능하면 한 프레임에서 CPU와 GPU 사이를 여러 번 오가지 않고, 큰 덩어리의 데이터를 한 방향으로 보내거나 GPU 안에 유지한다.

| 단계 | CPU가 맡기 쉬운 일 | GPU가 맡기 쉬운 일 |
| --- | --- | --- |
| 입력과 준비 | 마우스·키보드 입력, 매개변수 갱신, 초기 입자·기하 생성 | 이미 GPU에 있는 텍스처·버퍼의 형식 변환이나 전처리 |
| 반복 계산 | 소수의 복잡한 객체, 가변적인 분기와 작업 스케줄 | 많은 픽셀·정점·입자의 동일한 수식 평가 |
| 상태 유지 | 디버깅·저장·사용자 로직이 즉시 읽어야 하는 상태 | 프레임마다 이어지는 대규모 입자·격자 상태 |
| 최종 표현 | API로 장면과 드로잉 명령 구성 | 이미지·버퍼 결과를 렌더하거나 정점 입력으로 사용 |
| 관찰·저장 | 화면 캡처, 파일 기록, 결과 분석 | 표시나 후속 셰이더 계산에 필요한 중간 텍스처·버퍼 유지 |

예를 들어 CPU가 매 프레임 입자 위치를 만들고 GPU로 업로드한 뒤, GPU가 그 입자를 그리고, 픽셀 결과를 다시 CPU로 읽어 분석하는 파이프라인은 데이터 왕복이 반복된다. 데이터가 렌더링에만 필요하다면 GPU 버퍼에서 상태를 갱신하고 그 버퍼를 바로 그리는 편이 더 자연스러울 수 있다. 반대로 사용자가 매 프레임 모든 입자 좌표를 편집하거나 저장해야 한다면 CPU 상태가 단순한 설계일 수 있다.

GPU에 유지되는 반복 상태를 갱신할 때는 읽기와 쓰기의 경계를 분명히 한다. 한 단계가 전체 항목의 이전 상태를 읽으면서 새 상태를 기록한다면 입력 버퍼와 출력 버퍼를 따로 두고 다음 단계에서 역할을 바꾸는 핑퐁 방식을 사용할 수 있다. 같은 버퍼를 동시에 읽고 쓰면 실행 순서에 따라 결과가 달라지는 경쟁 상태가 생길 수 있다. 단계 사이에 메모리 장벽이나 API 수준의 동기화가 필요한지는 사용 중인 그래픽 API와 리소스 접근 방식에 맞춰 확인한다.

컴퓨트 셰이더가 만든 버퍼를 그리기 단계에서 읽는 경우도 마찬가지다. 디스패치가 끝났다는 사실과 다음 명령이 그 결과를 안전하게 읽을 수 있다는 사실은 API가 정의한 동기화 관계에 따라 달라진다. 프레임워크가 장벽을 추상화할 수도 있으므로, 무조건 장벽을 추가하거나 생략하지 말고 해당 API의 리소스 전환 규칙을 따른다. CPU가 결과를 읽어야 하는 경우에는 readback이 완료될 때까지 대기해야 하며, 그 대기가 매 프레임의 병목이 되지 않는지도 측정한다.

## 전송과 동기화까지 포함해 비용 계산하기

성능을 비교할 때 커널이나 셰이더 안의 계산 시간만 재면 전체 비용을 놓친다. end-to-end 실행에는 적어도 다음 항목이 관여한다.

$$
T_{\text{end-to-end}} =
T_{\text{prepare}} + T_{\text{transfer}} + T_{\text{dispatch}} +
T_{\text{compute}} + T_{\text{sync/readback}} + T_{\text{consume}}
$$

이 식은 비용 항목을 빠뜨리지 않기 위한 장부이지, 각 항목이 언제나 순서대로 모두 더해진다는 뜻은 아니다. CPU 준비, GPU 계산, 전송은 파이프라인에서 겹쳐 실행될 수 있다. 실제 프레임 시간은 의존 관계의 임계 경로와 대기 시간에 의해 결정된다. 데이터가 이미 GPU에 있다면 매 프레임의 업로드 항목은 사라질 수 있고, readback을 하지 않는 렌더링 경로에서는 CPU 대기 없이 다음 프레임을 준비할 수도 있다.

작업 항목이 적을 때는 GPU 명령 제출과 동기화 비용이 산술 계산보다 클 수 있다. 큰 데이터를 한 번 보내고 여러 단계에서 재사용하면 이 비용을 나눠 부담할 수 있지만, 작은 데이터를 매 프레임 보내고 곧바로 읽으면 GPU의 처리량 이점이 사라질 수 있다. 따라서 다음 항목을 기록한다.

- CPU에서 입력을 만들고 변환하는 시간
- 업로드·readback 등 CPU와 GPU 사이의 데이터 크기와 빈도
- 드로잉 호출·디스패치 횟수와 상태 전환
- 셰이더 또는 커널의 실제 GPU 실행 시간
- 동기화로 CPU나 GPU가 기다리는 시간
- 동일한 해상도와 품질에서 측정한 최종 프레임 시간

셰이더 호출을 제출한 직후 CPU 시계로 시간을 재면 GPU가 실제 계산을 끝내기 전의 제출 시간만 측정할 수 있다. GPU 타임스탬프 쿼리나 API가 제공하는 프로파일러를 사용하고, 결과를 읽기 위해 매번 강제로 동기화하면 원래 없던 대기 비용을 측정에 끼워 넣을 수 있으므로 측정 방법도 주의한다. 셰이더 컴파일·파이프라인 생성, 첫 프레임의 리소스 할당, 수직 동기화가 포함된 실행과 steady-state 반복 실행도 구분한다.

## 흐름 필드에 적용해 보기

30.8의 역추적 예제에서는 각 화면 표본이 64단계의 중점법 적분을 수행한다. 단계 내부는 순차적이지만 서로 다른 표본 위치의 경로는 독립적이다. 이 구조를 입자 시뮬레이션으로 확장하면 다음과 같이 나눌 수 있다.

| 작업 | 소수의 입자 또는 학습 단계 | 대규모 실시간 입자 작품 |
| --- | --- | --- |
| 시드와 매개변수 설정 | CPU에서 생성·수정 | CPU가 입력과 매개변수를 갱신해 GPU에 전달 |
| 입자 한 프레임 갱신 | CPU에서 적분하고 검증 | 컴퓨트 셰이더에서 입자별로 적분 |
| 프레임 간 입자 상태 | CPU 배열에 보관 | GPU 버퍼에 유지하고 입력·출력 버퍼를 교환 |
| 화면 표시 | p5.js 드로잉 API로 경로·점 그리기 | GPU 버퍼를 정점 입력으로 연결해 인스턴싱하거나 점으로 렌더링 |
| 위치를 CPU에서 분석 | 바로 읽을 수 있음 | 필요한 시점에만 비동기 readback 또는 요약값 전송 |

GPU 버전에서도 한 입자의 시간 단계가 자동으로 병렬화되는 것은 아니다. 각 입자 작업은 자신의 여러 단계를 순서대로 계산하지만, 많은 입자 작업이 서로 병렬로 실행된다. 입자끼리 서로의 위치를 읽어 충돌이나 힘을 계산한다면 이웃 탐색, 읽기·쓰기 상태 분리, 동기화가 추가되어 단순한 독립 입자 모델보다 복잡해진다. 반면 30.8처럼 각 화면 프래그먼트가 독립적인 역추적을 하는 화면 효과는 프래그먼트 셰이더로 직접 표현할 수 있으나, 화면 해상도와 추적 단계 수를 곱한 비용을 감당해야 한다.

OSL은 이 분할 표에서 임의의 프레임별 입자 작업을 사용자가 직접 디스패치하는 일반 컴퓨트 단계가 아니다. OSL을 사용할 때 계산 위치와 실행 방식은 렌더러의 셰이딩·조명 경로에 속하므로, 렌더러가 제공하는 지원과 리소스 경계를 따른다. 목적이 표면 재질의 반응이라면 OSL·재질 시스템을, 실시간 입자 상태 갱신이라면 호스트 계산이나 컴퓨트 셰이더를 검토하는 식으로 문제의 출력과 실행 경계를 먼저 맞춘다.

## 측정 가능한 기준 구현부터 시작하기

알고리즘을 나눌 때는 한 번에 전체 코드를 옮기기보다 다음 순서로 진행하면 결과 차이의 원인을 찾기 쉽다.

1. **기준 동작을 고정한다.** 작은 데이터로 단순한 CPU 구현을 만들고, 입력·초기 상태·난수 시드·매개변수·출력 규칙을 기록한다.
2. **독립성과 의존성을 표시한다.** 어떤 항목끼리 병렬 실행할 수 있는지, 한 항목의 반복 단계가 어떤 상태를 읽고 쓰는지 구분한다.
3. **표본과 정밀도를 정한다.** 좌표계, 해상도, 적분 단계, 허용 오차와 결정성 요구를 정해 구현 간 비교 기준을 만든다.
4. **측정으로 병목을 찾는다.** CPU 준비, 제출, 전송, GPU 계산, readback 중 실제 시간이 많이 드는 곳을 분리한다.
5. **데이터가 머무를 위치에 맞춰 분할한다.** 계산 코드를 옮길 때 가능한 한 큰 연속 작업 단위를 옮기고, 불필요한 왕복과 동기화를 줄인다.
6. **결과와 전체 시간을 다시 비교한다.** 화면 모양뿐 아니라 오차, 프레임 지연, 메모리 사용량, 입력 반응성까지 확인한다.

그래픽 결과가 비슷하다는 것만으로 계산이 동등하다고 단정하지 않는다. 같은 수식을 썼더라도 데이터 경합이나 누적 오차가 있을 수 있고, 더 빨라 보이는 셰이더도 측정에서 업로드와 동기화 시간이 빠졌을 수 있다. 반대로 계산 속도가 같더라도 GPU에 상태를 유지하면 CPU readback 없이 렌더링해 전체 응답성을 개선할 수 있다. 구현은 품질 기준과 전체 데이터 흐름을 만족하는지로 판단한다.

## 이 절의 핵심

CPU와 GPU 사이의 분할 기준은 반복문의 모양이 아니라 독립 계산의 수, 단계 간 데이터 의존성, 데이터가 머무는 위치, 전송과 동기화 비용이다. 한 궤적 안의 적분은 순차적이어도 여러 입자나 화면 표본은 병렬일 수 있다. GPU의 계산 시간만 보지 말고 준비·제출·전송·대기·결과 소비를 포함한 전체 경로를 측정하며, 작고 검증 가능한 기준 구현에서 점진적으로 옮긴다.
