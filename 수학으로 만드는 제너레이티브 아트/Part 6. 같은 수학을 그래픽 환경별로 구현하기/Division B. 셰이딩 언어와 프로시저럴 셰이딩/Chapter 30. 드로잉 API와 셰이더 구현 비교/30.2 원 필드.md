# 30.2 원 필드

원을 그리는 가장 간단한 방법은 드로잉 API의 원 도형 명령을 호출하는 것이다. 셰이더에서는 원을 도형 명령으로 제출하는 대신, 화면의 각 위치가 원의 안쪽인지 바깥쪽인지 판정하는 거리 필드를 계산할 수 있다. 두 방법은 같은 원형 영역을 만들지만, 하나는 도형을 요청하고 다른 하나는 정의역의 위치마다 함수를 평가한다.

원 중심을 $\mathbf{c}$, 계산 위치를 $\mathbf{p}$, 반지름을 $r$이라 하면 원의 부호 있는 거리 필드는 다음과 같다.

$$
d(\mathbf{p}) = \lVert \mathbf{p} - \mathbf{c} \rVert - r
$$

`d < 0`이면 내부, `d = 0`이면 경계, `d > 0`이면 외부다. 이 절에서는 캔버스의 중심에 짧은 변 길이의 25%를 반지름으로 하는 원을 그리고, 두 방식의 좌표와 출력 과정을 맞춰 비교한다.

## 드로잉 API: 도형을 제출하기

p5.js의 `circle(x, y, diameter)`는 중심과 지름을 받아 채워진 원 도형을 그린다. 다음 예제는 640×480 캔버스에서 지름이 240픽셀인 원을 만든다.

```javascript
function setup() {
  createCanvas(640, 480);
  noStroke();
}

function draw() {
  const radius = Math.min(width, height) * 0.25;

  background(14, 22, 34);
  fill(236, 92, 46);
  circle(width * 0.5, height * 0.5, radius * 2.0);
}
```

프로그램은 원의 중심과 지름, 채움색을 도형 API에 전달한다. 원의 경계를 어떤 삼각형이나 래스터 규칙으로 표현할지는 캔버스와 그래픽 백엔드가 처리한다. 코드에는 각 픽셀의 거리 계산이나 내부·외부 판정이 드러나지 않는다.

## 프래그먼트 셰이더: 위치마다 거리 평가하기

GLSL에서는 프래그먼트의 위치를 뷰포트 중심 기준 좌표로 바꾸고, 각 위치에서 원의 거리를 계산한다. 여기서 `uViewport`는 `(x, y, width, height)` 형식의 프레임버퍼 픽셀 단위 뷰포트이며, `uCenterPx`도 뷰포트 왼쪽 아래를 원점으로 한 픽셀 좌표다. 셰이더는 전체 화면을 덮는 사각형이나 삼각형을 그린다는 전제다.

```glsl
#version 460 core

uniform vec4 uViewport;
uniform vec2 uCenterPx;
uniform vec3 uBackground;
uniform vec3 uCircleColor;
uniform float uRadius;

layout(location = 0) out vec4 outColor;

float circleDistance(vec2 p, float radius) {
    return length(p) - radius;
}

void main() {
    vec2 size = uViewport.zw;
    vec2 pixel = gl_FragCoord.xy - uViewport.xy;
    float shortSide = min(size.x, size.y);

    vec2 p = (pixel - 0.5 * size) / shortSide;
    vec2 center = (uCenterPx - 0.5 * size) / shortSide;
    float d = circleDistance(p - center, uRadius);

    float aa = max(fwidth(d), 1e-5);
    float mask = 1.0 - smoothstep(-aa, aa, d);
    vec3 color = mix(uBackground, uCircleColor, mask);
    outColor = vec4(color, 1.0);
}
```

호스트 프로그램은 전체 화면 도형을 제출하고, 뷰포트와 중심 좌표, 반지름, 색상 유니폼을 설정해야 한다. `uRadius`는 짧은 변을 1로 본 정규화 단위이므로 `0.25`를 넣으면 p5.js 예제와 같은 반지름이 된다. `uCenterPx`에 뷰포트의 절반 크기를 넣으면 두 원의 중심도 일치한다. p5.js는 왼쪽 위가 원점이고 y축이 아래로 증가하지만, `gl_FragCoord`는 일반적으로 뷰포트 왼쪽 아래를 원점으로 한다. 중심 밖의 위치를 비교할 때는 y좌표를 변환해야 한다.

`fwidth(d)`는 프래그먼트 주변에서 거리값이 화면상 얼마나 변하는지 추정한다. 그 값을 경계 전이 폭으로 사용하면 화면 크기와 배율에 반응하는 가장자리 마스크를 만들 수 있다. `smoothstep()`의 전이가 없다면 `d < 0`을 바로 판정할 수 있지만, 경계가 픽셀 사이를 지날 때 계단 현상이 두드러질 수 있다. 드로잉 API의 원은 백엔드가 가장자리 피복을 처리하고, 셰이더 필드는 수학적 거리에서 마스크를 만들어 이를 해결한다.

## 같은 결과, 다른 중간 표현

두 코드의 입력과 출력 단위를 정리하면 비교 조건이 분명해진다.

| 항목 | p5.js 원 도형 | GLSL 원 필드 |
| --- | --- | --- |
| 캔버스·뷰포트 | 640×480 | 호스트가 설정한 동일한 크기 |
| 중심 | `(width/2, height/2)` | 뷰포트 픽셀 좌표 `(width/2, height/2)` |
| 반지름 | 짧은 변의 `0.25`배, 픽셀 단위 | 짧은 변으로 나눈 `0.25` |
| 도형의 표현 | 중심과 지름을 가진 원 명령 | 위치별 거리 `length(p-center)-radius` |
| 색 결정 | `fill()` 상태가 원 도형에 적용 | 각 프래그먼트의 마스크로 두 색을 혼합 |

동일한 화면 크기와 중심, 반지름을 사용하면 윤곽은 같아야 한다. 그래도 가장자리 픽셀은 같지 않을 수 있다. p5.js의 래스터화와 GLSL의 `fwidth()` 기반 전이는 서로 다른 표본화 규칙을 사용하며, 색상 공간과 출력 변환도 차이를 만든다. 정확한 픽셀 일치가 목표라면 안티앨리어싱, 프레임버퍼 해상도, 색 관리까지 함께 맞춰야 한다.

## 어느 표현이 유리한가

하나의 채워진 원을 그리는 일에는 도형 API가 직접적이다. 중심과 크기, 스타일만 지정하면 되고, 별도의 화면 좌표 변환이나 픽셀별 거리 계산을 작성할 필요가 없다. 반면 거리 필드는 원의 안팎뿐 아니라 경계까지의 거리도 제공하므로, 원형 윤곽선·글로우·부드러운 마스크·여러 형태의 합성처럼 경계 주변의 값을 계속 활용할 때 편리하다. SDF로 원을 다른 영역과 조합하는 방식은 30.6에서 이어진다.

어느 쪽이 더 빠르다고 일반화해서는 안 된다. 원 도형은 보통 원이 차지하는 영역을 래스터화하지만, 이 셰이더 예제는 뷰포트 전체를 덮는 도형의 프래그먼트에서 거리를 평가한다. 반대로 셰이더는 많은 독립 위치를 병렬로 처리할 수 있다. 실제 비용은 도형 개수, 화면 점유율, 구현 백엔드, 해상도에 좌우되므로 목표 환경에서 측정해야 한다.

이 예제의 GLSL은 화면 전체를 대상으로 하는 프래그먼트 구현이다. 같은 거리 공식은 HLSL에서도 사용할 수 있지만 입력·출력 시맨틱과 유니폼 전달 방식은 다르다. OSL에서는 해당 식을 화면 픽셀마다 실행하는 것이 아니라 표면의 셰이딩 위치에서 평가하고, 결과를 재질 데이터나 클로저에 연결한다. 수학 함수가 같아도 셰이더 단계와 결과의 의미가 같지는 않다.

## 이 절의 핵심

드로잉 API는 원의 중심과 지름을 도형 명령으로 제출하고, 프래그먼트 셰이더는 각 위치에서 `length(p-center)-radius`를 평가해 원형 마스크를 만든다. 같은 화면 결과를 비교하려면 좌표 원점, y축 방향, 반지름 단위, 뷰포트와 가장자리 처리를 맞춰야 한다. 단순한 원은 도형 API가 간결하고, 거리값 자체를 마스크·윤곽·합성에 재사용할 때는 원 필드가 유리하다.
