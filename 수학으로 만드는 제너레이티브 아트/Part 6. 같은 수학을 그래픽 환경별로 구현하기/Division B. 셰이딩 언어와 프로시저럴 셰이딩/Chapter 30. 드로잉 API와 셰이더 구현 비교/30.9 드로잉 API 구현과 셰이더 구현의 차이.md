# 30.9 드로잉 API 구현과 셰이더 구현의 차이

30.2부터 30.8까지는 원, 파동, 격자, 방사형 무늬, SDF, 노이즈, 흐름 필드를 p5.js와 GLSL로 나란히 구성했다. 두 방식은 같은 좌표와 수학식을 공유할 수 있지만, 프로그램이 무엇을 지정하고 계산 결과를 어디에 전달하는지는 다르다. 이 차이는 코드 문법보다 **계산의 입력 단위**, **결과의 의미**, **그 결과를 소비하는 렌더링 단계**에서 선명해진다.

## 무엇을 작성하고 무엇을 받는가

드로잉 API에서는 프로그램이 선·원·경로·이미지처럼 그릴 요소와 스타일을 지정한다. 셰이더에서는 정점, 프래그먼트, 컴퓨트 작업 또는 렌더러의 셰이딩 위치가 입력으로 주어지고, 그 위치에서 계산한 값을 정해진 출력으로 전달한다.

| 구현 방식 | 코드가 주로 지정하는 것 | 계산이 적용되는 단위 | 결과가 전달되는 곳 |
| --- | --- | --- | --- |
| p5.js 드로잉 API | `circle()`, `line()`, 경로와 채움·선 스타일 | 프로그램이 구성한 도형과 경로 | 캔버스의 래스터화 결과 |
| GLSL·HLSL 정점 셰이더 | 정점 위치와 보간할 속성의 변환 | 메시의 정점 | 클립 공간 위치와 다음 파이프라인 단계의 입력 |
| GLSL 프래그먼트·HLSL 픽셀 셰이더 | 프래그먼트 위치에서의 색·마스크·깊이 계산 | 래스터화된 프래그먼트 | 프레임버퍼나 렌더 타깃의 출력 첨부물 |
| GLSL·HLSL 컴퓨트 셰이더 | 작업 항목별 데이터 변환과 버퍼 접근 | 디스패치된 작업 항목 | 이미지나 버퍼 등 명시한 리소스 |
| OSL | 표면·볼륨의 좌표와 재질 계산 | 렌더러가 셰이딩하는 표면 또는 볼륨 위치 | 재질·조명 계산에 해석되는 값이나 클로저 |

표의 차이는 수행 위치와 결과 역할에 관한 것이지, 언어 이름만으로 CPU 또는 GPU 사용을 결정하는 표가 아니다. p5.js 같은 프레임워크는 그리기 명령을 그래픽 백엔드에 제출할 수 있고, GLSL·HLSL은 여러 셰이더 단계에서 실행되며, OSL의 실행 방식은 렌더러와 설정에 따른다. 특히 프래그먼트 셰이더는 화면 픽셀에 대응하는 출력을 만들지만, 모든 셰이더가 픽셀 색을 출력하는 것은 아니다.

## 같은 수학식도 연결 지점이 다르다

예를 들어 원의 경계를 $d(\mathbf{p})=\lVert\mathbf{p}-\mathbf{c}\rVert-r$로 표현할 수 있다. 드로잉 API에서는 중심과 지름을 가진 원 도형을 제출한다. 프래그먼트 셰이더에서는 현재 화면 위치에서 $d$를 계산하고, 그 부호를 색 마스크나 윤곽선으로 바꾼다. 계산식은 닮았어도 전자는 도형 명령이고 후자는 화면 위치별 필드 평가다.

OSL에서는 같은 거리나 파동 함수를 화면 전체의 픽셀색으로 직접 기록하는 대신, 렌더러가 제공하는 표면 위치와 좌표 속성을 바탕으로 재질 입력을 계산한다. 예를 들어 거리값이나 $\sin(kx+\phi)$의 결과를 확산 반사 클로저의 색이나 방출 클로저의 강도로 연결할 수 있지만, 최종 픽셀은 카메라 광선, 표면 방향, 조명, 재질 응답, 렌더러의 샘플링을 거쳐 만들어진다. 따라서 OSL에서 비슷한 원무늬를 얻더라도 이는 프래그먼트 셰이더와 동일한 화면 공간 구현이 아니라, 표면에 붙은 프로시저럴 재질이다. OSL의 표면 좌표와 클로저, Blender의 노드와 역할 분담은 29장에서 다룬 내용을 따른다.

## 세 방식은 서로 대체재만은 아니다

드로잉 API와 셰이더를 완전히 양자택일로 보는 것은 실제 그래픽 프로그램의 구조와 맞지 않는다. 프로그램은 창, 입력, 장면 상태, 메시와 그리기 순서를 관리하면서 일부 렌더 단계에 GLSL 또는 HLSL 셰이더를 끼워 넣을 수 있다. 이때 API는 무엇을 언제 그릴지 구성하고 셰이더는 지정된 단계에서 그 요소의 정점이나 프래그먼트를 어떻게 계산할지 맡는다.

OSL도 렌더러의 장면·재질 시스템과 함께 사용된다. 모델과 카메라, 광원은 렌더러가 관리하고 OSL은 셰이딩 위치에서 표면 반응을 구성한다. 이 구조에서는 드로잉 API가 만드는 2D 화면, GPU 파이프라인의 프래그먼트 출력, OSL이 제공하는 재질 응답을 같은 종류의 출력으로 취급하지 않는다.

| 필요를 먼저 묻기 | 자연스러운 출발점 | 이유와 주의점 |
| --- | --- | --- |
| 어떤 선·도형·경로를 어디에 그릴 것인가? | 드로잉 API | 화면 요소와 장면 구조를 직접 다루기 쉽다. |
| 화면의 각 위치에 따라 색·마스크·효과가 어떻게 달라질 것인가? | 프래그먼트 셰이더 | 화면 공간 필드를 위치별로 계산해 출력할 수 있다. |
| 정점 위치나 메시 속성을 파이프라인에서 어떻게 바꿀 것인가? | 정점·기하·테셀레이션 셰이더 등 해당 단계 | 계산 결과가 다음 그래픽스 단계의 입력으로 이어진다. |
| 표면 위치와 조명에 따라 재질이 어떻게 반응할 것인가? | OSL 또는 렌더러의 재질 시스템 | 셰이딩 결과를 렌더러의 재질·조명 계산에 연결한다. |
| 다수의 독립 데이터 항목을 갱신할 것인가? | 컴퓨트 셰이더 또는 호스트 측 계산 | 데이터 의존성과 출력 리소스를 보고 선택해야 한다. |

여기서 선택은 독점적인 규칙이 아니다. 파동 경로를 API로 그리면서 셰이더로 색을 처리할 수도 있고, 셰이더가 만든 텍스처를 드로잉 API의 이미지로 사용할 수도 있다. 하나의 작품 안에서 각 계산에 적합한 표현을 조합하는 것이 일반적이다.

## 결과 비교에서 분리해야 할 것

같은 수학 규칙을 사용해도 결과 이미지가 픽셀 단위로 일치하지 않을 수 있다. 앞선 사례에서 보았듯이 경로의 정점 간격, 화면 좌표와 UV의 원점, 프레임버퍼 해상도, 안티앨리어싱, 부동소수점 정밀도, 색 공간과 출력 변환은 모두 차이를 만든다. OSL에서는 여기에 표면의 노멀과 조명, 재질의 산란·반사 응답, 렌더러의 샘플링이 더해진다.

따라서 비교 결과를 읽을 때는 다음 질문을 분리한다.

1. 두 구현이 같은 수학 함수와 매개변수를 사용하는가?
2. 그 함수는 어떤 좌표 영역과 표본 위치에서 평가되는가?
3. 반환값은 화면색, 마스크, 정점 데이터, 재질 파라미터 중 무엇인가?
4. 래스터화·조명·색 관리처럼 함수 바깥의 단계가 최종 결과에 어떻게 개입하는가?
5. 성능 비교라면 준비 비용, 평가 횟수, 데이터 이동, 출력 해상도까지 같은 조건인가?

이 질문을 나누면 수학 함수의 오류와 렌더링 파이프라인의 차이를 혼동하지 않는다. 픽셀색을 직접 만드는 GLSL 예제와 조명 아래 재질을 만드는 OSL 예제를 비교할 때도, 같은 RGB를 출력한다고 가정하기보다 출력의 의미부터 맞춰야 한다.

성능과 계산 위치는 문법만으로 결정할 수 없다. API가 호출을 모아 GPU에 제출할 수 있고, 셰이더는 각 실행 항목의 입력과 메모리 접근 방식에 따라 병목이 달라진다. CPU와 GPU 사이에서 실제 알고리즘의 단계를 나누고 측정하는 방법은 30.10에서 이어서 다룬다.

## 이 절의 핵심

드로잉 API는 그릴 그래픽 요소를 구성하고, GLSL·HLSL은 파이프라인의 정해진 단계에서 위치나 데이터를 계산하며, OSL은 렌더러의 표면·볼륨 셰이딩에 재질 응답을 제공한다. 같은 수학 함수를 옮길 수 있어도 입력의 좌표와 실행 단위, 결과의 의미는 달라질 수 있다. 이 역할을 구분한 뒤 각 구현을 조합하면, 도형·필드·셰이더·재질을 서로의 장점에 맞춰 사용할 수 있다.
