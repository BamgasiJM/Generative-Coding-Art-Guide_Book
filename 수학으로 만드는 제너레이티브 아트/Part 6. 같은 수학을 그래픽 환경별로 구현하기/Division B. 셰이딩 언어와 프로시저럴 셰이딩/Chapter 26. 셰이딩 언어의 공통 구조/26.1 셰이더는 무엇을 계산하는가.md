# 26.1 셰이더는 무엇을 계산하는가

셰이더(shader)는 그래픽스 파이프라인의 특정 지점에서 실행되어 값을 계산하는 작은 프로그램이다. 드로잉 API가 "이 원을 이 위치에 그려라"처럼 도형 명령을 쌓는 방식이라면, 셰이더는 "이 정점의 최종 위치는 무엇인가", "이 픽셀의 최종 색은 무엇인가", "이 표면점의 재질 반응은 어떠한가"를 계산한다.

따라서 셰이더를 이해하는 출발점은 특정 언어의 문법이 아니라 다음 질문이다.

> 이 실행 지점은 어떤 입력을 받고, 어떤 값을 출력해야 하는가?

프래그먼트 셰이더의 가장 단순한 형태는 화면 또는 도형 위의 한 표본 위치에서 색 하나를 반환하는 함수로 생각할 수 있다.

$$
\mathbf{C}=F(\mathbf{p},t,\mathbf{u})
$$

여기서 $\mathbf{p}$는 위치나 UV 좌표, $t$는 시간, $\mathbf{u}$는 애플리케이션이 전달한 공통 파라미터다. GPU는 많은 표본 위치에서 이 함수를 병렬로 평가하고, 반환된 색을 프레임 버퍼에 기록한다.

```glsl
// GLSL 프래그먼트 셰이더의 개념 예시
vec3 colorAt(vec2 uv, float time) {
  float wave = 0.5 + 0.5 * sin(uv.x * 12.0 + time);
  return mix(vec3(0.05), vec3(0.9, 0.4, 0.2), wave);
}
```

위 함수는 한 위치의 색을 계산할 뿐이다. 화면 전체를 순회하는 `for each pixel` 반복문은 코드에 없다. 렌더러가 각 프래그먼트 또는 픽셀 후보에서 이 계산을 실행한다. 이것이 셰이더가 가진 핵심적인 사고 전환이다. 프로그램이 도형 목록을 돌며 화면에 명령을 보내는 대신, 각 실행 지점이 자기 입력값으로 결과를 계산한다.

## 셰이더의 계산 단위

"셰이더"는 하나의 고정된 종류의 프로그램을 뜻하지 않는다. 그래픽 파이프라인에서 어느 데이터를 처리하느냐에 따라 계산 단위와 출력이 달라진다.

| 셰이더의 역할 | 주된 입력 단위 | 대표 출력 | 제너레이티브 아트에서의 활용 |
| --- | --- | --- | --- |
| 버텍스 셰이더 | 메시의 정점 | 변환된 정점 위치·속성 | 기하 변형, 파도, 인스턴스 배치 |
| 프래그먼트/픽셀 셰이더 | 래스터화된 표면 또는 화면 위치 | 색, 알파, 깊이 | 거리 필드, 노이즈, 후처리, 재질 |
| 서피스 셰이더 | 렌더러가 표본화한 표면점 | 재질·빛 반응 | 절차적 질감, 거칠기, 범프 |
| 컴퓨트 셰이더 | 버퍼·텍스처의 일반 작업 항목 | 변경된 버퍼 값 | 입자, 격자 시뮬레이션, 대량 계산 |

각 단계의 세부 연결은 다음 절에서 다룬다. 지금은 셰이더가 실행되는 대상이 정점인지, 픽셀인지, 표면점인지, 일반 데이터 항목인지에 따라 입력과 출력의 의미가 달라진다는 점을 기억하면 충분하다.

## 셰이더는 위치에서 값을 평가한다

이 책에서 다룬 거리 함수, 노이즈, 파동, 좌표 변형, 대칭, 필드는 셰이더와 잘 맞는다. 이 규칙들은 대개 위치를 입력으로 받아 숫자·색·벡터를 반환하기 때문이다.

$$
v=n(\mathbf{p}),\qquad
d=\|\mathbf{p}-\mathbf{c}\|-r,\qquad
\mathbf{v}=G(\mathbf{p})
$$

프래그먼트 셰이더에서는 이 값들을 색으로 바꾼다. 예를 들어 거리 $d$를 마스크로 바꾸면 원을 그릴 수 있다.

```glsl
float circleMask(vec2 p, vec2 center, float radius, float edge) {
  float d = length(p - center) - radius;
  return 1.0 - smoothstep(-edge, edge, d);
}

void main() {
  float mask = circleMask(uv, vec2(0.5), 0.2, 0.002);
  vec3 color = mix(vec3(0.95), vec3(0.1, 0.2, 0.8), mask);
  // 환경별 문법으로 color를 최종 프래그먼트 색에 기록한다.
}
```

이 코드는 화면에 원 객체를 추가하지 않는다. 각 위치가 원 내부에 얼마나 가까운지를 계산하고, 그 결과로 색을 정한다. Part 2의 SDF, Part 3의 좌표 반복, Part 4의 노이즈 필드가 셰이더에서 자연스럽게 쓰이는 이유가 여기에 있다.

## 셰이더와 드로잉 명령의 차이

드로잉 API와 셰이더는 같은 이미지를 만들 수 있지만, 기본 질문이 다르다.

```text
# 드로잉 API의 관점
for each circle:
    drawCircle(center, radius, color)

# 셰이더의 관점
for each evaluated position:
    determine color from position and parameters
```

드로잉 API에서는 원이 개체이고, 그리기 순서와 블렌딩이 결과를 쌓는다. 셰이더에서는 위치가 개체에 가깝고, 그 위치가 여러 도형 또는 필드 중 어디에 속하는지 계산한다. 거리 함수의 최소값으로 두 원을 합성하는 방식은 이 차이를 잘 보여 준다.

$$
d_{union}=\min(d_1,d_2)
$$

셰이더는 도형을 추가하는 대신 함수를 조합한다. 물론 텍스처를 표본화하거나, 정점 버퍼를 처리하거나, 여러 번의 렌더 패스를 쌓는 방식으로 개체와 레이어의 개념도 사용할 수 있다. 다만 한 번의 셰이더 실행 안에서는 현재 입력 위치의 결과를 계산하는 관점이 중심이다.

## 병렬 실행과 독립성

프래그먼트 셰이더는 매우 많은 위치에서 동시에 실행될 수 있다. 그렇다고 각 픽셀이 서로 통신하며 순서대로 협력한다고 생각하면 안 된다. 일반적인 셰이더 실행은 다른 픽셀의 지역 변수에 직접 접근하지 못하며, 어떤 픽셀이 먼저 실행될지도 보장하지 않는다.

이 제약은 장점이기도 하다. 각 위치의 계산이 독립적이면 GPU는 대량의 작업을 효과적으로 병렬 처리할 수 있다. 노이즈, 거리 필드, 색상 보정, UV 타일링, 화면 후처리는 이런 독립 계산에 잘 맞는다.

```glsl
vec2 q = fract(uv * gridCount) - 0.5;
float d = length(q) - radius;
```

위 코드는 다른 픽셀의 값을 전혀 알 필요가 없다. 현재 `uv`만으로 격자 안의 원 패턴을 계산한다. 반대로 이전 프레임의 색, 이웃 픽셀의 값, 다른 입자의 위치가 필요하면 텍스처·버퍼·컴퓨트 셰이더 같은 명시적인 데이터 구조를 사용해야 한다. 피드백과 시뮬레이션은 단일 프래그먼트 셰이더의 범위를 넘어 여러 패스로 구성되는 이유가 여기에 있다.

## 입력은 어디에서 오는가

셰이더는 스스로 시간이나 마우스 위치를 알아내지 못한다. 필요한 입력은 그래픽 애플리케이션 또는 앞선 파이프라인 단계가 전달한다. 대표적인 입력은 다음과 같다.

| 입력 | 의미 | 예 |
| --- | --- | --- |
| 정점 속성 | 메시마다 다른 데이터 | 위치, UV, 법선, 색 |
| 보간된 값 | 정점 사이에서 계산된 값 | UV, 표면 위치, 법선 |
| 유니폼 | 실행 전체가 공유하는 값 | 시간, 해상도, 마우스, 파라미터 |
| 텍스처·버퍼 | 저장된 이미지 또는 데이터 | 이전 프레임, 노이즈 맵, 입자 데이터 |
| 내장 입력 | 파이프라인이 제공하는 값 | 프래그먼트 위치, 인스턴스 ID |

시간과 해상도를 유니폼으로 전달하는 개념은 다음처럼 쓸 수 있다.

```glsl
uniform float time;
uniform vec2 resolution;

vec2 centeredUV(vec2 fragmentPosition) {
  vec2 p = fragmentPosition / resolution - 0.5;
  p.x *= resolution.x / resolution.y;
  return p;
}
```

유니폼은 모든 셰이더 실행이 같은 값을 읽는다는 뜻이다. 반면 UV와 정점 위치는 실행 위치마다 다르다. 이 차이는 다음 절에서 어트리뷰트와 배리잉을 다룰 때 더 구체적으로 설명한다.

## 출력은 색에만 머물지 않는다

프래그먼트 셰이더의 대표 출력은 색이지만, 제너레이티브 규칙은 더 다양한 곳에 연결할 수 있다. 버텍스 셰이더에서 노이즈 값을 정점 위치에 더하면 메시가 변형되고, 표면 셰이더에서 같은 값을 거칠기에 연결하면 재질이 달라진다. 컴퓨트 셰이더에서는 값을 다음 상태 버퍼에 기록해 입자나 격자의 상태를 갱신할 수 있다.

```text
noise(position) -> fragment color
noise(position) -> vertex displacement
noise(position) -> surface roughness
noise(position) -> simulation force
```

따라서 셰이더에서 중요한 것은 "색을 그리는 법"만이 아니라, 입력 함수의 결과가 어느 파이프라인 출력으로 이어지는지 이해하는 일이다. 같은 노이즈 함수라도 연결 대상에 따라 구름 배경, 흔들리는 지형, 거친 금속, 흐름 필드가 될 수 있다.

## 셰이더는 전체 프로그램의 일부다

셰이더만으로 완전한 애플리케이션을 만들 수 있는 경우는 드물다. 일반 코드가 창을 만들고, 메시와 텍스처를 준비하고, 셰이더를 컴파일하며, 시간과 입력을 유니폼으로 전달하고, 어떤 렌더 패스를 어떤 순서로 실행할지 정한다. 셰이더는 그 과정 안에서 대량의 위치·정점·픽셀·표면 표본을 계산하는 전문화된 함수다.

이 역할 분담을 이해하면 셰이더 오류를 진단하기도 쉬워진다. 화면이 검정일 때 원인이 셰이더의 거리 식인지, 유니폼이 전달되지 않았는지, 렌더 타깃이 잘못되었는지, 블렌딩과 깊이 설정 때문인지 파이프라인의 위치를 기준으로 나누어 확인할 수 있다.

## 이 절의 핵심

셰이더는 정점, 픽셀, 표면점, 버퍼 항목 같은 실행 지점에서 입력을 받아 출력값을 계산하는 프로그램이다. 제너레이티브 아트의 거리 함수·파동·노이즈·좌표 변형은 위치 기반 함수이므로 셰이더와 잘 맞는다. 셰이더는 대량의 독립 계산에 강하지만, 시간·입력·이전 상태는 유니폼과 텍스처·버퍼 같은 명시적인 경로로 받아야 하며, 전체 그래픽 애플리케이션의 한 단계로 작동한다.
