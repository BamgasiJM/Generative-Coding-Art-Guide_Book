# 26.8 GPU 병렬 처리와 셰이더적 사고방식

셰이더가 제너레이티브 아트에 강력한 이유는 GPU가 많은 위치에서 같은 계산을 병렬로 수행할 수 있기 때문이다. 화면 전체의 노이즈, 수천 개 인스턴스의 변형, 텍스처의 색상 보정, 격자 기반 시뮬레이션은 각각의 계산 단위가 비슷한 규칙을 적용하는 작업이다. GPU는 이런 데이터 병렬성(data parallelism)을 활용하도록 설계되어 있다.

그러나 "GPU는 모든 것을 동시에 계산하므로 무조건 빠르다"는 설명은 정확하지 않다. GPU는 많은 실행 항목이 같은 종류의 명령을 비슷한 흐름으로 수행할 때 효율적이다. 셰이더적 사고방식은 병렬성의 이점을 얻기 위해 문제를 위치·정점·인스턴스·버퍼 항목처럼 많은 독립 작업으로 분해하는 방법이다.

## 하나의 규칙, 많은 실행 항목

프래그먼트 셰이더에서는 각 프래그먼트가 실행 항목이 된다. 전체 화면 패스라면 수백만 픽셀이 같은 프로그램을 실행하지만, 각 픽셀은 서로 다른 좌표를 입력으로 받는다.

$$
\mathbf{C}_i=F(\mathbf{p}_i,t,\boldsymbol{\theta})
$$

버텍스 셰이더에서는 메시 정점이, 인스턴싱에서는 각 인스턴스가, 컴퓨트 셰이더에서는 작업 ID가 실행 항목이 된다.

```text
for each pixel:     color[pixel] = field(pixelPosition)
for each vertex:    position[vertex] = deform(originalPosition)
for each instance:  transform[instance] = placement(instanceID)
for each particle:  nextState[id] = update(previousState[id])
```

이 의사코드는 실제로 CPU의 순차 반복문일 수도 있고 GPU의 병렬 실행일 수도 있다. 셰이더에서는 보통 반복문을 직접 작성하지 않고, 각 실행 항목이 자신의 ID·좌표·속성을 이용해 규칙 한 번을 계산한다. 프로그램의 중심은 "다음 항목을 처리하라"가 아니라 "현재 항목이 어떤 값을 반환해야 하는가"가 된다.

## 독립성은 병렬성의 조건이다

GPU가 많은 항목을 병렬로 처리하려면 각 항목의 계산이 가능한 한 독립적이어야 한다. 전체 화면 노이즈는 현재 픽셀의 좌표와 공통 유니폼만 사용하므로 이상적인 예다.

```glsl
float value = noise(uv * frequency + time * speed);
```

이 코드의 한 픽셀은 다른 픽셀의 지역 변수나 실행 결과를 기다리지 않는다. GPU는 픽셀들을 어떤 순서로, 어느 실행 묶음에 배치하든 같은 결과를 낼 수 있다.

반면 "왼쪽 픽셀의 새 값을 읽고 현재 픽셀의 새 값을 계산한다"는 규칙은 단일 패스에서 안전하지 않다. 어떤 픽셀이 먼저 실행될지 보장되지 않으며, 같은 버퍼에 읽고 쓰는 과정은 데이터 경쟁을 만들 수 있다. 이때는 이전 상태와 다음 상태를 분리한다.

```text
previous texture -> read-only input
shader evaluation -> next texture
swap previous and next after the pass
```

이 ping-pong 구조는 셀룰러 오토마타, 반응-확산, 블러, 잔상, 입자 상태 갱신에 사용된다. 한 패스 안에서는 이전 상태만 읽고 다음 상태만 쓰므로, 각 항목의 계산이 다시 독립적이 된다.

## SIMD와 실행 묶음

GPU는 내부적으로 여러 실행 항목을 묶어 비슷한 명령을 처리한다. 하드웨어와 API에 따라 warp, wave, subgroup 같은 이름을 쓰지만, 공통된 핵심은 한 묶음의 항목이 같은 명령 흐름을 공유할 때 효율적이라는 점이다.

```glsl
if (uv.x < 0.5) {
  // 경로 A
} else {
  // 경로 B
}
```

위 조건에서 같은 실행 묶음 안의 일부 프래그먼트는 A, 나머지는 B를 선택할 수 있다. 이 경우 하드웨어는 두 경로를 모두 처리하고 각 항목에서 필요한 결과만 취하는 방식으로 동작할 수 있다. 이를 분기 발산(branch divergence)이라고 한다. 조건문이 잘못된 것은 아니지만, 픽셀마다 복잡하고 긴 경로가 크게 갈라지면 병렬 효율이 떨어질 수 있다.

위치 기반 패턴에서는 조건문 대신 마스크와 보간을 사용하면 조합이 쉬운 경우가 많다.

```glsl
float mask = smoothstep(edge, -edge, distanceValue);
vec3 color = mix(outsideColor, insideColor, mask);
```

이 방식은 경계를 부드럽게 만들고, 마스크를 다른 필드와 곱하거나 더하기도 쉽다. 다만 모든 조건문을 수식으로 바꿔야 하는 것은 아니다. 드물게 실행되는 초기 탈출, 명확한 재질 분기, 알고리즘상 필요한 조건은 가독성과 비용을 비교해 사용한다.

## 메모리 접근도 계산의 일부다

셰이더의 성능은 산술 연산 횟수만으로 정해지지 않는다. 텍스처 표본화, 버퍼 읽기·쓰기, 큰 자료구조의 임의 접근은 메모리 대역폭과 접근 패턴에 영향을 받는다. GPU는 인접한 실행 항목이 인접한 데이터에 접근할 때 효율을 내기 쉽다.

```glsl
vec4 color = texture(imageTexture, uv);
```

인접 픽셀이 비슷한 UV를 읽는 일반적인 이미지 표본화는 캐시 효율이 좋을 수 있다. 반면 큰 난수 오프셋으로 텍스처 곳곳을 반복해서 읽거나, 각 항목이 멀리 떨어진 버퍼 인덱스를 많이 참조하면 비용이 커질 수 있다.

```glsl
vec2 warpedUV = uv + noise(uv * 100.0) * largeOffset;
vec4 color = texture(imageTexture, warpedUV);
```

이런 좌표 왜곡이 틀린 것은 아니다. 다만 고해상도 텍스처, 여러 번의 표본화, 복잡한 후처리가 겹치면 병목이 될 수 있다. 시각적으로 영향이 작은 표본을 줄이고, 낮은 해상도의 중간 버퍼를 쓰며, 공통 계산을 재사용하는 방식으로 조절한다.

## 병렬 축소와 집계의 어려움

각 항목이 독립적인 값을 계산하는 일은 쉽지만, 모든 항목의 합·최대값·평균처럼 전역 결과를 하나로 모으는 일은 더 복잡하다. 예를 들어 이미지 전체의 가장 밝은 픽셀을 찾거나, 모든 입자의 평균 위치를 계산하는 일은 병렬 축소(reduction) 과정을 여러 단계로 나누어야 할 수 있다.

```text
many values
    -> partial sums per workgroup
    -> smaller buffer of partial sums
    -> repeat until one value remains
```

프래그먼트 셰이더만으로는 이런 집계를 직접 구현하기 어려운 경우가 많다. 컴퓨트 셰이더, 여러 렌더 패스, CPU 읽기back 같은 구조를 사용한다. 하지만 GPU 결과를 매 프레임 CPU로 읽어 오면 동기화 비용이 커질 수 있으므로, 가능한 한 집계와 후속 계산을 GPU 안에서 이어 가는 편이 좋다.

## 동기화와 여러 패스

컴퓨트 셰이더는 작업 그룹 내부에서 제한된 동기화를 제공할 수 있지만, 전체 GPU 작업이 즉시 서로의 결과를 보는 것은 아니다. 한 패스에서 쓴 버퍼를 다음 패스에서 읽기 전에, API가 필요한 메모리 장벽과 실행 순서를 보장해야 한다. 그래픽 프레임워크가 이를 감춰 주기도 하지만, "쓰기 결과는 다음 패스에서 읽을 수 있다"는 경계를 의식해야 한다.

```text
pass 1: write velocity buffer
barrier or pass completion
pass 2: read velocity buffer, write position buffer
pass 3: render positions
```

복잡한 시뮬레이션을 하나의 거대한 셰이더에 넣기보다, 데이터 의존 관계에 따라 작은 패스로 나누면 상태의 흐름이 명확해진다. 각 패스는 입력 텍스처·버퍼와 출력 텍스처·버퍼를 명시적으로 가진 함수로 볼 수 있다.

## CPU와 GPU 사이의 경계

GPU 셰이더는 홀로 작동하지 않는다. CPU 쪽 애플리케이션은 셰이더를 컴파일하고, 메시·텍스처·버퍼를 준비하고, 유니폼을 설정하고, 어떤 패스를 어떤 순서로 실행할지 결정한다. 이 경계를 자주 넘나들면 전송과 동기화 비용이 생긴다.

```text
CPU -> GPU: uniforms, mesh data, textures, commands
GPU -> CPU: readback of rendered pixels or buffers
```

시간, 마우스 위치, 몇 개의 파라미터처럼 작은 값은 매 프레임 유니폼으로 보내도 부담이 작다. 하지만 수백만 픽셀의 결과나 수십만 입자의 상태를 매 프레임 GPU에서 CPU로 읽어 와서 다시 처리하면 성능이 크게 떨어질 수 있다. 결과가 계속 GPU에서 사용된다면 텍스처·버퍼 상태로 유지하고, 최종 저장이나 드문 분석이 필요할 때만 CPU로 가져오는 편이 낫다.

## 알고리즘을 병렬 문제로 다시 쓰기

CPU에서 자연스러운 알고리즘이 GPU에서도 자연스럽지는 않다. 연결 리스트를 따라가거나, 요소를 임의로 생성·삭제하고, 현재 결과에 따라 다음 항목을 순차적으로 결정하는 방식은 GPU에서 구현이 복잡해질 수 있다. 반대로 다음처럼 다시 질문하면 셰이더에 맞는 구조를 찾기 쉽다.

1. 처리할 모든 항목을 좌표 또는 ID로 미리 정할 수 있는가?
2. 각 항목의 결과를 이전 상태와 공통 파라미터만으로 계산할 수 있는가?
3. 이웃 정보가 필요하면 이전 버퍼의 제한된 표본으로 읽을 수 있는가?
4. 읽기와 쓰기를 별도 버퍼와 패스로 분리할 수 있는가?
5. 전역 집계가 꼭 매 프레임 필요한가?

예를 들어 입자 시스템에서 입자의 생성과 삭제를 CPU의 동적 배열처럼 다루는 대신, 고정된 최대 개수의 입자 슬롯을 두고 나이와 활성 상태로 재사용할 수 있다. 격자 시뮬레이션은 각 셀을 작업 ID에 대응시키고, 이웃 셀은 이전 텍스처에서 읽는다. 이처럼 자료 구조를 병렬 접근에 맞게 바꾸는 것이 셰이더적 사고방식이다.

## 성능을 판단하는 방법

성능은 기기, 해상도, 드라이버, 브라우저, 렌더링 파이프라인에 따라 크게 달라진다. "이 연산은 GPU에서 빠르다"는 일반론보다 실제 해상도와 목표 프레임률에서 측정하는 편이 중요하다. 성능을 점검할 때는 다음 순서가 유용하다.

- 해상도와 렌더 패스 수를 낮춰 병목이 픽셀 처리인지 확인한다.
- 노이즈 옥타브, 텍스처 표본 수, 반복 횟수를 줄여 어떤 계산이 영향을 주는지 비교한다.
- 중간 결과를 작은 오프스크린 버퍼에 캐시할 수 있는지 검토한다.
- CPU-GPU 사이의 readback과 불필요한 버퍼 전송을 확인한다.
- 시각적으로 거의 보이지 않는 고주파 세부와 과도한 해상도를 먼저 줄인다.

최적화는 규칙을 이해한 뒤에 한다. 제너레이티브 아트에서는 계산을 줄이는 일이 단지 성능 개선이 아니라, 패턴의 스케일과 밀도를 다시 설계하는 일이기도 하다.

## 이 절의 핵심

GPU 병렬 처리의 강점은 많은 실행 항목이 같은 규칙을 독립적으로 적용하는 데이터 병렬성에 있다. 프래그먼트·정점·인스턴스·작업 ID를 각각의 항목으로 보고, 이전 상태와 다음 상태를 분리하면 복잡한 규칙도 병렬 패스로 구성할 수 있다. 분기 발산, 메모리 접근, 동기화, CPU-GPU 데이터 이동은 성능과 알고리즘 구조에 직접 영향을 주므로, 문제를 작은 독립 계산과 명시적인 데이터 흐름으로 나누어 생각해야 한다.
