# 27.9 여러 그래픽 환경에서 GLSL 활용하기

GLSL은 셰이더의 계산을 표현하지만, 셰이더를 어디에 연결하고 어떤 값을 전달할지는 실행 환경이 정한다. 같은 프래그먼트 계산식도 어떤 프레임워크에서는 셰이더 파일로 컴파일되고, 어떤 환경에서는 자동 생성된 머티리얼 코드의 일부가 되며, ShaderToy처럼 정해진 함수 안에 작성되기도 한다. 따라서 GLSL을 다른 도구로 옮길 때는 수식만 비교하지 말고 입력 변수, 셰이더 진입점, 좌표계, 텍스처와 출력 연결 방식까지 함께 살펴야 한다.

이 절에서는 크리에이티브 코딩 프레임워크뿐 아니라 TouchDesigner, ShaderToy, Three.js, raylib, OGL에서 GLSL이 어떤 역할을 맡는지 비교한다. 각 API의 전체 코드를 익히기보다, 개발자가 작성하는 부분과 호스트가 대신 구성하는 부분을 구분하는 것이 목표다.

## 호스트가 맡는 일

일반적인 실시간 셰이더의 실행 흐름은 다음과 같다.

```text
셰이더 코드 입력
    -> 호스트가 전처리·컴파일하고 필요한 단계를 연결
        -> 버퍼, 텍스처, 유니폼을 셰이더 입력에 결합
            -> 렌더 호출에서 GPU가 실행
                -> 화면이나 다른 렌더 타깃에 결과 기록
```

각 환경은 이 흐름 중 일부를 감춘다. 저수준 라이브러리는 셰이더 소스와 GPU 자원을 직접 연결하도록 하고, 고수준 도구는 기본 버텍스 단계나 화면 좌표, 텍스처 입력, 머티리얼 설정을 미리 만들어 준다. 노드 기반 프로그램은 셰이더 소스를 직접 쓰지 않아도 내부적으로 코드를 생성해 같은 GPU 파이프라인을 사용할 수 있다.

| 환경 | GLSL을 넣는 방식 | 주로 맡기는 역할 |
| --- | --- | --- |
| p5.js | 정점·프래그먼트 소스 문자열로 셰이더를 만들고 `shader()`로 드로잉에 적용 | 캔버스의 도형·텍스처·전체 화면 패스에 사용자 정의 색과 변형을 적용 |
| openFrameworks | `ofShader`에 파일 또는 소스를 읽혀 컴파일·링크한 뒤 드로잉 호출에 바인딩 | 2D·3D 객체의 재질, 이미지 효과, 사용자 정의 렌더 패스 |
| OPENRNDR | `ShadeStyle`의 셰이더 변환 코드와 파라미터를 프레임워크의 드로잉 파이프라인에 결합 | 도형·메시의 버텍스/프래그먼트 변환을 확장 |
| TouchDesigner | GLSL TOP·MAT·COMP의 템플릿에 맞추어 셰이더 코드를 작성 | 이미지 처리, 3D 재질, GPU 데이터 계산을 노드 네트워크에 연결 |
| ShaderToy | `mainImage()`와 사전 정의 입력을 사용하는 온라인 편집 환경 | 전체 화면 절차적 이미지와 다중 패스 셰이더 아트 |
| Three.js | `ShaderMaterial` 또는 `RawShaderMaterial`에 정점·프래그먼트 코드를 지정 | WebGL 장면의 객체 재질과 사용자 정의 렌더 효과 |
| raylib | 셰이더 파일·문자열을 `LoadShader` 계열 함수로 불러와 드로잉 모드나 머티리얼에 적용 | 2D 드로잉과 3D 모델의 사용자 정의 렌더링 |
| OGL | WebGL 컨텍스트에 정점·프래그먼트 코드를 `Program`으로 연결 | 최소한의 추상화로 메시, 유니폼, 렌더 호출을 직접 구성 |

이 표에서 모두가 같은 GLSL을 받는다고 가정해서는 안 된다. 브라우저 기반 도구는 WebGL의 GLSL ES를 사용하고, 데스크톱 프레임워크는 OpenGL 코어 또는 OpenGL ES 컨텍스트를 선택할 수 있다. 셰이더의 `#version`, 정점 입력 문법, 프래그먼트 출력 변수는 호스트의 그래픽 API와 버전에 맞춰야 한다.

## 크리에이티브 코딩 프레임워크

### p5.js

p5.js의 WEBGL 모드에서는 `createShader()`에 정점 셰이더와 프래그먼트 셰이더 소스를 전달해 셰이더 객체를 만든다. `shader()`는 이후의 도형 그리기에 그 셰이더를 적용하고, `setUniform()`은 시간·색·마우스 위치 같은 값을 전달한다. 따라서 셰이더 코드는 GPU의 픽셀 또는 정점 계산을 맡고, JavaScript 쪽은 애니메이션 상태와 입력을 갱신하며 어느 도형을 그릴지 결정한다.

화면 전체에 절차적 이미지를 그릴 수도 있고, 메시나 텍스처가 있는 도형에 셰이더를 적용할 수도 있다. p5.js가 사용하는 WebGL 버전과 셰이더 예제가 기대하는 문법을 확인해야 한다. 데스크톱 GLSL 4.60 소스를 그대로 붙여 넣기보다, 대상 브라우저의 WebGL 및 GLSL ES 버전에 맞춰 입력·출력 선언과 내장 변수를 조정한다.

### openFrameworks

openFrameworks는 `ofShader`를 통해 셰이더 파일 또는 문자열을 로드하고, 버텍스·프래그먼트 단계를 컴파일해 링크한다. 이후 셰이더를 바인딩한 구간에서 도형이나 메시를 그리며, `setUniform` 계열 호출로 셰이더의 매개변수와 텍스처를 전달한다. 이 구조는 셰이더의 적용 범위와 렌더 호출이 비교적 명시적이어서, 특정 객체에만 재질을 적용하거나 별도 프레임버퍼에 효과를 계산하기 좋다.

실제 문법은 프로젝트가 만든 OpenGL 컨텍스트에 좌우된다. 셰이더 파일의 버전 선언, 속성 이름, 출력 형식과 텍스처 연결을 해당 컨텍스트에 맞춘다. 프레임워크의 기본 렌더링과 사용자 셰이더가 함께 쓰일 때는 행렬이나 텍스처 단위처럼 프레임워크가 자동으로 제공하는 값도 확인해야 한다.

### OPENRNDR

OPENRNDR에서는 Kotlin 코드가 창과 드로잉을 관리하고, `ShadeStyle`이 드로잉 파이프라인에 사용자 셰이더 계산을 보탠다. 일반적인 사용에서는 완전한 버텍스·프래그먼트 프로그램을 처음부터 작성하기보다 `vertexTransform`이나 `fragmentTransform` 같은 셰이더 조각을 지정하고, 필요한 파라미터를 스타일에 연결한다. OPENRNDR이 기본 셰이더 구조와 도형 렌더링을 구성하므로, 작성한 코드는 그 안의 특정 변환 단계에 삽입된다.

이 방식은 드로잉 API의 편의성과 셰이더의 픽셀·정점 단위 계산을 함께 활용하게 해준다. 대신 임의의 독립 GLSL 프로그램을 붙이는 것과 입력 계약이 다르다. 스타일에서 제공되는 좌표·색·파라미터의 이름과 타입, 코드가 실행되는 단계는 OPENRNDR 버전에 맞는 API 문서를 따른다. 화면 전체 패스나 렌더 타깃을 다루는 경우에도 OPENRNDR의 드로잉·버퍼 API와 셰이더 입력을 함께 설계한다.

### nannou: GLSL과 WGSL을 구분하기

nannou의 `Draw` API는 도형과 선을 추상화하며, 기본적인 제너레이티브 아트에서는 GLSL을 직접 작성할 필요가 없다. 사용자 정의 GPU 파이프라인을 만들 때는 nannou 0.20 계열의 그래픽 기반인 wgpu를 고려해야 한다. 이 경로의 셰이더 언어는 GLSL이 아니라 WGSL이 기본이다.

따라서 OpenGL용 GLSL을 nannou 셰이더에 그대로 전달할 수 있다고 생각해서는 안 된다. 기존 GLSL을 재사용하려면 WGSL로 다시 작성하거나, 변환 도구와 GPU 백엔드가 지원하는 기능을 확인해야 한다. 언어 변환이 성공해도 바인딩 그룹, 리소스 선언, 셰이더 단계의 인터페이스는 wgpu 규칙에 맞춰야 한다. nannou는 이 절의 다른 GLSL 호스트와 달리, GLSL을 표준적인 직접 입력 경로로 삼지 않는 사례다.

## 노드 기반 환경과 셰이더 아트

### TouchDesigner

TouchDesigner는 GLSL을 노드 네트워크에 직접 연결하는 상용 실시간 비주얼 도구다. GLSL TOP은 입력 TOP의 픽셀을 읽어 새 이미지나 이펙트를 계산하고, 출력 TOP은 다시 다른 TOP이나 화면에 연결된다. GLSL MAT은 3D 지오메트리에 적용할 재질의 버텍스·프래그먼트 계산을 맡는다. GLSL COMP는 지원되는 환경에서 컴퓨트 셰이더를 이용해 이미지 렌더링 이외의 데이터 병렬 계산을 수행한다.

각 노드는 셰이더의 목적에 맞는 템플릿과 입출력 계약을 제공한다. 예를 들어 TOP 셰이더는 입력 텍스처 배열과 텍스처 좌표, 출력 픽셀을 연결하고, MAT은 지오메트리의 정점·노멀·재질 계산을 연결한다. 사용자는 네트워크에서 텍스처·파라미터·출력을 시각적으로 배선하고, 셰이더 코드에서는 그 값으로 실제 픽셀이나 표면의 계산을 정의한다. 노드 종류에 따라 필요한 GLSL 버전, 출력 선언과 제공 변수들이 다르므로 템플릿을 기준으로 작성한다.

이 구조는 카메라, 영상, 오디오 분석, 센서, 피드백 텍스처를 셰이더에 빠르게 결합할 때 강력하다. 반면 TouchDesigner의 입력 이름이나 출력 보조 함수는 일반 OpenGL 프로그램의 표준 인터페이스가 아니다. 코드를 다른 프레임워크로 옮길 때는 그 부분을 새 호스트의 텍스처·유니폼·출력 설정으로 교체해야 한다.

다른 상용 도구에서는 셰이더가 사용되어도 사용자가 GLSL을 직접 작성하는 것은 아닐 수 있다. Blender의 머티리얼 노드나 Unreal·Unity의 머티리얼 그래프는 노드 표현을 내부 셰이더 코드로 변환하며, 사용자에게 GLSL 대신 노드나 HLSL 계열 인터페이스를 제공하는 경우가 일반적이다. 따라서 “GPU 셰이더로 렌더링한다”와 “GLSL 소스를 직접 입력한다”는 서로 다른 설명이다.

### ShaderToy

ShaderToy는 프래그먼트 셰이더 아트를 공유하고 실행하는 브라우저 기반 환경이다. 사용자는 보통 전체 프로그램의 `main()`과 창 생성 코드를 작성하지 않고 `mainImage()`에 각 화면 위치의 색을 계산하는 코드를 넣는다. 플랫폼은 해상도, 시간, 마우스 상태와 채널 텍스처 같은 입력을 정해진 인터페이스로 제공하고, 화면을 덮는 렌더링을 실행한다.

이 환경에서는 한 프래그먼트가 화면 좌표를 받아 색을 돌려주는 구조가 자연스럽다. SDF, 노이즈, 광선 행진, 반복 패턴 같은 수식이 곧 이미지 전체의 생성 규칙이 된다. Buffer 패스를 사용하면 이전 단계의 이미지나 프레임을 다음 단계의 입력으로 삼아 피드백과 다중 패스 효과도 구성할 수 있다.

ShaderToy 코드는 완전한 독립 셰이더라기보다 플랫폼이 정한 입력과 진입점에 맞춘 프로그램이다. `mainImage()`를 `main()`으로 감싸고, `iTime`·`iResolution`·채널 샘플러 등을 다른 호스트의 유니폼과 텍스처에 연결하면 다른 환경으로 옮길 수 있다. 다만 좌표 원점, 입력 텍스처의 크기, 색 공간과 프레임 누적 규칙까지 같다고 가정하지 않는다.

## 웹 3D와 경량 WebGL 라이브러리

### Three.js

Three.js의 `ShaderMaterial`은 정점·프래그먼트 셰이더 소스를 머티리얼로 제공해 장면의 메시 렌더링에 사용한다. 카메라와 지오메트리의 위치, 노멀, UV, 변환 행렬 등은 Three.js의 머티리얼 인터페이스에 맞춰 셰이더와 연결하고, 애플리케이션은 `uniforms`의 값을 갱신한다. 이처럼 GLSL이 표면의 모양과 색을 계산하는 동안, Three.js는 장면 그래프, 카메라, 버퍼, 렌더 순서와 드로우 호출을 관리한다.

`ShaderMaterial`은 엔진이 제공하는 선언과 기본 입력을 활용하는 방식이다. 더 낮은 수준에서 셰이더 인터페이스를 직접 제어하려면 `RawShaderMaterial`을 고려할 수 있지만, 필요한 선언과 입력 연결을 더 많이 책임져야 한다. `glslVersion`과 렌더러가 사용하는 WebGL 컨텍스트에 따라 GLSL ES 문법을 맞춰야 한다. WebGPU 렌더링 경로는 WebGL용 GLSL 머티리얼과 동일한 경로가 아니며, Three.js의 노드 머티리얼/TSL 같은 별도 셰이더 작성 방식을 고려해야 한다.

Three.js는 장면 안의 객체를 셰이딩하는 데 적합하지만, ShaderToy처럼 코드만으로 화면 전체를 채우는 방식과는 입력 구조가 다르다. 전체 화면 효과를 만들 수도 있으나 이때는 화면을 덮는 지오메트리나 후처리 패스, 카메라에 맞는 좌표와 깊이 처리를 함께 구성한다.

### raylib

raylib은 셰이더를 파일 또는 메모리의 소스로 불러오고, `BeginShaderMode()`와 `EndShaderMode()` 사이의 2D 드로잉에 적용하거나 3D 머티리얼에 연결한다. `SetShaderValue()` 계열 함수는 시간·색·벡터 같은 유니폼을, 텍스처용 함수는 샘플러 입력을 전달한다. 즉 셰이더가 픽셀과 표면의 계산을 수행하고, raylib은 창·입력·도형·텍스처와 셰이더 적용 시점을 간결한 C API로 관리한다.

raylib의 셰이더 예제와 빌드 대상은 데스크톱 OpenGL, OpenGL ES 등 플랫폼별로 다를 수 있다. 예제의 `#version`, 속성 위치, 텍스처 이름과 내장 유니폼을 선택한 그래픽 백엔드와 맞춘다. 셰이더를 2D 드로잉에 적용할지 모델 재질로 적용할지에 따라 자동으로 공급되는 데이터도 달라질 수 있다.

### OGL

OGL은 JavaScript에서 WebGL을 간결하게 다루도록 만든 저수준 라이브러리다. 정점·프래그먼트 코드를 `Program`에 연결하고, `Geometry`의 버퍼를 `Mesh`로 그리며, 렌더러와 함께 필요한 GPU 호출을 구성한다. 유니폼 갱신과 드로우 호출도 코드에서 명시적으로 관리하므로, GLSL과 WebGL의 관계를 비교적 직접적으로 볼 수 있다.

Three.js가 장면 그래프와 머티리얼 시스템을 제공하는 데 비해 OGL은 더 적은 추상화로 셰이더와 버퍼에 접근하게 한다. 그만큼 전체 화면 패스나 독특한 렌더링 구성을 직접 짜기 쉽지만, 카메라·좌표 변환·리소스 생명주기와 렌더 순서를 애플리케이션이 더 많이 책임진다. 셰이더 문법은 브라우저의 WebGL 버전과 GLSL ES에 맞춰야 한다.

## GLSL 코드를 옮길 때 확인할 것

다른 호스트로 셰이더를 이동할 때는 다음 항목을 순서대로 대조한다.

1. **언어 버전과 프로필:** 데스크톱 GLSL인지 GLSL ES인지, `#version` 선언과 사용 가능한 함수가 맞는지 확인한다.
2. **진입점과 단계:** `main()`, `mainImage()` 또는 프레임워크가 삽입하는 코드 조각 중 무엇을 작성해야 하는지 확인한다.
3. **입력과 출력:** 정점 속성, varying/`in`·`out`, 프래그먼트 출력, 텍스처 샘플러가 어떤 이름과 타입으로 연결되는지 확인한다.
4. **좌표와 픽셀 크기:** UV 범위와 원점, 종횡비, `gl_FragCoord` 사용 가능 여부, 렌더 타깃 크기를 비교한다.
5. **유니폼과 자원:** 시간·마우스·행렬·텍스처가 자동 제공되는지, 호스트 코드에서 직접 설정해야 하는지 확인한다.
6. **색과 합성:** 선형 색과 sRGB, 알파 블렌딩, 출력 타깃의 포맷과 피드백 규칙을 점검한다.

프로시저럴 수식은 대체로 여러 환경에서 재사용할 수 있지만, 셰이더의 바깥 인터페이스는 그렇지 않다. 가장 유지보수하기 쉬운 방법은 수학 함수와 호스트 연결부를 구분하는 것이다. 노이즈나 거리 함수는 공통 함수로 두고, 좌표를 얻는 부분과 결과를 출력하는 부분만 각 플랫폼의 계약에 맞춰 작성하면 이식 시 수정 범위를 줄일 수 있다.

## 이 절의 핵심

GLSL은 여러 프레임워크와 제작 도구에서 쓰이지만, 같은 소스를 같은 방식으로 실행하는 것은 아니다. p5.js·openFrameworks·raylib·OGL은 소스와 자원을 연결해 직접 렌더링하는 경로를 제공하고, OPENRNDR과 TouchDesigner는 프레임워크 또는 노드가 마련한 셰이더 계약에 코드를 결합한다. ShaderToy는 고정된 화면 셰이더 인터페이스를 제공하며, Three.js는 GLSL을 장면의 머티리얼로 편입한다. 반면 nannou의 wgpu 기반 사용자 셰이더 경로는 WGSL 중심이다. 환경을 가로질러 코드를 옮길 때는 수식보다 먼저 버전, 진입점, 좌표와 리소스 연결을 맞춰야 한다.
