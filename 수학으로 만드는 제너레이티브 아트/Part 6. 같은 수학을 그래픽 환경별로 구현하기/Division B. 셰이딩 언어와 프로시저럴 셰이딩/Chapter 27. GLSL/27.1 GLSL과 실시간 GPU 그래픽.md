# 27.1 GLSL과 실시간 GPU 그래픽

GLSL(OpenGL Shading Language)은 GPU 그래픽 파이프라인에서 실행할 셰이더를 작성하는 언어다. 이 책의 기준 시점인 2026년 10월 현재, 데스크톱 OpenGL의 최신 코어 셰이딩 언어 버전은 GLSL 4.60이다. 다만 모든 프로그램이 4.60을 지원하는 것은 아니다. 실제로 사용할 수 있는 문법과 기능은 그래픽 API, 드라이버, 브라우저 또는 호스트 프로그램이 제공하는 셰이더 환경에 달려 있다.

GLSL은 OpenGL과 같은 뜻이 아니다. OpenGL은 그래픽 자원과 렌더링 작업을 관리하는 API이고, GLSL은 그 파이프라인의 일부 계산을 표현하는 셰이더 언어다. 셰이더는 단독으로 창을 만들거나 화면에 표시되지 않는다. 애플리케이션 또는 시각 도구가 프로그램을 준비하고, 셰이더를 컴파일하고, 입력값과 텍스처를 전달한 뒤, 렌더링 결과를 표시한다. 셰이더 단계의 공통 역할은 26장에서 살펴보았으므로 이 절에서는 GLSL의 정체와 버전, 실시간 그래픽 안에서의 위치를 정리한다.

## GPU에서 실행되는 작은 프로그램

일반적인 그래픽 파이프라인은 수많은 정점과 화면 표본에 같은 셰이더 코드를 반복 적용한다. GLSL은 정점 위치를 변형하거나, 표면의 색을 계산하거나, 이미지 데이터를 처리하는 식을 작성한다. 셰이더 코드에는 보통 화면의 모든 픽셀을 순회하는 반복문이 없다. 그래픽 API가 렌더링할 기하와 실행 단위를 정하고, GPU가 각 정점 또는 프래그먼트에서 프로그램을 실행한다.

예를 들어 아래는 화면에 그려지는 프래그먼트의 색을 일정한 청록색으로 출력하는 최소한의 GLSL 4.60 프래그먼트 셰이더다.

```glsl
#version 460 core

layout(location = 0) out vec4 outColor;

void main() {
    const vec3 teal = vec3(0.05, 0.65, 0.63);
    outColor = vec4(teal, 1.0);
}
```

`#version 460 core`는 사용할 GLSL 버전과 데스크톱 코어 프로필을 선언한다. `vec3`는 세 개의 부동소수점 성분을 담고, `vec4`는 여기에 알파 성분을 더한다. `layout(location = 0)`은 색 출력이 렌더 타깃의 어느 출력 슬롯에 연결되는지 명시한다. 이 코드는 프래그먼트 셰이더 하나일 뿐 완전한 렌더링 프로그램은 아니다. 실제 장면에서는 이를 호출할 버텍스 단계와 그래픽 API의 파이프라인 설정이 함께 필요하다.

최신 코어 GLSL에서는 출력 변수를 명시적으로 선언하는 형태를 사용한다. 오래된 예제에서 보이는 `gl_FragColor`, `attribute`, `varying` 등은 과거 GLSL 프로필의 문법이다. 특히 데스크톱 코어 프로필을 사용하는 새 코드에서는 버텍스 입력과 단계 사이의 값을 `in`·`out`으로 선언하고, 프래그먼트 출력 변수도 직접 정의하는 방식이 기준이다. `texture2D()` 대신 일반적인 `texture()` 함수를 쓰는 것처럼, 오래된 문법이 현대 프로필에서 제거되거나 다른 문법으로 대체된 사례도 있다. 다만 GLSL ES 1.00을 대상으로 하는 구형 WebGL 코드는 별도의 규칙을 따르므로 문법을 섞어 쓰지 않는다.

## GLSL 버전은 실행 환경과 함께 읽는다

GLSL의 `#version`은 단순한 주석이나 취향 설정이 아니다. 컴파일러가 어느 문법과 기능을 허용할지 지정하며, 그래픽 API가 만든 컨텍스트도 그 버전을 지원해야 한다. 데스크톱, 임베디드, 브라우저, Vulkan은 서로 다른 버전 체계를 사용하거나 추가 제약을 둔다.

| 환경 | 대표적인 언어 표기 | 읽을 때 주의할 점 |
| --- | --- | --- |
| 데스크톱 OpenGL 4.6 | `#version 460 core` | 최신 데스크톱 코어 프로필의 기준. 실제 GPU와 드라이버의 지원 여부를 확인한다. |
| 데스크톱 OpenGL 4.5 | `#version 450 core` | 4.6 기능이 필요하지 않은 프로그램의 호환 기준으로 사용될 수 있다. |
| OpenGL ES 3.2 | `#version 320 es` | 모바일·임베디드 환경의 GLSL ES 3.20 계열이다. 데스크톱 코어 문법과 기능을 그대로 가정하지 않는다. |
| WebGL 2 | `#version 300 es` | GLSL ES 3.00을 기반으로 한다. WebGL 1은 GLSL ES 1.00 문법을 사용한다. |
| Vulkan | 도구 체인이 정한 Vulkan GLSL | GLSL 소스를 Vulkan이 직접 실행하는 것은 아니다. 컴파일러가 보통 SPIR-V로 변환하며, Vulkan 규칙과 확장도 적용된다. |

이 표의 숫자는 서로 일대일로 대응하지 않는다. 데스크톱 GLSL 4.60이 GLSL ES 3.20보다 단순히 “더 높은 숫자이므로 더 낫다”는 의미가 아니며, 한 환경의 소스를 다른 환경에 복사한다고 자동으로 호환되지도 않는다. 브라우저는 WebGL 사양이 허용한 기능을, 모바일 기기는 OpenGL ES 구현과 드라이버가 지원하는 기능을 기준으로 삼는다. Vulkan에서도 그래픽 API의 셰이더 모듈 형식과 기능 제한을 추가로 고려해야 한다.

따라서 `#version`을 정할 때는 다음 순서로 판단한다.

1. 결과를 실행할 API와 장치, 호스트 프로그램을 확인한다.
2. 그 환경이 지원하는 GLSL 또는 GLSL ES 버전을 확인한다.
3. 필요한 언어 기능이 해당 버전에 포함되는지 확인한다.
4. 버전으로 보장되지 않는 기능은 확장(extension) 사용 가능 여부를 확인한다.
5. 최종 셰이더를 목표 환경에서 컴파일하고 화면 결과를 확인한다.

데스크톱용 예제에서 4.60을 기준으로 설명하더라도, 웹이나 구형 장치까지 지원해야 한다면 필요한 최소 버전을 따로 정해야 한다. 반대로 특정 상용 프로그램이 자체적으로 GLSL 코드를 변환하거나 특정 버전에 맞춘 템플릿을 제공한다면 그 프로그램의 셰이더 편집 환경이 우선 기준이다.

## 컴파일과 실행의 책임 분담

OpenGL 기반 프로그램은 셰이더 소스를 GPU 드라이버에 전달해 컴파일하고, 여러 셰이더 단계를 하나의 프로그램으로 링크한다. 문법이 맞아도 입력과 출력 인터페이스가 연결되지 않으면 링크에 실패할 수 있다. 셰이더가 성공적으로 컴파일되더라도 애플리케이션이 유니폼, 텍스처, 버퍼를 올바르게 설정하지 않았다면 기대한 결과가 나오지 않는다.

실시간 프로그램은 보통 다음과 같은 흐름으로 동작한다.

```text
셰이더 준비 및 컴파일
    -> 파이프라인 또는 셰이더 프로그램 구성
        -> 프레임마다 입력 데이터와 매개변수 갱신
            -> GPU에서 셰이더 실행
                -> 렌더 타깃에 결과 기록
```

셰이더 소스를 직접 관리하는 프레임워크에서는 개발자가 이 과정의 일부를 코드로 구성한다. 반면 노드 기반 도구나 게임 엔진은 컴파일, 파라미터 전달, 렌더 타깃 연결을 사용자 인터페이스 뒤에서 처리할 수 있다. 코드가 보이지 않더라도 셰이더 계산이 수행될 수 있으며, 반대로 GLSL 코드를 입력하는 편집기가 있다고 해서 OpenGL 전체 API를 직접 다룬다는 뜻은 아니다. 도구별 문법 변환, 내장 변수, 텍스처 입력 규칙은 해당 환경의 계약이다.

셰이더 오류는 적어도 세 층위로 나누어 확인할 수 있다.

| 층위 | 확인할 항목 |
| --- | --- |
| 컴파일 | `#version`, 문법, 지원 확장, 자료형이 유효한가? |
| 링크·연결 | 단계 사이의 `in`·`out`, 출력 위치, 호스트가 요구하는 인터페이스가 맞는가? |
| 실행·표시 | 유니폼과 텍스처가 전달되었는가? 올바른 렌더 타깃과 좌표로 그렸는가? |

이처럼 GLSL 소스만 살펴보아서는 전체 결과를 진단하기 어려울 수 있다. 셰이더 로그, 호스트 프로그램의 입력 설정, 그래픽 API의 컨텍스트 버전을 함께 살펴보면 원인을 좁힐 수 있다.

## GLSL을 쓰는 영역

GLSL은 OpenGL 애플리케이션에서 시작한 언어지만, 오늘날에는 실시간으로 색과 표면을 계산하는 다양한 도구에서 사용되거나 입력 언어의 하나로 제공된다. 크리에이티브 코딩 프레임워크, 브라우저 기반 셰이더 편집기, 3D 제작 도구, 실시간 영상·비주얼 프로그래밍 환경은 서로 다른 방식으로 GLSL을 노출할 수 있다. 일부는 GLSL 소스를 거의 그대로 컴파일하고, 일부는 입력과 출력의 이름을 정하거나 코드 일부를 생성해 셰이더 프로그램을 구성한다.

중요한 것은 GLSL을 사용한다는 공통점이 실행 환경까지 같다는 뜻은 아니라는 점이다. `main()`의 입출력, 화면 좌표의 방향과 단위, 시간 변수, 색 공간, 텍스처 좌표, 프레임마다 호출되는 방식은 호스트가 정한다. 같은 수식이라도 한 프로그램에서는 `gl_FragCoord`를 직접 사용할 수 있고, 다른 편집기에서는 `vUV` 같은 입력 변수를 사용해야 할 수 있다. 여러 환경에서 GLSL을 연결하는 구체적인 사례는 27.9에서 살펴본다.

GLSL은 HLSL이나 OSL과도 역할이 다르다. HLSL은 Direct3D와 여러 게임 엔진의 실시간 셰이더 환경에서 널리 쓰이고, OSL은 오프라인 렌더링에서 표면 재질을 표현하는 데 초점을 둔다. 비슷한 벡터 연산과 수학 함수를 공유하더라도 버전 지시문, 자료형, 단계별 입출력, 호스트 API가 다르므로 코드를 그대로 교환할 수 없다. 세 언어의 대응 관계는 각 언어 장에서 다시 비교한다.

## 이 절의 핵심

GLSL은 OpenGL 자체가 아니라 그래픽 파이프라인의 계산을 작성하는 셰이더 언어다. 데스크톱 코어 GLSL의 최신 표준은 4.60이지만, OpenGL ES·WebGL·Vulkan은 각자의 버전과 기능 제약을 가지므로 실제 호스트 환경을 기준으로 문법을 선택해야 한다. 현대 코어 문법은 명시적인 `in`·`out`과 출력 변수를 사용하며, 셰이더의 컴파일·연결·입력 설정·화면 출력은 언어와 호스트 프로그램이 나누어 맡는다.
