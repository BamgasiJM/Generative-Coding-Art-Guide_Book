# 27.4 유니폼과 시간

프래그먼트 셰이더는 자체 시계나 애플리케이션 상태를 갖지 않는다. 애니메이션을 만들려면 호스트 프로그램이 시간과 조절값을 준비해 셰이더에 전달해야 한다. GLSL에서 이런 공유 입력을 선언하는 대표적인 방법이 `uniform`이다. 이 절에서는 GLSL 4.60 코어의 유니폼을 프레임별 시간값과 연결하고, 단순한 시간 함수와 상태 갱신을 구분하는 방법을 살펴본다. 유니폼의 공통 개념은 26.4에서 다루었으므로 여기서는 실제 셰이더 코드와 시간 설계에 집중한다.

## 유니폼 선언과 호스트의 값 전달

유니폼은 셰이더 코드에 이름과 타입을 선언하지만, 선언만으로 값이 정해지지는 않는다. 애플리케이션은 셰이더 프로그램을 사용하기 전에 해당 유니폼에 값을 설정한다. 프래그먼트 셰이더의 모든 실행은 한 번의 드로우 호출에서 같은 유니폼 값을 공유하지만, 호스트는 다음 드로우 호출 전에 다른 값으로 바꿀 수 있다.

```glsl
#version 460 core

uniform float u_time;
uniform float u_waveSpeed;
uniform vec3 u_colorA;
uniform vec3 u_colorB;
```

`float`, `vec2`, `vec3`, `vec4`, `mat4`와 같은 GLSL 타입은 호스트가 전달하는 데이터 타입과 맞아야 한다. 이름 앞의 `u_`는 유니폼임을 알아보기 위한 관례일 뿐 GLSL 문법의 특별한 규칙은 아니다. 변수 이름과 자료형이 맞더라도 값을 설정하지 않으면 의도한 매개변수가 전달되지 않으므로, 셰이더 링크 후 호스트 API로 유니폼을 찾아 업데이트해야 한다.

호스트 API의 호출 형태는 프레임워크에 따라 다르다. 개념적으로는 매 프레임 다음 값을 보내는 작업이다.

```text
setUniform("u_time", elapsedSeconds)
setUniform("u_waveSpeed", waveSpeed)
setUniform("u_colorA", colorA)
setUniform("u_colorB", colorB)
```

위 코드는 특정 프레임워크의 실제 함수명이 아니라 데이터 전달을 나타내는 의사 코드다. GLSL에서는 변수 선언과 계산을 작성하고, 애플리케이션·게임 엔진·노드 도구가 각자의 방식으로 값을 바인딩한다. 프레임워크별 호출법과 셰이더 입력 규칙은 27.9에서 살펴본다.

## 시간을 입력으로 한 절차적 애니메이션

시간을 좌표나 위상에 더하면 셰이더가 매 프레임 다른 결과를 계산한다. 다음 프래그먼트 셰이더는 27.3의 버텍스 단계에서 전달한 `v_uv`를 가로 좌표로 사용하고, 시간에 따라 이동하는 색 파동을 만든다.

```glsl
#version 460 core

layout(location = 0) in vec2 v_uv;
layout(location = 0) out vec4 outColor;

uniform float u_time;
uniform float u_waveSpeed;
uniform vec3 u_colorA;
uniform vec3 u_colorB;

void main() {
    const float TAU = 6.28318530718;
    float phase = TAU * 5.0 * v_uv.x - u_time * u_waveSpeed;
    float amount = 0.5 + 0.5 * sin(phase);
    outColor = vec4(mix(u_colorA, u_colorB, amount), 1.0);
}
```

`u_time`은 초 단위로 증가하는 경과 시간이고, `u_waveSpeed`는 위상이 초당 얼마나 변하는지 조절한다. `sin()` 결과를 0~1 범위로 옮겨 두 색의 보간값으로 쓰므로, 정점이나 픽셀마다 CPU가 새 색을 계산해 보내지 않아도 GPU가 위치와 시간으로 색을 산출한다. 주파수, 속도, 색을 유니폼으로 분리해 두면 수식은 그대로 둔 채 작품의 움직임을 조절할 수 있다.

이 방식은 현재 시간에서 결과를 직접 계산한다. 같은 좌표와 같은 시간값을 넣으면 같은 색이 나오므로, 특정 시점의 프레임을 다시 렌더링하거나 애니메이션을 재생하는 데 편리하다. 여기서 GLSL이 시간을 재는 것은 아니다. 호스트가 프레임마다 새 `u_time`을 전달해야 변화가 생긴다.

## 프레임 수가 아니라 시간으로 움직이기

호스트 코드에서 매 프레임 위상을 `phase += 0.02`처럼 늘리면 애니메이션 속도는 초당 프레임 수에 좌우된다. 프레임률이 바뀌거나 렌더링이 잠시 느려지면 초당 이동량도 달라진다. 경과 시간을 유니폼으로 전달하고 셰이더에서 `sin(phase - time * speed)`를 계산하면 프레임 간격이 달라도 같은 시각의 상태를 같은 값으로 만들 수 있다.

| 시간 방식 | 갱신 형태 | 적합한 작업 |
| --- | --- | --- |
| 절대 경과 시간 | `value = f(position, elapsedTime)` | 파동, 회전, 색 변화, 반복 가능한 절차 패턴 |
| 프레임 간격 | `state += velocity * deltaTime` | 입자 위치, 관성, 물리적 상태 변화 |
| 고정 시간 간격 | 일정한 `fixedDeltaTime`으로 상태 갱신 | 재현성이 중요한 시뮬레이션과 기록 |

위 표의 상태 갱신은 셰이더가 이전 프레임을 자동으로 기억한다는 뜻이 아니다. 누적 시뮬레이션에는 이전 상태를 CPU 변수, 버퍼, 텍스처 등의 형태로 보관하고 다음 갱신 단계에 전달해야 한다. `deltaTime`은 그 사이에 흐른 시간을 나타내며, 큰 프레임 지연이 생기면 한 번의 큰 갱신이 불안정해질 수 있다. 이 경우 여러 번의 고정 간격 갱신을 수행하는 방법을 고려한다. GPU 병렬 상태와 여러 패스에 관한 내용은 26.8과 27.8에서 더 확장한다.

반면 수식만으로 정해지는 반복 패턴은 매 프레임 상태를 누적하지 않고 절대 시간에서 직접 평가하는 것이 단순하다. 애니메이션을 멈추거나, 시간을 되감거나, 오프라인으로 일정한 프레임 간격을 렌더링하기도 쉽다. 목적이 시간에 따라 변하는 규칙인지, 이전 결과가 다음 상태에 영향을 주는 시뮬레이션인지 먼저 구별한다.

## 여러 매개변수와 유니폼 블록

작은 셰이더는 개별 유니폼으로 관리하기 쉽다. 여러 셰이더 단계와 드로우 호출에 공통인 카메라 행렬, 시간, 뷰포트 크기 등 값이 늘어나면 uniform block으로 관련 데이터를 묶을 수 있다.

```glsl
layout(std140, binding = 0) uniform FrameParameters {
    vec2 u_viewportSize;
    float u_time;
    float u_deltaTime;
};
```

`std140`은 블록 멤버의 메모리 배치를 정하는 규칙이고, `binding = 0`은 블록이 연결될 바인딩 지점을 지정한다. 호스트는 블록에 맞는 버퍼를 만들고 같은 바인딩 지점에 연결해야 한다. CPU 쪽 구조체의 패딩과 GLSL의 정렬이 어긋나면 엉뚱한 값이 읽힐 수 있으므로, 블록을 사용할 때는 양쪽의 바이트 배치를 맞춘다. 소수의 값만 전달하는 단계에서는 개별 유니폼이 더 간결할 수 있다.

## 긴 실행에서 시간 정밀도 관리하기

GLSL의 일반 `float`는 유한한 정밀도를 가진다. `u_time`에 프로그램 시작 후 수십 시간 또는 매우 큰 밀리초 값을 계속 전달하면, 값이 커질수록 그 주변의 작은 시간 차이를 표현하기 어려워진다. 사인파의 위상이나 빠른 움직임이 미세하게 흔들리는 현상은 이 정밀도 손실에서 생길 수 있다.

초 단위의 경과 시간을 사용하고, 주기적인 움직임이라면 호스트에서 주기에 맞춘 제한된 위상값을 계산해 전달하는 방법이 있다. 단, 주기와 관계없이 시간을 임의로 자르면 경계에서 애니메이션이 튈 수 있으므로 해당 효과가 반복 가능한 주기를 가졌는지 확인한다. 비주기적 시뮬레이션에서는 매 프레임 작은 `deltaTime`으로 상태를 갱신하거나, 시간 원점을 주기적으로 재설정하는 설계를 고려한다.

```glsl
#version 460 core

uniform float u_phase;
layout(location = 0) out vec4 outColor;

void main() {
    float pulse = 0.5 + 0.5 * sin(u_phase);
    outColor = vec4(vec3(pulse), 1.0);
}
```

호스트는 주기적인 효과의 위상을 `mod(elapsedSeconds * speed, TAU)`처럼 한 주기 안으로 줄여 `u_phase`에 전달할 수 있다. 아주 큰 절대 시간을 셰이더에 보낸 뒤 `mod()`를 적용하는 것만으로는 앞서 잃은 부동소수점 정밀도를 복원할 수 없다. 호스트의 시간 표현과 셰이더에 전달하는 범위를 함께 관리한다.

## 시간과 매개변수의 역할 나누기

시간은 변화의 진행을 나타내고, 유니폼 파라미터는 그 변화 규칙을 조절한다. 두 역할을 분리하면 같은 셰이더를 여러 방식으로 제어할 수 있다.

```text
u_time       -> 현재 애니메이션 시점
u_frequency  -> 반복 횟수 또는 공간 주파수
u_speed      -> 시간에 따른 위상 변화량
u_amplitude  -> 변화의 크기
u_colorA/B   -> 결과를 매핑할 색상
```

창 크기나 렌더 타깃 크기가 달라질 때는 해상도와 뷰포트 유니폼을 갱신하고, 사용자 조작으로 조절하는 값은 입력 이벤트가 바뀔 때 또는 프레임마다 전달한다. 다만 어떤 값이 전역 설정이고 어떤 값이 재질·오브젝트별 값인지 구분하여, 필요한 범위에서만 값을 변경한다. 27.3의 뷰포트 정규화와 결합하면 해상도가 달라져도 일정한 화면 기준으로 패턴을 계산할 수 있다.

## 이 절의 핵심

유니폼은 호스트가 셰이더에 전달하는 공유 입력이며 GLSL 코드 안에서 시간을 만들어 내지 않는다. 프레임률과 무관한 절차적 애니메이션은 경과 시간에서 결과를 직접 계산하고, 상태가 누적되는 시뮬레이션은 이전 상태와 `deltaTime` 또는 고정 시간 간격을 별도로 관리한다. 긴 실행에서는 `float` 정밀도와 반복 주기를 고려해 셰이더에 전달할 시간 범위를 제한한다.
