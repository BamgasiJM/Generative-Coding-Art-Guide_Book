# 18.3 CPU 기반 그래픽과 GPU 기반 그래픽

CPU와 GPU의 차이는 속도만으로 설명할 수 없다. 두 장치는 서로 다른 작업에 적합하도록 설계되었으며, 제너레이티브 아트에서는 그 차이가 프로그램의 구조와 표현 방식에도 영향을 준다.

CPU는 비교적 적은 수의 강력한 코어로 복잡한 제어 흐름을 처리하는 데 적합하다. 조건에 따라 전혀 다른 작업을 하거나, 목록을 관리하거나, 사용자 입력과 파일을 처리하고, 요소 사이의 불규칙한 관계를 탐색하는 작업이 여기에 속한다. JavaScript, Python, C++, Rust, Clojure로 작성하는 일반 애플리케이션 코드는 주로 CPU에서 실행된다.

GPU는 같은 종류의 작은 계산을 매우 많은 데이터에 동시에 적용하는 데 적합하다. 화면의 모든 픽셀에서 같은 색 계산을 하거나, 수십만 개 정점의 위치를 변형하거나, 큰 텍스처의 각 칸을 갱신하는 일은 GPU의 병렬 구조와 잘 맞는다.

| 관점 | CPU | GPU |
| --- | --- | --- |
| 강점 | 복잡한 제어 흐름, 데이터 관리, 순차적 의사결정 | 대량의 비슷한 계산, 이미지·정점·버퍼 처리 |
| 자연스러운 단위 | 객체, 배열, 이벤트, 함수 호출 | 픽셀, 정점, 텍스처 셀, 인스턴스 |
| 조건 분기 | 복잡해도 비교적 자연스러움 | 같은 묶음의 실행 경로가 갈리면 효율 저하 가능 |
| 데이터 위치 | 시스템 메모리 | 그래픽 메모리(VRAM) |
| 흔한 역할 | 입력, 장면 구성, 시뮬레이션 제어 | 렌더링, 필드 평가, 후처리, 대규모 병렬 갱신 |

CPU 기반 그래픽에서는 프로그램이 도형 목록을 만들고, 각 도형의 속성을 계산해 드로잉 API에 전달한다. 예를 들어 1,000개의 입자는 CPU 배열에 저장하고, 반복문에서 위치를 갱신한 다음 원이나 선으로 그릴 수 있다.

```text
for each particle:
    particle.velocity += force(particle.position) * deltaTime
    particle.position += particle.velocity * deltaTime
    drawCircle(particle.position, particle.radius)
```

이 방식은 입자마다 다른 수명, 충돌 조건, 이벤트, 데이터 구조를 적용하기 좋다. 그러나 해상도 전체를 매 프레임 순회하거나 요소 수가 매우 많아지면 CPU가 병목이 될 수 있다. 특히 JavaScript에서 수백만 픽셀을 반복 처리한 뒤 캔버스에 다시 올리는 작업은 프레임률을 낮추기 쉽다.

GPU 기반 그래픽에서는 CPU가 셰이더 프로그램과 입력 데이터를 준비하고, GPU가 정점 또는 픽셀마다 계산을 실행한다. 프래그먼트 셰이더의 다음 코드는 하나의 픽셀만 계산하는 것처럼 보이지만, 실제로는 렌더링 대상의 모든 픽셀에서 병렬로 실행된다.

```glsl
vec2 p = uv - 0.5;
float wave = sin(length(p) * frequency - time * speed);
vec3 color = vec3(0.5 + 0.5 * wave);
```

GPU가 빠른 이유는 모든 계산을 한순간에 처리하기 때문이 아니다. 많은 실행 단위가 같은 명령을 수행할 때 하드웨어 자원을 효율적으로 활용할 수 있기 때문이다. 따라서 각 픽셀이 크게 다른 경로를 택하는 복잡한 `if` 문, 데이터 의존적인 긴 반복, 서로 멀리 떨어진 메모리 접근은 기대만큼 효율적이지 않을 수 있다.

CPU와 GPU 사이의 데이터 이동도 중요한 비용이다. CPU에서 만든 배열을 매 프레임 GPU로 보내거나, GPU에서 계산한 큰 텍스처를 CPU 메모리로 다시 읽어 오면 전송과 동기화가 병목이 될 수 있다. 다음과 같은 흐름도 가능하지만, 고해상도에서 매 프레임 반복하면 비용이 크다.

```text
CPU: create image pixels
upload pixels to GPU
GPU: render texture
read rendered pixels back to CPU
CPU: analyze pixels
```

가능하면 데이터가 머무는 처리 장치에서 계산을 이어간다. 예를 들어 노이즈 배경과 색상 보정이 모두 GPU 작업이라면, 중간 이미지를 CPU로 가져오지 않고 텍스처와 프레임 버퍼 사이에서 처리한다. 반대로 사용자 입력을 바탕으로 복잡한 규칙을 결정하는 일은 CPU에서 처리하고, 최종 파라미터만 유니폼으로 GPU에 전달한다.

```glsl
// CPU가 프레임마다 보낼 수 있는 작은 입력의 예
uniform float time;
uniform vec2 pointer;
uniform float intensity;
```

유니폼은 모든 셰이더 실행 단위가 공유하는 값이다. 시간, 화면 크기, 마우스 좌표, 팔레트 파라미터처럼 작고 공통적인 데이터를 보내기에 적합하다. 많은 개체의 위치·색·크기처럼 항목별 데이터는 정점 버퍼, 인스턴스 버퍼, 텍스처 버퍼 같은 별도 구조를 사용한다.

입자와 시뮬레이션에서는 작업을 어떻게 나눌지도 고려해야 한다. 수천 개의 입자가 복잡한 이웃 관계를 갖고 자주 추가·삭제된다면 CPU 기반 구조가 이해하기 쉽다. 반면 각 입자가 독립적인 노이즈 필드에서 움직이거나, 격자의 모든 셀에 같은 반응-확산 규칙을 적용한다면 GPU 컴퓨트 셰이더나 프레임 버퍼 피드백이 유리할 수 있다. 중간 규모의 작업에서는 CPU가 상태를 갱신하고 GPU가 그 상태를 대량으로 시각화하는 혼합 방식도 흔하다.

성능 문제가 생기면 먼저 어느 단계에서 비용이 발생하는지 측정한다. 도형 호출이 많은지, 픽셀 순회가 많은지, 셰이더가 무거운지, 버퍼 전송이 잦은지에 따라 해결책이 달라진다. CPU 코드를 GPU로 옮긴다는 말만으로는 개선이 보장되지 않는다. 데이터를 옮기는 비용, 알고리즘의 분기 구조, 메모리 사용량, 원하는 출력 해상도를 함께 살펴야 한다.

마지막으로 CPU와 GPU의 역할은 도구에 따라 감춰져 있을 수 있다. p5.js의 일반 드로잉은 내부적으로 GPU 가속을 사용할 수 있고, Canvas API도 브라우저 구현에 따라 GPU를 활용한다. 그러나 프로그래머가 어떤 계산을 CPU 배열에서 하고 어떤 계산을 셰이더에서 하는지는 여전히 설계의 문제다. 이 책에서는 실행 장치의 이름에 앞서, 계산이 개체를 순회하는지 각 위치에서 독립적으로 평가되는지 살펴본다.

## 이 절의 핵심

CPU는 복잡한 제어 흐름과 데이터 관리에, GPU는 대량의 유사한 병렬 계산에 강하다. 작업을 나눌 때는 계산량뿐 아니라 CPU와 GPU 사이의 데이터 이동, 분기 구조, 데이터가 머무는 위치를 함께 고려한다.
