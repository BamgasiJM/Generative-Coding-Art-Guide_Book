# 18.1 드로잉 API와 셰이딩 언어

제너레이티브 아트를 구현하는 그래픽 환경은 크게 드로잉 API를 중심으로 하는 환경과 셰이딩 언어를 중심으로 하는 환경으로 나누어 생각할 수 있다. 둘은 모두 좌표, 색, 시간, 난수, 함수처럼 이 책에서 다룬 같은 수학을 사용한다. 차이는 그 수학을 어느 단계에서, 어떤 단위로, 어떤 하드웨어 위에서 실행하는가에 있다.

드로잉 API는 대개 프로그램이 그래픽 명령을 순서대로 호출하는 방식이다. 원을 그리려면 중심과 반지름을 지정하고, 선을 그리려면 두 점을 지정한다. 캔버스, 색, 변환 행렬, 선의 두께처럼 현재 그리기 상태를 설정한 뒤 도형을 배치한다.

```text
setFill(color)
drawCircle(center, radius)
drawLine(start, end)
```

Canvas 2D, p5.js, Processing, raylib, openFrameworks의 일반적인 2D 드로잉 코드는 이 흐름에 가깝다. 반복문으로 좌표를 만들고, 각 좌표에 도형 명령을 내리면 격자, 점묘, 선의 집합 같은 이미지를 얻는다. 개체의 목록을 만들고 하나씩 갱신하는 입자 시스템도 이 방식으로 이해하기 쉽다.

반면 셰이딩 언어는 화면의 정점이나 픽셀처럼 매우 많은 실행 단위에 같은 프로그램을 병렬로 적용한다. 프래그먼트 셰이더에서는 "이 픽셀에 원을 그려라"라는 명령보다 "이 픽셀 좌표에서 원까지의 거리는 얼마인가"라는 계산을 작성하는 일이 많다. 계산 결과를 색으로 반환하면 GPU가 화면 전체의 픽셀에서 이 함수를 실행한다.

```glsl
float d = length(uv - center) - radius;
float mask = 1.0 - smoothstep(-edge, edge, d);
vec3 color = mix(background, foreground, mask);
```

이 코드는 원이라는 그래픽 객체를 직접 추가하지 않는다. 대신 모든 위치 `uv`에서 거리 함수를 평가하고, 그 값으로 색을 정한다. 따라서 셰이더는 Part 2에서 다룬 거리 함수, Part 3의 좌표 변형, Part 4의 노이즈와 필드를 화면 전체에 적용하는 데 자연스럽다.

두 방식을 다음처럼 비교할 수 있다.

| 관점 | 드로잉 API | 셰이딩 언어 |
| --- | --- | --- |
| 기본 질문 | 어떤 도형을 어떤 순서로 그릴까 | 이 위치에서 어떤 값을 계산할까 |
| 대표 단위 | 도형, 경로, 이미지, 개체 | 정점, 픽셀, 표면의 표본 |
| 주된 흐름 | 명령을 호출해 장면을 구성 | 함수를 병렬로 평가해 출력 생성 |
| 잘 맞는 작업 | 개체 배치, 입력 처리, 구조적 드로잉 | 필드, 재질, 화면 효과, 대량 픽셀 계산 |
| 상태의 위치 | 프로그램 객체와 캔버스 상태 | 유니폼, 텍스처, 버퍼, 셰이더 입력 |

이 표는 두 방식을 완전히 나누는 경계가 아니다. 드로잉 API 환경에서도 셰이더를 호출할 수 있고, 셰이더로 만든 텍스처 위에 CPU 드로잉을 더할 수 있다. openFrameworks나 nannou처럼 두 방식을 함께 쓰는 환경도 많다. 또한 GPU에서 실행된다고 해서 모든 코드가 셰이더인 것은 아니다. 창 관리, 입력, 데이터 준비, 셰이더 파라미터 갱신은 보통 애플리케이션 코드가 담당한다.

같은 알고리즘을 두 방식으로 번역해 보면 차이가 더 선명해진다. 예를 들어 $20\times20$ 격자에 원을 배치하는 작업을 드로잉 API로 구현할 때는 400개의 셀을 순회하며 원을 그린다. 셰이더에서는 현재 픽셀의 좌표를 셀 좌표와 셀 내부 좌표로 분해한 뒤, 셀 중심까지의 거리를 한 번 계산한다. 전자는 개체 중심의 사고이고, 후자는 필드 중심의 사고다.

```text
# 드로잉 API의 의사코드
for each cell in grid:
    center = cellCenter(cell)
    drawCircle(center, radiusFor(cell))
```

```glsl
// 프래그먼트 셰이더의 개념 예시
vec2 cellUV = fract(uv * gridCount) - 0.5;
float d = length(cellUV) - radius;
```

성능도 선택 기준이 될 수 있다. 수천 개의 개체를 갱신하고 서로의 관계를 계산하는 일은 CPU 구조와 자료구조가 더 중요할 수 있다. 반면 화면 전체의 노이즈, 거리 필드, 색상 변환처럼 픽셀마다 독립적인 계산은 GPU 병렬 처리의 이점을 크게 얻는다. 그러나 GPU가 언제나 빠른 것은 아니다. CPU와 GPU 사이의 데이터 전송, 복잡한 분기, 큰 텍스처 버퍼의 반복 읽기는 병목이 될 수 있다.

학습 순서에서도 두 관점은 서로 보완적이다. 드로잉 API는 좌표와 반복문, 상태, 개체를 눈에 보이는 명령으로 연결하기 좋다. 셰이딩 언어는 같은 수학을 함수와 공간의 관점에서 더 직접적으로 다루게 한다. 어느 하나를 다른 하나의 하위 단계로 볼 필요는 없다. 작품이 요구하는 구조와 표현 방식에 따라 적절한 실행 모델을 고르는 것이 중요하다.

이 장에서는 먼저 두 환경을 구분하는 기준을 살피고, 이어지는 장에서 각 환경의 문법과 작업 흐름을 다룬다. 이후 Part 6의 목표는 하나의 수학적 규칙을 여러 도구에서 똑같이 복사하는 것이 아니라, 각 환경의 장점을 살려 같은 규칙을 번역하는 능력을 기르는 데 있다.

## 이 절의 핵심

드로잉 API는 도형과 명령의 순서로 장면을 구성하고, 셰이딩 언어는 정점·픽셀·표면 위치에서 함수를 병렬로 평가한다. 두 방식은 같은 수학을 공유하며, 개체 중심의 구조적 드로잉과 필드 중심의 픽셀 계산이라는 서로 다른 강점을 제공한다.
