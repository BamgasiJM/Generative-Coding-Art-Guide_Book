# 18.6 하나의 알고리즘을 환경별 코드로 번역하는 방법

같은 제너레이티브 규칙을 p5.js, raylib, GLSL, OSL처럼 서로 다른 환경으로 옮길 때 가장 먼저 바뀌는 것은 문법이다. 그러나 문법만 바꿔 옮기려 하면 쉽게 길을 잃는다. 반복문이 픽셀 셰이더에서는 보이지 않고, 하나의 색 반환문이 드로잉 API에서는 수백 번의 도형 호출로 바뀌기 때문이다. 번역의 출발점은 코드가 아니라 환경과 무관한 알고리즘이다.

알고리즘을 다음 네 층으로 분리하면 옮기기 쉽다.

| 층 | 물어볼 질문 | 예 |
| --- | --- | --- |
| 입력 | 무엇을 알고 시작하는가 | 좌표, 시간, 시드, 마우스 위치 |
| 규칙 | 입력에서 어떤 값을 계산하는가 | 거리, 노이즈, 파동, 이웃 합 |
| 구조 | 몇 번, 어떤 단위로 평가하는가 | 셀 반복, 픽셀 병렬 평가, 정점 순회 |
| 출력 | 계산값을 어디에 연결하는가 | 색, 도형 크기, 변위, 재질 |

예를 들어 "반복된 원 필드"를 만들고 싶다고 하자. 핵심 규칙은 정규화된 좌표를 격자로 반복하고, 각 셀 중심까지의 거리를 구한 뒤, 거리로 원의 안팎을 결정하는 것이다.

$$
\mathbf{q}=\operatorname{fract}(\mathbf{p}n)-\frac{1}{2},\qquad
d=\|\mathbf{q}\|-r
$$

이 식에는 아직 p5.js도 GLSL도 들어 있지 않다. $\mathbf{p}$가 어느 좌표계인지, $n$이 셀 수인지, $r$이 셀 내부 좌표에서의 반지름인지라는 의미만 정해져 있다. 먼저 다음처럼 의사코드로 규칙을 고정한다.

```text
function circleField(normalizedPosition, gridCount, radius):
    cellPosition = fractionalPart(normalizedPosition * gridCount) - 0.5
    distanceToCenter = length(cellPosition) - radius
    return distanceToCenter

for each output position:
    d = circleField(position, gridCount, radius)
    output = colorFromDistance(d)
```

이제 환경별로 세 가지 결정을 내린다. 첫째, `output position`은 무엇인가. 둘째, 그 위치를 어떻게 정규화하는가. 셋째, `output`은 실제로 어떤 API 호출 또는 셰이더 반환값이 되는가.

## 1. 반복 단위를 찾기

드로잉 API에서는 화면의 모든 픽셀보다 격자의 각 셀을 반복 단위로 삼는 편이 자연스럽다. 셀 중심과 반지름을 계산한 뒤 원 하나를 그린다. 반면 프래그먼트 셰이더에서는 GPU가 이미 각 픽셀을 반복하므로, 코드에서 셀을 순회할 필요가 없다. 현재 픽셀의 좌표를 셀 내부 좌표로 바꾸면 된다.

| 환경의 성격 | 자연스러운 반복 단위 | 흔한 출력 |
| --- | --- | --- |
| 드로잉 API | 개체, 셀, 입자, 선분 | `circle`, `line`, `fill` 호출 |
| CPU 픽셀 버퍼 | 이미지 픽셀 | 픽셀 배열의 색 값 |
| 프래그먼트 셰이더 | 화면 픽셀 또는 표면 표본 | 최종 색 반환 |
| 버텍스 셰이더 | 메시 정점 | 변환된 위치·속성 |
| OSL 표면 셰이더 | 렌더러가 표본화한 표면점 | 색·거칠기·클로저 |

이 선택은 성능을 위한 최적화 이전에 표현 모델의 선택이다. 원이 독립된 개체로 움직이고 상호작용한다면 드로잉 API의 셀·객체 반복이 자연스럽다. 화면 전체의 원 패턴을 마스크나 재질로 쓰려면 픽셀 또는 표면점 평가가 더 직접적이다.

## 2. 좌표계를 같은 의미로 맞추기

환경마다 원점, y축 방향, 좌표 범위가 다르다. p5.js의 기본 2D 캔버스는 왼쪽 위가 원점이고 y가 아래로 증가한다. 많은 셰이더의 UV 좌표는 왼쪽 아래를 원점으로 쓰거나 텍스처 설정에 따라 뒤집힐 수 있다. OSL에서는 UV, 오브젝트 공간, 월드 공간 중 하나를 직접 선택해야 한다.

따라서 알고리즘에 넣기 전 좌표를 공통 규약으로 변환한다. 예를 들어 화면의 짧은 변을 기준으로 중심이 $(0,0)$인 좌표계를 만들면, 가로세로 비율이 다른 화면에서도 원이 타원이 되지 않는다.

$$
\mathbf{p}=\frac{\mathbf{x}-\frac{1}{2}(W,H)}{\min(W,H)}
$$

```text
centered = pixelPosition - 0.5 * canvasSize
normalized = centered / min(canvasWidth, canvasHeight)
```

정규화는 단위도 통일한다. 픽셀 단위 반지름을 쓰는지, 셀 폭의 비율을 쓰는지, $[0,1]$ UV 범위를 쓰는지 명확히 정한다. 이 과정을 건너뛰면 알고리즘은 옮겼는데 화면 비율과 크기 때문에 전혀 다른 결과가 나타난다.

## 3. 규칙과 출력을 연결하기

드로잉 API에서는 거리 함수의 결과를 도형의 반지름, 색, 투명도에 연결할 수 있다. 여기서는 각 셀에 원을 하나씩 그리는 `p5.js 예제`를 보자.

```javascript
// p5.js 예제
function draw() {
  background(245);
  const count = 12;
  const cellW = width / count;
  const cellH = height / count;

  noStroke();
  for (let y = 0; y < count; y += 1) {
    for (let x = 0; x < count; x += 1) {
      const cx = (x + 0.5) * cellW;
      const cy = (y + 0.5) * cellH;
      const r = 0.32 * Math.min(cellW, cellH);
      circle(cx, cy, 2 * r);
    }
  }
}
```

이 예제는 셀의 중심을 계산하고 `circle()`을 호출한다. 원의 반지름을 노이즈나 시간 함수로 바꾸면 셀별 패턴과 애니메이션을 만들 수 있다. 반면 GLSL에서는 화면의 각 픽셀이 자신의 셀 내부 좌표와 거리를 계산한다.

```glsl
// GLSL 프래그먼트 셰이더 예제
vec2 p = uv - 0.5;
p.x *= resolution.x / resolution.y;

float count = 12.0;
vec2 cell = fract(p * count) - 0.5;
float d = length(cell) - 0.16;
float mask = 1.0 - smoothstep(-0.005, 0.005, d);

vec3 color = mix(vec3(0.96), vec3(0.08), mask);
```

두 코드는 줄 단위로 대응하지 않는다. p5.js 코드는 셀마다 하나의 원을 만들고, GLSL은 픽셀마다 원 필드를 평가한다. 그러나 반복, 중심 좌표, 반지름, 거리, 색이라는 수학적 역할은 대응한다. 이런 역할 단위의 비교가 환경 번역에서 더 유용하다.

## 4. 상태와 시간의 위치를 결정하기

정적인 규칙은 좌표를 입력으로 받아 바로 계산할 수 있다. 시간이 들어가면 각 환경에서 시간값을 어디서 얻는지가 달라진다. p5.js에서는 `millis()`나 `deltaTime`, raylib에서는 `GetTime()`, GLSL에서는 애플리케이션이 전달하는 `uniform float time`을 사용할 수 있다. 시간의 출처는 달라도 알고리즘에는 초 단위 실수 $t$ 하나만 전달한다고 생각한다.

상태가 있는 시스템은 더 주의가 필요하다. CPU 드로잉 환경에서는 객체 배열에 위치와 속도를 저장하는 방식이 자연스럽다. GPU 셰이더에서는 이전 프레임의 텍스처를 읽고 새 텍스처에 결과를 쓰는 피드백 버퍼를 사용할 수 있다. 즉, `state = update(state)`라는 공통 규칙은 유지되지만 상태의 저장 위치와 갱신 단위가 달라진다.

```text
CPU: particle array -> update each object -> draw objects
GPU: previous texture -> shader evaluates each texel -> next texture
```

## 5. 검증 가능한 작은 단위로 옮기기

환경을 바꿀 때 완성된 작품을 한 번에 옮기지 않는다. 먼저 고정된 배경과 하나의 도형을 만들고, 좌표 정규화와 방향을 확인한다. 다음으로 반복, 색, 시간, 노이즈, 상태를 하나씩 추가한다. 각 단계에서 같은 입력값과 시드를 사용하면 두 구현을 비교하기 좋다.

특히 다음 항목을 확인한다.

- 원점과 y축 방향이 같은가
- 시간과 속도의 단위가 초 기준으로 일치하는가
- 난수 시드와 노이즈의 출력 범위가 같은가
- 알파·색 공간·블렌딩 방식이 같은가
- 셀 수와 반지름이 같은 좌표 단위로 표현되는가

완전히 같은 픽셀 결과를 목표로 할 필요는 없다. 라이브러리의 안티앨리어싱, 노이즈 구현, 색 보정, 부동소수점 정밀도가 다르면 미세한 차이는 자연스럽다. 목표는 규칙의 구조와 시각적 의도가 다른 환경에서도 유지되는 것이다.

## 이 절의 핵심

알고리즘을 환경별 코드로 옮길 때는 입력, 규칙, 반복 단위, 출력으로 먼저 분리한다. 그 뒤 좌표계·시간·상태의 저장 위치를 환경에 맞게 번역한다. 문법의 일대일 대응보다 수학적 역할의 대응을 기준으로 삼아야 같은 규칙을 다른 그래픽 환경에서 안정적으로 구현할 수 있다.
