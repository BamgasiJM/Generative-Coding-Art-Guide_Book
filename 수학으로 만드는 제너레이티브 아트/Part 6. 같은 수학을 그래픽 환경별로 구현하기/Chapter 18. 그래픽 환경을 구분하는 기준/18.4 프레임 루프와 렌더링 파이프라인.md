# 18.4 프레임 루프와 렌더링 파이프라인

실시간 그래픽 프로그램은 한 번 그림을 그린 뒤 끝나지 않는다. 프로그램이 실행되는 동안 입력을 받고, 상태를 갱신하고, 장면을 그려 화면에 표시하는 일을 반복한다. 이 반복 구조를 프레임 루프(frame loop)라고 한다. 애니메이션, 인터랙션, 입자, 피드백 시스템은 모두 프레임 루프 위에서 작동한다.

가장 단순한 프레임 루프는 다음과 같이 요약할 수 있다.

```text
initialize()

while applicationIsRunning():
    input = pollInput()
    deltaTime = measureElapsedTime()
    update(state, input, deltaTime)
    render(state)
    presentFrame()
```

`initialize()` 단계에서는 창과 렌더링 표면을 만들고, 이미지·폰트·셰이더를 불러오며, 초기 상태와 파라미터를 설정한다. 반복 안에서는 보통 네 가지 일이 일어난다. 운영체제와 장치에서 입력을 받고, 이전 프레임 이후의 시간을 측정하고, 상태를 갱신하고, 현재 상태를 화면으로 렌더링한다. 마지막의 `presentFrame()`은 완성된 이미지를 화면에 표시한다.

환경마다 이름은 다르지만 구조는 비슷하다. p5.js와 Processing에서는 `setup()`이 초기화, `draw()`가 프레임 반복에 해당한다. openFrameworks는 `setup()`, `update()`, `draw()`를 분리하고, raylib은 윈도우가 닫힐 때까지 반복하는 명시적 게임 루프를 사용한다. 브라우저의 Canvas나 WebGL에서는 `requestAnimationFrame()`이 다음 프레임 시점을 알려 준다.

```javascript
// Canvas 또는 WebGL 환경의 개념 예시
function frame(now) {
  const deltaTime = (now - previousTime) / 1000;
  previousTime = now;

  update(deltaTime);
  render();
  requestAnimationFrame(frame);
}

requestAnimationFrame(frame);
```

프레임 루프에서 중요한 값 가운데 하나는 `deltaTime`, 즉 프레임 사이에 실제로 경과한 시간이다. 프레임률이 60fps라면 이상적으로는 약 $1/60$초마다 반복되지만, 운영체제 작업, 브라우저 상태, 화면 해상도, 렌더링 부하에 따라 간격은 달라진다. 속도에 `deltaTime`을 곱하지 않으면 프레임이 빠른 기기에서 객체가 더 빨리 움직인다.

$$
\mathbf{p}_{new}=\mathbf{p}_{old}+\mathbf{v}\Delta t
$$

```text
position += velocity * deltaTime
rotation += angularVelocity * deltaTime
age += deltaTime
```

렌더링 파이프라인(rendering pipeline)은 현재 상태가 화면 픽셀로 바뀌는 경로를 가리킨다. 2D 드로잉 API에서는 그리기 명령을 순서대로 해석하고, 변환·클리핑·블렌딩을 적용해 렌더링 표면에 기록하는 흐름으로 볼 수 있다. 3D와 GPU 셰이더 환경에서는 정점 처리, 래스터화, 프래그먼트 처리, 깊이 검사, 블렌딩 같은 단계가 더 명시적으로 나타난다.

```text
scene data
    -> vertex processing
    -> rasterization
    -> fragment or pixel processing
    -> depth and blending
    -> framebuffer
    -> display
```

정점 처리는 도형의 꼭짓점을 변환하고, 래스터화는 삼각형 같은 기하를 화면의 픽셀 후보로 바꾼다. 프래그먼트 셰이더는 각 후보 위치의 색을 계산한다. 그 뒤 깊이 검사와 블렌딩이 다른 도형이나 기존 화면과의 관계를 결정하고, 최종 결과가 프레임 버퍼에 기록된다. 2D 작업에서도 이 파이프라인의 일부는 내부적으로 작동하지만 API가 세부 단계를 감춰 줄 뿐이다.

프레임 버퍼는 현재 프레임의 픽셀을 담는 렌더링 대상이다. 그리는 중간 화면이 드러나지 않도록 보통 화면에 보이는 버퍼와 다음 프레임을 그리는 버퍼를 분리한다. 이를 더블 버퍼링(double buffering)이라고 한다. 보이지 않는 버퍼에 렌더링을 마친 뒤 두 버퍼를 교체하면, 그림을 그리는 중간 상태가 화면에 노출되는 것을 줄일 수 있다.

```text
render into backBuffer
swap frontBuffer and backBuffer
display frontBuffer
```

오프스크린 렌더링은 결과를 바로 화면에 표시하지 않고 별도의 버퍼에 그리는 방식이다. 블러, 그림자, 잔상, 마스크, 피드백, 여러 단계의 합성에 사용한다. 예를 들어 이전 프레임 버퍼를 조금 흐리게 하고 새 입자 선을 더한 뒤 그 결과를 최종 화면에 표시할 수 있다. 이때 버퍼는 단순한 그림판이 아니라 다음 계산에 사용되는 데이터가 된다.

프레임 루프의 순서도 결과를 바꾼다. 일반적으로는 입력을 읽고 상태를 갱신한 뒤 렌더링한다. 그러면 사용자가 이번 프레임에 움직인 마우스 위치가 바로 화면에 반영된다. 반대로 이전 상태를 먼저 그린 뒤 갱신하면 표현이 한 프레임 늦어진다. 대부분의 경우 차이는 작지만, 빠른 상호작용이나 충돌 처리에서는 체감될 수 있다.

업데이트나 렌더링에 시간이 오래 걸리면 프레임률이 낮아진다. 프레임률을 높이기 위해 무조건 계산을 줄이기보다, 어떤 단계가 비용을 쓰는지 구분한다. 많은 도형 호출이 문제인지, 고해상도 후처리 셰이더가 문제인지, 텍스처 전송이 문제인지에 따라 해결책이 다르다. 프로파일러나 간단한 시간 측정으로 병목을 확인하는 습관이 중요하다.

```text
start = currentTime()
update(state, deltaTime)
updateCost = currentTime() - start

start = currentTime()
render(state)
renderCost = currentTime() - start
```

프레임 루프는 실시간 작업만을 위한 구조는 아니다. 동일한 루프를 정해진 시간 간격으로 반복하면 영상용 이미지 시퀀스를 만들 수 있다. 이 경우에는 실제 시간 대신 프레임 번호로부터 시간을 계산한다. 예를 들어 30fps, 10초 영상은 300개 프레임을 만들고, 각 프레임의 시간은 $t=i/30$으로 정한다. 이렇게 하면 컴퓨터의 처리 속도와 무관하게 정확한 시간 간격으로 결과를 내보낼 수 있다.

$$
t_i=\frac{i}{\text{frameRate}}
$$

프레임 루프와 렌더링 파이프라인을 구분하면 각 작업을 둘 위치가 분명해진다. 상태 변화와 입력 처리는 업데이트에, 도형과 픽셀을 화면으로 옮기는 일은 렌더링에, 여러 렌더 결과를 축적하고 섞는 일은 버퍼와 파이프라인에 둔다. 이후 Part 6에서 만날 각 도구는 문법은 달라도 이 구조를 서로 다른 방식으로 드러낸다.

## 이 절의 핵심

프레임 루프는 입력, 시간 측정, 상태 업데이트, 렌더링, 화면 표시를 반복한다. 렌더링 파이프라인은 현재 상태를 프레임 버퍼의 픽셀로 바꾸는 과정이며, `deltaTime`, 더블 버퍼링, 오프스크린 버퍼는 안정적인 시간 변화와 합성의 기반이 된다.
