# 18.2 명령형 드로잉과 픽셀 단위 계산

화면에 원 백 개를 배치한 결과는 같아 보여도, 이를 만드는 프로그램의 사고방식은 크게 다를 수 있다. 명령형 드로잉은 무엇을 그릴지 순서대로 지시한다. 픽셀 단위 계산은 화면의 각 위치에서 최종 색이 무엇인지 계산한다. 전자는 장면을 구성하는 절차에, 후자는 공간 함수를 평가하는 일에 초점을 둔다.

명령형 드로잉에서는 보통 캔버스의 상태를 설정하고 도형 명령을 호출한다. 반복문은 여러 개체를 생성하거나 배치하는 도구가 된다.

```text
setBackground(white)

for row from 0 to rows - 1:
    for col from 0 to cols - 1:
        center = cellCenter(col, row)
        radius = radiusFor(col, row)
        setFill(colorFor(col, row))
        drawCircle(center, radius)
```

이 코드에서는 원이 독립적인 그래픽 객체다. 프로그램은 첫 번째 원, 두 번째 원, 세 번째 원을 차례로 그린다. 뒤에 그린 도형은 앞서 그린 도형을 덮을 수 있으며, 현재 설정된 색·변환·블렌딩 상태는 이후 명령에도 적용된다. 이런 상태 기반 흐름은 일러스트레이션, 타일 배치, 입자 목록, 사용자 입력에 따른 도형 추가처럼 개체가 분명한 작업에서 직관적이다.

픽셀 단위 계산에서는 화면의 각 위치에서 최종 색을 구한다. 화면의 픽셀 좌표 $\mathbf{p}$가 주어졌을 때, 그 위치가 어느 셀에 속하는지와 셀 중심까지의 거리를 계산한다. 그 거리로 원의 안팎을 판단한 뒤 색을 반환한다.

$$
\mathbf{c}=\operatorname{fract}(\mathbf{p}\,n)-\frac{1}{2},\qquad
d=\|\mathbf{c}\|-r
$$

여기서 $n$은 한 축의 셀 수이고, $\operatorname{fract}$는 좌표의 소수부만 남겨 각 셀 내부의 반복 좌표를 만든다. $d<0$인 위치는 원 내부, $d>0$인 위치는 원 외부다.

```glsl
// 프래그먼트 셰이더 예제
vec2 cell = fract(uv * gridCount) - 0.5;
float distanceToCenter = length(cell) - radius;
float circle = 1.0 - smoothstep(-edge, edge, distanceToCenter);
vec3 color = mix(backgroundColor, foregroundColor, circle);
```

이 코드에는 "원을 400번 그린다"는 명령이 없다. GPU는 화면의 각 픽셀에서 같은 코드를 실행해 해당 위치의 색을 계산한다. 반복 격자는 좌표의 소수부 연산으로 생긴다. 따라서 셀 수를 키워도 프로그램의 구조는 거의 변하지 않는다. 이 방식은 패턴을 개체 목록이 아니라 연속적인 필드로 다룬다.

도형이 겹칠 때 두 방식의 차이가 드러난다. 명령형 드로잉에서 두 반투명 원이 겹칠 때의 결과는 그리는 순서와 블렌딩 모드에 의존한다. 픽셀 단위 계산에서는 두 원의 거리 함수 $d_1$, $d_2$를 먼저 조합한 후 하나의 색을 결정할 수 있다.

$$
d_{union}=\min(d_1,d_2)
$$

```glsl
float d = min(circleSDF(p, a, rA), circleSDF(p, b, rB));
float mask = 1.0 - smoothstep(-edge, edge, d);
```

전자는 레이어를 쌓는 방식이고, 후자는 도형 자체의 공간적 정의를 합성하는 방식이다. 두 방식은 서로 다른 결과를 내므로, 의도한 겹침의 의미에 맞춰 선택한다. 예를 들어 수채화처럼 물감이 쌓이는 느낌에는 레이어 합성이 자연스럽고, 두 도형이 하나의 유기적 윤곽으로 합쳐지는 느낌에는 거리 필드 합성이 알맞다.

명령형 드로잉에서도 픽셀을 직접 읽고 쓸 수 있다. Canvas 2D의 `ImageData`, Processing의 `pixels[]`, openFrameworks의 이미지 버퍼처럼 픽셀 배열에 접근하는 API가 있다. 이 경우 CPU가 모든 픽셀을 순회하면서 색을 계산한다.

```text
for each pixel (x, y):
    p = normalizePixelCoordinate(x, y)
    pixels[x, y] = fieldToColor(pattern(p))
```

이 방법은 셰이더와 같은 필드 중심의 수학을 사용하지만, 실행 위치는 CPU다. 해상도가 높아질수록 반복 횟수가 빠르게 늘어난다. 따라서 매 프레임 전체 픽셀을 갱신할 때는 GPU 셰이더가 유리한 경우가 많다. 반대로 픽셀 값을 프로그램의 다른 데이터 구조와 복잡하게 결합하거나, 낮은 해상도의 이미지를 한 번만 만들 때는 CPU 픽셀 접근도 충분히 실용적이다.

성능을 이야기할 때는 도형 수와 픽셀 수를 함께 봐야 한다. 작은 원 열 개를 그리는 작업은 픽셀마다 복잡한 거리 함수를 평가하는 것보다 일반 드로잉 API가 간단할 수 있다. 반면 전체 화면에 fBm 노이즈를 입히거나 각 픽셀에서 여러 거리 필드를 조합하는 작업은 수백만 픽셀의 독립 계산을 병렬 처리하는 셰이더에 잘 맞는다. 단, 셰이더도 텍스처 표본화, 조건 분기, 여러 번의 화면 버퍼 읽기가 많아지면 비용이 커진다.

두 모델의 핵심 차이를 정리하면 다음과 같다.

| 항목 | 명령형 드로잉 | 픽셀 단위 계산 |
| --- | --- | --- |
| 기본 단위 | 그릴 개체 | 평가할 위치 |
| 반복의 대상 | 도형·입자·셀 목록 | 화면 픽셀 또는 표면 표본 |
| 겹침의 기본 | 명령 순서와 블렌딩 | 함수 조합과 최종 색 계산 |
| 자연스러운 자료 구조 | 배열, 장면 그래프, 객체 | 좌표 함수, 텍스처, 버퍼 |
| 대표적인 질문 | 다음에 무엇을 그릴까 | 이 위치의 값은 무엇인가 |

실제 작업에서는 두 모델을 결합하는 일이 많다. CPU는 입자의 위치를 업데이트하고 마우스 입력을 처리하며, GPU는 그 위치를 바탕으로 잔상이나 노이즈 기반 배경을 계산할 수 있다. 또는 셰이더가 만든 필드 이미지를 드로잉 API에서 텍스처로 사용하고, 그 위에 텍스트와 선을 올릴 수 있다.

구현 방식은 달라도 원의 거리, 좌표 반복, 노이즈, 시간 함수라는 수학적 규칙은 같다. 명령형 드로잉에서는 그 값을 개체의 속성으로 번역하고, 픽셀 단위 계산에서는 위치별 색이나 마스크로 번역한다. 이 번역의 차이를 의식하면 한 환경에서 만든 아이디어를 다른 환경으로 더 쉽게 옮길 수 있다.

## 이 절의 핵심

명령형 드로잉은 도형과 그리기 순서를 중심으로 장면을 만들고, 픽셀 단위 계산은 각 위치에서 함수를 평가해 색을 만든다. 같은 패턴도 개체의 반복으로 구현할 수 있고, 좌표·거리·마스크를 이용한 필드 계산으로 구현할 수도 있다.
