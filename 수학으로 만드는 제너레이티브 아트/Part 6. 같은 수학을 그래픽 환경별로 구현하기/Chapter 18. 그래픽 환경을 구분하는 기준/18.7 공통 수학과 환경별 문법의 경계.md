# 18.7 공통 수학과 환경별 문법의 경계

그래픽 도구를 바꾸면 처음에는 모든 것이 달라진 것처럼 보인다. 함수 이름, 자료형, 좌표의 원점, 창을 만드는 방법, 프레임 루프의 형태가 달라진다. 그러나 제너레이티브 아트의 핵심 규칙까지 매번 새로 배우는 것은 아니다. 좋은 번역과 학습의 출발점은 공통 수학과 환경별 문법의 경계를 구분하는 데 있다.

공통 수학은 특정 언어나 라이브러리에 속하지 않는 부분이다. 좌표, 벡터, 거리, 각도, 함수 합성, 보간, 난수, 노이즈, 행렬 변환, 시간, 상태 갱신은 환경이 바뀌어도 같은 역할을 한다. 원의 거리 함수는 GLSL의 `length()`로 쓰든, p5.js의 `dist()`로 쓰든, C++의 벡터 연산으로 쓰든 원의 안팎을 판단하는 같은 규칙이다.

$$
d(\mathbf{p})=\|\mathbf{p}-\mathbf{c}\|-r
$$

이 식은 다음과 같은 여러 출력으로 번역할 수 있다.

```text
if d < 0: draw a filled circle
mask = 1 when d < 0, otherwise 0
outline = values near d = 0
height = function of d
```

거리의 부호, 경계의 위치, 부드러운 전환이라는 개념은 동일하다. 하지만 실제 코드에서 `if`를 쓰는지, `smoothstep()`으로 마스크를 만드는지, 캔버스에 원을 그리는지는 실행 환경과 목적에 따라 달라진다.

환경별 문법은 공통 규칙을 컴퓨터와 그래픽 API에 전달하는 구체적인 방식이다. 여기에는 다음 항목이 포함된다.

| 구분 | 공통 수학 | 환경별 문법과 관례 |
| --- | --- | --- |
| 좌표 | 점, 벡터, 정규화, 변환 | `vec2`, `PVector`, `glm::vec2`, 좌표 원점과 y축 방향 |
| 반복 | 여러 입력에서 같은 규칙 평가 | `for` 루프, map/filter, GPU 병렬 실행, 인스턴싱 |
| 시간 | 경과 시간 $t$, 시간 간격 $\Delta t$ | `millis()`, `GetTime()`, `uniform time`, 프레임 콜백 |
| 난수·노이즈 | 시드, 분포, 연속성 | 라이브러리 함수의 범위·알고리즘·시드 API |
| 그리기 | 색, 도형, 합성 | `circle()`, Canvas 경로, 드로우 콜, 프래그먼트 색 반환 |
| 상태 | 이전값에서 다음값으로 갱신 | 객체 배열, 함수형 상태, 텍스처 버퍼, 컴퓨트 버퍼 |

예를 들어 벡터의 덧셈은 공통 수학이지만, 벡터를 표현하는 자료형은 환경마다 다르다.

```text
# 공통 알고리즘
position = position + velocity * deltaTime
```

```javascript
// p5.js 예제
position.add(p5.Vector.mult(velocity, deltaTime));
```

```cpp
// raylib 또는 C++ 스타일의 개념 예시
position = Vector2Add(position, Vector2Scale(velocity, deltaTime));
```

```glsl
// GLSL에서 벡터 식 자체는 더 직접적으로 쓸 수 있다
position += velocity * deltaTime;
```

세 코드의 표면적인 차이는 크지만, 위치가 속도에 시간 간격을 곱한 만큼 변한다는 모델은 같다. 라이브러리를 배울 때 함수 이름만 암기하면 도구가 바뀔 때 지식도 쉽게 끊어진다. 반대로 수학적 역할을 먼저 이해하면 새로운 API 문서에서 필요한 대응 함수를 찾는 일이 된다.

그러나 모든 차이를 문법의 문제로 축소해서도 안 된다. 환경은 때로 알고리즘 자체의 설계를 바꾼다. CPU 드로잉 환경에서는 입자 배열을 자유롭게 늘리고 줄이며 복잡한 자료구조를 쓸 수 있다. 프래그먼트 셰이더에서는 각 픽셀이 서로의 결과를 직접 참조하기 어렵고, 이전 결과는 텍스처 버퍼를 통해 간접적으로 읽는다. 이런 실행 모델의 차이는 단순한 문법 변환이 아니라 상태 표현과 데이터 흐름을 바꾸는 조건이다.

다음 질문은 번역 전에 확인할 가치가 있다.

1. 이 규칙의 입력은 무엇인가. 좌표, 시간, 객체 상태, 이미지, 사용자 입력 가운데 무엇을 받는가?
2. 규칙은 각 입력에서 독립적으로 계산되는가, 아니면 이웃·이전 프레임·다른 객체의 값이 필요한가?
3. 결과는 도형 명령, 픽셀 색, 정점 위치, 표면 재질, 다음 상태 가운데 어디로 나가는가?
4. 반복 단위는 객체, 격자 셀, 픽셀, 정점, 표면 표본 가운데 무엇인가?
5. 데이터는 CPU 메모리, GPU 버퍼, 텍스처, 파일 가운데 어디에 머물러야 하는가?

이 질문은 어떤 환경이 더 좋은지를 판정하기 위한 체크리스트가 아니다. 작업의 핵심을 드러내는 도구다. 예를 들어 "마우스 근처의 입자만 서로 반응하며 새 입자가 계속 생긴다"는 알고리즘은 상태, 이웃 탐색, 동적 목록이 중요하므로 CPU 중심 구현에서 시작하기 좋다. 반대로 "화면의 모든 위치에서 노이즈와 거리 함수를 합성해 재질을 만든다"는 알고리즘은 픽셀이나 표면 표본의 독립 계산이 핵심이므로 셰이더가 자연스럽다.

환경별 문법을 배울 때는 세 겹으로 기록하면 도움이 된다. 첫째, 수학적 정의를 수식 또는 의사코드로 적는다. 둘째, 그 정의에 필요한 좌표계와 단위를 명시한다. 셋째, 실제 환경의 자료형·함수·라이프사이클 API를 붙인다.

```text
# 1. 규칙
value = sin(distanceToCenter * frequency - time * speed)

# 2. 입력 규약
position: 중심 원점, 짧은 변으로 정규화한 2D 좌표
time: 초 단위 실수

# 3. 환경 구현
GLSL: length(p), sin(...), uniform float time
p5.js: dist(x, y, 0, 0), Math.sin(...), millis() / 1000
```

이 기록 방식은 특히 팀 작업과 장기 프로젝트에서 유용하다. 코드만 남기면 왜 특정 상수에 화면 크기가 곱해졌는지, 노이즈 입력이 왜 뒤집혔는지 알기 어렵다. 좌표와 단위를 적어 두면 다른 플랫폼으로 옮길 때도 의도를 보존할 수 있다.

공통 수학을 재사용한다는 말은 모든 결과를 똑같이 만들어야 한다는 뜻도 아니다. 같은 사인파라도 p5.js에서는 수백 개 선의 높이로, GLSL에서는 화면 색상으로, OSL에서는 표면의 범프나 거칠기로 연결할 수 있다. 규칙은 같지만 재료와 출력 매체가 다르면 작품의 성격도 달라진다. 환경별 문법은 제약이면서 동시에 표현을 바꾸는 선택지다.

Part 6의 다음 장들은 이 경계를 실제 도구에서 확인한다. 드로잉 API와 크리에이티브 코딩 환경에서는 개체, 상태, 입력, 캔버스 명령의 번역을 살핀다. 셰이딩 언어 장에서는 같은 규칙을 픽셀·정점·표면에서 평가하는 방법을 다룬다. 어느 환경을 먼저 사용하든, 수학적 규칙과 좌표의 의미를 중심에 두면 도구가 바뀌어도 작업의 기반은 유지된다.

## 이 절의 핵심

좌표, 거리, 벡터, 시간, 노이즈, 상태 갱신은 그래픽 환경을 넘어 재사용되는 공통 수학이다. 자료형, API 호출, 렌더링 단계, 데이터 저장 위치는 환경별 문법과 실행 모델에 속한다. 알고리즘을 옮길 때는 규칙 자체와 그 규칙을 평가·저장·출력하는 방식을 분리해서 판단한다.
