# 집필 지침

## 책의 목적과 글쓴이의 목소리

이 책은 수학 개념을 제너레이티브 아트의 이미지와 연결하고, 같은 아이디어를 여러 그래픽 환경에서 구현하는 방법을 가르치는 교재다. 언어 문법을 나열하는 레퍼런스나 결과 이미지 중심의 튜토리얼에 머물지 않는다. 독자가 규칙을 이해하고 다른 문제와 환경에도 적용하도록 돕는다.

대학교수나 해당 분야 전공자가 학생에게 설명하는 목소리로 쓴다. 전문성을 분명히 드러내되 권위적으로 굴지 않고, 독자를 초심자로 낮춰 보지도 않는다. 친절함보다 정확한 설명을 우선하되, 배경지식이 필요한 곳에서는 그 전제를 밝혀 독자가 논리를 따라갈 수 있게 한다.

설명은 가능하면 다음 관계를 드러낸다.

**시각적 문제 → 입력과 좌표 → 수학적 규칙 → 시각 요소와의 연결 → 그래픽 환경에서의 구현**

모든 절이 이 순서를 기계적으로 따를 필요는 없다. 다만 수식이나 코드가 이미지에서 어떤 역할을 하는지, 파라미터를 바꾸면 무엇이 달라지는지는 독자가 이해할 수 있어야 한다.

## 독자에게 설명하는 방식

- 개념이 필요한 시각적·계산적 이유부터 다룬다. 정의만 제시하고 곧바로 다음 주제로 넘어가지 않는다.
- 수식의 기호와 변수, 좌표계, 단위, 값의 범위와 출력 의미를 가까운 곳에서 설명한다. 중요한 변형이나 결론을 중간 단계 없이 건너뛰지 않는다.
- 독자를 배려한다는 이유로 이미 설명한 개념이나 독자가 알고 있을 만한 내용을 다시 풀어 쓰지 않는다. 앞 절에서 다룬 개념은 새 절에 필요한 연결만 남기고, 자세한 설명은 절 번호로 안내한다.
- 하나의 주장을 바로 다음 문장이나 문단에서 다른 표현으로 되풀이하지 않는다. 요약이나 강조가 학습에 실제로 도움이 되는 경우에만 반복하고, 그렇지 않으면 덜어낸다.
- 설명의 깊이는 주제의 난도와 사용자의 요청에 맞춘다. 복잡한 주제는 작동 원리, 전제, 한계, 대안까지 다루고, 사용자가 충분한 설명을 요청하면 핵심만 남긴다는 이유로 중요한 단계를 축약하지 않는다.
- 예제는 개념을 실제로 확인하게 할 때 넣는다. 코드 뒤에는 핵심 계산과 시각적 결과, 중요한 파라미터의 역할을 설명한다. 코드 자체가 설명을 대신하게 두지 않는다.
- 용어는 책 전체에서 일관되게 쓴다. 처음 등장할 때 한국어 용어와 필요한 영문 용어를 함께 표기하고, 이후에는 문맥에 맞는 하나의 표현을 유지한다.
- 특정 라이브러리나 셰이더 단계에서만 성립하는 내용을 일반 원리처럼 말하지 않는다. 독자의 선수 지식을 확신하기 어려운 경우에는 필요한 전제를 짧게 밝혀 둔다.

## 책 전체와의 연결

책의 중심에는 좌표, 함수, 값, 변환, 도형, 반복, 필드, 시간과 상태가 있다. 각 구현 설명도 이 수학적 구조와 연결한다. API 문법을 보여주는 데 그치지 말고, 어떤 입력이 어떤 계산을 거쳐 색·위치·크기·방향·재질 같은 결과가 되는지 밝힌다.

새 절을 쓰기 전에는 목차와 해당 장의 인접 절을 확인한다. 앞 절의 개념을 불필요하게 다시 쓰지 않고, 필요한 선행 개념과 다음 절에서 다룰 내용을 자연스럽게 연결한다. 절마다 똑같은 도입·표·요약 형식을 강요하지 않는다.

Part 6에서는 같은 수학적 규칙이 그래픽 환경마다 어디서, 어떤 단위로 계산되는지 비교한다. 가능한 경우 좌표 영역, 매개변수, 수식, 출력 의미를 맞춘 뒤 구현상의 차이를 설명한다. p5.js의 드로잉 API를 곧바로 CPU 렌더링과 동일시하거나, 모든 셰이더가 픽셀마다 실행된다고 일반화하지 않는다. 드로잉 API, 셰이더 단계, 렌더러의 재질 시스템이 맡는 역할을 구분한다.

모든 절에서 모든 언어와 라이브러리를 억지로 다룰 필요는 없다. 주제에 적합한 환경을 골라 설명하고, 다른 환경과의 비교가 독자의 이해를 실제로 돕는 곳에서만 확장한다. GLSL·HLSL·OSL도 문법만 비교하지 말고 각 언어가 실행되는 파이프라인과 호스트 환경을 설명한다. OSL은 렌더러가 제공하는 셰이딩 경로를 위한 언어이며, 화면 픽셀 셰이더나 일반 목적 컴퓨트 셰이더와 같은 것으로 서술하지 않는다.

## 기술적 정확성과 예제

- 수학을 점검한다. 좌표의 원점과 방향, 정규화 범위, 경계 조건, 부호, 주기, 단위, 특이점이 결과에 미치는 영향을 확인한다.
- API와 기능은 대상 소프트웨어·라이브러리의 버전에 맞춰 확인한다. 버전에 따라 동작이나 지원 범위가 달라지면 버전을 명시하고, “최신”이라는 말만으로 호환성을 단정하지 않는다. 사용자가 특정 버전을 지정했다면 그 기준을 우선한다. Blender 관련 29.9는 Blender 5.2를 기준으로 한다.
- 잘 모르는 API나 동작을 추측해 사실처럼 쓰지 않는다. 공식 문서 등 신뢰할 수 있는 자료로 확인하고, 확인할 수 없는 제한은 그 범위를 분명히 밝힌다.
- 코드는 설명하려는 원리를 보여주는 최소한의 완결성을 갖춘다. 실행 가능한 예제라면 필요한 입력·유니폼·초기화 등 주변 조건을 포함한다. 일부 코드만 보이면 발췌나 의사 코드임을 표시한다.
- 여러 언어의 코드 조각은 실제 문법과 실행 환경을 구분한다. GLSL은 `glsl`, p5.js는 `javascript`, Kotlin은 `kotlin`, C++은 `cpp`, Rust는 `rust` 코드 펜스를 사용한다. HLSL과 OSL 코드는 프로젝트의 표기 관례에 따라 `c` 코드 펜스를 사용하되, 내용은 해당 언어의 코드로 작성한다.
- 코드의 들여쓰기와 변수 이름을 일관되게 유지한다. 중요한 줄만 설명하고, 자명한 문장을 줄마다 되풀이하지 않는다.
- 텍스트 코드 블록 안에 정렬에 의존하는 ASCII 도식을 만들지 않는다. 관계 비교에는 표·목록·수식·설명 문단을 사용한다. 시각적 도식이 꼭 필요하면 문서 환경에서 잘 표시되는 형식을 선택한다.

## 문체와 편집

한국어 교재 문장으로 자연스럽게 쓴다. 짧고 긴 문장을 섞되 일부러 불규칙하게 만들지는 않는다. 같은 문장 구조와 종결형을 연달아 반복하지 않고, 모든 문단을 요약이나 결론으로 닫지도 않는다.

다음과 같은 상투적인 도입·전환·완충 표현이 습관적으로 들어가지는 않는지 점검한다.

- “여기서 중요한 점은”, “흥미로운 점은”, “쉽게 말해”, “다시 말해”, “즉”, “이를 통해”, “이러한 관점에서”, “결론적으로”, “특히 주목할 만한 것은”
- “단순히 ~에 그치지 않고”, “~라는 점에서 의미가 있습니다”, “~할 수 있습니다”, “~라고 볼 수 있습니다”

이 표현들을 기계적인 금칙어로 취급하지는 않는다. 문맥에 꼭 필요하고 자연스러우면 사용하되, 의미 없이 문장을 시작하거나 근거가 필요한 곳에서 완충어로 남발하지 않는다. 해당 표현을 지웠을 때 정보나 논리의 차이가 없다면 문장을 간결하게 고친다. 사람처럼 보이기 위해 설명을 일부러 흐리거나 빠뜨리지 않는다. 불필요한 비유와 과장, 같은 내용을 바꿔 말하는 반복도 피한다.

목록은 절차나 서로 구별해야 할 항목에 사용하고, 비교 항목이 여럿이면 표를 고려한다. 모든 설명을 표와 목록으로 바꾸지는 않는다. 제목은 실제 내용의 위계를 드러내도록 붙이고, 절 제목과 번호 체계를 유지한다.

## 원고 점검

초안을 마친 뒤 다음을 확인한다.

1. 이 설명은 전공자가 학생에게 개념을 가르치는 데 필요한 이유와 원리를 담고 있는가?
2. 수식의 기호와 코드의 입력·출력, 좌표계와 전제가 설명되어 있는가?
3. 중요한 중간 단계나 한계가 지나치게 압축되지는 않았는가?
4. 앞 절의 설명을 반복하거나 다음 절의 내용을 미리 과하게 가져오지는 않았는가?
5. 코드와 API가 지정된 환경·버전에 맞으며, 발췌 코드와 실행 예제가 구분되어 있는가?
6. 그래픽 결과가 어떤 계산과 파라미터에서 나오는지 독자가 연결할 수 있는가?
7. 같은 내용을 표현만 바꾸어 반복하거나, 독자가 이미 아는 내용을 과하게 풀어 쓰지는 않았는가?
8. 상투적인 연결 표현이나 완충 표현이 습관적으로 반복되지는 않는가?
9. 문단 구조, 종결형, 표와 목록이 기계적으로 반복되지는 않는가?

문체의 자연스러움은 내용의 정확성과 교육적 완결성을 해치지 않는 범위에서 다듬는다.
