## 1. <span style="color: #f6b384">OSL 스크립트를 Blender에서 활용하는 방법</span>

1. Render Properties → **Render Engine을 <span style="color: #06f3d4">Cycles</span>로 설정**
2. **Device를 <span style="color: #06f3d4">CPU</span>로 설정**
3. <span style="color: #06f3d4">"Open Shading Language"</span> 체크박스를 선택
4. Shader Editor를 열고, 만들려고 하는 머티리얼의 노드 그래프에 **`Add` → `Script 노드`를 추가**
5. Script 노드의 모드를 선택
   - **<span style="color: #ff7fdf">Internal</span>**: Text Editor에 있는 텍스트 데이터블록을 소스로 사용. `.blend` 파일 안에 함께 저장되므로 배포가 간편함
   - **<span style="color: #ff7fdf">External</span>**: 디스크의 `.osl` 파일 경로를 지정. 저장 시 자동으로 `.oso` 바이트코드로 컴파일됨
6. 소스가 컴파일에 성공하면 노드에 입력/출력 소켓이 자동으로 생성됨. 이 소켓을 Material Output 노드의 Surface 입력에 연결

컴파일이 실패하면 노드에 소켓이 생기지 않고, 에러 메시지는 노드 UI가 아니라 **시스템 콘솔**(Window → Toggle System Console)에 출력됩니다. macOS/Linux는 터미널에서 Blender를 실행했을 때 사용한 터미널에서 확인해야 합니다.

## 2. <span style="color: #f6b384">Script 노드 소켓의 구조</span>

다른 소프트웨어에서 OSL을 쓸 때와 Blender에서 쓸 때는 통합 방식이 다릅니다. Arnold나 RenderMan 같은 렌더러는 명령행 도구나 씬 디스크립션 파일(`.ass`, RIB 등)에서 `ShaderGroupBegin`/`ConnectShaders` 같은 OSL 자체의 API 호출로 셰이더 네트워크를 구성할 수 있습니다. 즉 노드 에디터라는 GUI 없이도, 코드나 스크립트만으로 여러 OSL 셰이더를 연결한 네트워크를 만들 수 있다는 뜻입니다. 반면 Blender는 이런 경로를 제공하지 않고, 모든 OSL 셰이더를 예외 없이 **Shader Editor의 노드 그래프 안에 있는 Script 노드 하나**로만 다룹니다. 그리고 이 노드에 생기는 입력/출력 소켓을 통해 데이터를 주고 받을 수 있습니다.

### **<span style="color: #06f3d4">1. 왜 소켓으로 변환되는가.</span>** 
Cycles의 머티리얼 시스템은 Diffuse BSDF, Mix Shader, Image Texture 같은 모든 노드가 타입이 정해진 소켓을 통해 값을 주고받는 하나의 통합된 그래프로 설계되어 있습니다. Script 노드도 이 그래프 안에서 다른 빌트인 노드와 동일한 방식으로 동작해야 하므로, OSL 셰이더의 파라미터 목록을 Blender가 인식하는 소켓 목록으로 변환하는 과정이 필요합니다. 이 변환은 소스를 컴파일할 때(또는 Script 노드의 Update 버튼을 눌렀을 때) 자동으로 일어나며, 그래서 파라미터를 추가하거나 삭제하면 소켓 구성도 그에 맞춰 다시 생성됩니다. Diffuse BSDF처럼 소켓 구성이 고정된 빌트인 노드와 달리, Script 노드는 소스 코드 자체가 곧 노드의 인터페이스 정의를 겸하는 유일한 노드 타입입니다.

### **<span style="color: #06f3d4">2. 어떤 입력이 소켓이 되는가.</span>** 
`output`이 붙지 않은 입력 파라미터 중 `float`, `color`, `int`, `point`/`vector`/`normal`은 각각 Value, Color, Integer, Vector 소켓으로 1:1 대응되어 자동으로 생성됩니다. 이 소켓은 비워두면 `.osl` 코드에 적어둔 기본값을 그대로 쓰고, 다른 노드를 연결하면 그 값으로 대체됩니다. 반면 `string`이나 `matrix` 타입은 Blender의 노드 소켓 체계에 대응하는 소켓 종류가 없어서, 이 파라미터들은 소켓으로 노출되지 않고 셰이더 내부에 고정된 값으로만 남습니다. 텍스처 파일 경로처럼 실행 중에 동적으로 바뀔 필요가 없는 값이 주로 이 타입에 해당합니다.

### **<span style="color: #06f3d4">3. 어떤 출력이 어디로 연결되는가.</span>** 
`output closure color`로 선언한 출력은 Blender의 Shader 소켓(보라색)으로 노출되며, Material Output 노드의 Surface/Volume 입력에 직접 연결하거나, 다른 클로저를 조합하는 노드(Mix Shader, Add Shader 등)로 연결할 수 있습니다. 반면 `output float`나 `output color`처럼 일반 값을 반환하는 출력은 Value · Color 소켓으로 노출되어, Mix Color나 다른 Script 노드의 입력처럼 데이터를 받는 소켓 어디로든 연결할 수 있습니다. 

### **<span style="color: #06f3d4">4. 클로저 함수는 Cycles에 구현된 것만 사용 가능</span>** 
`diffuse()`, `emission()`, `glossy_ggx()` 같은 클로저 함수는 OSL 언어 사양이 아니라 그 클로저를 구현하는 렌더러가 결정합니다. Blender 매뉴얼도 "Cycles에서 사용 가능한 클로저는 Cycles의 셰이더 노드 및 그 소켓과 대응한다"고 명시하고 있습니다. 즉 Arnold나 RenderMan용으로 작성된 OSL 소스를 그대로 Blender에 가져와도, 그 소스가 참조하는 클로저 함수가 Cycles에 구현되어 있지 않으면 컴파일이 실패합니다. OSL 자체는 렌더러 중립적인 언어이지만, 클로저라는 핵심 출력 형식만큼은 렌더러별 구현에 묶여 있다는 뜻입니다.

### **<span style="color: #06f3d4">5. Light 셰이더 타입은 Blender에서 사용 불가</span>** 
OSL 언어 사양은 `surface`, `volume`, `displacement`와 함께 `light` 셰이더 타입도 정의하지만, Blender의 조명은 별도의 Light 데이터블록 시스템으로 관리되어 OSL 광원 셰이더가 개입할 지점이 없습니다. 따라서 Blender의 Script 노드는 사실상 <span style="color: #ff7fdf">**`surface`, `volume`, `displacement`**</span> 세 종류만 다루게 됩니다.

## 3. <span style="color: #f6b384">만들 수 있는 Shader의 종류</span>
Blender의 OSL은 **Surface, Volume, Displacement** 셰이더만 지원하며, **Light 셰이더는 Cycles 엔진의 별도 시스템**으로 처리됩니다. 그래서 Blender의 OSL로 작업할 때는 "어떤 표면을 빛나게 할까"에 집중하고, 실제 광원은 Blender의 Light 시스템에 맡기는 것이 일반적인 워크플로우입니다.

### 1. OSL 표준 vs Blender의 차이

OSL 언어 표준 스펙 자체에는 `light` 셰이더 타입이 정의되어 있습니다. RenderMan이나 다른 렌더러에서는 이를 사용해 커스텀 라이트를 만들 수 있습니다.

```c
// OSL 표준에는 존재하지만 Blender에서는 미지원
light my_light(...)
{
    ...
}
```

하지만 **Blender Cycles는 이 `light` 셰이더 타입을 지원하지 않습니다.** 컴파일조차 되지 않습니다.

### 2. Blender에서 라이트의 구조

Blender에서 라이트는 OSL과 완전히 분리된 시스템으로 동작합니다.

- **Light 오브젝트**: Point, Sun, Spot, Area, HDRI 환경광
- **내부 처리**: Cycles 엔진이 자체적으로 라이트 샘플링, GI, 그림자 계산
- **OSL 관여 불가**: 라이트의 동작 방식, 감쇠, 분포 등을 OSL로 제어할 수 없음

즉, OSL 셰이더는 "빛을 받는 물체"만 정의할 수 있고, "빛을 내는 오브젝트 자체"는 정의할 수 없습니다.

### 3. 대안: Emission 클로저로 발광 표면 만들기

Light 셰이더는 못 만들지만, **표면에서 빛을 내는 효과**는 `emission()` 클로저로 구현할 수 있습니다.

```c
shader glowing_surface(
    float Intensity = 1.0,
    color EmitColor = color(1.0, 0.5, 0.2),
    output closure color BSDF = 0
)
{
    // emission()은 인자 없이 호출하고, 거기에 색상과 강도를 곱함
    BSDF = emission() * EmitColor * Intensity;
}
```

이렇게 만든 발광 표면은 Cycles에서 **간접광(Indirect Lighting)의 광원**으로 작용합니다. 즉, 네온사인, 발광 패널, 마법진 같은 "표면 기반 라이트"는 OSL로 만들 수 있습니다.

### 4. 실질적인 차이

| 구분 | OSL Emission | Blender Light 오브젝트 |
|------|--------------|----------------------|
| **역할** | 표면이 빛남 | 공간에 독립적인 광원 |
| **GI 기여** | 가능 (면적광처럼 동작) | 가능 |
| **제어 방식** | OSL 코드로 패턴, 애니메이션 제어 | 라이트 속성, 드라이버로 제어 |
| **샘플링** | 표면 샘플링에 의존 | 전용 라이트 샘플링 |
| **제한** | 작은 면적에서는 노이즈 발생 가능 | 안정적인 샘플링 |

### 5. 팁

- **넓은 발광면**(천장 조명, 발광 벽) → OSL `emission()`으로 충분히 구현 가능
- **강한 점광원**(태양, 전구)**이 필요한 경우** → Blender Light 오브젝트 사용
- **복합적인 경우** → OSL로 발광 패턴을 만들고, Emission으로 출력 + Blender Light로 보조 광원 배치

---

  ## 3. <span style="color: #f6b384">실행 환경 제약</span>

OSL은 **CPU 렌더링과, 제한적으로 OptiX 백엔드의 GPU 렌더링에서만 동작**합니다. CUDA/HIP/Metal 백엔드에서는 지원되지 않고, OptiX에서도 텍스처 조회나 일부 노이즈 함수 등 몇 가지 기능이 제한적입니다. 게다가 OptiX + OSL 조합은 특정 드라이버에서 컴파일 자체가 실패하는 알려진 버그(`Failed to load OptiX OSL shadeops kernel`)가 있어서, CPU 렌더링으로 고정해서 쓰는 게 가장 안정적입니다.
